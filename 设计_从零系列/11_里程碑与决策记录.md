## 1. 先看懂"为什么是这个顺序"：全局依赖主干

> 依据：`设计/08` §5.1（全局依赖主干）。里程碑不是平铺的清单，而是**有前置依赖的施工树**：

```text
主线（D1 → D2 → D3）
  M0 评测集解耦（一切改造的安全网，必须先建）
   └→ M1 D1 工具接入平台（统一工具出口 —— D15 收回的前提）
        └→ M2 D4 去轮询（总线事件化）
             └→ M3 MCP 常驻化 + 拆锁（执行层并发的两个前提）
                  ├→ M3.5 SQLite WAL（并行写的兜底，不可跳过）
                  ├→ M4 D8 沙箱补强
                  ├→ M5 D2 状态机 + D5 追问治理 + D14 收敛
                  ├→ M6 依赖动态化 + 批量派发（兑现并行收益，必须在 M3 之后）
                  └→ M7 D3 可观测（span 树）
                       └→ M8 用户文档库接管 RAG
                            ├→ M9 D15 工具资产收回
                            ├→ M11 D16 finance 防幻觉（在 M9/M10 之后）
                            ├→ M12 D6 上下文预算
                            ├→ M13 D7 收口（单图退役）
                            └→ M14 D17 模型接入层 harness
```

关键点（为什么 M0 第一个、M3 系列为什么锁死顺序）：
1. **M0 评测集解耦最先**：任何改造前先有"没改坏"的判定基准（`设计/11` §3 M0）；
2. **M1 工具平台是地基**：D15（工具收回）、安全/审计/计时全部依赖"唯一出口"先存在；
3. **M2/M3/M3.5 是执行层的锁链**：并行派发（M6）必须建立在常驻（M3）+ 拆锁（M3）+ WAL（M3.5）之后，否则收益为零（`设计/03` §9.4 ③）。

## 5. 从零视角：如果重新做，里程碑会怎么排（面试高光）

如果这个系统从零开始写（不是改造），里程碑建议按**依赖序而非编号序**排：

```
从零里程碑（建议）
 S1 需求与评测集（01/12 先行：先定义"对"，再写代码）
 S2 单 Agent 记账 + 工具平台地基（M1 的 ToolSpec/Registry 直接建，不返工）
 S3 A2A + 状态机一起建（M2+M5 同构，不做轮询版本）
 S4 MCP 常驻 + WAL 一次到位（M3+M3.5，不为 stdio 短连接写兼容）
 S5 批量派发 + 可观测（M6+M7 同步，埋点随代码长出来）
 S6 finance 防幻觉（M9+M11 一步到位，不留 db. 直连后门）
 S7 harness（M14 前置设计，避免 D17 的参数透传事故）
```

> **要点**：从零时，原"缺陷驱动"的里程碑可以压缩成"能力驱动"的顺序——但**每个里程碑的验收与回归红线不变**（10 §4）。
> 这正是本系列 00 §6.2 方法论的产品化表达：bug 不是等 D 编号攒出来，而是用守则挡在设计/施工期。

## 6. 小结

1. 里程碑 M0–M14 有严格依赖树：M0 安全网 → M1 地基 → M3 锁链 → 后续能力逐层兑现；
2. 缺陷 D1–D17 全部映射到里程碑，改前查覆盖度（`设计/08` §5.0）；
3. 决策五类编号（Q/T/D/M/R-C）各存一处、互相引用，不留双份；
4. M10 待启动——编号顺序 ≠ 执行顺序；
5. 从零视角：能力驱动排期 + 守则不变的验收，是面试讲方法论的高光点。
