## 1. 先立一条"免死金牌"话术

面试没做过别的技术，最忌讳硬装。合格的答法是三步：

1. **承认边界**："AutoGen 我没有在生产里用过，只做过选型调研。"
2. **给出可判定的对比维度**（说明你知道该比什么）："选型我有一套固定问法——控制粒度 / 运维成本 / 生态成熟度 / 和约束的匹配度。"
3. **落到本项目数据**："以我们的约束（单用户单机零部署、本地 1.8B 模型、预算敏感）看，X 的重是它的卖点，但不是我们要的。"

> 记住一个句式：**"X 很好，它是为『规模/多人/企业』设计的；我的需求是『单机/单用户/可交付』，选它是大炮打蚊子，还会引入运维债务。"**
> 这不是辩解——02 §6 已写明本项目选型的唯一逻辑是"对这个需求成本最低且够用"。

## 2. Agent 编排框架：LangGraph / LangChain / AutoGen / CrewAI / 自研

### 2.1 先建立坐标系（面试开篇就靠这个）

| 维度 | LangChain | LangGraph | AutoGen | CrewAI | 自研状态机 |
|---|---|---|---|---|---|
| 一句话定位 | LLM 应用工具链：提示词/模型/工具串成可复用组件 | LLM 应用**图运行时**：节点+边+共享 State+可持久化 | 微软的多 Agent 对话/事件框架 | "给 AI 组团队"的角色化多 Agent 框架 | 自己写状态机 |
| 抽象层级 | 高（封装多） | 低（贴近控制流，可控强） | 中 | 高（声明式） | 任意 |
| 状态表达 | 链式为主 | **显式 StateGraph + 共享 State** | 对话消息流/actor 事件 | Task 流转 | 自定 |
| 适合谁 | 快速做 RAG/单 Agent 工具调用 | 要精确控制分支/循环/人工介入的生产 Agent | 研究多 Agent 对话协作 | 最少代码搭"角色团队"Demo | 想彻底掌控/极简需求 |
| 本项目结论 | —— | ✅ 现役 | ❌ 调研过 | ❌ 调研过 | ❌ 已退役（02 §2.2） |

> 外部事实口径：LangChain 是最早流行的 LLM 框架（链/LCEL/海量集成），2025 起官方重心拆为 LangGraph（底层图运行时）+ LangSmith（可观测）；AutoGen 为微软出品，v0.4 重写为事件驱动 actor 模型；CrewAI 主打 role/goal/backstory 声明式角色编排。（以官方文档为准）

### 2.2 本项目为什么是 LangGraph（对应 02 §2.2）

编排本质 = "多步有状态流转"（plan → dispatch → wait → collect → 可能追问回跳）。LangGraph 的 **StateGraph + 共享 State + 节点用 `Command(goto=...)` 运行时动态跳转**，与需求"一一对应"：节点即子 Agent 执行，回边即追问/按波次再派发（09 §2.3 orchestrator_graph：`wait_result→dispatch` 回边）。自研版曾存在（`agentCore/`），因"语义弱、维护成本高"退役（02 §2.2）。

### 2.3 面试弹药：接住"你为什么不选 AutoGen / CrewAI"

面试官真正想听的不是"它不好"，而是**你有没有把选型讲成"需求匹配"**：

- **对 AutoGen**："AutoGen 强在『多智能体自由对话协作』和『人机协同』的研究场景；我们是**生产流水线**——步骤固定（记账→统计→建议）、状态要可对账、要防死循环，这更需要**显式图控制**而非 Agent 互相聊天。对话自由度高，反过来收敛性要靠自己约束。"
- **对 CrewAI**："CrewAI 上手最快，适合『组队跑任务』的声明式场景；但我们的子 Agent **有依赖关系、要按波次并发、要精确等结果**，不是『各自干完活汇总』。这些控制点用图显式表达更可靠。"
- **加分句（体现你真懂）**："共同假设是『Agent 自己决定下一步』；billAgent 的假设是**『确定性流程 + Agent 只在表达层做决策』**（价值主张 3"数字可信"= 回复里的数字 100% 来自 SQL/数值、不由模型编造，00 §2；防幻觉防线见 07 方案 C）——所以我们需要的是把死流程和活分支都画出来的引擎。LangGraph 的图 = 把控制流写死、把不可控留给节点内部的最低成本载体。"

## 3. 工具协议：MCP vs Function Calling vs 自研网关

### 3.1 先讲清两者不在一个层面（最常见的混淆点）

| | Function Calling | MCP |
|---|---|---|
| 本质 | **模型的一项能力**：要求模型输出"调哪个函数 + 参数 JSON" | **一套标准协议**：约定工具如何被发现/调用/返回的通用标准 |
| 类比 | 充电技术本身 | USB-C 接口标准（谁都能插） |
| 谁提出 | OpenAI（2023 年中随 GPT 引入） | Anthropic（2024-11 开源），后转 Linux 基金会治理 |
| 解决什么 | 让 LLM 输出结构化函数调用 | 让"同一套工具"被不同客户端/模型复用，免 N×M 适配 |
| 典型形态 | 定义 schema→请求模型→后端执行 | Host + Server，走 stdio/HTTP，暴露 tools/resources/prompts |

> 外部事实口径：2026 年 MCP 生态已成熟为事实标准。Function Calling 是"引擎能力"，MCP 是"接口标准"——**上下层叠加**而非替代。

### 3.2 本项目为什么两样都用（对应 02 §2.4）

Agent 需要两类能力：调 LLM（读模型）、读写 SQL。真问题不是"用哪个协议"，而是"**不能让 Agent 散着裸调**，否则鉴权/审计/超时处处重写"（缺陷 D1）。
解法两层：

- **对内**：Agent 一律走自研网关 `ToolRegistry`（04 逻辑视角），工具 = 可管理资产（注册/权限/审计/计时）；
- **对外**：模型侧用 Function Calling 输出结构化调用；工具暴露遵循 **MCP**（FastMCP server：`llm_chat`/`sql_query`…，client/server 分离，传输 stdio→streamable-http 可演进且业务代码不变，02 §2.4/T3）。

### 3.3 面试弹药

- 主线：**"Function Calling 是模型怎么『说』，MCP 是工具怎么『被找到和被调』；我都用——协议层解耦工具与模型，网关层收口权限与审计。"**
- 被问"自写 MCP server 图什么"："图传输层演进不影响业务（stdio→HTTP 常驻，冷启动 26~29s 只付一次），未来换 MCP 客户端/模型，工具资产可复用。"
- 被问"不用 MCP 直接函数调用行不行"："行，只要接受每次加工具手写接入、每个调用点自己管鉴权。我们早期就这么散的——D1 告诉我们不可持续。"

## 4. 数据库：SQLite vs PostgreSQL vs MySQL

### 4.1 横向认知

| | SQLite | PostgreSQL | MySQL |
|---|---|---|---|
| 形态 | **嵌入式文件库**，无服务进程 | 独立数据库服务 | 独立数据库服务 |
| 部署 | 零部署，单文件随应用走 | 装/配/运维/备份 | 同左 |
| 并发写 | 单写者为主（WAL 下多读一写） | 强（MVCC） | 强 |
| 扩展 | 弱（无网络/无插件体系） | 极强（JSONB、**pgvector**、GIS…） | 云生态大（Aurora 等） |
| 最合适 | 桌面/移动/单机工具/嵌入式 | 多用户 Web 后端、复杂查询 | 大规模 Web、云托管 |

### 4.2 本项目决策（02 §2.5）

数据量 = 个人消费（月几十~几百笔）+ 单用户 + 单机 + 零部署（R1）。此量级 SQLite 够用 = 唯一不过度设计的答案：并发写靠 WAL + `busy_timeout` + 单写者语义（05 数据视角）。引入 PG = 给单机单用户应用引入安装/运维/备份的纯债务。

### 4.3 面试弹药

- **主动说出 SQLite 的已知代价**（并发写弱、不能网络共享、无 pgvector 类扩展），避免像只看到优点："它的代价正是这三条——而它们都不是我们的需求。"
- 被问"会不会锁死"："有撤退路线：写库全走网关层隔离的 SQL 工具（MCP `sql.*`），DDL 参数化且表结构集中登记在 09 §8。真要多用户，SQLite→PG 的迁移点已提前封好。"

## 5. 消息/任务总线：asyncio.Queue vs Redis vs Celery vs Kafka

### 5.1 先分清四件事（很多人混为一谈）

| 技术 | 类别 | 一句话 | 何时才需要 |
|---|---|---|---|
| `asyncio.Queue`（本项目） | **进程内队列** | 协程间传消息，零网络 | 单进程、单机、不需跨重启存活 |
| Redis（Stream/List） | 外部 KV+队列 | 消息存内存服务，跨进程共享/pub-sub | 多进程/多机、要广播 |
| Celery | **分布式任务框架** | 把任务发给 worker 异步执行（配 broker） | 后台长任务、定时、要横向扩 worker |
| RabbitMQ | 消息代理（AMQP） | 可靠投递、多语言解耦 | 微服务间可靠异步消息 |
| Kafka | **事件流平台** | 高吞吐日志式事件、可回放 | 大数据事件流、审计/数仓 |

### 5.2 本项目决策（02 §2.3 / T4）

- 架构 = 单进程多协程；子 Agent **不进程化**（T2：推理负载本就在主进程外的 Ollama/API，进程化是负优化）；
- A2A 总线 = 进程内 `asyncio.Queue + Event`（`mcpGateway/a2a_queue.py`），**消息即事件、不靠轮询**（防 D4：轮询空转 P95 慢 101×，06 执行视角）；
- 结论：单进程内通信引入 Redis = 平白加外部依赖、违背零部署红线。**Redis Stream 是 P2 演进**（跨进程/持久化/广播）。

### 5.3 面试弹药

- 主线：**"不进 Redis 不是不知道 Redis，而是单进程内协程队列已满足；Redis 的价值（跨进程/持久化/广播）在单进程场景等于零，负债却是部署+常驻+运维。"**
- 被问"以后多机怎么办"："消息通道已封装成 A2A 总线接口，换 Redis Stream 只动实现，业务侧 `send_task/wait_result` 契约不变（09 §3）。演进路线已登记 P2。"

## 6. 本地推理：Ollama vs llama.cpp vs vLLM vs LM Studio

### 6.1 横向认知

| | 定位 | 关键词 |
|---|---|---|
| **Ollama**（本项目） | 个人开发者一键本地模型服务（Go，OpenAI 兼容 REST） | 简单、体验好 |
| llama.cpp | **推理引擎库**（C/C++，GGUF 量化格式源头） | 性能、底层可控、无开箱服务 |
| vLLM | **高吞吐推理服务**（PagedAttention+连续批处理） | 吞吐、生产级、吃显存吃运维 |
| LM Studio | 桌面 GUI 跑模型 | 可视化、零命令行 |

> 外部事实口径：GGUF/Ollama/llama.cpp/vLLM 均活跃于 2026 本地推理生态；SGLang、MLX(Apple) 亦为常见选项。（官方为准）

### 6.2 本项目决策（02 §2.6）

R5 = 本地可跑、零 API、免费基线。瓶颈不是吞吐而是"别让我运维"：Ollama 一条命令拉模型+起服务、OpenAI 兼容接口，与 `ChatModel` harness 对齐成本最低。1.8B qwen 只是免费基线，更强表达由可选外部 API 承担（方案 C 防幻觉兜底，07）。

### 6.3 面试弹药

- 被问"为什么不用 vLLM"："vLLM 为**高并发高吞吐**而生，需 GPU 显存与工程运维；我们单用户低并发，vLLM 在 1 并发下卖点≈0，负债却真实。真到多用户线上，模型通道已抽象成 `ChatModel` harness（09 §6），换 vLLM 是换一个 Provider，不碰业务。"
- 被问"llama.cpp 不是更底层更强"："强在引擎性能，但它是库不是服务、接入成本高；Ollama 底层兼容 GGUF，等于用一点性能换整层交付体验。对我们的量级，这笔交易划算。"

## 7. 语义检索/向量：FAISS vs pgvector vs Milvus vs Chroma vs Qdrant

### 7.1 横向认知（先按"要不要装服务"分两拨）

| | 形态 | 规模定位 | 一句话 |
|---|---|---|---|
| **FAISS**（本项目） | **库**（内存索引，Meta 出品） | 单进程内、几十万~百万级可跑 | 快、自由；持久化/过滤/并发自己管 |
| Chroma | 轻量向量库 | 原型/小规模 | 开发友好，大了吃力 |
| pgvector | PostgreSQL 扩展 | 中等规模 | 已有 PG 就白捡向量能力 |
| Qdrant | 独立向量库（Rust） | 中小~大规模 | 性能好、默认落盘 |
| Milvus | 分布式向量库 | **十亿级/高 QPS** 企业级 | 全功能，也重运维 |
| Elasticsearch | 搜索引擎（全文+向量） | 已有 ES 的团队 | 全文是主场，向量是顺带 |

> 外部事实口径（选型口诀）：数据小且不想装服务 → FAISS/Chroma；已用 PG → pgvector；要独立服务求性能 → Qdrant；十亿级 → Milvus。（公开资料口径，官方为准）

### 7.2 本项目决策（02 §2.7 / 05 数据视角）

- 长期记忆 = FAISS（IndexIDMap）+ pkl 落盘；用户文档库 = **BM25 内嵌兜底 + embedding 可选**（`rank_bm25` 没装也能跑、embedding 不可用自动降级）。
- 逻辑：单用户数据量**连"独立向量数据库"都够不上**——FAISS 内存索引 + 文件落盘已覆盖，还少两个常驻服务。BM25 兜底守住"外部依赖缺失时 RAG 不可用"的交付红线。

### 7.3 面试弹药

- 被问"为什么不用专用向量库"："先反问自己：我的向量规模到哪了？我们是个人记忆 + 几十篇用户文档，**装一个分布式向量库比数据本身还重**。FAISS 是库不是服务，内存索引 + pkl 落盘足够；等规模涨到要独立服务，我们的检索入口是隔离的（05 记忆分层），换 Qdrant/Milvus 只动一个模块。"

## 9. 面试官爱问的横向 QA（背熟能扛一轮追问）

**Q1：这个项目你自研了什么，为什么不自研 / 为什么用现成？**
- 自研：A2A 进程内总线（单进程约束下现成中间件全超配）；"自研但小"。
- 用现成：LangGraph 图编排（自研版踩坑后退役，02 §2.2）；MCP（协议生态自研不值得）。
- 判断标准一句话：**"自研的下限是『我知道它该有什么语义』，上限是『它不会变成另一个要维护的产品』。"**

**Q2：如果让你把 billAgent 扩成多用户 SaaS，你动的第一刀是什么？**
（这是测"你是不是只会单机"）参考答案，按影响从小到大排：
1. SQLite → PostgreSQL（多写并发+网络访问，迁移点已在网关层封好）；
2. A2A 进程内队列 → Redis Stream（跨进程/多实例，契约不变，P2 已登记）；
3. 本地 Ollama → vLLM 服务化（多租户吞吐，`ChatModel` harness 换 Provider）；
4. 会话记忆 dict → 持久化存储（短期记忆升级，05）；
5. 加租户隔离列 + RBAC 升级（现在是单用户最小权限，09 §4.3）。
> 关键在**顺序**与"每一步都不碰上层契约"——这正是当初抽象层的价值。

**Q3：你这些对比，多少是真做过的，多少是查来的？**
（诚实 + 展示调研方法）
- "LangGraph/SQLite/MCP 是**生产用**的；AutoGen/vLLM/Milvus 是**选型调研级**——我写过一个固定的对比框架（控制粒度/运维成本/生态/约束匹配），拿公开资料+官方文档填表，结论记录在 13 这篇。真正动手前，我按 09 §0.4 接口走查第 3 项写 ≤30 行原型实测，防止『文档说能 import』当通过（10 §2 动工门禁第 4 项契约收敛的前提也是这个）。"

## 10. 一页记忆表（面试前 10 分钟扫这张）

| 技术点 | 我们选 | 面试一句 | 反方一句话（不选的理由） |
|---|---|---|---|
| 编排 | LangGraph | 显式图+动态 goto=把确定性流程画死 | AutoGen/CrewAI 让 Agent 自己聊=收敛靠自觉 |
| 工具协议 | MCP+网关 | 协议解耦工具与模型、网关收口权限 | 裸 function call=每调用点自己管鉴权 |
| 数据库 | SQLite | 单用户量级零部署=不过度设计 | PG/MySQL 强在多写/网络，均非所需 |
| 消息 | asyncio.Queue | 单进程内事件驱动 | Redis 价值在跨进程，此处=纯负债 |
| 本地推理 | Ollama | 要的是"别让我运维" | vLLM/llama.cpp 强在吞吐/底层，1 并发≈无感 |
| 向量 | FAISS+BM25 | 数据小到不用装服务 | 独立向量库比数据本身还重 |
| 模型抽象 | ChatModel harness | 换模型=换 Provider 不碰业务 | 双平级入口是 D17 的病根 |

> **总纲**：所有"为什么不选 X"的共同答案 = **02 §6：选的不是最强，是"对需求成本最低且够用"**；约束（R1–R10/C1–C7，01）是每个否定的合法性来源。
