## 1. 技术栈总览（先看结论）

| 类别 | 选择 | 一句话理由 |
|---|---|---|
| 语言 | **Python 3.10+** | AI 生态最全；全项目一致 |
| Agent 编排 | **LangGraph**（StateGraph + `Command(goto)`） | 图状态机天然表达"规划→执行→汇总" |
| 消息总线 | **自研进程内队列**（asyncio.Queue + Future） | 单机单用户，无需外部中间件（R1/C7） |
| 工具协议 | **MCP**（FastMCP；常驻 streamable-http） | 统一 LLM/SQL 工具通道，协议标准化 |
| 本地模型 | **Ollama + 1.8B qwen** | 免费基线，零 API 依赖（R5） |
| 外部模型 | **OpenAI 兼容 API**（混元/DeepSeek/glm） | 可选增强，走方案 C 防护 |
| 数据库 | **SQLite**（pysqlite3）+ 参数化 SQL | 单用户量级，零部署（R1） |
| 语义检索 | FAISS（IndexIDMap）+ embedding + **BM25 内嵌** | 记忆/用户文档的向量+词法混合检索 |
| 会话记忆 | 进程内 dict（short）+ pkl/FAISS 落盘（long） | 多轮 + 跨会话 |
| WebUI | Gradio | Python 生态内最快出对话界面 |
| 日志 | loguru | 统一日志 |
| 数据处理 | pandas / numpy | 统计计算 |

> 依据：`设计/03` §三 技术栈表（含版本与说明）。

## 2. 核心选型推演（从零做决定的过程）

### 2.1 语言：为什么必然选 Python

- 需求核心是"自然语言 + LLM + 统计"，Python 的 LangChain/LangGraph/FAISS/transformers 生态是唯一候选；
- 不是"Python 最好"，而是"**这个需求在 Python 里成本最低**"。
- 依据：`设计/03` §三（全项目 Python 3.10+）。

### 2.2 编排框架：LangGraph 还是自研状态机？

| 选项 | 说明 | 结论 |
|---|---|---|
| A. 自研图/状态机 | 早期 `agentCore/` 单图架构即自研 | ❌ 已退役（维护成本高，语义弱） |
| B. **LangGraph** | 官方 StateGraph，节点 + 边 + `Command(goto)` 动态流转 | ✅ 现役 |

**为什么 B**：
1. 编排的本质是"多步有状态流转"（plan → dispatch → wait → collect），LangGraph 的 StateGraph 与之一一对应；
2. `Command(goto)` 支持**运行时动态跳转**（追问、条件分支），不必把所有路径画死；
3. 官方维护、社区成熟，自己写状态机=重复造轮子且易错。

> 依据：技术栈表 `设计/03` §三；LangGraph 动态流转用法见 `设计/03` §1.2 时序与 §9.7。
> 历史证据：早期自研单图（`agentCore/`）的图栈已整体退役，仅 `parsers/json_parser.py` 一个文件被现役复用——`设计/03` §9.2 退役清单、`设计/08` §5.2 M13 行。

### 2.3 Agent 之间通信：为什么是"进程内自研队列"而非 Redis？

| 选项 | 说明 |
|---|---|
| A. 进程内 asyncio.Queue | 现役（A2A 总线，`mcpGateway/a2a_queue.py`） |
| B. Redis Stream + 消费组 | P2 演进方向（当前不做） |

**为什么 A（当前）**：
- 需求 R1 = 单用户单机，约束 C7 = 单进程部署，无外部中间件；
- 引入 Redis = 新增一个外部依赖，违背"零依赖部署"红线；
- 进程内队列在单机单用户规模下**完全够用**，且没有网络开销。

**为什么留 B 当 P2**：
- D2/D4/D11 的"彻底解决"（跨进程、持久化、广播）需要外部中间件；
- 但当前只做事件化改造即可满足（本系列 06 执行视角）。

> 依据：`设计/03` §八 T4（A 当前 → B P2）。D4 消息总线改造（事件驱动去轮询）见本系列 06。

### 2.4 工具协议：为什么引入 MCP 而不是直接函数调用？

先理解问题：Agent 需要两类能力——**读模型（LLM）**和**读写数据库（SQL）**。最简单做法是 Agent 直接 import 函数调用。为什么不行？

- Agent 直接调 `client.call_bill_sql(...)` → 每个调用点各自处理鉴权/审计/超时，能力散落（缺陷 D1，本系列 04 逻辑视角详述）；
- 工具是"可管理资产"，不是"调用点"——需要注册、发现、权限、审计、计时的统一平台。

**MCP（Model Context Protocol）提供的价值**：
- 工具调用走**标准协议**（FastMCP server 暴露 `llm_chat`/`sql_query` 等），业务侧只面向协议；
- server 与 client 分离：`client.py`（调用方）+ 3 个常驻 server（`llm_base`=`server_llm_base.py` / `llm_finance`=`server_llm_finance.py` / `sql_bill`=`sql_server/server_bill.py`，见 `client.py` 的 `SERVER_CMD_MAP`）；
- 传输层可演进：stdio 短连接 → streamable-http 常驻（本系列 06 执行视角），业务代码不变。

> 依据：`设计/03` §三（MCP 技术栈行）与 §五运行；网关层职责见 `设计/03` §2.5。
> 更完整的"为什么是工具平台而非裸调用"论证见本系列 04 逻辑视角·工具平台模块。

### 2.5 数据库：为什么 SQLite 而不是 PostgreSQL/MySQL？

| 维度 | 分析 |
|---|---|
| 数据量 | 个人消费，月几十~几百笔 → 单文件 SQLite 绰绰有余 |
| 部署 | 单机单用户，SQLite 零部署零运维（R1） |
| 一致性 | 单写者场景 + WAL + `busy_timeout` 足够（本系列 05 数据视角） |
| 代价 | 并发写需锁；无网络访问——但本项目恰恰不需要 |

**结论**：不是"SQLite 最好"，而是"**在单用户量级，引入数据库服务是过度设计**"。

> 依据：约束 C4（`设计/01` §7.2）；WAL/并发写策略见 `设计/04` §4.2/§4.3。
> 表结构设计见本系列 05 数据视角。

### 2.6 模型策略：为什么是"本地 + 外部"双通道？

| 通道 | 角色 | 触发 |
|---|---|---|
| 本地 Ollama（1.8B） | 默认基线，免费零依赖 | 无外部配置时 |
| 外部 OpenAI 兼容 API | 可选增强（更强表达） | 配置 `BILLAGENT_EXT_*` 后 |

**为什么双通道**：
- R5（本地可跑）+ 零成本默认路径：不配 API 也能全流程跑通（免费基线）；
- 但 1.8B 表达力有限 → 允许用户接更强的外部模型（增强表达，非改事实）；
- 外部模型输出经方案 C 三层防护（数字白名单）兜底（本系列 04/07）。

> 依据：`设计/01` §6 非功能需求、`设计/03` §四（双通道回退）；模型接入层 harness 见本系列 04 逻辑视角。

### 2.7 语义检索：FAISS + BM25 混合？

- 长期记忆（`memory/long_memory.py`）：FAISS 向量索引 + pkl 原文落盘；
- 用户文档库（`memory/user_docs.py`，M8 落地）：**BM25 内嵌 + embedding 可选**——`rank_bm25` 未装也能跑（BM25-only 降级），embedding 不可用时自动降级；
- 为什么 M8 后 BM25 成为内嵌兜底：外部依赖（`rank_bm25`）未安装时不能让 RAG 不可用。

> 依据：`设计/03` §三（RAG 行，含 BM25 Okapi k1=1.5/b=0.75 与 FAISS IndexIDMap 细节）；M8 用户文档库落地 `设计/08` §5.2（M8 行）。
> 记忆分层设计见本系列 05 数据视角。

## 3. 决定技术栈的"隐性力量"：11 项关键取舍（T1–T11）

> 这是 `设计/03` §八 8.2 的取舍表。**每行 = 一个"我们讨论过并拍板的决策"**。
> 从零视角看：这 11 行就是"如果重新设计系统，要拍板的全部关键选择题"。

| # | 议题 | 选项 | 结论 | 一句理由 |
|---|---|---|---|---|
| T1 | 能力如何暴露给 Agent | 硬编码方法 / 声明式 ToolSpec | **ToolRegistry 注册** | 注册即得鉴权+审计+计时+文档；需兼容层保护 ~40 处按名 patch 测试 |
| T2 | 子 Agent 是否进程化 | 多进程 / 单进程多协程 | **不进程化** | 推理负载在主进程之外（Ollama/API），协程已够；进程化是负优化 |
| T3 | MCP 传输层形态 | stdio 短连/长连 / HTTP 常驻 | **Streamable HTTP 常驻** | 冷启动 26~29s 只付一次；长连有 cancel 跨 task 崩溃问题 |
| T4 | 消息总线选型 | asyncio.Queue / Redis Stream | **Queue 现役 → Redis P2** | 单机单用户无需外部中间件 |
| T5 | 任务依赖从哪来 | 静态表 / LLM 动态 / 并集 | **动态+静态取并集** | 最坏退化为现状，绝不更差；误判有兜底 |
| T6 | 数据模型抽象度 | 字典表+多租户 / 硬编码 | **保持硬编码五分类** | Q1–Q3 锁定简单模型；抽象无收益 |
| T7 | RAG 装什么 | 内置规则 / 仅记忆 / 用户文档 | **用户文档库** | 内置规则本属确定性层；用户笔记是确定性层覆盖不到的 |
| T8 | finance 防幻觉 | RAG 增强 / 确定性底稿+白名单+记忆 | **三件套** | 只有确定性层产出的事实才可白名单校验 |
| T9 | 会话态存在哪 | graph state / 会话级存储 | **会话级（ShortSessionMemory）** | graph state 每次 ainvoke 重建，无法承载跨轮计数 |
| T10 | 编排器怎么拿事实 | 禁止取数 / 裸连 DB / 走 fact:read | **走正门** | 汇总必须拿到事实，问题只是走哪条路 |
| T11 | 模型接入层形态 | 双平级入口 / 标准 harness | **ChatModel harness** | 换模型不崩的根因是缺统一抽象（本系列 04） |

## 4. 架构红线（选型之后必须时刻记得的"不可违背项"）

1. Agent 之间**不直接调用函数**，一律 A2A 异步通信；
2. Agent **不直接访问 DB 与 LLM**，一律经网关/工具平台；
3. 业务能力沉淀在 coreModules/工具，Agent 只做编排与状态；
4. 记忆分长短两层；
5. 确定性优先：统计/物价/预警全是 SQL/数值计算；
6. 方案 C：白名单 → 修正重试 → 回退本地渲染；
7. 本地基线可交付：无 API 也完整运行。

> 依据：`设计/00` §1.1（红线 1-5）与 §1.2（核心设计要点 6-7）；`设计/03` §9.3.1（分层与依赖方向铁律）。
> 这套红线在 04 逻辑视角会变成"分层依赖铁律"，在 07 横切视角会变成"唯一入口"机制——**红线是横切能力的基石**。

## 5. 从零视角的"选型树"（一图记住为什么）

```
需求 (01)：单用户 · 仅支出 · 五分类 · 月预算 · 数字可信 · 本地可跑
   │
   ├─ 单用户/单机  ─────────────► SQLite + 进程内 A2A（不要 Redis/MySQL/多租户）
   ├─ 对话式多 Agent ────────────► LangGraph 图编排 + 1 编排 Agent + 4 子 Agent
   ├─ Agent 要用能力 ────────────► 工具平台 ToolRegistry（声明式，不裸调 client）
   ├─ 能力要走协议 ──────────────► MCP（FastMCP；常驻 HTTP 传输）
   ├─ 本地可跑(免费基线) ────────► Ollama 1.8B 默认 + 外部 OpenAI 兼容可选
   ├─ 数字可信(最高优先) ────────► 确定性事实层 + 方案 C 白名单三层
   ├─ 记消费习惯(跨会话) ────────► long_memory(FAISS+pkl) + short_memory(dict)
   └─ 个性化知识 ────────────────► userDocs 用户文档库（RAG 唯一入口，BM25+FAISS）
```

## 6. 小结

- **地基技术选的不是"最强"，而是"对这个需求成本最低且够用"**（SQLite vs MySQL、Queue vs Redis、协程 vs 进程都是这个逻辑）；
- **约束（R1–R10 / C1–C7）是选型的合法性来源**——每个"为什么不用 X"都能追溯到一条需求或现实约束；
- 真正花心思的是**抽象层设计**：工具平台、模型接入层、消息总线——这些才是系统可演进的骨架（T1/T3/T4/T11）。
