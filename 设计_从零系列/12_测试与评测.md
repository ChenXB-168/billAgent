# 12 · 测试与评测（软件工程 Stage 4：凭什么说它"对"）

> 软件工程闭环的最后一环：**验证**。一个 LLM 驱动的系统，"能跑通"不能证明质量——
> 模型输出非确定、语义会误判、数字会编造。本文讲：**用什么分层证明它对、指标怎么定义、基线长什么样、评测怎么反过来驱动修 bug**。
>
> 互引表：本篇依赖 07（防幻觉防线）与 08（评测环境的运行前提）；
> 也是 10 开工守则里"验收用数据说话"的证据来源。
>
> 依据：体系定义见 `设计/09_评测体系设计.md`；L3 基线数据见 `测试报告_总览.md` §六 与 `eval_reports/`；代码内嵌自检见 `tests/unit/test_contract_check.py`。

## 1. 为什么必须建评测体系（动机）

### 1.1 LLM 输出是非确定性的

同一条输入，每次输出都可能不同。实测遇到过的真实问题（`设计/09` §1.1）：

- JSON 键名插入空格：`"operate_sub_type"` → `"operate sub type"`，标准 `json.loads` 直接抛异常；
- 一次输出多个顶层对象并列，需拆分合并；
- 规划阶段漏掉用户明确要求（如"存账单"），或**脑补**出用户没提的任务；
- **金额幻觉**：原文 `45元`，模型输出 `200元`；把 `-30元` 的负号丢掉当正数；
- 语义误判：把"发奖金 5000 元"当支出记账。

> 共同点：**代码本身没写错，是上游模型输出不可信**。没有评测体系时只能靠肉眼，且无法量化"修好多少"。

### 1.2 评测体系守护的三类东西 + 一层保障

| 守护对象 | 破坏风险 | 手段 |
|---|---|---|
| 系统正确性（流程不崩/数据不丢） | 图控制流错误、超时、异常未兜底 | **L1** 确定性测试 |
| 子系统能力（检索找得对/全） | embedding 退化、索引漂移、阈值失效 | **L2** 检索评测 |
| Agent 回答质量（意图对/参数准/不幻觉） | 小模型语义误判、字段缺失、编造 | **L3** 回答质量评测 |
| 可持续演进（改一行不崩一片） | 回归、指标退化无人察觉 | **L4** 工程化（CI/存档） |

> 依据：`设计/09` §0（评测体系要守护的三类东西）。

### 1.3 设计五原则

1. **确定性优先**：能用代码断言解决的绝不用人眼/大模型判断；
2. **可复现**：固定种子数据（`evaluation/seed_memory_data.py`）、固定链路；
3. **防漂移**：评测集期望值**直接引用数据源原文**，数据源改动立刻暴露"seed 与 eval 不同步"；
4. **分维度**：意图/抽取/检索/格式分开评，问题能定位到具体能力；
5. **可对比**：产出结构化报告，指标可跨版本对比。

> 依据：`设计/09` §1.3。

## 2. L1：确定性测试层（pytest）

### 2.1 三层递进结构

| 层 | 目录 | 职责 | 依赖 |
|---|---|---|---|
| 单元 | `tests/unit/` | 单函数/单模块：JSON 容错、规划启发式、各 Agent 节点、A2A、记忆、RBAC | 无需 MCP，离线 |
| 集成 | `tests/integration/` | 模块协作：MCP 协议、记忆集成、**账单数据库正确性** | 需 LLM MCP |
| 端到端 | `tests/e2e/` | 完整链路：输入 → 规划 → 派发 → 子 Agent → 汇总 | 需 LLM MCP + 4 worker |

> **为什么分三层**：e2e 失败无法快速归因（规划错？派发错？子 Agent 错？）。三层把失败范围逐层缩小：
> unit 证"零件对"，integration 证"接口对"，e2e 证"整机对"。
> 依据：`设计/09` §3.1/§3.5。

### 2.2 断言业务语义，不只断言 pass/fail

```python
# 记账：必须回执"记账成功" + 正确分类"餐饮"
assert "记账成功" in result["final_reply"]
assert "餐饮" in result["final_reply"]
```

- `final_reply` 是自由文本，不能断言全文相等；
- 断言"关键业务语义词" = 校验流程走到了正确分支 + 内容质量对；
- 这些关键词是**产品文案**，断言它们等于校验用户可感知的结果。
- 依据：`设计/09` §3.2。边界用例（收入拦截/空输入不崩/多轮上下文）见 §3.4。

### 2.3 数据正确性测试（抓文本断言发现不了的问题）

`tests/integration/test_bill_db_integrity.py` 直连真实 `bill.db` 验证：

| 用例 | 验证 | 实证 |
|---|---|---|
| 写读回环 | INSERT 66.6/餐饮 → 查回一致 | 一致性最低保证 |
| 统计 SQL | seed 10/20/30 → SUM=60/COUNT=3 | SQL 错则一切统计皆错 |
| 负金额被拒 | INSERT -5 → 不落库 | 负数入账是数据毒瘤 |
| 非法类别被拒 | INSERT 非法五分类 → 不落库 | 约束是规则的物理实现 |

> **实证**：首跑 2/4 失败——`bill` 表是旧版本建的**没有 CHECK 约束**（`CREATE TABLE IF NOT EXISTS` 不会升级已有表）。
> 经 `init_db.py::migrate_bill_table()`（建约束新表→清理→复制→换名，幂等）修复。
> 这就是"L1 文本断言永远发现不了的问题"。依据：`设计/09` §3.3。

## 3. L2：检索质量评测（找得对、找得全）

### 3.1 为什么独立一层

检索是子系统内部能力，e2e 只能看到"最终回答对不对"，无法回答"是检索错了还是生成错了"；
故用信息检索标准指标离线评测，**无需 LLM**。

### 3.2 三个指标（缺一不可）

| 指标 | 回答的问题 |
|---|---|
| hit@k | "问得对，能不能问到东西"（可用性） |
| recall@k | "该给的给全了没"（多意图不丢信息） |
| MRR@k | "排得准不准"（答案靠前还是要翻很久） |

每个指标按 k=1/3/5 三档输出。

### 3.3 当前评测对象（M8 起）

| 源 | 脚本 | 状态 |
|---|---|---|
| ~~旧 RAG 常识库~~ | ~~`rag_recall_eval.py`~~ | 🗑 M8 下线（`ragKnowledge/` 删除） |
| 用户文档库 | `user_docs_recall_eval.py`（13 条 GT） | ✅ 现役（唯一 RAG 源） |
| 长期记忆 | `memory_recall_eval.py` | ✅ 现役 |

**userdocs 源基线（M8 首跑）**：13/13 可评 —— hit@1 **61.54%** / hit@3 **100%** / recall@5 **92.86%** / MRR@3 **0.7821**；
含来源标注硬断言（`doc_id` 与期望文件一致）与「GT 缺失即失败」。

> ⚠️ 跨源指标不可比：M8 起一切回归对照 userdocs 新基线（存档 `eval_reports/l2_baseline_userdocs_*.txt`）。
> 依据：`设计/09` §4 与 §7.1。

## 4. L3：Agent 回答质量评测（意图对、不幻觉、落库真）

### 4.1 为什么 pass/fail 不够

两个都"通过"的回答质量可能天差地别："记账成功。金额45元，分类购物。" vs "记账成功。"——必须**分维度打分**才能指导优化方向。

### 4.2 Rubric 五维评分（0–10 分）

| 维度 | 权重 | 0 分示例 |
|---|---|---|
| 意图正确性 | 高 | 该记的没记 / 收入被记账 / 任务漏规划 |
| 参数抽取 | 高 | 金额/类别/日期缺失或错 |
| 业务语义 | 高 | 金额幻觉（非原文数字）/ 统计虚构 |
| 格式完整 | 中 | 空回复 / 半截 JSON |
| 无幻觉 | 高 | 编造不存在的消费/金额/知识 |

> 高权重为"高"的原因：意图/参数/语义/幻觉任何一错，用户得到的是**错误信息**（比没信息更糟）。
> 依据：`设计/09` §5.2。

### 4.3 评分方式：规则 + LLM-as-a-Judge 混合

| 方式 | 适用 | 理由 |
|---|---|---|
| 规则打分（正则抽金额/关键词比对） | 参数/语义/无幻觉 | **确定性优先**，可复现零成本 |
| LLM-as-a-Judge | 意图/表述开放维度 | 只能交给模型 |

> Judge 本身也是 LLM → **规则能判的绝不用 Judge**（`设计/09` §5.3）。

### 4.4 db_accuracy：数据正确性硬校验

**动机**：五维 rubric 评的是"回复文本"，但记账系统最核心的真相在数据库里。"记账成功"背后可能没数据或数据是错的。

| 校验类型 | 判定 |
|---|---|
| `record`（应写入） | 按 `[测试标记]` 查库比对金额/类别 → **硬校验**：不过则 FAIL |
| `no_record`（应不写） | 运行前后 `MAX(id)` 快照对比 → 硬校验 |
| `stat_sum`（统计一致） | 回复数字 vs `SUM` 比对 → 软校验（DB 共享，只记录） |

> **实证（最有说服力的故事）**：`single_bill_001` 文本评分 10/10（回复满分），但落库金额 **25.0 vs 期望 38.0**——
> "文本对、数据错"，旧基线（仅文本断言）误判为 PASS，加 db_accuracy 后暴露。依据：`设计/09` §5.6/§5.7。

### 4.5 L3 基线（`测试报告_总览.md` §六 / 报告存档）

| 维度 | 本地基线 | 混元 hy3（方案 C 后） |
|---|---|---|
| 通过率 | **12/12（100%）** | **12/12（100%）** |
| 平均分 | **10.0** | 9.83 |

关键结论：
1. 数据层双模式 100% 正确（确定性计算不受表达层影响）；
2. 混元数字幻觉由方案 C 三层防护修复（原 2 条失败复跑 10/10）；
3. 推荐基线 = 本地确定性渲染（免费零依赖 12/12 均分 10.0）；hy3 为可选增强。

> 报告存档：`eval_reports/eval_report_20260816_local.json`（本地）、`eval_report_20260816.json`（hy3 方案 C 后）。

## 5. 评测驱动修复（这个项目最值得讲的方法论）

> 实证链（`设计/09` §1.2）：全量跑测 → 失败 → 定位根因 → 修复 → 回归，最终挖出并修复 11 个独立根因，包括：
> - e2e 全超时 = A2A worker 未启动（**评测环境自身错误！**）；
> - stat 崩溃 = LangGraph 静态边吞掉 `Command(goto=...)`；
> - SQL SUM 空结果 `float(None)` 崩溃。

**三条启示**：
1. 评测不只是"证明正确"，更是**为根因定位提供快速反馈回路**（失败用例即最小复现）；
2. **评测环境本身必须正确**（4 个 worker 没启动导致全红——先测评测，再测系统）；
3. 文本断言有盲区 → 数据正确性校验补上（L3 + integration 双保险）。

## 7. 已知局限与演进（诚实清单）

1. L3 基线暴露的个别缺陷未全修（如 1.8B 对"花了X"偶发脑补记账意图）；
2. e2e 依赖真实模型，存在偶发红（演进：固定 seed / 温度 0 / 重试语义）；
3. 检索评测集规模偏小（userdocs 13 组、记忆 10 组）；
4. 无覆盖率门禁（演进：对 json_parser/启发式等防御代码设 `--cov-fail-under`）；
5. LLM-as-a-Judge 二次不确定性（演进：双 Judge 投票）；
6. 统计一致性是软校验（演进：stat 用例独立 seed 库 → 升级硬校验）。

> 依据：`设计/09` §8。

## 8. 小结

1. L1 证明"系统对"（含库里写对没）、L2 证明"知识找得准"、L3 证明"回答质量高 + 落库真"；
2. 断言业务语义而非全文、分维度打分而非 pass/fail、规则优先于 Judge——三个方法论贯穿全体系；
3. **数据正确性硬校验**是记账系统的灵魂（文本满分 ≠ 数据对）；
4. 基线：L1 263 passed；L2 userdocs hit@3 100%；L3 本地 12/12 均分 10.0 / hy3 12/12 均分 9.83；
5. 评测的价值是**反馈回路**——失败用例即最小复现，驱动根因修复；
6. 评测与 10 开工守则闭合：**每个里程碑的验收标准都在这里找得到判据**。
