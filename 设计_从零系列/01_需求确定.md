## 1. 我们到底要解决什么问题

### 1.1 用户的真实痛点

记账理财产品很多，但日常用户的核心摩擦是：

1. **记账太麻烦**——打开 App、找分类、填金额，三步起，坚持不下来；
2. **记了也没反馈**——只有一本流水账，看不出"花得对不对、超没超、该怎么调整"；
3. **数字不可信**——AI 助手答非所问、编数字，反而添乱。

> 依据：`设计/01` §1 三条价值主张（零摩擦 / 主动提醒 / 数字可信）。

### 1.2 产品定位（一句话）

> **billAgent = 单用户的对话式个人消费管家**：
> 说一句话完成记账，系统自动归类、统计、比价、给建议，预算异常时主动提醒；
> 所有出现在回复里的数字都来自确定性计算（SQL/数值），不由模型编造。

依据：`设计/01` §1。

### 1.3 为什么定位成"对话式"

- 记账行为天然是"事后一句话"（"记午饭56元"），对话是最短路径；
- 用户随时可能问"这个月花了多少 / 打车贵不贵 / 怎么省钱"，对话能承载开放式查询；
- 一个主 Agent 做意图识别 + 多个专职子 Agent 分工执行，是把"一句话"变成"一组确定动作"的桥（详见 04 逻辑视角·产品功能模块）。

## 2. 功能全景：四大能力 + 一组配置 + 知识管理

### 2.1 能力矩阵

| 能力 | 意图 | 用户说什么 | 系统做什么 | 数字来源 |
|---|---|---|---|---|
| 记账 | `bill:add` | "记午饭56元" | LLM 结构化提取 → 规则校验 → 入库 → 沉淀习惯 → 触发预警链 | 全确定性 |
| 改账 | `bill:edit` | "把刚才那笔改成60" | 定位 → 更新 | 同上 |
| 删账 | `bill:delete` | "删掉刚才那笔" | 定位 → 删除 | 同上 |
| 统计 | `stat:query` | "这个月花了多少" | SQL 取数 → 汇总 + 同比环比 → 文本渲染 | **纯 SQL，零 LLM** |
| 比价 | `price:query` | "打车贵不贵" | 本城均价 → 同级城市兜底 → 溢价四档 | **纯数值计算** |
| 理财分析 | `finance:analyse` | "给我点省钱建议" | 确定性注入 + 规则事实底稿 + 用户资料(可选) → LLM 生成建议 | 事实确定，表达 LLM |
| 配置 | 隐含 | "设置月预算3000" | 写 `user_config` | — |
| 知识管理 | `doc:add/delete/list` | "记下：我们那香蕉8块一斤" | 写文件 → 索引对齐 | — |

> 依据：`设计/01` §3.1。细节（子类型、多意图拆分）见 `设计/01` §3.1；每条能力与产品需求的对应关系见 `设计/01` §4。

### 2.2 核心亮点：记账后的"预警链"（纯确定性，零 LLM）

一次记账完成后，系统不只说"记账成功"，还会按三条规则链主动给出反馈：

| 层 | 规则 | 触发 | 说明 |
|---|---|---|---|
| L1 单笔溢价 | 本类目均价对比 | 仅"偏高/过高"才提示 | 本地无均价→同级城市兜底→仍无则**跳过不打扰** |
| L2 品类进度 | 餐饮额度对比 | 接近/超出额度 | 额度来源：用户设定 > 历史月均 > 城市估算 |
| L3 总量预警 | 月预算四档 | over/warn 才提醒 | 分档：reward 犒劳 / ok 不打扰 / warn 预警 / over 超支点名主因 |

> 依据：`设计/01` §3.2（端到端示例）与 §3.3（预警规则表）。
> 设计要点：**"不打扰"和"提醒"同等重要**（R6：无异常不提示）——产品不做成话痨。

## 3. 五条原始需求 → 一个核心价值的五次细化

项目是**逐步提需求**攒起来的，表面看着散，其实五条需求全部落在「**预警与建议**」这一个核心价值上：

| # | 原始需求（用户原话摘要） | 落在 | 状态 |
|---|---|---|---|
| 1 | 每笔记账按预算管理消费，超大提醒，给后续建议；充裕也告知 | 记账+预警链（预算四档） | ✅ |
| 2 | 判断单笔是否过大；估算剩余天数消费，不足警告 | 比价 + 理财分析 | ✅（推算部分未 e2e） |
| 3 | 长期记忆记录消费习惯（月/品类金额+次数），供推算；拮据时警告 | 记账沉淀 + 理财分析 | ✅ |
| 4 | 预算充裕时提醒可以犒劳自己 | 预警链 reward 档 | ✅ |
| 5 | 主 Agent 识别意图，多子 Agent | ⚠️ **架构要求，非产品需求** | ✅ |

> ⚠️ 第 5 条特别值得注意：它是**实现手段**，不是用户要的。用户只关心"能听懂、办对事"。
> 把架构要求混进需求清单，正是后期架构复杂度上升的源头之一（A2A 总线、多 worker、跨 Agent 状态）。
> **启示：每次加需求前先问——这是用户要的，还是我们实现它的方式？**
>
> 依据：`设计/01` §4（含原始需求原话与实现要点）。

## 4. 边界：明确"不做什么"（比功能清单更重要）

> 以下"不做"均有**代码级证据**，不是猜测。它们是后续所有"简化决策"的合法性来源。

| 不做 | 代码级证据 | 后果（架构简化） |
|---|---|---|
| ❌ 多用户/登录/权限 | `bill`、`user_config` **无 user_id** | 无多租户抽象、无鉴权体系 |
| ❌ 记录收入 | `bill` 表 `CHECK(amount>0)`；`nodes.py` 明确拒绝收入 | 统计口径恒为总支出，无净结余概念 |
| ❌ 自定义品类 | 五分类硬编码 CHECK 约束 | 不建字典表，`city_price`/`monthly_habit` 品类联动保持简单 |
| ❌ 年度预算 | `budget_type` 的 `year` 未实现（遗留） | 预警链只处理"月"（该遗留已被收敛，见 `设计/04` D14） |
| ❌ 移动端/多端同步 | 单机 SQLite | 无服务端、无同步 |
| ❌ 银行流水自动导入 | 全靠对话记账 | 无外部金融接口 |
| ❌ 图表可视化 | 回复纯文本 | WebUI 只是对话界面 |
| ❌ 跨会话复杂状态 | 短期记忆在进程内 | 长期记忆只沉淀"月×品类"习惯 |

> 依据：`设计/01` §5。用法：任何新增需求先问"是否要打破某一条"？若是 = 产品升级（需改数据模型），不是"补个需求"。

## 5. 非功能需求（决定技术选型的约束）

| 类别 | 要求 | 对架构的影响 |
|---|---|---|
| **数字准确性（最高优先级）** | 金额/占比/溢价率 100% 确定性 | 确定性事实底稿 + 方案 C 三层防护 → 影响模型层/汇总层设计 |
| **本地可用** | 不配 API 也能完整跑通 | 本地 Ollama + 确定性渲染 → 影响模型层双通道设计 |
| **零成本默认路径** | 默认免费，外部 LLM 只是可选 | `EXTERNAL_LLM_ENABLED` 自动推导 |
| **容错** | 外部模型失败不崩、有兜底 | 双通道回退 + 超时 |
| **可验证** | 质量可量化、可回归 | L1–L4 评测体系（本系列 12） |
| **可观测（后补，R10）** | 每次 LLM 调用采集 token/耗时/成败，可归因 | Tracer + `llm_call_stat` 表 |
| **性能** | 可接受即可（非实时系统） | 不做激进优化；曾存在的 MCP 冷启动 26~29s 为已知瓶颈 |

> 依据：`设计/01` §6。⚠️ 注意"可观测性"是 2026-08-31 补的 R10——它的故事是"出了事才意识到要埋点"，详见本系列 07 横切视角。

## 6. 关键需求决策（Q1–Q6，全是"收缩型"决策）

> 还原需求时发现模糊点，全部拍板。**这六条决策共同把系统锁死在简单模型上**，
> 让后续架构"放心不做"多租户、不做收入、不做字典表、不做预算周期泛化、不为 RAG 建复杂链路。

| # | 决策 | 结论 | 一句话理由 |
|---|---|---|---|
| Q1 | 多用户？ | **不做** | 单用户省掉整座权限大厦 |
| Q2 | 记收入？ | **不做** | `CHECK(amount>0)` 保持，口径恒为支出 |
| Q3 | 品类可扩展？ | **不做** | 五分类硬编码够用，抽象无收益 |
| Q4 | 年度预算？ | **不要** | 只做月预算，`year` 是声称支持未实现 |
| Q5 | 追问几轮放弃？ | **3 轮** | 超限放弃并报错，防死循环纠缠 |
| Q6 | 理财建议事实走 RAG 吗？ | **分两层** | ①系统内置规则清理（属参数/规则，确定性层覆盖）；②**用户文档库**走 RAG 作"用户资料"参考，不进白名单 |

> 依据：`设计/01` §8。Q5 的追问治理落地为"会话级 3 轮上限 + 超限清草稿"，见本系列 04/05；Q6 的落点是用户文档库 `userDocs/` + `memory/user_docs.py`（本系列 05 数据视角）。

### 6.1 用户文档库（R9，2026-08-30 新增需求）

**它是"用户告诉系统的生活知识"**——`city_price` 表覆盖不到的细分地区/品类，由用户笔记补齐。

| 项 | 规则 |
|---|---|
| 存储 | `userDocs/`，文件系统是唯一真相源 |
| 格式 | v1 支持 txt/md，解析器注册制可扩展 |
| 上限 | 1000 条文档，超出明确提示 |
| 检索使用 | finance 分析时检索 top_k → 注入 prompt，**标注「用户资料」** |
| 冲突 | **确定性事实永远赢**；冲突时必须向用户说明差异 |
| 数字 | 用户资料数字**不参与白名单校验**，但允许 finance 引用做简单对比 |
| 分工 | price_agent 只处理 `city_price` 表；个性化知识全部走 finance 的 RAG |

> 依据：`设计/01` §3.5。为什么这么分工（简单化原则）详见 `设计/01` §3.5——不做"用户价格入库污染全局比价基线"，不做 `city_price` 个性化覆盖。

## 7. 约束清单（R = 需求派生，C = 现状技术约束）

### 7.1 需求派生约束 R1–R10

| # | 约束 | 来源 |
|---|---|---|
| R1 | 单用户、单机、SQLite | §2 |
| R2 | 品类固定五分类 | §4 |
| R3 | 只记支出 | §4 |
| R4 | 数字必须确定性（LLM 不得产出数字事实） | §5 最高优先级 |
| R5 | 必须本地可跑 | §5 |
| R6 | 预警不得打扰 | §2.2 |
| R7 | 预算周期仅"月" | Q4 |
| R8 | 追问最多 3 轮，超限放弃报错 | Q5 |
| R9 | 用户文档仅作参考，不进白名单；确定性优先 | §6.1 |
| R10 | 禁止静默失败；LLM 调用必须采集可观测数据 | §5（2026-08-31 补） |

### 7.2 现状技术约束 C1–C7（改造必须面对的现实）

| # | 约束 | 实证 | 对设计的影响 |
|---|---|---|---|
| C1 | Worker 是进程内协程，非独立进程 | `startup/bootstrap.py` | 持久化 ≠ 跨进程恢复；并发改造不能引入多进程 |
| C2 | Worker 消费不传 session_id | `bootstrap.py` | 总线不能改成"每 session 一队列"，保留 agent 级消费 |
| C3 | Worker 串行消费 | `bootstrap.py` | 重投必须防重复副作用 |
| C4 | 数据库是 SQLite | `database/bill.db` | 并发写需锁，状态机受限；但零新增依赖 |
| C5 | ~40 处测试按名 patch | `@patch(...call_bill_sql)` | 兼容层是必选项 |
| C6 | MCP 为 stdio 短连接 | `mcpGateway/client.py` | 冷启动开销大（后改常驻 HTTP，见本系列 06 执行视角） |
| C7 | 单进程部署，无外部中间件 | — | 无分布式一致性，也无水平扩展 |

> 依据：`设计/01` §7（两表）。C1–C7 是"为什么最终架构长这样"的隐形决定力量——本系列 02 的选型会不断引用它们。

## 8. 一篇小结（本篇产出清单）

从零想清楚产品，得到的关键结论：

1. **只服务一个人**（R1）→ 一切多租户/登录复杂度出局；
2. **只记支出**（R3）→ 数字模型简单，统计口径唯一；
3. **数字可信 > 功能丰富**（R4）→ 这是全系统最高优先级，驱动出"确定性优先 + 防幻觉方案 C"；
4. **本地可跑**（R5）→ 外部服务全部是可选项；
5. **边界写清楚**（§4）→ 以后拒绝"顺便加个功能"有依据。
