## 0. 手册用法与权威声明

### 0.1 三层文档结构

| 层 | 文档 | 职责 | 是否可写接口细节 |
|---|---|---|---|
| 解释层 | 01–08 / 10–12 | 需求为什么这样定、架构为什么长这样、怎么施工、怎么验收 | ❌ 涉及接口一律引用本文 |

| 校验层 | `utils/contract_check.py` + 测试 | 机器校验本文与代码零漂移，CI/测试强制门禁 | — |

### 0.2 基线冻结与变更流程

1. 冻结基线 v3.0（2026-09-04）= 当前生产代码快照；
2. 接口变更走三步：**改代码 → 回写本文对应契约卡（含修订记录表） → `python utils/contract_check.py` 全绿**；
3. 禁止"只改代码不回写契约"，禁止"文档里写两套接口"；
4. 若代码与本文冲突：**以代码为准**回改本文，并在 §0.5 登记"过期描述来源"。

### 0.3 契约卡统一格式

```
① 模块边界卡  → 职责 / ✅能做 / ❌不能做（红线）/ 所有权 / 状态
② 接口表      → 每个接口：签名 · 职责 · 返回 · 异常 · 连接（上游← / 下游→）
③ 契约卡      → 仅跨模块接口展开：前置条件 · 后置保证 · 参数约束 · 边界红线
```

- **签名（逐字）**：照抄代码 `def` 行，含默认值与类型注解；
- **返回与异常**：写清何时抛、抛什么、是否可重试；
- **连接**：`← 上游调用方` / `→ 下游依赖`，必填——改动时评估影响面的唯一依据。

### 1.4 契约卡：启动与关闭顺序

**`bootstrap_all()` 启动顺序（`bootstrap.py:317`，顺序不可颠倒）**

| 步 | 动作 | 失败后果 |
|---|---|---|
| 1 | `db.execute_sql("SELECT 1;")` | 抛（启动终止） |
| 2 | `load_user_docs()` | **告警不阻断**（首次检索时重建，§7） |

|---|---|---|
| 顶层错误 | `state["error_msg"]` 非空 | `执行终止：{error_msg}` |
| 空结果 | 无 `done` 任务 | `state["final_reply"]`（plan 阶段的确定性拦截文案优先）→ 否则通用兜底 |
| 追问超限 | `incr_ask_round(key) >= ASK_ROUND_LIMIT(3)` | `ASK_GIVEUP_TIP`，**清草稿 + 重置计数**，不再追问 |
| 有成功结果 | — | `text_blocks`（确定性渲染）→ `EXTERNAL_LLM_ENABLED` 时用 LLM 汇总 + **数字白名单闸门**（违规→修正重试 1 次→仍违规回退本地渲染）；否则本地渲染 |
| 仅有追问 | 无成功结果、有 `prompt_list` | 直接输出 `prompt_list[0]` |

> 收尾：`mem.add_msg("agent", final)`（与入口的 `add_msg("user")` 成对）→ 清空 `agent_result_cache`。

### 2.6 统一结果信封（子 Agent → orchestrator，★跨模块契约）

`wait_result_node` 收到的是 `reply_node` 发出的 **JSON 字符串**，解析后必须满足：

```json
{ "success": true|false|null, "agent_type": "bill_agent|stat_agent|price_agent|finance_agent",
```

|---|---|
| 异常/超时兜底 | `wait_result` 抛错 → 组装 `{success:false, error:str(e)}`；JSON 解析失败 → `{success:null, msg:"旧版非结构化文本", error:原文}`（`L1264-1283`） |

### 3.3 契约卡：消息格式与路由

**任务消息（`send_task` 组装，`L33-37`）**

```json
{
  "session_id": "<会话ID>",
  "task_id":    "<全局唯一路由键>",
  "task_data":  { ...按目标 Agent 差异化... }
}
```

- `task_id` 是**结果路由的唯一键**：`send_result(task_id)` 与 `wait_result(task_id)` 必须成对使用同一 `task_id`；
- `task_data` 四套差异（由 orchestrator `_build_task_data` 构造，消费方见 §1.3 的 init_state 映射）：

| 目标 | task_data 关键键 |
|---|---|
| bill_agent | `raw_segments`, `operate_sub_type`, `city`, `month`, `run_id`, `parent_span_id` |
| stat_agent | `raw_segments`, `user_input`, `session_memory`, `target_control`, `run_id`, `parent_span_id` |
| price_agent | `raw_segments`, `run_id`, `parent_span_id` |
| finance_agent | `raw_segments`, `operate_sub_type`, `session_memory`, `target_control`, `bill_result`, `stat_result`, `price_result`, `habit_data`, `user_docs`, `run_id`, `parent_span_id` |

> ★ finance 的前置结果由 **orchestrator 收齐后透传**，子 Agent 之间互不感知（拓扑红线）。

**结果回传**：子 Agent `reply_node` 调 `send_result(task_id, payload)`；payload 形态各异（bill/stat/price/finance 各自 `final_struct` 的 JSON 字符串或结构），消费方 `orchestrator.wait_result_node` 反序列化——详见 §2 各子 Agent 的 `final_struct` 卡。

### 3.4 契约卡：超时与一致性（★签名看不出）

| 语义 | 规则 | 出处 |
|---|---|---|
| 结果一次性消费 | `wait_result` 成功后 `pop` 掉 `_result_store[task_id]` 与事件；超时也清理 | `L153-159` |
| **结果无自动过期** | 若某 task 永远无人 `wait_result`，结果将常驻 `_result_store`（内存不释放） | `L135`（无 TTL） |
| 超时对齐 LLM | `wait_result` 默认取 **`config.MODEL_TIMEOUT`**（★M22 起 **150s**）——**引用常量，禁止硬编码**；M22 前为 240s（按本地 CPU 推理 189s 基线所设，本地通道已弃用） | `mcpGateway/a2a_queue.py` |
| 会话过滤不丢消息 | 会话不匹配的消息进 `_parked` 旁路（**不放回主队**——放回会让 `await queue.get()` 立即再取到同一条，退化为 100% CPU 忙循环） | `L11-14`, `L87` |
| 接收快路径 | `recv_task` 先 `get_nowait()`：若直接 `await queue.get()` 会让出控制权，同 loop 内的常驻 worker 会抢走本该由调用方接收的消息 | `L61-72` |
| 去轮询 | 已由 `get_nowait + sleep` 轮询改为 `asyncio.wait_for(queue.get())`，空闲零空转 | `L46-48`, `L94-97` |
| 日志副作用 | `send_task` / `recv_task_blocking` 直接 `print` 到 stdout（非 logger），排障时看 stdout | `L40`, `L102-124` |

### 3.5 契约卡：队列生命周期与事件循环（★红线）

1. `asyncio.Queue` 在**首次 `await get()` 时绑定所属事件循环**；跨 loop 复用会抛 `is bound to a different event loop`。
   → 故 `clear_all()` 采用**重建字典**而非逐个取空（`L20-24`）；多 loop 场景（e2e 两个 `asyncio.run`）必须先 `clear_all()`。
2. `send_task` / `send_result` 是**同步方法**，禁止 `await`；它们用 `put_nowait` / 直接赋值，不绑定 loop。
3. worker 与 orchestrator 必须运行在**同一进程同一事件循环**内——总线是进程内内存队列，跨进程不可用（跨进程改走 MCP，见 §5）。

### 3.6 拓扑红线（结构必然，非约定）

- **orchestrator 是唯一派发者**：A2A 单层（orchestrator ↔ 4 个子 Agent）；
- `wait_result` **只等 orchestrator 自己派发的 `task_id`**：子 Agent 若再行派发，链路不闭合（无人 `wait_result`），属结构性错误。

### 3.9 M23 契约（三层进程退出防御 · **已落地**）

> ✅ **本节已落地**（2026-10-09；方案见 `设计/21_三层进程退出防御方案.md`）。
> 来源：拷打复盘发现「`SIGTERM` 后 MCP 子进程成孤儿」—— 优雅关闭的**实现**完整（`shutdown_system`），
> 但触发路径**只接了 UI 按钮 / Ctrl+C**，且「被强杀」场景**零覆盖**。
> ★**为什么登记在 G3 下**：本节改的是**子系统生命周期**（父进程退出 → A2A 下游的 MCP 通道随之收敛），
> 与 §3.7 / §3.8 同属"进程间边界"的契约。

**（1）三层防御的分工（★本节核心口径）**

| 层 | 前提 | 机制 | 落点 |
|---|---|---|---|
| **L1 触发层** | 父进程有机会执行代码 + 已触发 | `shutdown_system()` | `startup/bootstrap.py`（**既有；本节不改其实现**） |
| **L2 信号层** | 父进程有机会执行代码 + 需 OS 通知 | `SIGTERM` / `SIGINT` → **统一转 `KeyboardInterrupt`** | `webUI/app.py::_install_signal_handlers`（新增） |
| **L3 内核层** | **父进程无任何执行机会**（强杀 / 崩溃） | Win `Job Object KILL_ON_JOB_CLOSE`；Linux `PR_SET_PDEATHSIG` | `mcpGateway/sandbox.py`（新增函数 / 改标志） |

> **L2 与 L3 是互补而非替代**：`kill -9` / `TerminateProcess` / 崩溃**原理上**无法被 L2 覆盖
> （内核直接回收，进程**无从感知**），只有 L3 有效。

**（2）L3-a：Windows Job Object（`mcpGateway/sandbox.py`）**

| 项 | 规则 |
|---|---|
| 变更 | `LimitFlags`：`_JOB_OBJECT_LIMIT_PROCESS_MEMORY` → **按位或** `_JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`（`0x00002000`） |
| 语义 | **Job 句柄全部关闭时**（父进程死亡 → OS 回收句柄），Job 内所有进程被**内核终止** |
| ★为何不误杀 | `_ACTIVE_JOBS[proc.pid] = job` **在父进程存活期始终持有句柄** → 触发条件在正常运行期**不可达** |
| 既有前提（恰好满足） | ① `CreateJobObjectW` 建的是**新 Job**，父进程不属于它；② `_ACTIVE_JOBS` **刻意不 `CloseHandle`**（原注释即为"句柄随 bootstrap 生命周期回收"） |
| 失败降级 | `AssignProcessToJobObject` 失败（父进程已在某 Job，如 IDE / shell）→ **告警、不阻断启动**（**既有行为不变**） |

**（3）L3-b：POSIX 父死信号（`mcpGateway/sandbox.py`）**

| 项 | 规则 |
|---|---|
| 新增符号 | `def apply_parent_death_signal() -> bool` |
| 实现 | `ctypes` 取 libc（`CDLL(None)`）→ `prctl(PR_SET_PDEATHSIG, SIGTERM, 0, 0, 0)` |
| 目标信号 | **`SIGTERM`**（**非** `SIGKILL`）—— 给 uvicorn 留自行优雅收尾的机会 |
| ★竞态处理 | `prctl` 在**父已死**时**不会**触发 → 设置后立即检查 `os.getppid()`；若为 `1`（已被 init 收养）则**主动退出**，不留孤儿 |
| 落点 | 由 `apply_process_limits()` 在 **POSIX 分支内**调用 → **3 个 MCP server 的 `__main__` 零改动获得** |
| 非 POSIX | 直接返回 `False`（不抛）；沙箱关闭（`memory_mb <= 0`）时一并跳过 |
| 失败降级 | 任何异常**只告警**（"沙箱是加固，不是故障点"） |

**（4）L2：信号 handler（`webUI/app.py` + `startup/chat_loop.py`）**

| 项 | 规则 |
|---|---|
| 新增符号 | `def _install_signal_handlers() -> None`（`webUI/app.py`） |
| 行为 | 对 `SIGTERM` / `SIGINT` 注册 handler，handler 内 **`raise KeyboardInterrupt`** |
| ★为何抛 `KeyboardInterrupt` | **复用已验证的异常冒泡路径** —— 从 `demo.launch()` 冒泡 → `main()` 的 `finally: shutdown()`。**不新写关闭逻辑** |
| 线程约束 | `signal.signal` **仅限主线程**；`main()` 在主线程 ✅；仍以 `try/except (ValueError, OSError)` 包裹 |
| CLI 入口 | `startup/chat_loop.py::run_chat` 的 `while` 外层补 **`try/finally: await shutdown_system()`** —— 修复"输入 `exit` 后 MCP 子进程泄漏" |

**（5）本节红线**

1. **不得只做 L2 或只做 L3** —— 两者覆盖场景**不重叠**，缺一即有明确反例；
2. **L3 不得改变 M4 内存限制语义** —— 必须是**按位或**，不是替换 `LimitFlags`；
3. **`_ACTIVE_JOBS` 不得改为 `CloseHandle`** —— 提前关句柄会**立即触发** `KILL_ON_JOB_CLOSE`，杀掉正在运行的 MCP 服务；
4. **PDEATHSIG 目标信号必须是 `SIGTERM`** —— 不得用 `SIGKILL`（剥夺 server 自行收尾机会）；
5. **`apply_parent_death_signal` 不得抛异常** —— 失败只告警，不阻断 server 启动；
6. **PDEATHSIG 必须做"父已死"竞态检查** —— 否则该场景下 server 仍成孤儿。

**（6）不改变的契约**

| 契约 | 状态 |
|---|---|
| `shutdown_system()` 的实现与语义 | **不变**（本节只补触发入口） |
| `stop_mcp_servers()` 的 `terminate()` → 5s → `kill()` 流程 | **不变**（L3 是**兜底**，不是替代） |
| M4 内存限制（`_JOB_OBJECT_LIMIT_PROCESS_MEMORY` / `RLIMIT_AS`） | **不变** |
| `SERVER_CMD_MAP` / 端口 / M3 常驻拓扑 | **不变** |
| `apply_process_limits(memory_mb, cpu_seconds)` 签名 | **不变**（仅函数内多一次 POSIX 分支调用） |

**（7）新增常量**

| 常量 | 值 | 用途 |
|---|---|---|
| `_JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` | `0x00002000` | Job 句柄全关时终止 Job 内所有进程 |
| `PR_SET_PDEATHSIG` | `1` | Linux `prctl` 选项号 |

| ★校验 | `load_user_docs` 对账时：`meta.version != _INDEX_VERSION` → **全量重建** |
| 为何必须有 | 对账依据是**文档内容哈希**，与索引格式无关 → "改了逻辑但文档未变"会**静默复用旧索引** |
| **红线** | **任何影响索引内容的逻辑变更，必须令 `_INDEX_VERSION` +1** |

**（4）本节红线**

1. **不得修改 `chunk["text"]`** —— 它是用户可见内容，也是 L2 评测 GT 的匹配基准；
2. **文档名词项不得"全量入"** —— 必须过滤掉正文已含的词（A/B 证据见方案 §2.1）；
3. **任何分块 / 词项逻辑变更必须递增 `_INDEX_VERSION`** —— 否则改动**静默失效**；
4. **`search_user_docs` 签名与 RRF 融合算法不变** —— 本节只改**索引侧**。

**（5）不改变的契约**

| 契约 | 状态 |
|---|---|
| `search_user_docs(query, top_k)` 签名与返回结构 | **不变** |
| `load_user_docs()` / `add_doc` / `delete_doc` / `list_docs` 签名 | **不变** |
| 索引四件套（`faiss.index` / `bm25.pkl` / `store.json` / `meta.json`）落盘格式 | **不变**（仅 `version` 值 1 → 2） |
| `_BM25` 打分实现（k1=1.5 / b=0.75） | **不变** |
| `chunk["text"]` 的内容 | **不变** |

| 常量 | 值 | 用途 |
|---|---|---|
| `_INDEX_VERSION` | `2` | 索引格式版本；与 meta 不符即全量重建 |
| `_HEADING_RE` | `^#{1,6}\s+\S` | ATX 标题行识别（不进索引） |

### 3.11 M25 契约（检索融合权重 + 残缺索引自愈 · **已落地**）

> ✅ **本节已落地**（2026-10-10；方案见 `设计/23_检索融合权重与残缺索引自愈方案.md`）。
> 来源：追查 M24 遗留待办 **T-1「BM25 高频词干扰」** 时 —— **原假说被实测证伪**，
> 但追查中发现两个**真实的**问题。
> ★**为什么登记在 G3 下**：本节改的是 `search_user_docs` 的**融合策略**与 `load_user_docs` 的
> **对账策略**，仍属 userDocs 子系统内部契约。

**（1）融合权重（D28-a：`search_user_docs`）**

| 项 | 规则 |
|---|---|
| 变更 | RRF 由**等权**改为**按路加权**：`score = Σ 1/(60+rank)` → **`Σ w/(60+rank)`** |
| 新增常量 | `_RRF_BM25_WEIGHT = 1.0`（词法路） / **`_RRF_VEC_WEIGHT = 1.5`**（向量路） |
| ★为何向量路加权 | 消费笔记是**口语化表述**，同一意图措辞差异极大（查询"交通/每天" vs 笔记"通勤/一天"——**零词重叠**，纯词法路无法召回）；向量路是**主力**召回通道 |
| 实证（两套形态不同语料交叉验证） | 真实库 hit@5 97.96% → **100%**、recall@5 96% → **98%**；fixture 持平（已饱和）；**反向**：`vec_w=0.5` 两套语料分别崩到 95.92% / 67.57% |
| 取值依据 | 1.5 与 2.0/3.0 结果**相同**（已达饱和）→ 取温和值更稳 |
| 不变 | `search_user_docs` 签名与返回结构；RRF 常数 60；候选池倍数 3；`_BM25` 实现 |

**（2）残缺索引自愈（D28-b：`load_user_docs`）**

| 项 | 规则 |
|---|---|
| 缺陷形态 | 磁盘索引标 `vector_ok=False`（无向量）时**永不修复** —— 对账的向量校验要求"模型**已加载**"，而模型是**懒加载**的，对账发生在启动期 → 校验被跳过 → 残缺索引长期复用 |
| ★实测代价 | 同一 50 条 GT：hit@1 **75.51% → 51.02%**、hit@5 97.96% → 91.84%、recall@5 96% → 90%（**静默**退化，无任何告警） |
| 修法 | 当 `not meta.vector_ok` **且** `EMBEDDING_ENABLED` 为真时，**强制探测一次**（代价 = 一次模型加载）以触发重建 |
| ★单向性 | **仅**对"残缺索引"生效；`vector_ok=True` 的索引仍走原懒加载路径，**不拖慢正常冷启动** |
| 开关约束 | `EMBEDDING_ENABLED=False`（"纯词法极速"模式）**不得**为其加载模型 → 不触发自愈 |

**（3）本节红线**

1. **两路都不可废** —— `vec_w` 不得设为 0（`vec_w=0.5` 即已使 hit@1 崩 20pp；`_RRF_BM25_WEIGHT` 必须保留）；
2. **`_RRF_VEC_WEIGHT` 不得低于 `_RRF_BM25_WEIGHT`** —— 向量路是口语场景的主力通道；
3. **自愈必须受 `EMBEDDING_ENABLED` 约束** —— 关闭 embedding 时不得为"修索引"而加载模型；
4. **自愈必须单向** —— 不得让 `vector_ok=True` 的索引也强制探测（否则拖慢每次冷启动）；
5. **本次不改索引内容** → `_INDEX_VERSION` **保持 2**（融合权重与对账策略都不影响索引字节）。

**（4）不改变的契约**

| 契约 | 状态 |
|---|---|
| `search_user_docs(query, top_k)` 签名与返回结构 | **不变** |
| `load_user_docs()` 签名 | **不变** |
| 分块规则 / 词项构造（M24/D27） | **不变** |
| `_INDEX_VERSION` | **保持 2**（本次不改变索引内容） |
| 索引四件套落盘格式 | **不变** |
| `EMBEDDING_ENABLED` 既有语义 | **不变** |

**（5）新增常量**

| 常量 | 值 | 用途 |
|---|---|---|
| `_RRF_BM25_WEIGHT` | `1.0` | 词法路 RRF 权重 |
| `_RRF_VEC_WEIGHT` | **`1.5`** | 向量路 RRF 权重 |

| ⑤ 超时 | `asyncio.wait_for(coro, timeout=spec.timeout)`；**`timeout<=0` = 关闭超时**（否则 `wait_for(0)` 会立即超时） |
| ⑥ 重试 | 见 4.7 |
| ⑧ 后置审计 | `auditable` 即记（**读也审**），`success=result.ok` |
| ⑨ 埋点 | 优先注入的自定义 tracer；否则 `record_tool_span(...)`；异常全吞（不阻断主链路） |

### 4.7 契约卡：重试闸门、异常映射与幂等

**重试决策（`_execute`，`L138-160`）**

| 异常 | kind | `retriable` 取值 |
|---|---|---|
| `asyncio.TimeoutError` | `TIMEOUT` | `not spec.side_effect` |
| `ToolError` | 沿用 | `e.retriable and not spec.side_effect` |
| `CONNECTION_EXC` | `CONNECTION` | `not spec.side_effect` |
| 其它 `Exception` | `INTERNAL` | `False`（不重试） |

- ★**重试安全性由 `side_effect` 决定，不是 `idempotent`**：有副作用 → 永不重试（机制层防重复记账）；
- 退出条件：`not last_err.retriable or attempt >= spec.max_retry`；**已达上限不再 sleep**（否则最后一次失败白等退避时长）；
- 指数退避 `min(2 ** attempt, 5)`（1, 2, 4, 5, 5…）；
- ⚠️ 捕获顺序敏感：Python 3.11+ `TimeoutError` 是 `OSError` 子类，必须排在 `CONNECTION_EXC`（含 `OSError`）之前，否则超时被误判为连接故障（`executor.py:136-137`）。

**`unwrap()` 异常映射表（`tool_model.py:127-135`）**

| ToolErrorKind | 原生异常 |
|---|---|
| `PERMISSION` | `PermissionError` |
| `VALIDATION` | `ValueError` |
| `TIMEOUT` | `TimeoutError` |
| `CONNECTION` | `ConnectionError` |
| `NOT_FOUND` | `ValueError` |
| `REMOTE` | `RuntimeError`；若 `origin` 非 None 则直接抛 `origin` |
| `INTERNAL` | `RuntimeError` |

**幂等边界**：`ToolSpec.idempotent` 仅作语义标注（"结果是否确定"），**不参与任何重试/去重判定**；真正的幂等键是 `task_id`（§1 TaskManager）。

3. `context_window` 供 ContextManager 按**实际所选后端窗口**换算，不得写死。

> ★**M20（D22）：白名单中文数字归一化语义（`extract_numbers`）**
>
> `extract_numbers` 现**同时抽取中文数字**，与阿拉伯数字**同等严格**地参与白名单比对：
> `五十`→50、`一百二`→**120**（省略尾"十"，非 102）、`两百`→200、`三千五`→3500、`五十多`→**50**。
>
> **★为何"五十多"取 50 而非 51**：白名单闸门的目的是**防编造**，不是"精确对齐口语"。
> 取 51 需假设"多"= "+1"，是**无依据的推断**（"多"可能是 51~59 任意值）；
> 取 50 使**下界确定** —— 模型若输出 51 而白名单只有 50，容差 0.5 下会被判幻觉并触发修正重试，
> 属"**多拦一次**"的保守失败。**在防幻觉场景，宁可误拦，不可漏放。**
>
> **已知边界（不得过度承诺）**：仅覆盖常规数词 + 口语量词（两/俩）；
> **不覆盖**"半"（"五十半"）、分数、成数（"八成"）；**不做上下文消歧**
> （"十点"中的"十"会被抽取 —— 该行为**与既有阿拉伯数字一致**，属既存边界，非本次引入）。

## 10. 红线与硬语义汇总（G10）

> 各节卡片已写"签名看不出但必须守"的语义，本节汇总便于开工前速查。**改任何一项都属架构级变更**。

### 10.1 六条架构红线

| # | 红线 | 违反后果 |
|---|---|---|
| 1 | **Agent 之间不直接调用函数**，一律 A2A 总线（`mcpGateway/a2a_queue.py`） | 破坏单层拓扑 |
| 2 | **Agent 不直接访问数据库与 LLM**，一律经 MCP 网关 / 工具平台 | 绕网关 = 无鉴权、无审计、无超时、无打点 |
| 3 | **业务能力沉淀在 `coreModules/` 与工具**，Agent 只做编排与状态流转 | 逻辑散落不可测 |
| 4 | **记忆分长短两层**：短期随会话（进程内）、长期跨会话（pkl + FAISS） | 跨轮状态丢失或污染 |
| 5 | **prompts 与代码分离**（`agents/*/prompts/*.j2` + `prompt_loader.py`） | 提示词不可维护 |
| 6 | **orchestrator 是唯一派发者**：子 Agent 不得自行派发；`wait_result` 只等自己派发的 `task_id` | 链路不闭合，结果永远无人收 |

### 10.2 生命周期红线（★跨循环即崩）

| 对象 | 规则 |
|---|---|
| webUI 事件循环 | **禁用 `asyncio.run`**：run 结束即关 loop，常驻 worker 被取消（`webUI/app.py:22-24`） |
| `asyncio.Queue`（A2A） | 首次 `await get()` 绑定 loop；跨 loop 复用抛 `is bound to a different event loop` → 多 loop 场景先 `clear_all()`（重建而非取空） |
| MCP 子进程句柄 | 用 `subprocess.Popen` 而非 `asyncio.create_subprocess_exec`（后者的 `wait()` Future 绑 loop） |
| MCP 客户端连接 | 短连接：每次调用**同一 task 内** `async with` 建立并释放（跨 task 复用的 cancel scope 会崩） |
| `DatabaseCRUD` 单例 | `close()` **单向不可重开**；进程内/测试调用 `init_all_tables(close_after=False)` |
| `contextvars` | **不跨独立协程传播**：run_id / parent_span_id 必须经 `task_data` 显式下发并在 worker 侧重建 |

### 10.3 重试与幂等红线

| 规则 | 说明 |
|---|---|
| 有副作用 → 永不重试 | 由 `ToolSpec.side_effect` 决定，**不是** `idempotent`（后者仅语义标注）。`sql.write` / `habit.upsert` 一旦落库，重试即重复记账 |
| 底层重试不叠加 | `MCPClient._call_server` 自带 `MAX_CONNECT_RETRY=2`；引擎层 `max_retry=0`，否则 2×N 乘数效应 |
| 写工具关闭底层重试 | `MCPAdapter` 对 `side_effect=True` 传 `max_retry=0`（`adapters.py:172`） |
| 有副作用任务禁直接重投 | `SIDE_EFFECT_AGENTS={"bill_agent"}`：崩溃后先按 `bill.task_id` 对账，禁止直接重投 |
| 幂等键 | `task_id` 是唯一幂等键（`INSERT OR IGNORE`）；它防"重投"，**不防"重说"** |
| 超时捕获顺序 | `asyncio.TimeoutError` 必须排在 `CONNECTION_EXC` 之前（3.11+ `TimeoutError` 是 `OSError` 子类） |

3. 违规处理：修正重试 **1 次** → 仍违规 → **回退确定性底稿渲染**（`_render_local_final` / `_render_fact_fallback`）；
4. 建议性数字豁免：含"建议/预计/下调至/控制在"等词且可推算的数字，须以建议口吻呈现，不得写成实际发生额；
5. `ASK_GIVEUP_TIP`（"信息不全，执行失败，请重新来"）为需求明文，**改动即属需求变更**。
