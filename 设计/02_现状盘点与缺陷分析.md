## 第 2 章 P0 架构级缺陷详解（5 条）

### D1 · 工具接入平台抽象层缺失

**严重度**：★★★★★ ｜ **命中 JD**：职2c（Skills 编排与 MCP 协议集成）、加1

#### 现状

你**有 MCP 客户端网关，没有工具接入平台**。二者区别：

| | 你有（网关） | 你没有（平台） |
|---|---|---|
| 解决 | 这一次调用怎么安全发出去 | 工具怎么被定义/注册/发现/归一/复用 |
| 层次 | 传输 + 安全（最后一公里） | 抽象 + 生命周期（最前一公里） |
| 代码 | `mcpGateway/client.py`、`rbac_config.py`、`audit_recorder.py` | **零实现** |

#### 证据

**① `ToolSpec` / `ToolRegistry` / `register_tool` 代码零命中**——全项目搜索仅命中 `.md` 文档：学习手册 214-244 行（设计伪码）、SSP 文档 243 行（"预留 ToolRegistry"话术）、对标评估 170/185 行。**抽象层停在纸面**。

**② `client.py` 是"手写方法"而非"统一入口"**——对外仅 3 个方法，每个各自硬编码五件事：

```91:116:d:/MyCode/billAgent/mcpGateway/client.py
    async def call_bill_sql(self, agent_id: str, sql: str, params: list = None):
        """账单数据库SQL调用，自动权限校验+审计"""
        # 权限校验
        perms = get_agent_permission(agent_id)
        sql_upper = sql.strip().upper()
        if sql_upper.startswith("SELECT"):
            required_perm = DBPerm.BILL_READ
        else:
            required_perm = DBPerm.BILL_WRITE
```

`SERVER_CMD_MAP` 只到 **server 粒度**（3 个启动命令），工具 schema 散落在各 server 的 `@tool` 装饰器里，平台侧无法枚举。

**③ 本地工具与 MCP 工具双轨**：`coreModules/` 5 个确定性模块（`bill_analyzer`/`bill_parser`/`finance_advice`/`price_compare`/`target_control`）是 `import` 直调，与 MCP 工具无任何归一接口。

#### 影响

- 加一个工具 = 改 `client.py` 加方法 + 改 RBAC + 改审计 + 改调用方（**违反你自己定的"加工具 = 注册一行"目标**）
- 无法 LLM 自主选工具（缺 `list_tools` + schema）
- **Skills 无法编排**——Skill 不能声明"我依赖哪些工具"
- 工具资产无法被外部系统复用

#### 进阶方案

```python
# mcpGateway/registry.py  (~80 行)
@dataclass
class ToolSpec:
    name: str
    description: str                    # 决定 LLM 选不选它
    params_schema: dict                 # JSON Schema
    executor: Callable | None = None    # 本地 callable
    transport: Literal["local", "mcp"] = "local"
    server_key: str | None = None       # transport=mcp 时的 SERVER_CMD_MAP key
    mcp_tool_name: str | None = None
    side_effect: bool = False           # → 决定是否强制审计
    required_perm: str | None = None    # → 接 RBAC
    timeout: float = 120.0
    idempotent: bool = True             # → 决定是否可自动重试

class ToolRegistry:
    def __init__(self, mcp_client, audit): 
        self._tools, self._mcp, self._audit = {}, mcp_client, audit

    def register(self, spec: ToolSpec):
        self._tools[spec.name] = spec

    # ② 发现：权限过滤即发现过滤（复用你已有的双层 RBAC）
    def list_tools(self, agent_id: str) -> list[dict]:
        perms = get_agent_permission(agent_id)
        return [{"name": t.name, "description": t.description,
                 "parameters": t.params_schema}
                for t in self._tools.values()
                if not t.required_perm or t.required_perm in perms]

    # ③④ 执行引擎 + 协议适配：业务只认 ToolSpec，协议是最后一公里
    async def invoke(self, name, args, *, agent_id, session_id=None):
        spec = self._tools[name]
        t0 = time.time()
        try:
            if spec.transport == "mcp":
                return await asyncio.wait_for(
                    self._mcp._call_server(spec.server_key, spec.mcp_tool_name, args), spec.timeout)
            return await asyncio.wait_for(asyncio.to_thread(spec.executor, **args), spec.timeout)
        finally:   # 审计/耗时/归因统一在此，所有工具自动生效
            self._audit.write(agent_id, name, args, (time.time()-t0)*1000, session_id)
```

**收益**：加工具 = 注册一行；本地/MCP 同构；`list_tools` 一出，同时解锁"LLM 自主选工具"与"Skills 依赖注入"两个能力。

**验证方式**：新工具从"注册一行"到可被 agent 调用，全程不改 `client.py` / RBAC / 审计代码。

```python
    session_id TEXT NOT NULL,
    agent_id   TEXT NOT NULL,
    status     TEXT NOT NULL,          -- submitted|running|completed|failed
    payload    TEXT,                   -- JSON
    result     TEXT,
    retry_cnt  INTEGER DEFAULT 0,
    created_at REAL, updated_at REAL
);
CREATE INDEX idx_task_status ON task_state(status, updated_at);

# 2) 状态机 + 幂等键
# submitted →(worker 领取)→ running →(成功)→ completed
#                              └→(失败且 retry<3)→ submitted（幂等键 = task_id，重投不重复写库）
#                              └→(失败且 retry>=3)→ failed

# 3) 崩溃恢复：启动时扫描残留
def recover_orphans(self):
    """启动时把上次进程遗留的 running 任务标记为 failed 或重新入队"""
    rows = db.execute("SELECT task_id FROM task_state WHERE status='running'")
    for (tid,) in rows:
        db.execute("UPDATE task_state SET status='submitted', retry_cnt=retry_cnt+1 "
                   "WHERE task_id=? AND retry_cnt<3", (tid,))
```

**验证方式**：`kill -9` 掉进程 → 重启 → 观察残留任务被扫描恢复；重复投递同一 `task_id` → 库表无重复写入。

### D4 · 消息总线设计缺陷（定时轮询 + 回插扫描 + 死参数）【已按真实代码校正】

**严重度**：★★★☆☆（**已由 ★★★★☆ 下调**）｜ **命中 JD**：加3（高并发）、职2a

> 这条是本次复盘**新发现**的缺陷，SSP 文档未记录。
>
> ⚠️ **勘误**：早期描述为"单队列混装所有会话 + 忙等自旋 + O(n²) 退化"，与真实代码不符。
> 真实结构是 `self._task_queues: Dict[str, asyncio.Queue]`（**每个 agent 一个独立队列**，L8），
> 且 `await asyncio.sleep()` **会让出控制权，不空耗 CPU**。缺陷依然成立，但形态与严重性重界定如下。

#### 现状三处硬伤

**① 定时轮询（`recv_task_blocking` L67-72）——生产路径真实存在**：

```67:72:d:/MyCode/billAgent/mcpGateway/a2a_queue.py
        while True:
            try:
                msg = queue.get_nowait()
            except asyncio.QueueEmpty:
                await asyncio.sleep(0.1)
                continue
```

队列空时**每 0.1 秒醒一次**重试。因为 `await asyncio.sleep()` 会 yield，它**不占 CPU、不卡其他协程**——
所以这不是"忙等自旋"。真实代价是：**消息最坏要等 100ms 才被取到** + 空闲时每秒 10 次无谓唤醒。

**② 回插扫描（`recv_task` 传了 session_id 时，L52-56）——仅测试/业务路径**：

```52:56:d:/MyCode/billAgent/mcpGateway/a2a_queue.py
            if session_id is None or msg["session_id"] == session_id:
                return msg
            # 会话不匹配，放回队列尾部
            queue.put_nowait(msg)
            await asyncio.sleep(0.1)
```

队内混装**该 agent** 的所有会话，取消息时是"取出→比对→不匹配→回插队尾→sleep"的扫描循环，并发 N 个会话时退化到 O(N) 次尝试。

**关键限定**：4 个 worker 调用 `recv_task_blocking(agent_name)` **都不传 session_id**（`startup/bootstrap.py` L36/60/86/109），
`session_id is None` 直接短路返回 → **生产路径永不触发回插**。只有测试 `test_a2a_session_isolation` 走这条路。

**② `send_result` 的 `target_agent` 是死参数**：

```89:96:d:/MyCode/billAgent/mcpGateway/a2a_queue.py
    def send_result(self, target_agent: str, session_id: str, task_id: str, result: Any):
        """Worker回传执行结果"""
        # 无论是否存在等待者，先存入结果
        self._result_store[task_id] = result
```

`target_agent` 在函数体内**完全未使用**——结果只按 `task_id` 存，没有 agent 维度路由，说明结果寻址机制未真正落地。

**③ 无背压（backpressure）**：`put_nowait` 无界队列，生产者快于消费者时内存无上限增长。

#### 影响（修正后）

- **投递延迟最坏 100ms**：本地 CPU 推理单次调用动辄数十秒，100ms 占比极小 → **不是当前瓶颈**
- 空闲时每秒 10 次无谓唤醒（CPU 占用极低，但设计不优雅）
- 路径②跨会话取出顺序不稳定（**仅影响测试语义**，生产路径不触发）
- **无背压**：`put_nowait` 无界队列，生产者快于消费者时内存无上限增长（**这条比 ①②更值得关注**）

> **严重性下调理由**：不存在 O(n²) 退化、不存在 CPU 空转、**不存在"多会话并发最先崩"**。
> 按真实代码，当前架构最先崩的是 **D5（会话态全局 dict 无上限无 TTL，长跑必泄漏）**
> 与 **worker 串行导致的吞吐天花板**（每个 agent 同时只能处理 1 个任务）。

#### 进阶方案

**方案 B（~10 行，推荐先做）**：保留每 agent 单队列，只把轮询换成 `await queue.get()`：

### D26 · 进程退出防御**不完整**（`SIGTERM` 无 handler + 强杀无内核级兜底 + CLI 入口无收尾）

**严重度**：★★★★☆ ｜ **命中 JD**：职2（可靠性 / 进程生命周期）
**来源**：拷打复盘被问「你的项目有没有做 SIGTERM 优雅关闭」时**逐层核查**暴露。

**证据**（★典型「**机制存在但没接上**」型缺陷）：

- **全项目 0 个 `signal.signal()` 注册**：全仓检索 `signal.signal` / `add_signal_handler` / `atexit`，
  仅命中 `utils/retry_utils.py` 的注释（提及 `KeyboardInterrupt`），**无任何注册调用**；
- **`SIGTERM` 下 `finally` 不执行**：Python 对 `SIGTERM` 的默认行为是**直接终止进程** ——
  不抛异常、**不执行 `finally`**、不跑 `atexit`。故 `webUI/app.py::main()` 的
  `finally: shutdown()` **根本不执行** → 3 个 MCP 常驻子进程（8001/8002/8003）**全部成孤儿**；
- ★**`SIGINT`（Ctrl+C）之所以可用，是 Python 的默认待遇**（自动转 `KeyboardInterrupt`），
  **不代表项目做了信号处理** —— 这是极易误判为"已经做了"的一点；
- **强杀场景 100% 无覆盖**：Job Object 只设了 `_JOB_OBJECT_LIMIT_PROCESS_MEMORY`，
  **缺 `KILL_ON_JOB_CLOSE`** → `taskkill /F` / 崩溃时子进程无人回收；
- **CLI 入口无收尾**：`startup/chat_loop.py::run_chat` 的 `while` 循环 `break` 后直接返回、**无 `finally`**
  → 4 个 worker（协程）被 `asyncio.run` 取消而收敛，但 3 个 `Popen` 子进程**必然泄漏**
  （现状靠下次启动 `_cleanup_stale_mcp_ports()` **事后清理**兜底）；
- **注释误导**：`utils/docker_compose.yml` 称「tini 转发信号 → `shutdown_system` 生效」，
  **因果链断裂** —— tini 只解决"信号**送达**"与"僵尸回收"，**不解决"收到信号后执行清理"**
  （后者取决于 Python 侧是否注册 handler）。

**方案（代码已落地 · M23）**：**三层防御**，按「**父进程是否还有机会执行 Python 代码**」划分：

| 层 | 前提 | 机制 |
|---|---|---|
| **L1 触发层** | 有机会执行 + 已触发 | `shutdown_system()`（**既有**，本次只补触发入口） |
| **L2 信号层** | 有机会执行 + 需 OS 通知 | `SIGTERM` / `SIGINT` → 转 `KeyboardInterrupt`（**复用既有冒泡路径**） |
| **L3 内核层** | **无任何机会**（强杀 / 崩溃） | Win `Job Object KILL_ON_JOB_CLOSE` / POSIX `PR_SET_PDEATHSIG` |

三层**互补不可替代**：`kill -9` / `TerminateProcess` / 崩溃**原理上**无法被 L2 覆盖
（内核直接回收，进程无从感知）。（`设计/21`，契约 `09` §3.9）

> ★**这类缺陷的通用形态**：「**机制存在但没接上**」—— `shutdown_system` 的**实现**完整且可用，
> 但**从没人验证过 `kill -15` 这条路径**。与 D25（基线变更后派生项未同步）同属"**局部正确、整体不全**"。
> **对策**：能力落地时须显式列出"**该能力的全部触发路径**"并**逐条验证**
> （本例即漏了 `SIGTERM`、CLI 入口、强杀三条）。

### D27 · userDocs 检索质量缺陷（标题行进索引 / 文档名未参与检索 / 索引版本不校验）

**严重度**：★★★☆☆ ｜ **命中 JD**：职2（检索质量 / 工程质量）
**来源**：拷打复盘追问「个人笔记的检索链路有做测试吗」时，**补规模化测试**（55 篇语料）暴露。

**证据**：

- **① 标题行进索引**：`_chunk_lines` 按行分块但**未过滤 Markdown 标题行** ——
  真实库 68 个 chunk 中 **7 个是纯标题**（占 10.3%）。L2 评测查询 #8「我怎么给消费分档」
  的 top1 即 `# 我的日常消费习惯` —— 一个**不含实质信息**的标题行，却占掉了一个 top_k 名额；
- **② 文档名未参与检索**：`_rebuild` 的词项**只用 `chunk["text"]`**，`doc_id`（文档名）完全不参与 ——
  分块粒度是**行**，而主题词常只出现在文档名里（如 `物价_水果_香蕉.md` 正文写的是"香蕉"，
  **全篇无"水果"二字**）→ 查询「水果的物价怎么样」时**三篇水果笔记只能召回一篇**；
- **③ 索引版本不校验**：`meta.json` 的 `version` 字段**只写不读**，`load_user_docs` 对账仅比对
  `meta.files`（文件内容哈希）→ **改了分块 / 词项逻辑而文档未变时，旧索引被静默复用，
  改动"看起来生效、实际没生效"**（本次实施中**实际踩到**，靠手工探针才发现）。

**方案（代码已落地 · M24）**：

| 项 | 修法 |
|---|---|
| ① | `_chunk_lines` 过滤 `^#{1,6}\s`（`_HEADING_RE`）；丢失的主题信息由 ② 补回 |
| ② | 新增 `_chunk_tokens`：chunk 词项 = **文档名独有词**（★**不得全量入**）+ 正文词 |
| ③ | 新增 `_INDEX_VERSION`，对账时校验，不符即**全量重建** |

（`设计/22`，契约 `09` §3.10）

> ★**② 的取舍过程值得记住**：第一版实现是"文档名**全量**入词项"—— 它在刚造的 55 篇**专题**语料上
> 效果极好（hit@5 **83.78% → 97.30%**），但在**真实库（综合笔记 + 专题笔记混排）**上反而
> 让 **hit@1 下降 7.7pp**。原因是泛化文件名词（`消费习惯.md`）与专题名（`习惯_冲动消费控制.md`）
> **语义重叠** → 泛化词跨多篇出现 → df 抬高、IDF 下降 → 区分度被稀释。
> **只补"正文里没有的文档名主题词"** 才同时满足两边（真实库回到基线、专题语料保住收益）。
> **教训：单一语料上的 A/B 会骗人，必须用"形态不同的多套语料"交叉验证。**
>
> ★**③ 的通用形态**：「**派生逻辑变更后索引不重建**」—— 与 D25（基线变更后派生参数未同步）
> **完全同源**，只是这次发生在**索引层**而非参数层。**对策**：任何"派生物"都必须带**版本号**
> 并参与对账校验。

### D28 · 检索融合权重失衡 + 残缺索引不自愈

**严重度**：★★★☆☆ ｜ **命中 JD**：职2（检索质量 / 可观测性）
**来源**：追查 M24 遗留待办 **T-1「BM25 高频词干扰」** 时 —— **原假说被证伪**，但追查中发现两个真实问题。

**证据**：

- **① 融合权重失衡**：`search_user_docs` 的 RRF 是**两路等权**（`Σ 1/(60+rank)`，各贡献 1.0）。
  但消费笔记是**口语化表述**，同一意图的措辞差异极大 —— 查询「每天交通花多少」与笔记
  「工作日通勤坐地铁，单程 4 元」（**零词重叠**）只能靠向量路跨表述匹配。
  实测反向验证：`vec_w=0.5`（偏词法）时 hit@1 **75.51% → 55.10%**、fixture 81.08% → 67.57%。
- **② 残缺索引不自愈**：`load_user_docs` 的向量一致性校验**只在"模型已加载"时进行**
  （为冷启动速度刻意设计），而模型是**懒加载**的、对账发生在**启动期** → 校验被跳过 →
  `vector_ok=False` 的**残缺索引被长期复用**，检索**静默退化**为 BM25-only。
  实测代价：同一 50 条 GT 下 hit@1 **75.51% → 51.02%**、hit@5 97.96% → 91.84%、
  recall@5 96% → 90%，**全过程无任何告警**。
  **修复前真实库索引正处此态**：`meta.vector_ok=False`、`dim=0`、`faiss.index` **0 字节**。

**方案（代码已落地 · M25）**：

| 项 | 修法 |
|---|---|
| ① | RRF 改为**按路加权** `Σ w/(60+rank)`；`_RRF_VEC_WEIGHT = 1.5` / `_RRF_BM25_WEIGHT = 1.0` |
| ② | `load_user_docs`：`not meta.vector_ok and EMBEDDING_ENABLED` → **强制探测一次**以触发重建（**单向**） |

（`设计/23`，契约 `09` §3.11）

> ★**这次的通用形态是「隐性降级」**：缺陷①是**能力被低估**（设计上没体现"口语场景向量为主"），
> 缺陷②是**能力被静默剥夺**（索引缺向量却不告警、不自愈）—— 后者更危险：
> **数据仍然"看起来正常"，只是质量悄悄掉了 24.5pp**。
>
> ★**方法论收获（T-1 的证伪过程同样有价值）**：本项起点是一个**错误假说**
> （"高频词干扰"），若直接按假说去做停用词表，会得到一次**零收益甚至负收益**的改动
> （实测标点过滤使 hit@3 97.96% → 95.92%）。
> **故：改动前先做"归因实证"（df 统计 / 交集验证 / A/B），比"先改再看"更省时。**
>
> ★**过程中的一次自我纠错**：`vec_w` 落地后跑评测得到 51.02%（"变差"），一度以为加权有害；
> 用**受控环境（临时副本 + 干净重建）复测**才发现那次跑的是**残缺索引**（即缺陷②）。
> **教训：两个都会改变结果的改动，必须逐项对照验证，不能混测**（见 `设计/23` §六 R-1）。

## 第 4 章 根因分析：缺陷是怎么形成的

理解根因，才能在面试里把缺陷讲成"有意识的取舍"而非"没做到"。

### 4.1 根因一：单机闭环优先的战略取舍（主因，且是正确的）

为了在单机把记账场景**做深**（评测体系、防幻觉、长期记忆），你主动放弃了分布式、持久化、平台化。这个取舍**在当时是对的**——它让你在有限时间内产出了 4 个强项（编排/记忆/评测/安全）。

**代价**：D1/D2/D5/D11 都是这条取舍的账单。
**面试表述**："我优先保证了单机闭环的深度，所以基础设施层是按需演进的——现在回头补，成本我已经评估过：Registry 80 行、Durable 80 行、trace 50 行。"

### 4.2 根因二：演进式重构留下的双轨制（资产沉没）

LEGACY 层（`agentCore/`：graph/nodes/skills/state/guardrails/session_manager）与新架构层（`agents/*`）并存，造成：

| 沉没资产 | 状态 |
|---|---|
| `skills.py` 12 个 skill 函数 | 活着，但只服务离线脚本 |
| `task_memory.py` | 仅 `tests/unit/test_task_memory.py` 引用 |
| `graph.py` / `guardrails.py` / `session_manager.py` | `10_模块契约手册.md` 439 行确认不再被新链路引用 |

**这是"重构不彻底"的典型代价**——旧资产没删（还能跑），也没接进新链路（不产生价值）。面试被问"你项目有多少死代码"要能诚实回答。

### 4.3 根因三：工具被当作"调用点"而非"可管理资产"

这是 D1 的深层原因。你的心智模型是"工具 = 一个能调通的函数"，所以做出来的是**网关**（把调用调通、调安全）。而平台的心智模型是"工具 = 需要被定义、注册、发现、治理的一等公民"。

**这个认知升级的成本极低**（80 行代码），但收益极大——它是 D7（Skills）、LLM 自主选工具、工具生态复用的共同地基。

**D15 正是这条根因的活证据**：因为工具没归一，编排器"需要数据时没有工具可调"，只能裸连 `db`——
后门不是恶意绕过，是**工具平台缺失的必然结果**。D1 修好（ToolRegistry + 细粒度工具），D15 的 9 处直连自然有正门可走。

### 4.4 缺陷之间的依赖关系（决定补强顺序）

```
        D1 工具抽象层（ToolRegistry）
             │
    ┌────────┼─────────────┐
    ▼        ▼             ▼
  D7 Skills  LLM自主选工具  统一审计/限流（D3 的 span 挂载点）
    
        D2 Durable（sqlite 状态机）
             │
             ▼
        D11 跨进程 A2A（Redis）──→ 顺带解决 D4 消息总线缺陷
        
        D3 可观测（trace）──→ 让 D10 评测飞轮真正闭环
```

> **结论：D1 是地基，D2/D3 是支柱。先做 D1，其余边际成本骤降。**

## 第 6 章 面试策略：把缺陷讲成加分项

> "你的项目有什么不足？"是必问题。**SSP 级答法 = 主动说出真实缺陷 + 讲清当时的权衡 + 给出已想好的方案**。这比"我的项目很完美"高两个段位，因为它证明你有架构判断力。

### 6.1 三段式结构（每个缺陷都这么讲）

```
① 诚实承认：XX 我没做（具体到代码层面，不模糊）
② 讲清权衡：当时我优先保证 YY，所以主动放弃了 XX（证明是取舍不是做不到）
③ 给出方案：如果要补，我会 Z，成本评估是 N 行代码（证明你想清楚了）
```

### 6.2 三个必背话术

**Q："你有工具注册中心吗？"**
> "没有独立的注册/发现层，我只有 MCP 客户端网关——工具调用是代码写死的三个方法，各自处理权限和审计。这是当年的取舍：我的架构是编排器加确定性执行 worker（LLM 只做局部解析，不自主选工具），注册中心的收益为零。**但如果要做 LLM 自主选工具或 Skills 编排，我会先加 ToolRegistry**——本地函数和 MCP 工具统一注册成 ToolSpec，权限过滤即发现过滤，协议适配放最后一公里，大约 80 行。"

**Q："任务执行到一半服务挂了怎么办？"**
> "目前会丢——A2A 总线是进程内的内存队列，任务结果存在 dict 里，重启即失。这是我为单机闭环做的取舍，长任务场景是硬伤。**补法是加 sqlite 任务状态机**：submitted/running/completed/failed 四态，写入即持久化，启动时扫描 running 残留做幂等恢复，重试带幂等键防重复写库，大约 80 行。"

**Q："评测失败了你怎么定位根因？"**
> "目前靠日志人肉翻，这是我的短板——有评测集但没有链路追踪，所以'发现失败'容易、'定位根因'难，**飞轮的闭环是断的**。补法是引入 run_id 和 span 树，在编排入口、worker 执行、工具调用三处打点，失败用例导出 span 树就能看到是规划错、工具错还是生成错。"

### 6.3 主动抛的"缺陷→亮点"转换

讲完缺陷后**立刻接一句**，把它转成加分项：

| 缺陷 | 转换话术 |
|---|---|
| 无工具平台 | "但我的安全层是超配的——双层 RBAC、DDL 拦截、双端审计，多数生产项目都没有。Registry 一上，这些能力自动覆盖所有工具。" |
