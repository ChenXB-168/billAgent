# 15 · 意图分档决策与保守规划方案（梳理稿，未实施）

> **状态**：✅ **已实施**（2026-10-08：第 0–3 步全部落地；L1 **481 → 491 passed**、`contract_check` FAIL 0）
> **日期**：2026-10-08
> **触发**：用户提出——① 提示词应从「规则清单」改为「能力说明 + 原则」，让模型自主规划；
> ② 但必须有**分界线**：明确契合能力集时禁止脑补，模糊时可追问或做**无害的保守规划**；
> ③ 关键是**怎么区分**这两种情况（契合度怎么量化）；④ 写操作用户已设计为「**显式授权触发**」而非追问。
> **结论先行**：**引入 `fit_level` 四档判定 + 按「承诺级别（Commitment Level）」分配自主度——
> 写操作由【显式授权】触发（无授权不规划，非追问）；只读操作可在【有话语依据】前提下保守规划
> （对应业界 Least Commitment Principle 与 Explicit Authorization for Side Effects）。**

## 一、需求说明（要改什么）

### 1.1 需求汇总

| # | 需求 | 性质 |
|---|---|---|
| **R1** | 提示词从「规则清单」→「能力说明 + 规划原则」，让模型自主规划 | **范式迁移** |
| **R2** | 建立**分界线**：明确契合 → 禁脑补；模糊 → 保守规划 / 追问 | **决策模型** |
| **R3** | 分界线须**可判定**（契合度如何量化） | **可操作性** |
| **R4** | 模糊时的自主度分配：HITL 追问 vs 无害保守规划 | **自主度分配** |
| **R5** | **写操作两段规则**：① 无显式授权 → **不规划**（非追问）；② 已授权但缺参 → 追问 | **边界修正** |
| **R6** | 保住「**花费前的决策辅助**」：「该花多少」→ 价位 + 预算 + 建议 | **产品目标** |
| **R7** | 只读缺参走保守规划 → 依赖 `price` 支持「有品类无金额」查价位 | **外部依赖** |

### 1.2 用户已明确的设计原则

1. **明确即直通**：用户指令非常明确契合子能力集时，**禁止脑补**，直接执行。
2. **模糊即保守或追问**：模糊时要么追问，要么做**无害的规划**（比价 + 理财咨询），
   ——目的：**做不到"花费前的决策辅助"就是功能缺失**（R6）。
3. **写操作的触发是"授权"而非"追问"**（★ 2026-10-08 纠正）：
   用户有「记一下」之类**明确话语**就直接记账；**没有**就不规划 `bill` —— **不是问用户要不要记账**。
4. **四基元约束不变**：`bill` / `stat` / `price` / `finance` 不新增类目。
5. **全 barrier 不变**：一轮内任一任务缺参即整轮不派发（M16 既定）。

### 1.3 本方案不做什么（范围边界）

- ❌ **不改** `task_plan` 结构 / `raw_segments` 契约 / A2A（沿用 M16 的不变式）
- ❌ **不改** 4 个子 Agent 的入参契约
- ❌ **不做** `price` 的无金额查询能力（属 M18，本方案只消费其接口）
- ❌ **不移除**提示词中"宁少不多"的红线（只调整其**表述层级**）
- ❌ **不做**"模糊时直接执行写操作"——**任何**写操作都必须有显式授权

## 二、业界对照（设计依据）

### 2.1 问题定性

用户描述的决策问题，在业界是**任务型对话（TOD）的核心决策问题**：

> **"When to ask vs when to act"** —— 系统在信息不足时，应"追问澄清"还是"保守执行"。

### 2.2 三个直接对应的业界范式

| # | 范式 | 核心主张 | 与本需求的对应 |
|---|---|---|---|
| **F1** | **Confidence-tiered Policy**（分档策略） | 用**两个阈值**划出三段（执行 / 澄清 / 拒识），而非单一开关 | 直接回答 R2/R3：**分界线是两个阈值，不是一次判定** |
| **F2** | **Least Commitment Principle**（最小承诺原则）★ | 不确定时选择**承诺级别最低**的动作 | 是 R4「无害规划」的**理论基础** |
| **F3** | **Explicit Authorization for Side Effects**（副作用显式授权）★ | 不可逆操作必须有**显式授权**，不能靠推断 | 正是 R5「记一下才记账」的业界形态 |

**承诺级别（Commitment Level）阶梯**：

```
低承诺 ────────────────────────────────────────────→ 高承诺
Observation      Query        Suggestion      Action
（只读观察）   （查询）      （建议）        （执行/写入）
    └──── 模糊时可自由落到这一段（无害）────┘   └─ 必须先有授权 ─┘
```

### 2.3 本项目已有的对应实现（不是从零引入）

| 业界范式 | 项目现有落点 | 状态 |
|---|---|---|
| **F3 副作用显式授权** | `startup/task_manager.py` 的 `SIDE_EFFECT_AGENTS = {"bill_agent"}`；M15「按环节分配自主」（读环节给自主、写环节锁死） | ✅ **已有，但只用于执行层** |
| **F3 授权触发** | 提示词「准入校验 1：bill 任务必须由用户**显式记账指令**触发，否则拦截」 | ✅ 已有 |
| **F2 最小承诺（只读优先）** | 无 | ❌ **缺口（本方案补）** |
| **F1 分档策略** | M16 已有三分支（OOD/缺参/低置信），但缺参**一律追问** | ⚠️ **需细分为四档** |

> **判断**：本方案**不是引入新范式**，而是把项目在**执行层**已用的「副作用授权」思想
> **上移到意图层**，并补上「最小承诺」这一环。

## 三、架构结论

### 3.1 契合度的定义（回答 R3：怎么量化）

**不用加权打分**（那是规则地狱的换皮），改用**一个可判定的问题**：

> **契合度 = 从「用户话语」直接映射到「能力集」，需要补什么？**

| 需要补什么 | 档位 | 例 |
|---|---|---|
| 什么都不用补（话语即完整指令） | `direct` | "记打车35元" → `bill.add` |
| 补**数据来源**（只读能力，系统自己可查） | `inferable` | "我想去唱歌，预算多少合适" → `price`+`stat`+`finance` |
| 补**用户提供**（必须用户给，或写操作缺参） | `need_user` | "记一下"（未给金额） |
| 补不出来（四基元都不沾边） | `out_of_scope` | "帮我订张机票" |

**⭐ 相比裸 `confidence` 的优势**：它**直接决定动作**（M16 的 `confidence` 只用于"是否澄清"一个分支）。

**模型输出形态（替代/补充 M16 的 `confidence`）**：

```jsonc
{
  "fit_level": "direct | inferable | need_user | out_of_scope",
  "fit_reason": "用户问预算决策，需价位与余额数据，均可由系统只读获取"
}
```

> **保留 `confidence` 的原因**：`fit_level` 管"走哪条路"，`confidence` 管"这条路走得稳不稳"
> （同为 `inferable`，置信 0.9 与 0.5 的处理可以不同）。二者**互补**，不互斥。

### 3.2 分界线的真正依据（回答 R2/R5）

**关键判断（本方案的核心）**：

> **分界线不是「模糊与否」（表象），而是「推断产物的承诺级别」+「是否有话语依据」。**

| 维度 | 说明 |
|---|---|
| **承诺级别** | 产物是**只读**（stat/price/finance）还是**写入**（bill） |
| **话语依据** | 规划出的任务能否从用户话语找到支撑（复用 M16 的 `_verify_grounding`） |

### 3.3 四象限决策表（★ 本方案的核心产出）

| | **明确（显式授权 / 0 推断）** | **模糊（需推断）** |
|---|---|---|
| **只读产物**<br>（stat / price / finance） | ✅ **执行** | ✅ **保守规划**<br>（低承诺、无害；须**有话语依据**） |
| **写产物**<br>（bill） | ✅ **执行**<br>（**缺参数 → 追问**） | 🚫 **不规划**<br>（无授权 ≠ 追问，是**不做**） |
| **推断不出 / 无依据** | — | 🚫 **OOD 引导**（能力清单 + 示例） |

**⭐⭐ 三条读法（务必分清）**：

1. **写产物在"模糊"格是「不规划」，不是「追问」** ——
   用户没说"记"，就**不该记账**，**也不该问**他"要不要记账"（那是打扰）。
   这是 R5 的纠正落点。
2. **写产物在"明确"格才可能出现「追问」** ——
   仅当**已获显式授权**（"记一下"）但**缺关键参数**（没说金额/品类）时。
3. **只读产物在"模糊"格可保守规划，但必须有依据** ——
   找不到依据的推测**一律降级为追问**（防"瞎猜"，见 §六 R-2）。

### 3.4 写操作的两段规则（★ 本轮纠正的形式化）

```
第一段【触发层】—— 授权闸门（判定发生在"要不要规划 bill"之前）
    有显式授权词（记/记账/记录/记一下/记一笔/写入/入账/帮我记…）
        → 允许规划 bill
    无
        → 【不规划 bill】（按咨询处理；**不追问**）
    ⚠️ 现有实现：提示词「准入校验 1」+ 代码 `_is_force_bill` / `_has_record_cmd`
        —— 该段**已正确**，本方案**不改**，仅在文档中固化

第二段【参数层】—— 缺参闸门（判定发生在"已规划 bill"之后）
    已授权但缺参数（"记一下"未给金额）
        → ✅ 追问（M16 现状，正确）
```

> **本方案对写操作的唯一改动**：在四象限表中**显式声明**"模糊 + 写 → 不规划"，
> 使 §3.3 的决策表与 R5 一致（**避免把"不规划"误实现成"追问"**）。
