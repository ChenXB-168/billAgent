## 第一章：三个执行单位——进程、线程、协程

### 1.1 餐厅比喻

| 概念 | 比喻 | 关键特征 |
|---|---|---|
| **进程 Process** | 一家**独立餐厅**：独立地址、独立厨房、独立仓库 | 互不干扰，一家着火不影响别家；但要"传菜"得靠外卖（跨进程通信，慢） |
| **线程 Thread** | 同一家餐厅里的**多个厨师**：共享一个厨房 | 传菜方便（直接拿），但会抢锅（要用锁），一人把厨房炸了全体完蛋 |
| **协程 Coroutine** | **一个厨师同时做多道菜** | 炖汤要等 10 分钟，他**不站着干等**，而是去切菜、炒菜 |

**协程的精髓就一句：等待的时候切走干别的。**

### 1.2 正式定义

| | 进程 | 线程 | 协程 |
|---|---|---|---|
| **是什么** | 资源分配的基本单位 | CPU 调度的基本单位 | 用户态的"轻量级线程" |
| **谁来管理** | 操作系统内核 | 操作系统内核 | **程序自己（用户态）** |
| **切换成本** | 最高（要换页表、换内存映射） | 中（要进内核、保存寄存器） | **最低（只保存几个变量）** |
| **内存开销** | ~10MB+ | ~1MB（默认栈） | **~几 KB** |
| **能否利用多核** | ✅ 能 | ⚠️ Python 受 GIL 限制 | ❌ 不能（单线程内） |
| **切换时机** | 内核决定（抢占式） | 内核决定（抢占式） | **自己说了算（协作式）** |
| **数据隔离** | 完全隔离 | 共享内存（要加锁） | 共享内存（**通常不用加锁**） |

### 1.3 为什么协程切换不用加锁？

这是协程最被低估的优势。

- **线程**：内核可能在**任何一条指令**中间把你切走。所以 `count += 1` 这种看似一步的操作，实际是"读—改—写"三步，切走就会出错 → **必须加锁**。
- **协程**：只在**你写了 `await` 的地方**才可能切走。两行普通代码之间绝不会被打断 → **不加锁也安全**。

```
# 线程：危险，要加锁
count += 1          # 内核可能在这里切走！

# 协程：安全，不用加锁
count += 1          # 绝不会被切走（中间没有 await）
await asyncio.sleep(0)   # 只有这里才可能切走
count += 1          # 安全
```

**代价**：协程是"协作式"的——**一个协程不讲武德（不 await、死循环、阻塞调用），全体跟着陪葬**。这是协程最大的风险，也是第三章"阻塞是死敌"的由来。

### 1.4 本项目的选择

> ⚠️ **先看这里，避免误解**：下面这张图**只画了"Agent 编排层"**（你自己写的那部分代码）。
> 把 MCP 子进程和线程池算进来，真实全景是「**1 个主进程 + 临时子进程 + 多个线程池**」——
> 见 **6.6 节**。本节先聚焦编排层，因为协程是理解全系统的钥匙。

```
Agent 编排层（位于主进程内）
└── 1 个线程
      └── 1 个事件循环
            └── 5 个协程（orchestrator + 4 个 worker）
```

**编排层用的是纯协程方案**：在编排层内部，1 线程 + 5 协程，零线程、零进程池。

> **一句话本质**：
> **你的 4 个 worker 不是 4 个工人，是 1 个工人在 4 件事之间来回切换。**
> `asyncio.create_task()` 没有开线程、更没有开进程——它只是往"调度员"那里登记了 4 件可以暂停/恢复的活。

### 1.5 并发的本质：什么才**真正**产生并发？

**先分清两个常被混用的词**：

| 概念 | 英文 | 含义 | 硬件要求 |
|---|---|---|---|
| **并发** | Concurrency | 多个任务**交替推进**，宏观上"同时进行" | 单核即可 |
| **并行** | Parallelism | 多个任务**真正同时**执行 | 必须多核 |

```
并发（单核，交替推进）              并行（多核，真正同时）
  ──A──   ──A──   ──A──              ─────────A─────────
     ──B──   ──B──                   ─────────B─────────
  ┌────────────────────┐            ┌────────────────────┐
  │ 一个厨师轮流做两道菜 │            │ 两个厨师各做各的     │
  └────────────────────┘            └────────────────────┘
```

**协程是并发，不是并行**——同一时刻只有一个协程在真正执行。

#### ⚠️ 最常见的误解：`await` 一个协程 **不等于** 并发

```python
async def inner():
    await asyncio.sleep(1)
    return 1

async def outer():
    r = await inner()      # ← 这只是"等它做完"，不是并发！
    return r
```

`await inner()` 的语义是：**暂停 `outer`，等 `inner` 跑完拿到结果，再继续**。
这在**时序上和普通函数调用完全一样**——都是串行。区别只在于等待期间会让出控制权给别人。

**对比实验**（跑一下立刻明白）：

```python
import asyncio, time

async def job(n):
    await asyncio.sleep(1)
    return n

# ① 挨个 await → 串行，3 秒
async def serial():
    await job(1)
    await job(2)
    await job(3)                                   # 1 + 1 + 1

# ② gather → 并发，1 秒
async def concurrent():
    await asyncio.gather(job(1), job(2), job(3))   # max(1, 1, 1)
```

#### 那什么才真正产生并发？

**只有一个动作：把协程交给事件循环去"后台调度"，而不是原地 `await` 等它。**

| 写法 | 是否并发 | 说明 |
|---|---|---|
| `await coro` | ❌ **串行** | 原地等它做完 |
| `asyncio.create_task(coro)` | ✅ 并发 | 登记到事件循环，立刻返回 Task |
| `asyncio.gather(*coros)` | ✅ 并发 | 内部就是逐个 `create_task` 再一起等 |
| `asyncio.wait({...})` | ✅ 并发 | 同上，可设 `FIRST_COMPLETED` |
| `asyncio.to_thread(fn)` | ✅ 并发 | 交给线程去做，协程 `await` 结果 |

> **一句话口诀：`await` = 等（串行）；`create_task` = 派活（并发）。**

#### 关于"嵌套"：这是两个完全不同的问题

**维度①：`await` 的调用链能无限嵌套吗？—— 能，但嵌套不产生并发**

```python
async def f1(): return await f2()
async def f2(): return await f3()
async def f3(): return await asyncio.sleep(1)
```

这只是**三层调用链**：`f1` 等 `f2`，`f2` 等 `f3`。总耗时 **1 秒**——嵌套 100 层也是 1 秒。
**嵌套层数 ≠ 并发度**，它只是把"等"这件事一层层传递下去。

**嵌套上限有多深？（本机实测，Python 3.14）**

| 场景 | 实测结果 |
|---|---|
| `await` 链式嵌套 | **991 层**为上限，第 992 层抛 `RecursionError` |
| 同步函数递归（对照组） | 同样约 1000 层 |
| `sys.setrecursionlimit(10000)` 之后 | 9000 层嵌套 OK |

上限由 `sys.getrecursionlimit()` 控制（**默认 1000**）——每层 `await` 占一个 Python 栈帧。

> ✅ **但"循环 await"完全不受此限制——这才是关键**：
>
> ```python
> async def worker():
>     while True:
>         msg = await queue.get()      # ← 循环，不是嵌套
>         await process(msg)
> ```
>
> 实测**循环 10 万次 `await` 毫无压力**。因为每次 `await` 完成后栈帧就释放了，**栈深度不累积**。
> 你的 4 个 worker 就是这种形态，所以能一直跑下去。
>
> **记法：嵌套累积栈（有上限 ~991）；循环不累积栈（无上限）。**

**维度②：并发能开多少个？—— 理论很多，实际卡在外部资源**

| 限制 | 说明 |
|---|---|
| 内存 | 每个 Task 约几 KB，开 1 万个也就几十 MB |
| **外部资源** | **真正的瓶颈**：数据库连接池大小、LLM 服务并发上限、文件句柄数 |
| 你的项目 | 并发度 = **worker 数量 = 4**（每个 agent 一个），**与嵌套层数无关** |

#### 回到项目：你的并发到底从哪来？

```python
# startup/bootstrap.py L162-164 —— ★这里才产生并发
for coro in worker_coroutines:
    task = asyncio.create_task(coro)     # ← 派活！4 个 worker 同时在飞
```

```python
# startup/bootstrap.py L48 —— 这里是串行（worker 一次只干一件事）
await bill_agent_graph.ainvoke(init_state)
```

**所以并发的画面是**：

```
create_task 派了 4 个活 → 4 个 worker 协程"同时在飞"（并发）
        ↓
每个 worker 内部用 await 串行走完自己的流程
        ↓
某个 worker 在 await 等 LLM 时 → 让出 → 事件循环去跑别的 worker
        ↓
宏观上 4 个任务同时推进（并发），微观上任一时刻只有 1 个在跑（非并行）
```

> **关键洞察**：并发**不是**来自"嵌套 await"，而是来自
> **"有多少个协程被 `create_task` 同时调度，且它们在等待时能互相让出"**。

## 第二章：协程的语法基础——async / await

### 2.1 两个关键字

```python
async def foo():        # 声明：这个函数"可以被暂停、被恢复"
    ...

await bar()             # "我要等这件事。等的期间，调度员你去安排别人干活，好了再叫我"
```

### 2.2 `await` 的三重含义（面试高频）

| 含义 | 说明 |
|---|---|
| ① **等待结果** | 拿到 `bar()` 的返回值才继续往下走 |
| ② **让出控制权** | 等待期间，事件循环可以去执行别的协程 |
| ③ **暂停点标记** | 这里是**唯一**可能被切换的地方 |

**只有 ① 是显式语义，② 和 ③ 是隐式的、但才是 async 的灵魂。**

### 2.3 协程对象 ≠ 正在运行的任务

这是新手最大的坑：

```python
async def foo():
    print("hello")

foo()               # ❌ 什么都不会打印！只是创建了一个"协程对象"，还没执行
                    #    还会报警告：coroutine 'foo' was never awaited

await foo()         # ✅ 在协程里 await 它 —— 真正执行
asyncio.create_task(foo())   # ✅ 交给事件循环调度执行
```

| 形态 | 说明 | 类比 |
|---|---|---|
| **协程对象** `coroutine` | 一份"菜谱"，本身不会自己动 | 写在纸上的步骤 |
| **任务** `Task` | 被事件循环接管的协程，会真正跑起来 | 厨师开始照着做 |

### 2.4 常见误区

| 误区 | 真相 |
|---|---|
| "`async def` 就变快了" | ❌ 单看一个函数反而略慢（多了调度开销）。**快的是"多个协程一起跑"的总吞吐** |
| "`await` 就是等待，会卡住" | ❌ await 会让出控制权，事件循环去干别的。**只有阻塞式调用才会真卡** |
| "没写 `await` 也能并发" | ❌ 函数里一个 await 都没有 = 永远不会让出 = 退化成同步串行 |

**判断一个 async 函数是否真的会并发：看它内部有没有 `await`。**

```python
async def bad():            # 伪 async：内部零 await
    time.sleep(5)           # 阻塞！整个事件循环停摆 5 秒
    return 1

async def good():
    await asyncio.sleep(5)  # 真正的让出，这 5 秒事件循环可以去干别的
    return 1
```

## 第三章：事件循环——协程的调度员

### 3.1 事件循环是什么

**事件循环（Event Loop）= 一个单线程的死循环，专门负责"谁现在能干活就安排谁"。**

它的工作伪代码：

```python
while True:
    ready = 找出所有"等待已就绪"的协程      # 比如 IO 完成、定时器到期
    for task in ready:
        task 往下执行一步，直到遇到下一个 await
    # 所有协程都在等？那就休眠，直到有事件到来（由操作系统通知）
```

### 3.2 调度过程图解

假设有 3 个协程，都是"请求 LLM → 等待 → 处理"：

```
时间轴 ──────────────────────────────────────────────────►

协程A  [发请求]······等待······[处理]  ✅完成
协程B      [发请求]······等待······[处理]  ✅完成
协程C          [发请求]······等待······[处理]  ✅完成

事件循环实际执行（单线程，同一时刻只有一个在跑）：
  A发请求 → A await 让出
           → B发请求 → B await 让出
                     → C发请求 → C await 让出
                               → (全在等，循环休眠)
                               → A 响应到 → A 继续 → A完成
                               → B 响应到 → B 继续 → B完成
                               → C 响应到 → C 继续 → C完成

总耗时 ≈ 一次请求的耗时（而不是三次之和）  ← 这就是并发的收益
```

### 3.3 "同时"是错觉吗？

**是的，但有用。**

- 严格来说：同一时刻只有一个协程在真正执行（单线程）。
- 但因为**等待时间占比极高**（LLM 推理、网络 IO、数据库查询动辄几百毫秒到几十秒），这些等待被完全重叠利用了。
- **对于 IO 密集型任务，协程的吞吐可以接近多线程，而开销只有它的百分之一。**

| 场景 | 3 个任务各等 1 秒 | 总耗时 |
|---|---|---|
| 同步串行 | 挨个等 | **3 秒** |
| 协程并发 | 一起等 | **≈1 秒** |

### 3.4 阻塞是协程的死敌（最重要的一节）

**协程是协作式调度——你不让出，谁也别想跑。**

```python
# ❌ 毒药：阻塞调用会卡死整个事件循环
async def worker():
    while True:
        msg = queue.get()          # 同步阻塞：卡住整个线程，所有协程陪葬
        requests.get(url)          # 同步阻塞：同上
        time.sleep(1)              # 同步阻塞：同上
        result = model.predict()   # CPU 密集：同上（CPU 被占满，循环转不动）

# ✅ 解药：全部换成可 await 的版本
async def worker():
    while True:
        msg = await queue.get()      # asyncio.Queue，让出等待
        await aiohttp.get(url)       # 异步 HTTP
        await asyncio.sleep(1)       # 异步睡眠
        result = await asyncio.to_thread(model.predict)   # CPU 密集卸载到线程
```

**三类阻塞及其解法**：

| 阻塞类型 | 例子 | 解法 |
|---|---|---|
| **同步 IO** | `requests.get`、同步 DB 驱动 | 换异步库（`aiohttp`、`asyncpg`）；没有异步库就卸载到线程 |
| **同步睡眠** | `time.sleep()` | `await asyncio.sleep()` |
| **CPU 密集计算** | 本地模型推理、向量检索、大循环 | **卸载到线程池**（见第五章） |

### 3.5 一个最小可运行例子

```python
import asyncio, time

async def job(name, delay):
    print(f"{time.strftime('%H:%M:%S')} {name} 开始等 {delay}s")
    await asyncio.sleep(delay)          # 让出，事件循环去安排别人
    print(f"{time.strftime('%H:%M:%S')} {name} 完成")
    return name

async def main():
    t0 = time.time()
    # 并发跑 3 个
    results = await asyncio.gather(job("A",3), job("B",2), job("C",1))
    print(f"总耗时 {time.time()-t0:.1f}s")   # ≈3s（不是 3+2+1=6s）

asyncio.run(main())     # asyncio.run = 创建事件循环 + 跑 main + 关闭循环
```

**`asyncio.run()` 是整个异步程序的入口**，一个进程通常只调一次。

## 第四章：Future / Task——取货凭证

### 4.1 为什么需要 Future

`await` 只能"等一个东西"。但如果我想**先发起一堆任务，谁先好就先处理谁**呢？

```python
# await 的局限：串行
r1 = await job("A", 3)    # 必须先等完 A
r2 = await job("B", 2)    # 才能开始 B
# 总耗时 5s ❌
```

需要一种"**先拿凭证、后取货**"的机制 → 这就是 **Future**。

### 4.2 Future 是什么

> **Future = 一张"取货凭证"。任务在后台跑，你拿着凭证，随时可以来取（或等待）结果。**

```
你 ──提交任务──► 事件循环
   ◄──Future───  （凭证，此刻结果还没好）

稍后：
你 ──await Future──► 结果好了就返回，没好就挂起等待
```

| 概念 | 关系 | 说明 |
|---|---|---|
| **Future** | 基类 | 一个"未来会有结果"的容器，可以 `await`、可以查状态、可以加回调 |
| **Task** | Future 的**子类** | 专门用于包装协程的 Future。`asyncio.create_task()` 返回的就是 Task |

```python
import asyncio

async def job():
    await asyncio.sleep(1)
    return 42

async def main():
    task = asyncio.create_task(job())   # 立即调度，返回 Task（= Future 子类）
    print(task.done())                  # False —— 还没好，但我已经可以做别的事了
    await asyncio.sleep(0)              # 做点别的
    result = await task                 # 现在来取货
    print(result)                       # 42
```

#### ⚠️ 易混淆：Python 里有**两个** Future，同名不同类

Future **不是线程的专利**，它是一个**通用的设计模式**——"一个还没完成的结果的占位符"。
只要有"**先发起、后取结果**"的需求就需要它，线程有，协程同样有。

| 语言/框架 | 这个模式叫什么 |
|---|---|
| Java | `java.util.concurrent.Future` |
| JavaScript | `Promise`（就是 Future 的另一种叫法） |
| C# | `Task<T>` |
| **Python 线程/进程池** | `concurrent.futures.Future` |
| **Python 协程** | `asyncio.Future`（`Task` 是它的子类） |

实测确认它们是两个不同的类（Python 3.14）：

```
asyncio.Future            : <class '_asyncio.Future'>
concurrent.futures.Future : <class 'concurrent.futures._base.Future'>
SAME CLASS?               : False          ← 完全不同

asyncio.Task MRO:
    <class '_asyncio.Task'>
    <class '_asyncio.Future'>              ← Task 继承 asyncio.Future
    <class 'object'>

type(create_task(...)) : <class '_asyncio.Task'>
isinstance(t, asyncio.Future)           : True
isinstance(t, concurrent.futures.Future): False
```

#### 两者最本质的区别：**等待方式**

| | `asyncio.Future` | `concurrent.futures.Future` |
|---|---|---|
| 等待写法 | `await fut` | `fut.result()` |
| 等待时干什么 | **让出控制权**给事件循环 → 别的协程继续跑 | **阻塞当前线程** → 什么都干不了 |
| 在协程里用 | ✅ 正确 | ❌ **会堵死整个事件循环** |

**实测对比**（等待 1 秒期间，另一个协程能跑几次）：

```
A) await asyncio.sleep(1)      -> other coroutine ticks: 6    ← 让出，别人照跑
B) concurrent Future.result()  -> other coroutine ticks: 1    ← 阻塞，别人全停
```

> **这是"协程里禁止用同步阻塞调用"的又一个例证**：
> 在 `async def` 里写 `executor.submit(f).result()`，等于把协程的并发优势全部作废。

**反过来也有桥接方法**：协程要等线程的结果，用 `await asyncio.wrap_future(thread_future)`
（或直接用 `asyncio.to_thread`），把"阻塞式 Future"转成"可 await 的 Future"。

### 4.3 Future 的生命周期与常用 API

```
pending（进行中）
   │
   ├── 成功 ──► finished，set_result(v)，await 拿到 v
   ├── 失败 ──► finished，set_exception(e)，await 抛出 e
   └── 取消 ──► cancelled，task.cancel()，await 抛 CancelledError
```

| API | 作用 |
|---|---|
| `await fut` | 阻塞等待结果（期间让出控制权） |
| `fut.done()` | 是否已完成（不阻塞，立刻返回） |
| `fut.result()` | 拿结果（**没完成会抛异常，必须先 done**） |
| `fut.cancel()` | 取消任务 |
| `fut.add_done_callback(fn)` | 完成时回调 |

### 4.4 组合器：多个 Future 一起等

| 函数 | 语义 | 用途 |
|---|---|---|
| `asyncio.gather(*futs)` | **全部**完成才返回，结果按传入顺序组成列表 | 最常用，"一批都做完" |
| `asyncio.wait(futs, ...)` | 返回 `(已完成集, 未完成集)`，可设 `FIRST_COMPLETED` | 精细控制 |
| `asyncio.as_completed(futs)` | **谁先好先出谁**（迭代器） | 流式处理 |
| `asyncio.wait_for(fut, timeout)` | 带超时的等待 | **熔断**（本项目 `a2a_queue.wait_result` 在用） |

```python
# 竞速：谁先返回用谁（多模型兜底场景）
done, pending = await asyncio.wait(
    [t1, t2, t3],
    return_when=asyncio.FIRST_COMPLETED
)
winner = done.pop()
for p in pending:
    p.cancel()      # 取消没跑完的
```

- `mcpGateway/a2a_queue.py` L109：`await asyncio.wait_for(event.wait(), timeout=240)` —— 用 Future/Event + 超时做熔断
- `startup/bootstrap.py` L174-176：退出时 `task.cancel()` + `gather(..., return_exceptions=True)`

## 第五章：线程池 ThreadPoolExecutor

### 5.1 为什么有了协程还需要线程池

**协程解决不了 CPU 密集问题。**

协程的收益来自"等待时切走"。但 CPU 密集任务**不等待**——它一直在算，事件循环根本拿不到控制权：

```python
async def worker():
    result = local_model.predict(x)   # CPU 满载跑 30 秒，期间没有任何 await
    # → 这 30 秒里，事件循环被彻底堵死，其他所有协程全部停摆
```

**解法：把 CPU 密集任务丢给另一个线程去跑，协程 `await` 它的完成。**

```
主线程（事件循环）          工作线程（线程池）
   │                            │
   ├─ await to_thread(fn) ─────►│ 开始算 fn()
   │  （让出，去服务其他协程）    │ ...CPU 满载...
   │  ← 继续服务其他请求         │
   │                            │ 算完了
   │◄────── 结果回来 ───────────┤
   └─ await 返回，继续往下走
```

**事件循环始终没被堵住**，因为真正耗 CPU 的活儿在别的线程里。

### 5.2 归属澄清：它是 Python 标准库

> **ThreadPoolExecutor 既不是操作系统内置的，也不是第三方库——它是 Python 标准库的一部分**（`concurrent.futures` 模块），装好 Python 就有，`import` 直接用，**不需要 pip install**。

| 层次 | 是谁 | 例子 | 要不要装 |
|---|---|---|---|
| **操作系统** | Windows / Linux 内核 | `CreateThread` / `pthread_create`（最底层线程原语） | 系统自带 |
| **Python 标准库** | 装 Python 时一起装好 | `asyncio`、`concurrent.futures`、`threading`、`json` | **不需要** |
| **第三方库** | 别人写的，需 pip 安装 | `requests`、`pandas`、`pymysql` | **需要** |

**为什么不算"操作系统内置"**：操作系统只提供"线程"这个**原材料**，不提供"线程池"这个**管理方案**。

| | 操作系统 | ThreadPoolExecutor |
|---|---|---|
| 创建线程 | ✅ 有 `CreateThread` | 复用了它 |
| **预先建一批线程** | ❌ 没有 | ✅ 池 |
| **任务排队分配** | ❌ 没有 | ✅ 队列 |
| **线程复用/回收** | ❌ 没有 | ✅ 生命周期管理 |
| **Future / 回调** | ❌ 没有 | ✅ |

**线程池是工程方案，不是系统原语** → 所以它住在 Python 标准库里。

### 5.3 完整封装链条

```
操作系统内核（Windows / Linux）
   │   提供最底层线程原语：CreateThread() / pthread_create()
   ▼
Python 解释器
   │   标准库 _thread 模块，直接调用上面的系统调用
   │   （你永远不会直接碰这一层）
   ▼
concurrent.futures.ThreadPoolExecutor   ← 标准库
   │   在 _thread 之上封装了：
   │     · 线程池（预先创建 N 个线程，用完复用不销毁）
   │     · 任务队列（排队分配）
   │     · Future（取货凭证，第四章的概念在这里同样适用）
   │     · 生命周期管理（预热、复用、优雅关闭）
   ▼
你的代码
   │   from concurrent.futures import ThreadPoolExecutor
   ▼
asyncio 默认用它
   │   await asyncio.to_thread(fn) 内部就是它
```

验证它内置（不需要装任何东西）：

```bash
python -c "from concurrent.futures import ThreadPoolExecutor; print('内置，直接用')"
```

它在标准库里和 `asyncio` 是邻居：

```
Python安装目录/Lib/
  ├── asyncio/                  ← 事件循环（协程调度）
  ├── concurrent/futures/
  │     └── _base.py            ← ThreadPoolExecutor 住在这里
  ├── threading.py              ← 更底层的线程库
  └── json.py
```

### 5.4 核心参数与用法

```python
from concurrent.futures import ThreadPoolExecutor

# 方式一：手动管理
executor = ThreadPoolExecutor(
    max_workers=4,            # 池里最多几个线程
    thread_name_prefix="cpu"  # 线程名前缀，排查问题时很有用
)
future = executor.submit(fn, arg1, arg2)   # 提交，立刻返回 Future（不阻塞）
result = future.result(timeout=30)         # 同步取货（会阻塞当前线程！）
executor.shutdown(wait=True)               # 优雅关闭

# 方式二：with 自动关闭（推荐）
with ThreadPoolExecutor(max_workers=4) as ex:
    futures = [ex.submit(fn, i) for i in range(10)]
    for f in as_completed(futures):       # 谁先好先处理谁
        print(f.result())
```

**`max_workers` 怎么定**：

| 任务类型 | 建议 | 理由 |
|---|---|---|
| **CPU 密集** | `os.cpu_count()` 或 +1 | 再多也没用，核就那么多，多了反而增加切换开销 |
| **IO 密集** | 可以远大于核数（如 2~4 倍） | 线程大部分时间在等 |

### 5.5 协程 ↔ 线程池的桥：`asyncio.to_thread`

**这是协程项目里用线程池的标准姿势**：

```python
# ❌ 在协程里同步阻塞取结果 —— 会堵死事件循环
result = executor.submit(fn, x).result()

# ✅ 正确：交给事件循环去等，期间服务其他协程
result = await asyncio.to_thread(fn, x)
```

`asyncio.to_thread(fn, *args)` 做的事：

1. 把 `fn(*args)` 丢进 `asyncio` 的**默认线程池**
2. 返回一个**可 await 的对象**（内部包装成 Future）
3. 协程 `await` 它 → 让出控制权 → 事件循环继续服务别人
4. 线程算完 → 事件循环被唤醒 → 协程继续

**等价写法**（更可控，可自定义池大小和名字）：

```python
loop = asyncio.get_running_loop()
result = await loop.run_in_executor(my_executor, fn, x)
```

### 5.6 决策树：什么时候该卸载到线程池

```
这个函数要跑很久吗？
  ├─ 否（<10ms）────────────────► 直接调用，别折腾
  └─ 是 ──► 它在"等"还是在"算"？
              ├─ 在等（网络/磁盘/DB）──► 用异步库 await（首选）
              │                          没有异步库 → to_thread 兜底
              └─ 在算（CPU 满载）────► to_thread / run_in_executor
```

### 6.2 Worker 是怎么跑起来的（实证）

`startup/bootstrap.py` L155-164：

```python
# 启动各个子Agent常驻worker
worker_coroutines = [
    _bill_agent_worker(),      # 4 个协程对象（此刻还没跑）
    _stat_agent_worker(),
    _price_agent_worker(),
    _finance_agent_worker()
]
for coro in worker_coroutines:
    task = asyncio.create_task(coro)      # ← 登记到事件循环，开始调度
    WORKER_TASKS.append(task)
```

**关键点**：`asyncio.create_task()` **没有开线程、更没有开进程**。它只是把协程登记给事件循环，事件循环在 `await` 点之间来回切换。

每个 worker 的结构（`startup/bootstrap.py` L31-52，以 bill 为例）：

```python
async def _bill_agent_worker():
    agent_name = "bill_agent"
    while not SHUTDOWN_FLAG:                              # ① 常驻循环
        try:
            msg = await a2a_bus.recv_task_blocking(agent_name)   # ② 等任务（让出）
            init_state = {...}                            # ③ 组装 state
            await bill_agent_graph.ainvoke(init_state)     # ④ 执行（让出）
        except Exception as e:
            logger.exception(...)
            await asyncio.sleep(0.5)                      # ⑤ 异常退避（让出）
```

**这个 worker 是"一次只干一件事"的**：

```
while 循环第 N 轮：
  取任务 → 执行 graph（await 让出，可能几十秒）→ 完成 → 回到 ①
                    ↑
        在这期间，事件循环去服务别的协程（其他 worker、WebUI 请求）
        但【这个 worker 自己】是停在这里等的，不会去取下一个任务
```

> **重要推论**：单个 worker 是**串行消费**的。同一时刻，一个 agent 只会处理一个任务。并发能力 = worker 数量（4），不是无限的。

### 6.3 消息总线怎么配合（实证）

`mcpGateway/a2a_queue.py` L8 —— **按 agent 分队列，不是单队列混装**：

```python
self._task_queues: Dict[str, asyncio.Queue] = defaultdict(asyncio.Queue)
#                   ↑ key = agent_name，每个 agent 一个独立 asyncio.Queue
```

| 方法 | 谁调用 | 行为 |
|---|---|---|
| `send_task(target_agent, session_id, task_id, data)` | orchestrator 派发 | `put_nowait` 入对应 agent 的队列 |
| `recv_task_blocking(agent_id, session_id=None)` | worker 常驻消费 | 无限循环取消息 |
| `send_result(task_id, result)` | worker 回传 | 存结果 + `Event.set()` 唤醒等待者（**D4 已删死参数** `target_agent`/`session_id`；结果存储与唤醒均只按 `task_id` 路由） |
| `wait_result(task_id, timeout=240)` | orchestrator | `await asyncio.wait_for(event.wait(), 240)` 熔断等待 |

**消费者调用实况**（`startup/bootstrap.py` L36/60/86/109）：4 个 worker **都只传 `agent_name`，不传 `session_id`**：

```python
msg = await a2a_bus.recv_task_blocking(agent_name)
#                                      ↑ 只有 agent_name，session_id 默认 None
```

→ `a2a_queue.py` L79 的匹配条件 `if session_id is None or ...` **直接短路返回**，队列里的消息按顺序 FIFO 取出，**不走"会话不匹配→回插队尾"的分支**。

### 6.4 用地基知识看当前实现：一个典型例子

`a2a_queue.py` L67-72，worker 的取消息循环：

```python
while True:
    try:
        msg = queue.get_nowait()      # 非阻塞：没消息立刻抛 QueueEmpty
    except asyncio.QueueEmpty:
        await asyncio.sleep(0.1)      # 睡 0.1 秒再试
        continue
```

**用第三章的知识评价**：

| 维度 | 现状 | 更优写法 |
|---|---|---|
| **会不会卡死别人** | ❌ 不会。`await asyncio.sleep(0.1)` 会让出控制权，事件循环正常服务其他协程 | — |
| **延迟** | ⚠️ 最坏 100ms。消息在 sleep 期间到达，也要等这一觉睡完 | `await queue.get()` 消息一到立刻唤醒 |
| **空转** | ⚠️ 空闲时每秒仍唤醒 10 次 | `queue.get()` 零空转 |
| **实现复杂度** | 手写轮询循环 | 一行 `await queue.get()` |

**根因**：`asyncio.Queue.get()` 内部就是用**第四章的 Future** 实现的——没消息时把协程挂起登记，有消息时事件循环**精确唤醒**。手写 `get_nowait() + sleep` 等于把这个高效机制降级成了定时轮询。

> 这个例子是"地基知识 → 看懂项目缺陷"的完整链路。**具体改造方案不在本文范围**，将在第二部分（执行架构设计）展开。

#### 两个值得注意的点（本轮新发现）

**① MCP 是"短连接"：每一次调用 = 启动一个子进程**

`mcpGateway/client.py` L42-43 的注释说得很清楚：

> 现改为短连接模式：每次调用在同一 task 内 async with 建立并释放连接……调用频率低，子进程启停开销可接受。

即每次 LLM 或 SQL 调用都要：启动 Python 子进程 → MCP 握手 → 调用 → 退出。
流程上还用 `asyncio.Lock`（L48、L67）**串行化**了，同一时刻只允许一个 MCP 调用。

> ⚠️ 另有一条**可能已过时**的记录：`client.py` L56-58 写着"子进程启动需加载 embedding/rerank 模型（实测 26~29s）"，
> 握手超时因此放宽到 120s。但看当前三个 server 脚本：`server_llm_base.py` 只发 Ollama HTTP 请求、
> `server_bill.py` 只跑 SQL——**都不加载 embedding/rerank 模型**。
> 建议实测一次真实启停耗时：若仍有 20s+，这是**远比 D4 严重的性能问题**；若只有 1~2s，则这条注释需删除，
> 免得面试时被追问"为什么你的 MCP 每次调用要 30 秒"。

**② Gradio 模式下存在"跨线程驱动事件循环"隐患**

`webUI/app.py`：
- L44 `def respond(...)` 是**同步函数** → FastAPI/Gradio 会把同步端点丢进**线程池**执行
- L67 `_loop.run_until_complete(orchestrator_graph.ainvoke(init_state))` → 在**工作线程**里驱动主事件循环

**asyncio 的事件循环不是线程安全的。** 单用户串行点击没问题；
一旦**两个请求并发**（开两个标签页、或上一轮没跑完又发一轮），两个线程同时 `run_until_complete` 同一个 `_loop`，
行为未定义——可能抛异常，也可能请求间互相串扰。

> 这条此前缺陷文档**未记录**。⚠️ **编号冲突（2026-09-02 收口）**：本文原"建议新增为 D14"——但 **D14 编号已被 `02`/`03` 占用**（`user_config.budget_type` year 遗留，"数据模型声称支持未实现"）。WebUI 跨线程驱动事件循环是**另一个独立缺陷**，权威缺陷清单尚未给它正式编号。**已登记到 `10` §8.2「待收口问题清单」#2**，在此之前**不得占用 D14**。

### 7.1 概念速查

| 概念 | 一句话 | 归属 |
|---|---|---|
| **进程** | 独立资源容器，互不干扰 | 操作系统 |
| **线程** | 共享内存的执行流，需加锁 | 操作系统 |
| **协程** | 用户态轻量执行流，await 处让出 | Python 语言特性 |
| **并发** | 多任务**交替推进**，宏观同时（单核即可） | 概念 |
| **并行** | 多任务**真正同时**执行（必须多核） | 概念 |
| **`await coro`** | **等它做完 → 串行**，不产生并发 | Python 语法 |
| **`create_task`** | **派活 → 并发**，协程交给事件循环后台跑 | `asyncio`（标准库） |
| **事件循环** | 单线程调度器，安排就绪的协程 | `asyncio`（标准库） |
| **`async def`** | 声明函数可被暂停/恢复 | Python 语法 |
| **`await`** | 等待 + 让出控制权 + 标记暂停点 | Python 语法 |
| **Future** | 未来结果的"取货凭证" | `asyncio`（标准库） |
| **Task** | Future 子类，包装协程 | `asyncio`（标准库） |
| **ThreadPoolExecutor** | 线程池管理器 | `concurrent.futures`（**标准库**） |
| **`asyncio.to_thread`** | 协程↔线程池桥接，卸载 CPU 密集 | `asyncio`（标准库） |

### 7.2 阻塞 vs 非阻塞对照

| ❌ 阻塞（毒药） | ✅ 异步（解药） |
|---|---|
| `time.sleep(1)` | `await asyncio.sleep(1)` |
| `requests.get(url)` | `await aiohttp.get(url)` 或 `await asyncio.to_thread(requests.get, url)` |
| `queue.get()`（同步队列） | `await queue.get()`（`asyncio.Queue`） |
| `queue.get_nowait() + sleep` 轮询 | `await queue.get()` |
| `model.predict(x)`（CPU 密集） | `await asyncio.to_thread(model.predict, x)` |
| `fut.result()` | `await fut` |
| `executor.submit(f).result()` | `await loop.run_in_executor(executor, f)` |

### 7.3 面试高频（结合本项目）

| 问题 | 要点 |
|---|---|
| **并发和并行什么区别？** | 并发 = 交替推进（单核即可，协程属此类）；并行 = 真正同时（必须多核） |
| **`await` 一个协程算并发吗？** | **不算**。`await coro` 是"等它做完"，时序上就是串行。要并发必须用 `create_task` / `gather` |
| **嵌套 await 能提高并发度吗？** | **不能**。嵌套只是把"等"层层传递，N 层嵌套总耗时仍是各层之和。并发度 = 被 `create_task` 调度的协程数 |
| **协程和线程的区别？** | 协程用户态调度、切换成本极低、**await 点才切换所以不用加锁**；线程内核调度、抢占式、要加锁 |
| **协程能利用多核吗？** | 单线程内不能。要利用多核用多进程，或把 CPU 密集卸载到线程池（部分绕开 GIL） |
| **为什么 async 函数里不能 `time.sleep`？** | 阻塞整个事件循环，所有协程停摆。协程是协作式，你不让出别人就没机会 |
| **`asyncio.create_task` 和直接 `await` 的区别？** | `create_task` 立即调度并返回 Task（可并发）；直接 `await` 是串行等完才继续 |
| **本地 CPU 密集怎么不阻塞事件循环？** | `await asyncio.to_thread(...)`（本项目用它跑 FAISS 向量检索与记忆读写，`orchestrator/nodes.py` L494/L819/L1270） |
| **你的 4 个 worker 是并行吗？** | **并发但不并行**。同一时刻只有一个在执行；且每个 worker 串行消费，总并发度 = 4 |
| **你的系统是"单进程单线程"吗？** | **不是**。编排层是 1 线程 + 5 协程；往外还有 **MCP 临时子进程**（stdio，每次调用启停）+ `to_thread` **默认线程池** + WebUI 的 **Gradio 线程池**（见 6.6） |
| **MCP 服务是怎么通信的？** | `stdio_client` 起**子进程**、走 stdin/stdout 管道；当前是**短连接**模式（每次调用启停一个子进程），并用 `asyncio.Lock` 串行化（`client.py` L48/L67） |
| **WebUI 里怎么跑异步 Agent？** | 同步 `def respond()` 里用 `_loop.run_until_complete()` 驱动常驻 loop——但同步端点由线程池执行，存在**跨线程驱动事件循环**隐患（见 6.6 ②） |
| **Future 和 Task 什么关系？** | Task 是 Future 的子类，专门用于包装协程 |
| **怎么给异步任务加超时？** | `asyncio.wait_for(fut, timeout)`（本项目 `wait_result` 用 240s 对齐 `MODEL_TIMEOUT`） |

## 第 8 章 执行架构现状总结

### 8.1 全景：四层定位

【建议】用"四层"描述本项目，避免"单进程单线程"这种不严谨说法：

| 层 | 现状 | 承载内容 |

### 8.2 任务流：严格串行（**本轮最重要的发现**）

### 8.3 依赖 DAG：并行空间客观存在

`dispatch_node` 为 `finance` 组装 `task_data` 时（`nodes.py` L1035-1037）：

```python
"bill_result":  cache.get("bill_agent"),
"stat_result":  cache.get("stat_agent"),
"price_result": cache.get("price_agent"),
```

依赖关系是：

```
bill  ──┐
stat  ──┼──►  finance
price ──┘
```

`bill` / `stat` / `price` **互不依赖 → 可并行**；`finance` 依赖三者结果 → 必须等。

**耗时对比**（记各任务耗时为 `T_bill` / `T_stat` / `T_price` / `T_finance`）：

| 模式 | 总耗时 |
|---|---|
| **现状（串行）** | `T_bill + T_stat + T_price + T_finance` |
| **DAG 并行（建议）** | `max(T_bill, T_stat, T_price) + T_finance` |

### 8.5 D6 · ContextManager 分层上下文预算——执行时行为（M12 落地，2026-09-04 回写）

**背景**（`02` D6）：无 token 级上下文管理，仅靠 `get_history(limit=3)` 硬截断；多任务结果 + 长期记忆 + RAG 片段同时注入时易超窗（本地 ollama `num_ctx=4096`，输出预留 ~1024 → 输入预算 ~3072 token）。

**组件**（`agents/context_manager.py`，零项目内依赖纯函数）与**分层预算表**见 `10` §5.6.3.1（权威契约）。执行时行为要点：

1. **预算内零行为**：各层估算 ≤ 层预算即原样返回（`truncated=False`）→ 常规输入与改造前输出**逐字节一致**，回归零风险。
2. **触发路径（3 个接入点，全部超限才截断）**：
   - `orchestrator plan_node`：会话历史（history 层，25%）**滑窗保留最近** + 长期记忆（20%）**段落化保留头部**（检索靠前段最相关）——超限后二者按层预算各自裁剪再合成 `history_context` 进模板 `{{ history }}`。
   - `orchestrator collect_node`（`EXTERNAL_LLM_ENABLED` 汇总分支）：多 worker 结果（task_results 层，30%）**保序逐块放入、放不下当前块截尾并停**——保留靠前 worker 结果头部结论（确定性渲染文本，头部即结论+数字）；数字白名单随治理后块计算。
   - `stat_agent build_stat_prompt`：会话历史（history 层）滑窗，只喂最近内容。
3. **红线**（R9 防幻觉关联）：
   - system 层不可截（组件独立统计、超限 WARN 保留全文；调用方分传 sys/user，system 不混入 user 拼接）；
   - task_results 受保护块（确定性事实底稿，`(text, protected=True)`）**宁超预算不截**（R9：确定优先）；finance fact_sheet 属确定性底稿——当前 finance 各层体量均远低于预算（user_docs 3×128 字符、stat/price/底稿数百 token）故 M12 未接入，组件预留、接入时以受保护块传入；
   - user_docs **最低保留 1 段**（宁可不给，不可拖慢——`06` §6.1.1）。
4. **故障语义**：组件不抛业务异常（截断打 `logger.warning`）；接入点均包 `try/except` → 异常回退原始拼装（维持改造前行为），**永不阻断**规划/汇总/统计链路。
5. **窗口换算**：默认 `context_window − output_reserve`（4096−1024，对齐本地 ollama）；M14 `Capabilities.context_window` 落地后由调用方传实际窗口接管（本组件不 import `config`）。

**明确不覆盖（M12 回滚点，压缩后置）**：摘要式压缩未实现（先只做预算+截断）；system+user_input 主体本身超窗时组件不兜底（各层上限只保护辅助层）——最终窗口守卫依赖 M14 harness / 模型侧行为。

**② "MCP 只是一个需要接入的协议"——它不该在执行架构层讨论** —— ✅ **本条成立且重要**，

即：**M3 做传输层改造，M1/D1 做抽象层**——两者是**先后**关系，不是**从属**关系。

**③ 而且成本尚未实测** —— ⚠️ 本条**仍需实测**（`client.py` L56-58 的 26~29s 注释可能过时，
三个 server 均不加载 embedding/rerank 模型）。**实测作为 M3 的验收项**，不改变其 P0-1 定位。

**① 长连接的坑尚未解决，不是"想改就能改"**

`client.py` L39-41 记录了当初改为短连接的根因：

> 原实现用 `__aenter__` 建立长连接并跨 task 复用（心跳/调用/shutdown 不同 task），
> `stdio_client` 的 cancel scope 被绑定在首个进入的 task，其它 task 退出时报
> "Attempted to exit cancel scope in a different task" 直接崩溃。

**在正面解决 cancel scope 跨 task 之前改回长连接，就是重蹈覆辙。**

**② "MCP 只是一个需要接入的协议"——它不该在执行架构层讨论**

MCP 是**众多可接入协议中的一种**。正确的层次划分是：

```
业务 Agent
    ↓   只认「工具名 + 参数」
D1 Registry（工具抽象层）              ← 架构层，协议无关
    ↓
协议适配器：MCP / HTTP / 本地函数        ← 实现层，连接模式是这里的私事
```

一旦 D1 立起来，**MCP 用长连接、短连接、还是整个换成别的协议，都只改适配器内部，上层零感知**。
届时再评估连接模式才是安全的——而且可以在适配器里统一加"健康检查 + 自动重连 + 退避重试"，
**这恰恰是短连接当前缺失的能力**。

**③ 而且成本尚未实测**

`client.py` L56-58 称"子进程启动需加载 embedding/rerank 模型（实测 26~29s）"，
但当前三个 server 脚本**均不加载** embedding/rerank 模型（`server_llm_base.py` 只发 Ollama HTTP、
`server_bill.py` 只跑 SQL）→ **该注释很可能已过时**。

**【建议】动作**：将 E3 从执行架构清单移出，登记为 **D1 的子任务**；
在 D1 完成后再评估，评估前先做一次实测（见第 11 章 M0 ①）。

## 第 10 章 优化方案（逐条建议）

### 【建议 1】E1：串行派发 → DAG 并行派发

**思路**：`dispatch_node` 一次派发**所有**就绪任务；`wait_result_node` 用 `gather` **并发等**这一批。

```python
# ── dispatch_node（改造要点）──
ready_tasks = ready                      # 不再只取 ready[0]，派发全部就绪任务
running = {}
for t in ready_tasks:
    tid = str(uuid.uuid4())
    a2a_bus.send_task(target_agent=task_plan[t]["agent_id"],
                      session_id=state["session_id"],
                      task_id=tid,
                      task_data=_build_task_data(t, state, cache))
    running[t] = tid
return Command(update={"task_plan": new_plan, "running_tasks": running},
               goto="wait_result_node")

# ── wait_result_node（改造要点）──
pending = state["running_tasks"]
raw_list = await asyncio.gather(
    *[a2a_bus.wait_result(tid, timeout=240) for tid in pending.values()],
    return_exceptions=True                # 单个失败不拖垮整批
)
for t, raw in zip(pending.keys(), raw_list):
    _store_result(t, raw)                 # 逐个解析入库到 agent_result_cache
return Command(update={...}, goto="dispatch_node")
```

**配套改动**：`OrchState` 增加 `running_tasks: Dict[str, str]` 字段。

**收益**：`T_all` → `max(T_无依赖) + T_有依赖`，理论省约 50%。

**风险（必须实测）**：

| 风险 | 说明 | 缓解 |
|---|---|---|
| **本地 CPU 推理扛不住并发** | 1.8B 模型跑 CPU，3 个并发可能比串行更慢（核数有限、内存争抢） | 先试 2 并发；必要时加"并发上限"节流阀 |
| **Ollama 自身并发限制** | 服务端可能有并发上限 | 查配置 / 实测；必要时串行化 LLM 调用 |
| 部分失败语义 | 一批中某个失败如何处置 | `return_exceptions=True` + 逐个兜底 |

**工作量**：约 60 行（含 state 字段与测试调整）

**【建议】优先级：最高。但必须先完成 M0 实测再动手。**

## 第 11 章 统一路线图：逻辑架构 vs 执行架构，谁先？

### 11.1 直接回答：先逻辑架构，后执行架构

> **术语澄清**（此前使用"组件架构"一词不够严谨，此处修正）
>
> 业界标准参考 **Philippe Kruchten 的 4+1 架构视图模型**：
>
> | 标准视图 | 英文 | 关注点 | 本文对应 |
> |---|---|---|---|
> | **逻辑视图** | Logical View | 组件、接口、职责边界 | **逻辑架构**（D 系列，原称"组件架构"） |
> | **进程视图** | Process View | 并发、同步、线程/进程/协程 | **执行架构**（E 系列） |
> | 开发视图 | Development View | 代码组织、模块划分 | — |
> | 物理视图 | Deployment View | 部署、网络、硬件 | — |
> | 场景视图 | Scenarios | 用例，串联以上四视图 | — |
>
> "组件架构"（Component Architecture）确有其词，但通常指**基于组件的开发方法（CBD）**，
> 用来描述"D 系列 vs E 系列"的分野时，**"逻辑架构 vs 执行（进程）架构"才是标准说法**。
> **下文统一改用后者。**

【建议】**核心原则：先定接口与语义，再改性能与并发。**

| | 对应 | 回答的问题 |
|---|---|---|
| **逻辑架构**（D 系列） | 房间的**功能布局** | 哪里是厨房、哪里是卧室（模块职责、接口边界） |
| **执行架构**（E 系列） | 房子的**水电管线** | 水怎么流、电怎么走（任务怎么跑、并发多少） |

> 你不会在房间功能还没定之前就埋管线——因为你不知道厨房要不要进水、卧室要不要网线。
> **接口定不下来，执行优化就是给错误的结构提速。**

### 11.2 三条判据（判断谁先谁后）

| 判据 | 规则 | 本项目中的例子 |
|---|---|---|
| **① 谁定义了"接口"** | 定义了别人要依赖的东西 → **先做** | **D1 Registry**：所有工具调用都经过它 |
| **② 谁会被并发放大** | 并发一上去就爆 → **提并发之前先治理** | **D5 会话态**、**D2 持久化** |
| **③ 谁只是实现细节** | 被接口收敛在内部 → **最后做**（⚠️ **前提：它不构成其他项的前置**） | **E3 MCP 连接模式** |

按这三条一判，之前的排序错误就很清楚了：

- ~~E3 属于 ③ → 不该排 P0，应并入 D1 之后~~ → 🔴 **2026-08-30 修正**：E3 虽属 ③（实现细节），
  **但它同时是 E1 的前置**——`03` §9.8.4 L555 明确"本项收益必须在 P0-1 之后才成立"，
  否则"派发层并行而执行层仍在排队"，**E1 收益为零**。故 **E3 排 P0-1，在 E1 之前**（不是最后）。
- E1 会被 ② 放大 → 应在 D5 / D2 之后
- D1 属于 ① → **第一**

> **判据补充**：③ 的完整表述应是"被接口收敛在内部、**且不构成其他项的前置** → 最后做"。
> E3 正因不满足后半句而从 ③ 中例外——**"实现细节"不等于"可以最后做"**。

### 11.5 关键排序的论证

**为什么 D1 第一？**
- 它是"收敛点"：**没有它，后续任何工具相关改动都要碰散落各处的 MCP 调用点**
- 有了它，E3 从"全局风险"降为"适配器内部的一处小改动"
- 它是 D3（可观测）的天然打点位置
- 对应 JD 职2 的核心职责，面试价值最高

**为什么 E1 排在 D5 / D2 之后（而不是越早越好）？**
- E1 提升并发度 → 并发越高，**状态问题（无 TTL、无持久化）爆发越快**
- 若先做 E1，压测时会同时暴露并发 bug 与状态 bug，**难以归因**
- 先把状态治理好，再提并发：出了问题能快速定位

**为什么 E3 最后？**
- 你已踩坑：长连接断开，根因是 `stdio_client` 的 cancel scope 跨 task
- D1 **之前**改 = 在散落的调用点上改 = 高风险
- D1 **之后**改 = 只改适配器一处 = 低风险，且可统一加"健康检查 + 自动重连 + 退避重试"
