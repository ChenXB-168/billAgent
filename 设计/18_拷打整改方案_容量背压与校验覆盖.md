## 二、业界对照

### 2.1 F3：容量与背压（Backpressure）

| 概念 | 业界做法 | 本项目对应 |
|---|---|---|
| **有界队列** | 生产系统一律给队列设上限（Bounded Queue）——无界队列等价于"把 OOM 推迟到进程崩溃" | 本方案补 `maxsize` |
| **背压策略** | 满时四种选择：**阻塞 / 拒绝（reject）/ 丢弃最旧（drop-oldest）/ 降级到磁盘** | 本项目选**拒绝**（清单明确要求） |
| **为何不阻塞** | 阻塞 `put()` 会把**派发方**（Orchestrator，即用户请求的持有者）一并挂死 → **故障扩散**；拒绝只是**优雅失败**（fail fast） | 与清单结论一致 |
| **可观测** | 队列深度是**四黄金信号之一（饱和度 Saturation）**，必须暴露用于告警 | 补深度日志 + 阈值告警 |

> **本项目的特殊性**：`send_task` 是**同步方法**（禁止 `await`），故**天然只能用 `put_nowait`**——
> 这反过来意味着"满时拒绝"是唯一可行且正确的策略（想阻塞也做不到，除非改成 async）。

### 2.2 F5：数字归一化（Numeric Normalization）

| 层 | 业界做法 | 本项目现状 |
|---|---|---|
| **防幻觉白名单** | 输入侧（抽取）与输出侧（校验）**必须同一套归一化**，否则中文数字形成**校验盲区**（bypass） | 白名单**只做阿拉伯数字** → 模型写"五十"即绕过 |
| **中文数字解析** | 通用做法：正则 + 分段递推（万/千/百/十 + 个位）；**歧义取保守下界**（"五十多" → 50） | 本方案补 |
| **为何取下界** | 校验的目的是"防编造"：取**下界**使白名单更**严格**（宁可多拦，不可漏放）；且"多"本身不构成确定数值 | 见 §3.2 |

## 三、架构结论

### 3.1 F3：队列背压设计（拒绝式 + 可观测）

```
send_task(target, session, task_id, data)
    ↓
queue = _task_queues[target]           # 有界（maxsize=A2A_QUEUE_MAXSIZE，默认 100）
    ↓
try:  queue.put_nowait(msg)            # 同步、不阻塞（★签名约束）
      depth = queue.qsize()
      if depth >= A2A_QUEUE_WARN_DEPTH:  → WARNING 日志（堆积预警）
      return True
except asyncio.QueueFull:              # ★满时拒绝，而非阻塞
      WARNING 日志（含 target/depth/task_id）
      return False                     # ← 新增返回值（调用方可选检查）
```

**三条设计决策**：

| # | 决策 | 理由 |
|---|---|---|
| **D-1** | **满时拒绝**（`QueueFull` → 返回 `False`） | 阻塞会连 Orchestrator 一起挂死（故障扩散）；拒绝是优雅失败 |
| **D-2** | `send_task` **返回 `bool`**（原返回 `None`） | 最小侵入：Python 下不检查返回值的既有调用方**不受影响**（向后兼容） |
| **D-3** | 深度**只写日志 + 暴露查询接口**，不写 trace 表 | 深度是**瞬时指标**（in-memory gauge），写表会污染 span 树语义；调用方可按需轮询 `snapshot_depths()` |

**★ 关于"容量"的取舍说明（面试口径）**：

> 单机单用户场景下，队列深度实际只有个位数（一次请求最多 4 个子任务）；
> `maxsize=100` 是**防御性上限**，覆盖"用户快速连发 + 子 Agent 消费慢"的最坏情况。
> **真正的价值不是 100 这个数，而是"有界"这个性质**——它把"OOM 崩溃"转化为"可观测的拒绝"。

### 3.2 F5：中文数字归一化设计

**方案：在 `extract_numbers` 的"日期 → 序号 → 数字"三步中，把"数字"步扩展为"阿拉伯 + 中文"。**

```
text → 剔日期 → 剔列举序号 → ⌈阿拉伯数字⌉ ∪ ⌈中文数字⌋ → set[float]
                                    ↑ 新增
```

**中文数字解析规则**：

| 输入 | 输出 | 说明 |
|---|---|---|
| `五十` | `50` | 十位 + 个位 |
| `一百二` | `120` | 省略尾"十"（"一百二"= 120，非 102） |
| `两百` | `200` | 口语量词 |
| `三千五` | `3500` | 千位 + 省略尾 |
| `五十多` | **`50`** | ★**取下界**：校验取严不取宽（"多"非确定值） |
| `十块` | `10` | 裸"十" |

**★ 为何"五十多"取 50 而不是 51**（正面回答清单 Q15-L4）：

> **因为白名单闸门的目的是"防编造"，而非"精确对齐口语"。**
> 取 51 需要假设"多"= "+1"，这是**无依据的推断**（"多"可能是 51~59 中任意值）；
> 取 50 则使**下界确定**——若模型输出 51 而白名单只有 50，容差 0.5 下 51 会被判**幻觉**并触发修正重试，
> 属"**多拦一次**"的保守失败；反之若取 51 则模型输出 50 会被误放。
> **在防幻觉场景，宁可误拦，不可漏放。**

**边界与限制（写入契约，避免过度承诺）**：

- 仅覆盖**常规数词**（零/一~九/十/百/千/万 + 口语量词两/俩）；**不覆盖**"半"（"五十半"）、分数、成数（"八成"）；
- 不做**上下文消歧**（"十点"中的"十"会被抽取——与既有阿拉伯数字行为一致，属已知边界）；
- **一旦归一化，中文数字即进入白名单比对**，与阿拉伯数字**同等严格**。

## 八、验收标准

### 8.1 F3 验收

| 场景 | 期望 |
