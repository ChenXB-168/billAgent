# 20 · 弃用本地通道 + 超时预算收紧（M22 · R5 废止）（已实施）

> **状态**：✅ **已实施**（2026-10-09：P0–P2 全部落地；`tests/unit` **508 passed**、`contract_check` FAIL 0、lint 0）
> **日期**：2026-10-09
> **触发**：用户确认「**彻底弃用本地 1.8B 通道**」——该决定实为 2026-09-15（M15 P0-a）的生产形态
> 变更（`config.py` 注释已记载"默认全链路走外部强模型"），但**超时链与需求约束一直未同步**。
> **结论先行**：
> **① 本地通道从"默认回退"改为"默认封死"**（`DISABLE_LOCAL_LLM` 默认 `True`）；
> **② 超时链按外部形态重排为内环先超时**：`工具(60) < 任务(120) < 编排器等待(150)`，
> 并**关闭 M19 遗留的 T-3（超时预算倒挂）**；
> **③ 正式废止 `01` §7.1 的 R5 与 §6 的两条非功能需求**（本地可用性 / 零成本默认路径）。**

## 一、需求说明（要改什么）

### 1.1 真实诉求

| # | 场景 | 期望行为 | 改造前实际 |
|---|---|---|---|
| **R1** | 未配外部 API 时 | **启动即明确报错**（快速失败） | ⚠️ 静默回退本地 1.8B（生产形态下"降级到慢且不可靠的通道"） |
| **R2** | 外部 API 故障（超时/不可用） | 用户**尽快**拿到明确的失败回执 | ❌ 编排器盲等 **240s**（4 分钟）才超时——而正常请求只需 **10~30s** |
| **R3** | 超时预算 | 形成**递增链**（内环先超时，失败能向上传递） | ❌ `TOOL_TIMEOUT_LLM(300) ≥ MODEL_TIMEOUT(240)` **倒挂**（M19 §八 T-3 已登记） |

### 1.2 ★ 约束变更（本方案的核心影响）

**放弃两条既有约束**（`01` §6 / §7.1，已在原文标注废止）：

| 编号 | 原约束 | 变更后 |
|---|---|---|
| **R5** | 必须本地可跑（零 API 也能用） | **必须配外部 API**；未配 → `ModelRouter.resolve` 抛 `RuntimeError` |
| §6 | 本地可用性：不配任何 API 也能完整跑通全流程 | **废止**（同上） |
| §6 | 零成本默认路径：默认免费，外部 LLM 仅为可选增强 | **废止**（默认路径即外部 API，有成本） |

> **⚠️ 这是"能力收缩"而非"能力增强"**，必须在文档与面试口径中如实表述：
> **换来的是**：单一形态 → **路由复杂度下降**、超时可控、失败语义明确（M19）；
> **代价是**：**失去离线可用性与零成本路径**，且引入 API 依赖（可用性、成本、合规）。
> **保留的缓解**：本地 Provider 与路由逻辑**代码不删**（软弃用），`BILLAGENT_DISABLE_LOCAL_LLM=0`
> 可临时恢复 —— 使该决策**可回滚**。

### 1.3 本方案不做什么（范围边界）

- ❌ **不删除** `OllamaProvider` / `_FakeLocal` / 本地相关配置（**软弃用**，保留回滚能力，§2.2）
- ❌ **不改** 路由决策表的**逻辑**（`test_model_service.py` 的 8 组路由用例全部保留，仅默认值变化）
- ❌ **不改** M19 的终止语义、M21 的结果回收与心跳（三者正交）
- ❌ **不改** `EXTERNAL_LLM_AGENTS`（默认已含 5 个 Agent，无需调整）

## 二、架构结论

### 2.1 超时链为什么必须「内环先超时」（★核心论证）

**改造前（M19 形态）**：

```
TOOL_TIMEOUT_LLM(300) ≥ MODEL_TIMEOUT(240) ≥ TASK_TIMEOUT(300)
                              ↑ 编排器先超时
→ 编排器 240s 放弃 → 但 worker 仍在跑 → 只能"盲等后放弃"
```

**改造后（M22 形态）**：

```
EXTERNAL_LLM_TIMEOUT(60) = TOOL_TIMEOUT_LLM(60) < TASK_TIMEOUT(120) < MODEL_TIMEOUT(150)
                                                        ↑ worker 侧先超时
→ worker 120s 超时 → track() ④ 分支 mark_failed + **代传失败结果**
→ 编排器【立即】收到失败 → 触发 M19 终止语义（明确回执，不用盲等）
```

**★ 语义反转的价值**（这是 M22 相对 M19 的关键改进）：

| | M19（编排器先超时） | **M22（worker 先超时）** |
|---|---|---|
| 超时判定者 | **编排器自己**（它对 worker 状态一无所知） | **worker 自己**（它知道任务真的跑了多久） |
| 失败如何上报 | ❌ **不报**——编排器只是"不等了"，worker 还在跑 | ✅ **主动代传失败结果**（`_failed_result`） |
| 编排器何时知道 | 等到自己 150s 闹钟响 | **立即**（130s 前就收到失败） |
| 用户看到 | 等到上限才失败 | **更早**、且**原因明确**（"任务执行超时 120s"） |

**→ 结论：让"最了解情况的一方"做超时判定，失败才能沿链条正确上抛。** 这正是 M19 §八 T-3 想解决而当时未解决的问题。

**同时**：`MODEL_TIMEOUT` 从"本地 Ollama 单次请求超时"**语义变更为"编排器等待上限"** —— 因为本地已弃用，它不再约束任何 Provider。

### 2.2 为什么"软弃用"而不是"删除代码"

| 若硬删（删 Provider / 配置 / 依赖） | 软弃用（本方案） |
|---|---|
| 无法回滚（除非 revert 一大片） | ✅ `BILLAGENT_DISABLE_LOCAL_LLM=0` 一行恢复 |
| 路由用例需**删除或重写** | ✅ **全部保留**（它们验证的是路由表逻辑完整性） |
| 与项目"回滚开关"惯例不符（`MCP_STDIO_FALLBACK` / `BATCH_DISPATCH_ENABLED` / `ABORT_ON_TASK_FAILURE` 均有开关） | ✅ 一致 |

**故**：**只改默认值 + 语义注释**，代码结构零变更。

## 四、改造顺序（依赖关系）

```
第 0 步（配置先行——全部改动的前提）
  P0-1  DISABLE_LOCAL_LLM 默认 True
  P0-2  MODEL_TIMEOUT 150 + 开放 env + 改语义
  P0-3  EXTERNAL_LLM_TIMEOUT 60
      └─ 验收：常量可 import；值符合预期

第 1 步（超时链贯通——消除硬编码）
  P1-1  TOOL_TIMEOUT_LLM 60
  P1-2  TASK_TIMEOUT 120
  P1-3  a2a_queue.wait_result 引用 MODEL_TIMEOUT
  P1-4  orchestrator._wait_one 引用 MODEL_TIMEOUT
      └─ 验收：全仓无硬编码 240；递增链 60 < 120 < 150 成立

第 2 步（注释与约束同步）
  P2-1  track() 注释改语义
  P2-2  设计/01 约束变更标注
      └─ 验收：文档与代码口径一致

第 3 步（收口）
  D1  回归：`tests/unit` 全量 + `contract_check` FAIL 0 + lint 0
  D2  文档回填：`09`（超时卡 + 模型接入）、`设计/02`、`设计/11` M22、
      ★反转 `设计/17` R-5 与 `设计/19` §八 T-3 的结论
```

**顺序原则**：
1. **配置先行**（第 0 步）—— 后续都读它；
2. **超时链必须一次贯通**（第 1 步）—— 只改配置而不同步 `wait_result` / `_wait_one` 的硬编码 240，
   会出现"配置 150 但实际仍等 240"的静默漂移；
3. **★约束变更必须与代码同批**（第 2 步）—— R5 废止若只改代码不改 `01`，文档会声称"本地可跑"而实际启动即报错。
