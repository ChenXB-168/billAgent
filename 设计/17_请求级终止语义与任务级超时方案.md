# 17 · 请求级终止语义统一 + worker 任务级超时（M19 · D20）（已实施）

> **状态**：✅ **已实施**（2026-10-09：P0–P2 全部落地；`contract_check` FAIL 0）
> **日期**：2026-10-09
> **触发**：拷打复盘「子 Agent 挂起 / 任务超时」一题时发现——**编排器对失败任务只在"等待"层面放弃，
> 没有在"终止语义"层面收口**：① 失败任务仍被标 `status="done"`（**下游误判依赖已满足、照常派发**）；
> ② 失败结果溜进 `collect_node` 的 `struct_success_list` 被当作汇总素材 → **产出"看似正常但没有数据"
> 的回复（静默降级，比明确报错更危险）**；③ worker 侧无任务级超时 → **挂死的 runner 会永久占住
> 单协程消费循环**。
> **结论先行**：**把 M16 用户取消已建立的「请求级终止」四机制（先落终态 → 中断执行 → 代传结果 →
> 收口不产出业务回复）复用到「任务级失败」路径，用 `abort_reason` 区分回执文案；并为 worker 侧补
> 任务级执行超时，根治"挂死任务占死通道"。**

## 一、需求说明（要改什么）

### 1.1 真实诉求

| # | 场景 | 期望行为 | 改造前实际 |
|---|---|---|---|
| **R1** | 子任务超时（`wait_result` 240s 兜底） | 明确报"执行超时，已终止" + **如实说明已完成部分** | ❌ 失败结果 `status=done` → 下游照常派发 → 溜进汇总 → 用户看到"看似正常但无数据"的回复 |
| **R2** | 子任务异常**穿透子图**（未被内部捕获） | 编排器**立即**收到失败结果并收口 | ❌ `track()` 异常分支只落状态、**不代传** → 编排器**盲等 240s** 才收口 |
| **R3** | runner **挂死**（卡在无超时保护的 await） | 该任务被中断，worker 继续服务后续任务 | ❌ worker 单协程串行消费 → **该 Agent 通道永久停摆**、队列持续堆积、**零提示** |

### 1.2 本方案不做什么（范围边界）

- ❌ **不改** 子 Agent 入参契约与子图结构（`raw_segments` / `task_plan` / A2A 消息格式**均不变**）
- ❌ **不改** M16 用户取消的语义与回执（`abort_reason="user_cancel"` 走原路径，**逐字不变**）
- ❌ **不做** 副作用回滚（已落库账单不撤销）——"停止"≠"当作没发生"，理由见 §六 R-3
- ~~❌ **不重排**超时预算递增链~~ → ✅ **已由 M22 关闭**（2026-10-09）：本地通道弃用后按外部形态
  重排为 `工具(60) < 任务(120) < 编排器等待(150)`（见 `设计/20`）
- ❌ **不引入** 心跳 / 运行期健康检查（属独立能力，§六 R-6）

## 二、架构结论：终止语义的统一

**核心判断**：**"用户取消"与"任务级失败"的后续行为完全一致**（都是终态、都不重投、都不再派发、
都不产出业务回复），**只有回执文案不同** —— 故**共用一套机制、用原因区分**，而不是各写一套。

```
【改造前】两条"异常中断"路径能力严重不对等：

  用户取消（M16，已完整）          任务失败 / 超时（M19 前）
  ├─ 先落终态 cancelled  ✅        ├─ 只标 done（调度语义 = 成功）        ❌
  ├─ 中断 runner         ✅        ├─ runner 继续占住 worker             ❌
  ├─ 代传结果唤醒        ✅        ├─ 异常路径不回传 → 盲等 240s         ❌
  └─ 收口不产出业务回复  ✅        └─ 溜进汇总 → 产出误导性回复           ❌

【改造后】统一为「请求级终止」，按 abort_reason 分文案：

  abort_reason ∈ { None | "user_cancel" | "task_timeout" | "task_error" }
        │
        └─→ cancelled = True
              ├─ 不再派发后续波次（dispatch_node / wait_result_node 双闸）
              ├─ 中断本会话在途 runner（复用 cancel_session：先落终态、再 cancel）
              └─ 收口出对应回执（失败时**如实附上"已完成部分"**）
```

**§2.1 为什么"失败也要传下去"是错的（改造前的两个具体危害）**

| # | 危害 | 机制 |
|---|---|---|
| **①** | **下游基于空数据继续跑** | `wait_result_node` 无条件 `task_plan[name]["status"] = "done"` → 依赖检查 `deps ⊆ done_tasks` 判定满足 → `finance` 等下游照常派发，拿到的是**空的上游结果** |
| **②** | **静默降级成"看似正常"的回复** | `collect_node` 只把 `error == "need_more_info"` 分流为追问，**其余（含超时）一律进 `struct_success_list`** → 作为素材送 LLM 汇总 |

> **② 比"报成功"更危险**：报成功时用户至少知道有回应、能自己核实；静默降级让用户**不知道是成功还是失败**。

|---|---|---|
| `TASK_TIMEOUT` | **300s**（`BILLAGENT_TASK_TIMEOUT`） | worker 侧单任务执行上限；**≤0 = 关闭** |

## 四、改造顺序（依赖关系）

```
第 0 步（契约/配置先行）
  P0-1  config 加 TASK_TIMEOUT / ABORT_ON_TASK_FAILURE
  P0-2  OrchState 加 abort_reason
      └─ 验收：import 通过 + 字段可读（`abort_reason in OrchState.__annotations__`）

第 1 步（worker 侧补偿——独立可验证，先做）
  P0-4  _failed_result
  P0-3  track 新增超时分支 + 异常分支补代传
      └─ 验收：runner 抛异常 → send_result 被调用；runner 挂死 → 超时后 worker 可继续

第 2 步（编排器侧终止语义）
  P1-1  wait_result_node 识别失败并终止
  P1-2  _abort_inflight
  P1-3  collect_node 按原因出回执（含"已完成部分"）
      └─ 验收：超时 → goto=collect_node + abort_reason=task_timeout + 回执含已完成项

第 3 步（成对同步 + 收口）
  P2-1  三个入口 init_state 同步
  P2-2  新增 8 条单测
  D1    回归：tests/unit 全量 + contract_check FAIL 0
  D2    文档回填：`09` §2.2/§2.17、`设计/02` D20、`设计/11` M19
```

**顺序原则**：
1. **配置与 state 先行**（第 0 步）——后续两步都依赖它们；
2. **worker 侧先于编排器侧**（第 1 步先做）—— 它是**独立可验证的缺陷修复**（异常盲等 240s），
   且**不依赖编排器改动**即可生效；
3. **编排器侧必须"识别 + 中断 + 回执"同批**（第 2 步）—— 只做识别会导致"终止了但用户看不到原因"，
   只做回执而无中断会导致"回执说终止、worker 仍在跑"。

## 六、风险点

| # | 风险 | 说明与对策 |
|---|---|---|
| **R-1** | **把可恢复的业务拒绝误判为"任务级失败"** | 判据若用 `success is False` 一刀切，则 `need_more_info`（追问）与收入不入账拦截等**正常业务交互**都会被终止。**✅ 实施中已修**：判据改为 `msg` 白名单 `_TASK_FAILURE_MSGS = ("任务执行失败", "任务执行异常")`——只认**平台层**产生的两类失败载荷（`track()` 代传 / `_wait_one` 等待兜底），业务拒绝一律放行；并有专项用例 `test_wait_result_business_rejection_does_not_abort` 锁定 |
| **R-2** | **终止阈值过激导致正常慢任务被中断** | `TASK_TIMEOUT=300 > MODEL_TIMEOUT=240`，正常路径仍由编排器先超时；且超时只影响"编排器已放弃"的任务 |
| **R-3** | **终止时账单已落库，而回执说"已终止"** | **不引入回滚**（"停止"≠"当作没发生"；且回滚自身会失败、引入递归问题）。**对策**：回执**如实附上"已完成部分"**，用数据同构的 `success is True` 结果渲染 |
| **R-4** | **`_abort_inflight` 与用户取消路径重复调用** | 已用 `if reason != "user_cancel"` 排除 —— 用户取消由 WebUI 侧 `on_stop` 触发，编排器侧不重复 |
| ~~**R-5**~~ | ~~**超时预算倒挂**（`TOOL_TIMEOUT_LLM=300 ≥ MODEL_TIMEOUT=240`）~~ | ✅ **已由 M22 关闭**（2026-10-09）：本地通道弃用后按**外部形态**重排为 `工具(60) < 任务(120) < 编排器等待(150)` —— **内环先超时**，worker 超时会 `mark_failed` + **代传失败结果**，编排器**立即**收口而非盲等（`设计/20` §2.1）。<br>⚠️ 本节 R-2/T-3 中"`TASK_TIMEOUT` 刻意 > `MODEL_TIMEOUT`"的论证**已被 M22 反转**，以 `设计/20` 为准 |
| **R-6** | **无心跳，主 Agent 分不清子 Agent "慢"还是"死"** | 本方案只把"永久挂起"降级为"最多 300s"。**根治需运行期健康检查**（独立能力，不在 M19 范围） |

## 七、验收标准（实施后）

| 场景 | 期望 |
|---|---|
| 子任务超时（触发 `wait_result` 240s） | `goto=collect_node`、`abort_reason="task_timeout"`、**不再派发下游**；回执含"执行超时" |
| 部分任务成功 + 部分超时 | 回执**如实列出已完成部分**（如"已完成部分：记账成功：消费类目 餐饮，金额 30.0 元，日期 …"） |
| 子任务抛异常穿透子图 | 编排器**立即**收到失败结果（不再盲等 240s）；`abort_reason="task_error"` |
| runner 挂死超过 `TASK_TIMEOUT` | 内层 Task 被取消、落 `failed`、代传失败结果；**worker 消费循环继续**（不被占死） |
| 全部任务成功 | **零回归** —— 照常 `goto=dispatch_node` 继续调度，不写 `abort_reason` |
| 用户点「停止」 | **零回归** —— 回执仍为"已按您的要求停止本次请求。"（不带"已完成部分"） |
| 回滚 | `BILLAGENT_ABORT_ON_FAIL=0` → 退回改造前行为（失败结果继续溜进汇总） |
| 回归 | M19 专项 **9 passed**；`tests/unit` 全量通过；`python utils/contract_check.py` **FAIL 0**；`read_lints` 0 |

| **Q-3** | `cancelled` 是否替换为 `abort_reason` | ❌ **并存** | 既有三处 `state.get("cancelled")` 判断零改动，只增量补"原因"维度 |

| **Q-5** | `TASK_TIMEOUT` 取值 | ✅ **300s（> MODEL_TIMEOUT）** | 保证正常路径零变更，仅在"编排器已放弃"时兜底；取小于 240 会误杀正常慢任务 |
| **Q-6** | 是否引入心跳 | ❌ **不在本方案** | 属独立能力（R-6 / T-4），避免范围蔓延 |
| **Q-7** | 回滚开关 | ✅ `BILLAGENT_ABORT_ON_FAIL=0` | 与既有 `BATCH_DISPATCH_ENABLED` / `DYNAMIC_DEPS_ENABLED` 同惯例 |
