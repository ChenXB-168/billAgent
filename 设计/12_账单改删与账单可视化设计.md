## 0. 一句话方案

> **顶层（orchestrator）保持确定性：定"做哪个任务、是 add 还是 edit/delete"，并由此**
> **锁定子 agent 的工具可见面**——`edit` 任务里模型根本看不到 `bill.delete`（操作类型不靠提示词约束，靠可见面物理锁定）；
> **子层（bill_agent）在这个被剪裁过的选项域内自主**：自己去看、去定位、去决定要不要追问；
> **落库仍是确定性 workflow**（SQL 写死在工具内部）。
>
> 自主性边界一句话：**编排器给的不是答案，是一副被限定范围的牌；出哪张牌是子 agent 自主的。**

## 1. 需求与边界

### 1.1 做什么

| # | 需求 | 用户可见效果 |
|---|---|---|
| R1 | 修改已记账账单（金额 / 品类 / 日期，可只改一项） | "把刚才那笔打车改成 50" → 该条记录被更新，回复回显改后值 |
| R2 | 删除已记账账单 | "删掉昨天那笔奶茶" → 先确认，确认后该条记录被删除 |
| R3 | 目标可指认（**自主消解**） | 支持"最近一笔 / 那天那笔打车 / 清单第 2 条"；歧义或找不到则追问，**绝不猜** |
| R4 | 账单可视化 | WebUI 展示账单（按月折叠），并提供"选中 → 生成一句话"的定位入口 |
| R5 | 派生数据一致 | 改删后统计 / 月度习惯 / 预算预警随之变化，不留残差 |
| R6 | **范式达标** | bill_agent 内存在真实的 tool loop（模型自主选工具 + 观察结果再决策 + 有界终止） |

### 1.2 不做什么（明确划界）

| # | 不做 | 理由 |
|---|---|---|
| N1 | 不做批量改删 | 影响面不可控，与"逐条确认"的交互模型冲突；超范围一律追问 |
| N2 | 不做窗口外指代（"上个月 3 号那笔"） | 可操作窗口限定为"最近 N 笔"（§4.2.5），窗口外追问 |
| N3 | 不做"模糊去重式"自动改删 | 与 `设计/11` §2 已登记取舍一致：误改比重复更糟 |
| N4 | UI 按钮**不直写数据库** | 写操作必须收敛在 `bill_agent`（否则绕过 RBAC / 审计 / 对账 / 习惯重算） |
| N5 | **不让子 agent 自主决定操作类型** | 见 §2 定稿：操作类型由顶层定，子层只自主"目标消解 + 参数补全" |
| N6 | 不让模型生成 SQL | 工具内部 SQL 写死；模型只传结构化参数（保住 `nodes.py:395-397` 的既有保证） |
| N7 | 不动 orchestrator 的路由（`TASK_AGENT_MAP`） | 4 个 agent 的枚举路由，确定性收益 > 自主收益（§2.3 判据） |

## 2. 范式决策：自主性按"环节"分配（★本文核心）

### 2.1 分歧点

改删能力有两种落法，本质是**范式之争**：

| 划法 | 顶层定什么 | 子层自主什么 |
|---|---|---|
| **A 全下沉** | 只给用户原话 | 操作类型 + 目标 + 参数全自主 |
| **B 操作锁定 + 目标自主** | `operate_sub_type`（add/edit/delete） | 目标消解 + 参数补全 |
| **C 全确定性**（初版设计） | 操作类型 + 目标 `bill_id`（代码把序号映射成 id） | 无 |

### 2.2 三划法对比（取舍记录）

| 维度 | A 全下沉 | **B 操作锁定 + 目标自主（定稿）** | C 全确定性 |
|---|---|---|---|
| 是否有真实 tool loop | ✅ | ✅ | ❌ |
| 意图判定逻辑份数 | **2 份**（orchestrator + bill_agent，会打架） | **1 份**（顶层） | 1 份 |
| 提议-执行分离 | ❌ 破坏（bill_agent 既能定又能写） | ✅ 保住（顶层提议、子层执行，见 §2.4） | ✅ |
| 目标定位方式 | 模型观察数据库后自行判断 | **模型观察数据库后自行判断** | 代码把"序号/描述"映射成 id（模拟 observation 的补丁） |
| 失败归因难度 | 高（两层都可能判错） | 中（顶层判错 vs 目标消解失败，可区分） | 低 |
| 加新操作（如转账） | 不改 orchestrator | 需顶层加枚举 + 工具打 tag | 需顶层加枚举 + 代码分支 |
| 可测性 | 差 | 中（自主循环边界被收敛成一个子问题，可穷举） | 最好 |
| 面试可讲性 | "全自主"但经不起追问（为何要两层意图识别） | **能讲清"为什么这一环自主、那一环不自主"**（判据见 §2.3） | 只能讲"确定性优先" |

### 2.3 定稿与判据

**定稿：划法 B。** 设计判据（可作为本项目的通用原则，用于自检任何新功能）：

> **步骤不确定 → 用 agent；步骤确定 → 用 workflow。自主性给"不确定性最高的那一环"，不给"某个 agent"。**

按此判据逐环节打分：

| 环节 | 不确定性 | 采用的范式 | 归属 |
|---|---|---|---|
| 意图识别 / 任务拆解 | 中 | workflow + LLM 结构化输出（含启发式兜底） | orchestrator |
| 任务派发 / 依赖 / 并行 / 幂等 | **低** | workflow（DAG + `task_id` + `deps` 只增不减） | orchestrator |
| **目标消解**（哪一条账、改成什么） | **高** | **agent（tool loop + observation）——但选项域由顶层裁剪（bounded autonomy）** | **bill_agent 内** |
| 落库 / 校验 / 数字渲染 | **低** | workflow（SQL 写死 + 白名单 + 后校验） | bill_agent 内（工具层） |

> ⚠️ **"自主"的准确含义（本节易被误读，务必对齐）**：子层的自主**不是"自由选择工具"**，而是
> **"在顶层剪裁过的选项域内自主决策"**——先看什么、看几次、把哪个候选当真、要不要追问，由它决定；
> 但**它能看到的工具集合由顶层给定的 `operate_sub_type` 决定**（§4.2.2）。这是 bounded autonomy（受限自主），
> 不是 full autonomy；写文档/面试时不要把两者混为一谈。

> **与既有文档的关系（重要）**：本项目文档曾记录"确定性调用架构下，LLM 自主选工具收益为零"
> （`工具接入平台与MCP系统学习.md:197/207`）。该结论**在派发与落库环节仍然成立**，本文不改它；
> 本文只补充限定：**在"目标消解"环节该结论不成立**——那是真正模糊、需要观察与多轮的环节。

### 2.4 职责边界表（红线，入 `09` 契约）

> 顶层实际定**三样**（容易被漏掉第三样）：任务、操作类型、**由前两者派生的工具可见面**。

| 能力 | orchestrator | bill_agent | 说明 |
|---|---|---|---|
| 决定是 add / edit / delete | ✅ | ❌ | 顶层独占 |
| **决定子 agent 能看见哪些工具（可见面）** | ✅（经 `operate_sub_type` → `tags`） | ❌（只能在该集合内选） | 可见面 = **RBAC 权限 ∩ 任务标签**（两层过滤，§4.2.2）；它与上一行是**同一个决定的两个面**（语义层 → 能力层投影），不是"多管了一层" |
| 决定操作哪一条账（`id`） | ❌ | ✅（自主循环 + 观察） | 这是唯一下放的自主权 |
| 决定新值（金额/品类/日期） | ❌ | ✅（工具参数 + 代码层兜底） | 沿用现有 `_fix_category` / `_fix_date` 兜底 |
| 生成 SQL | ❌ | ❌ | 工具内部写死（N6） |
| 决定要不要写（最终落库） | ❌ | ✅（但受幂等闸门 + 二次确认约束） | 写权限仅 bill_agent 持有（`mcpGateway/rbac_config.py:72-78`） |
| 数字渲染给用户 | ✅（`build_user_display_text`） | ❌ | 子 agent 禁止拼文案（既有红线，`agents/orchestrator/nodes.py:579-620`） |

**保留的架构性质**：能"提议写什么"的 Agent（orchestrator）没有写权限（`rbac_config.py:66-71`），
有写权限的 Agent 不擅自决定操作类型、也看不到操作类型之外的工具——即"提议-执行分离"不被破坏。

## 4. 方案设计（To-Be）

### 4.1 顶层：只定"操作与任务"，不定目标

- `plan_node` 产出 `operate_sub_type ∈ {add, edit, delete}`（沿用现有 LLM + 兜底表，`agents/orchestrator/nodes.py:88-93`）。
- **不新增"清单注入"，不新增 `target_bill_id` 下发**（初版设计的 §3.2 整体作废）：目标定位下放给子层。
- task_data 保持 bill 那套字段不变（`raw_segments` / `operate_sub_type` / `session_memory` / `city` / `month`），
  **只需修通 `session_memory` 的丢弃问题**（§3.2 缺口 1）——改动面因此比初版设计更小。
- 归一化防御：`operate_sub_type` 出现 `update`（旧手册漂移值，见 `设计/10` §5.1）时归一为 `edit`。

### 4.2 子层（bill_agent）：目标消解循环（★核心新增）

#### 4.2.1 职责收敛为一个子问题

> **输入**：`{operate_sub_type, raw_segments, 会话历史}`
> **输出**：`{目标 id, 新值（edit 时）}` 或 `{追问话术}`

循环里**只解这一件事**。落库、习惯重算、结果渲染全部在循环之外由确定性代码完成。

#### 4.2.2 工具可见面即"操作锁"（替代提示词约束）

**这是本方案最关键的机制**：操作类型不靠提示词"请不要删错"，而靠**模型根本看不到不该用的工具**。

| `operate_sub_type` | 暴露给模型的工具 | 模型能做的事 | 覆盖的指代 |
|---|---|---|---|
| `add` | `bill.add` | 只能新增（**只有 1 个工具，选无可选**——发现层在此基本是形式，价值集中在 edit/delete） | — |
| `edit` | `bill.recent_list` + `bill.update` | 定位哪一条 + 决定改成什么（可只改一项） | "刚才那笔 / 昨天打车的 / 面板第 2 条" |
| `delete` | `bill.recent_list` + `bill.delete` | 定位哪一条（+ 触发二次确认） | 同上 |

实现方式**复用现成能力**：`to_openai_schema(agent_id, tags=...)` 已支持 tags 过滤（`mcpGateway/registry.py:224-239`），
为四个工具打 tag（`op:add` / `op:edit` / `op:delete` / `op:read`），bill_agent 按 `operate_sub_type` 选 tag 取工具清单。

**可见面是两层过滤的交集**（勿只记 tags 那一层）：

| 层 | 过滤器 | 性质 | 依据 |
|---|---|---|---|
| 第一层 | RBAC：`list_tools(agent_id)` 按该 Agent 的权限集合过滤 | **静态**（Agent 权限画像固定） | `mcpGateway/registry.py:208-222` |
| 第二层 | `tags`：按 `operate_sub_type` 收窄 | **动态**（每个任务不同） | `mcpGateway/registry.py:224-239` |

> 即：**可见面 = RBAC 权限 ∩ 任务标签**。第一层保证"不该给这个 Agent 的能力永远看不到"；
> 第二层保证"这个任务不该用的操作看不到"。**第一层归属 Agent 画像（顶层定不了），第二层由顶层经 `operate_sub_type` 决定**——
> 所以准确表述是"顶层**在既有 RBAC 边界内**进一步收窄可见面"，不是"顶层授予工具权限"。

**代价（已知取舍，且是正确行为）**：操作类型锁死后，子 agent **无法在执行中途切换操作类型**——
例如用户说"把那笔打车改成 50"，查库却发现那笔已被删除，此时子 agent 想"那就删掉别的"是**做不到的**（看不到 `bill.delete`）。
正确处置是**追问并交回顶层**：用户重新表述后由顶层重新规划出新的 `operate_sub_type`。此行为已登记进失败矩阵（§4.6）。

> 收益：① 意图判定只有一份（顶层），子层无"再判一次操作类型"的余地；② 即使模型幻觉，也**调用不出越权操作**；
> ③ 新增操作类型时只需加工具 + 打 tag + 顶层加枚举，不动子层逻辑。

**为什么"看"只需要一个工具（推导）**：目标消解的候选指代方式与所需信息逐一对应——

| 用户指代 | 需要系统给出什么 | 由谁满足 |
|---|---|---|
| "刚才那笔 / 最近一笔" | 按记账时间倒序的最近几笔 | `bill.recent_list` |
| "昨天那笔打车的 35 块" | 日期 + 品类 + 金额 + 原文备注 | `bill.recent_list`（返回字段齐备） |
| "面板里第 3 条" | 与 UI 面板**同一序号口径**的清单 | `bill.recent_list`（与面板共用同一实现） |

#### 4.2.3 循环控制（有界、幂等、可观测）

| 项 | 规则 | 理由 |
|---|---|---|
| 循环形态 | `模型 → tool_calls → 引擎执行 → 回填 observation → 再决策`，**无 `tool_calls` 即结束** | 标准 tool loop；**追问 = 模型不调工具、直接输出话术**（因此不需要 `ask_user` 工具，见 §4.2.6） |
| 最大轮次 | `FC_MAX_TURNS`（建议 4，落 config） | 防无限试探（必须做，不是可选） |
| **写操作幂等闸门** | 单次 task 内**写工具只允许成功执行一次**；再次调用直接返回错误 observation 并终止循环 | 防模型重复调 `bill.add` 导致重复记账（破坏 M5/D2 成果） |
| observation 精简 | 工具返回只保留关键字段（`id/amount/category/consume_time/remark/create_time`），限制条数 | 防上下文爆炸（D6 预算） |
| 可观测 | 每轮 tool 调用经引擎自动落 `tool.{name}` span（现成） | 失败可定位到"第几轮调了什么" |
| 失败语义 | 工具返回权限/校验错误时，作为 observation 回填**而非抛异常**；连续失败达 `FC_MAX_TURNS` → 转追问 | 循环内不崩 |

> **★P3b 落地修订（2026-09-15，3 条）**：
> ① **`add` 不进入自主循环**（本表"add 任务可见面只有 `bill.add`"仅作能力预留）：`add` 恒走确定性
> workflow——它已有 8 层兜底，换成模型自主是用不确定性换不确定性；而自主性的价值集中在 edit/delete
> （需要定位与多字段决策），本表自己写的"发现层在 add 上基本是形式"正是这个道理。
> ② **成功判据 = 写工具真的成功过**（`_fc_finalize`）：模型文本只作为 `data.reply` 展示，绝不作为成功依据
> （§6 红线 7 的落地）。
> ③ **`habit.recalc` 在写成功后立即触发**（不等终态）：循环可能多轮，"中途成功、后续失败"的情形若等到终态
> 就算不到；而月份信息（`changed` 的旧/新值或删除快照）本就由工具返回，无须额外查询。

#### 4.2.4 工具清单（4 个，SQL 全部写死在工具内部）

| 工具 | 入参（JSON Schema 约束） | 返回 | 权限 / 副作用 | 内部实现要点 |
|---|---|---|---|---|
| `bill.recent_list` | `limit: integer`（服务端 **clamp 到 `[RECENT_BILL_WINDOW, RECENT_BILL_MAX]`**，默认 3 / 上限 20） | `[{id, amount, category, consume_time, remark, create_time}]`，按 `id DESC` | `FACT_READ` / 只读 | **必须返回 `id`**（否则模型拿到清单也无法调 update/delete）；`create_time` 是"刚才那笔"的口径 |
| `bill.update` | `id: integer`（**必填**）+ 可选 `amount` / `category` / `consume_date` | `{ok, id, changed: {字段: [旧值, 新值]}}` | `BILL_WRITE` / ✅ | 固定模板 `UPDATE ... SET x = COALESCE(?, x) WHERE id=?`；**先读存在性 → 写 → 后回读校验**；不修改 `id`/`task_id` |
| `bill.delete` | `id: integer`（**必填**） | `{ok, id, deleted: {原行快照}}` | `BILL_WRITE` / ✅ | 先查存在性 + 写后校验已消失；**删 0 行判失败**（不得沿用"删 0 行算成功"旧语义，`utils/common.py:320-324`） |
| `bill.add` | `amount: number` / `category: string` / `consume_date: string`（均必填）+ `remark` | `{ok, id}` | `BILL_WRITE` / ✅ | 内部 `INSERT`，**代码层写 `task_id`**（不依赖模型生成） |

> **`id` 在 Schema 里是必填 `integer`**：模型**传不了自然语言**，参数不合规会被执行引擎的 JSON Schema 校验挡住（`mcpGateway/executor.py:33-50`）——"温和的错"进不到工具里。

补充：

- `habit.recalc`（`HABIT_WRITE`，async + 协程内持 `db_lock`）用于改删后**整月重算**月度习惯（§4.5）。**不打 `op:*` tag → 不对模型可见**（由代码在写操作成功后自动触发）。
- `bill.add` 的引入**不改变 add 路径的业务语义**（仍由代码拼 SQL + 写 `task_id`），只是把"拼 SQL 的位置"从节点移到工具内部——这是本里程碑唯一触碰 add 的地方，需专项回归（§8.2 红线 1）。
- **实现落点定稿**：新建 `mcpGateway/bill_tools.py`（bill 专属工具，避免 `fact_tools.py` 膨胀）；`habit.recalc` 仍落 `fact_tools.py`（与 `habit.upsert` 同族）。

> **★P1 落地修订（2026-09-15，3 条）**：
> ① **`bill.recent_list` 的权限取 `DBPerm.BILL_READ`**（本文上表与 `09` §4.10 原标 `FACT_READ`）——
> 该工具读的就是账单表，`BILL_READ`（"账单查询权限 SELECT"）语义精确对应；改用 `FACT_READ` 会迫使给
> bill_agent 扩一条它并不需要的 `fact:read`（该权限覆盖 user_config / city_price / monthly_habit 读，
> 属**越权面扩大**，违反最小权限）。副产物：stat/price/finance 本就持有 `BILL_READ`，故 `bill.recent_list`
> 对它们也可见——这是"权限与可见面一致"而非扩权（它们不参与 FC 循环）。
> ② **`task_id` 落地为「引擎注入」**：新增 `InvokeContext.task_id` + `binding["inject_ctx"]`，两个适配器共用
> 模块级 `_apply_ctx_injection`。故 `add_bill(..., task_id)` 的该形参**由引擎填、不进 `params_schema`**
> （与既有 `inject_agent_id` / `inject_run_id` 同构）。*原设计只写了"代码层写 `task_id`"，未定义它如何抵达
> 工具函数*——本机制即该缺口的补齐；它同时让 P3b 循环**无需为写工具"补参"**（注入由平台保证，不会漏）。
> ③ **`bill.recent_list` 的 `limit` 定为可选**（schema 的 `required` 不含它），函数默认 `RECENT_BILL_WINDOW`
> ——让模型少犯错（原设计的 `limit: int` 未区分"未传"与"传得过小"两种情形，而后者正是 §5.1 实测到的坑）。

#### 4.2.5 可操作窗口

- `RECENT_BILL_WINDOW = 3`（config）：即"最近 3 笔"可指代；窗口外或歧义 → 追问。
- **为什么按"最近 N 笔账单"而不按"最近 N 轮会话"**：① 会话历史是易失滑窗，只留末尾最多 6 条消息（`memory/short_memory.py:66-83`）；② 一轮对话可能记多笔，"轮"与"笔"不对齐；③ `id` 是持久事实源，与 `task_id` 对账同源。
- 序号（清单内相对编号）**只在当前清单/当前轮有效**；草稿按 `id` 存储，不存序号。

#### 4.2.6 明确**不做**的工具（与"不做什么业务"同等重要）

> 原则：**给模型的可见工具越少，选择准确率越高、越权与误用的面越小**（这也是 tags 过滤存在的意义）。

| 候选工具 | 加不加 | 理由 |
|---|---|---|
| `ask_user`（追问工具） | ❌ | **追问不需要工具**：模型判断信息不足时**不调工具、直接输出话术**即可——循环的终止条件就是"无 `tool_calls`"（§4.2.3） |
| `bill.get(id)`（读单条） | ❌ | `recent_list` 已返回 `remark` 全文（用户原话，本身很短），无额外信息需求 |
| `bill.confirm_delete`（跳过确认） | ❌ **红线** | 二次确认走草稿槽 + 顶层确认快路径（§4.4）；**模型不该拥有"跳过确认直接删"的能力** |
| `bill.batch_update` / `bill.batch_delete` | ❌ | 批量改删明确不做（§1.2 N1：影响面不可控，与逐条确认的交互模型冲突） |
| `bill.find_bills`（条件查询） | ⚠️ 第二版（§4.2.7） | v1 窗口 3 笔够用；加它会扩大可操作范围，与"先收敛"取舍冲突 |
| `habit.recalc` | ❌（不对模型可见） | 内部一致性动作，模型既无权也无必要触发 |

#### 4.2.7 扩展路径（工具化的可扩展性）

用户说"**上个月买鞋那笔**"时，`recent_list`（最近 3 笔）够不着。扩展**不改循环、不改顶层**：

| 版本 | 加什么 | 影响面 |
|---|---|---|
| v1（M15） | `bill.recent_list(limit)` | — |
| v2（可选，按需） | `bill.find_bills(start_date / end_date / category / keyword / min_amount / max_amount)`，打同一个 `op:read` tag | **只加工具 + 打 tag**；循环、图、顶层、A2A 契约零改动 |

> 这正是"工具化"相对"节点内硬编码分支"的价值：**加能力 = 加工具**，而不是往 `execute_node` 里再塞一个 `if`。

### 4.3 tools 通道在契约里的位置（★易踩坑）

**两个必须显式声明的通道，且都不走 `options` 白名单**：

| 通道 | 为什么单独走 |
|---|---|
| `tools` | 它是**协议结构**（与 `messages` 同级），不是调参项。塞进 `options` 会被 `filter_options` 白名单滤掉并告警（M14 铁律：`modelService/chat_model.py:4-5`、`:155-179`） |
| `extra_messages`（tool 结果回填） | 现签名只有 `system` + `user` 两个字符串（`chat_model.py:136-137`）**承载不了多轮 tool 消息**；不解决这点，循环第二轮就没法把 observation 交给模型 |

设计要点：

- `ChatModel.generate` 新增 keyword-only `tools: list | None = None`、`extra_messages: list | None = None`（**默认 None，对现有调用零影响**）；
- `ChatResult` 新增 `tool_calls: list | None`，归一为 `[{"id": str, "name": str, "arguments": dict}]`；
- `Router.execute/generate` **原样透传**这两个参数（不 merge、不转译、不白名单）；
- `llm.chat` 的 `params_schema` 增可选 `tools`（JSON 数组）；server 侧 `llm_chat` 透传；
- 工具清单从哪进模型：**仍走网关**（`registry.to_openai_schema(agent_id, tags=...)` → 作为 `llm.chat` 的 `tools` 参数），
  以维持"Agent 只经网关访问模型/数据"的红线（`设计_从零系列/09` §0.3 原则 2），不新增直连 provider 的旁路。
- `agent_id` / `run_id` 仍由适配器注入，**不进 schema**（防 LLM 伪造提权，`mcpGateway/adapters.py:119-127`）。

> **★P2 落地修订（2026-09-15，2 条）**：
> ① **FC 通道落地为「新增独立工具 `llm.chat_fc`」，而非改 `llm.chat`**。原设计未闭合一个缺口：
> `llm.chat` 的返回契约是**纯文本 `str`**（MCP content 只取第一条 text），而本方案需要**结构化 `tool_calls`**。
> 用"传了 tools 就返回 JSON、否则返回文本"来表达会让同一工具的契约**二义**，且 18+ 处生产调用与
> ~40 处测试 patch 依赖其返回类型。新增工具的三个好处：旧契约零风险、可单独 `unregister` 回退
> （满足 `11` 的回滚要求）、符合"加能力 = 加工具"的既有范式（§4.2.7）。
> 配套：server 侧新增 `llm_chat_fc`（返回 JSON 字符串 `{"text","tool_calls"}`），兼容层新增
> `client.call_llm_fc`（还原 dict；`FINANCE_ERROR:` 前缀与非法 JSON 均抛 RuntimeError——
> **通道故障不得静默为空 tool_calls**，否则循环会把"通道坏了"误读为"模型不想调工具"）。
> ② **外部 Provider 的"空内容"判定改为 `not text and not tool_calls`**（原为 `not text`）。
> 原因：FC 场景下模型用工具调用代替自然语言回复、`content` 为空是**正常形态**（P0-b 实测已见）；
> 沿用旧判定会把正常 FC 响应判成 `EMPTY_CONTENT` 并触发 3 次无意义重试。

### 4.4 删除二次确认（复用草稿槽，机制不变）

```text
第 1 轮（"删除 X"）
  bill_agent.delete：
    ① 循环内先 recent_list 观察 → 定位到 id；定位不到/歧义 → 追问
    ② 草稿槽 bill_delete 中已有同一 id 的待确认记录？
         ├─ 有 且 本轮文本命中确认词 → 执行 bill.delete → 清草稿
         └─ 否 → 写草稿 {id, amount, category, consume_time, remark} → need_more_info
                  prompt = "确认删除这笔吗？09-13 交通 35 元（昨天打车35元）"
第 2 轮（"确认 / 确定 / 对 / 是的 / 删吧"）
  orchestrator.plan：确认词 + bill_delete 草稿存在 → 确定性快路径直接产出 delete 任务（不调 LLM）
  bill_agent：确认词 + 草稿同 id → 执行删除
```

- 确认词表 `CONFIRM_KEYWORDS`：`确认 / 确定 / 是的 / 对 / 嗯 / 可以 / 删吧 / 删除吧 / 同意`。
- 草稿**读**可从 `state["session_memory"]["draft_store"]` 读（下发快照）；**写/清**必须经
  `get_session_memory(session_id).set_draft/clear_draft`——`export_all()` 是**浅拷贝**（`memory/short_memory.py:202-219`），
  就地改快照不会写回全局。
- 前提：worker 与 orchestrator **同进程同一事件循环**（`设计_从零系列/09` §3.5 第 3 条），不得跨进程改造。
- 超轮放弃沿用现成机制（`ASK_ROUND_LIMIT`，`agents/orchestrator/nodes.py:1833-1838`）。

### 4.5 派生数据一致性：`monthly_habit` 整月重算

- 现有 `habit.upsert` 是**增量累加**语义（`utils/common.py:498-508`），**无法处理"改小/删除"**。
- 方案：改删后调 `habit.recalc(month)` → 复用 `recalc_month_habit(month)`（`utils/common.py:532-564`，以 `bill` 为唯一事实源全量重算，**幂等**）。
- 触发：edit → 重算旧月；若日期改动跨月 → 再重算新月；delete → 重算该行 `consume_time` 所在月。
- **静默失败不阻断**（照抄 `_settle_month_habit` 三重短路 + `except: pass`，`agents/bill_agent/nodes.py:216-235`）。

### 4.6 失败模式与兜底矩阵（每个兜底至少一条测试）

| 场景 | 出口 | 用户看到 |
|---|---|---|
| 循环内定位不到目标 | 追问 | "没找到符合条件的账单，您是指哪一条？" + 清单 |
| 目标歧义（多命中） | 追问 | 列出候选让用户选 |
| 越出可操作窗口 | 追问 | "只能处理最近 N 笔，请说明日期或品类" |
| edit 无任何新值 | 追问 | "您想改成什么？" |
| 新金额 ≤ 0 | 失败（不写库） | "消费金额必须大于 0" |
| 目标不存在（id 查无） | 失败（不写库） | "未找到该账单，可能已被删除" |
| 模型重复调写工具 | 闸门拦截 + 终止循环 | 以第一次结果为准（不重复记账） |
| 循环达 `FC_MAX_TURNS` | 转追问 | "请把要改的内容说得更具体一点" |
| 模型产出非法工具名/参数 | 引擎校验失败作 observation 回填 | 循环继续；连续失败转追问 |
| SQL 写失败 | 失败 | "账单更新失败" / "账单删除失败" |
| 写后回读校验不一致 | 失败 | "账单更新未生效" |
| 习惯重算失败 | 静默 + 日志 | 无感 |
| 未确认就换话题 | 不删（草稿留待覆盖/超限清理） | — |
| **用户中途要换操作类型**（改→删） | 追问 + **交回顶层重规划** | "这笔已不存在；若要删除请直接说'删掉…'"——子 agent 看不到目标工具（操作锁的代价，§4.2.2） |

> **★P3a 落地修订（2026-09-15）**：本节失败矩阵在**确定性驱动路径**上已全部有出口与测试
> （`BILL_FC_ENABLED=0` 时的实际执行路径，同时也是功能保底）。规则集不在本文展开（避免两处维护），
> 见 `设计_从零系列/09` §4.10(8)「P3a 确定性驱动路径」。要点三条：
> ① 定位规则**显式化且可穷举**（序号 > 金额 > 金额+属性 > 属性 > 指代词，且指代词仅在"窗口唯一且原文无金额线索"时生效）——
> 定位错 = 改错/删错账，属不可逆事故，不能靠临场发挥；
> ② **新值紧缩政策**：只有**金额**可能来自模型（且仅当"改写动词+数字"提取不到时才问模型），
> **品类与日期只认原文线索**——防"改金额顺手把品类/日期也改了"；
> ③ 新值数字与日期片段**必须从定位线索中剔除**（"把 35 那笔改成 50"），且**相对日期优先于绝对日期**
> （"把昨天那笔改到 2026-10-05"）——这两条都是首轮实现被测试暴露出来的**真缺陷**，不是预设的谨慎。
> 验收：`tests/unit/test_bill_edit_delete.py` 共 20 用例。

### 4.7 降级路径（FC 不通时功能不丢）

> **★★输入形态分流（2026-09-16 修订）**：`BILL_FC_ENABLED` 不再是 edit/delete 的**唯一**开关，
> 执行路径按**输入形态**分流——这是"UI 点选必须可预期"的直接落地：
>
> | 输入形态 | 执行路径 | 理由 |
> |---|---|---|
> | **显式主键**（`把 id=515 那笔改成 50`，即 UI 点选产物） | **P3a 确定性**（代码定位 + 代码改） | 目标已由主键唯一确定，**不需要也不该**再交给模型"自主定位"；实测 FC 路径下模型会把 `bill.update` 的 tool_call 形态当**正文**输出而工具未执行 → 用户看到一段 JSON、数据没改 |
> | **自然语言指代**（`把昨天那笔打车改成 50`） | **FC 自主循环**（开关关闭时回落 P3a） | 需要在候选里自主定位，正是 §2 范式要交付的能力，不因噎废食 |
> | **删除**（无论哪种形态） | **恒走 P3a** | 删除不可逆，§4.4 的"先确认后删"必须确定性执行（实测 FC 路径会跳过确认直接删库） |
>
> 于是"三层降级"的实际形态为：**第 1 层工具化（功能保底）→ 第 2 层 P3a（显式指认与删除的确定性执行）→ 第 3 层 FC（自然语言指代的自主定位增益）**。
> 验收：`把 id=245 那笔改成 35` 真落库（`DB_AFTER_35 {'amount': 35.0}`）并可改回；`删掉 id=245 那笔` 只追问确认、数据不动。

| 层 | 内容 | 是否白做 |
|---|---|---|
| **第 1 层：工具化（必做）** | 4 个 `bill.*` 工具 + `habit.recalc` + `bill.recent_list`，SQL 全部写死 | **不白做**：功能（改删）在此层即可闭环，且 SQL 从节点收敛进工具，安全性反而提升 |
| **第 2 层：自主循环（增益）** | tools 通道 + tool loop + 熔断 + 幂等闸门 | 范式达标项，可独立开关（`BILL_FC_ENABLED`） |
| **第 3 层：降级** | 若 FC 不可用：① 把 `bill_agent` 加进 `EXTERNAL_LLM_AGENTS`（已决定全链路外部，此项自动满足）；② 仍不通 → 走 ReAct 文本协议（项目已有模板参考 `modelService/llm/examples/react_prompt.md`）；③ 最终退回"确定性目标消解"（初版 §3.2 的清单 + 代码映射，工具层复用不变）；**实现上对应施工序 P3a**（`11` §3 M15，`BILL_FC_ENABLED=0` 时生效） | 功能不丢 |

## 5. 前置门禁：FC 能力实测（✅ 已通过 · 2026-09-15）

> 依据 `设计_从零系列/09` §4.4 走查项 3：**禁止"文档说支持"当通过，必须 ≤30 行原型实测**。

| 项 | 要求 |
|---|---|
| 测什么 | 外部模型（`EXTERNAL_LLM_BASE_URL` 指向的实际后端）在 `/chat/completions` 下**是否返回结构化 `tool_calls`**、`arguments` 是否为合法 JSON |
| 怎么测 | ≤30 行临时脚本，带 `tools` 定义直连，覆盖 3 类输入（新增 / 修改 / 删除）各 2~3 次 |
| 通过标准 | ≥2/3 返回结构正确 `tool_calls`（**不是**在正文里编一段 JSON）；且第二轮能正确消费 `tool` 结果消息 |
| 不通过 | 启用 §4.7 第 3 层降级（功能照做，范式降级为 ReAct 文本协议） |
| 注意 | 很多兼容层/代理会**静默丢弃 `tools` 字段**——必须端到端验证，不能只看"模型支持 function calling" |

**门禁性质**：go/no-go 点 → **本项已判定为 go**，第 2 层（自主循环）按 §4.2 实施；第 1 层（工具化）不受影响、照做。

### 5.1 实测结论（2026-09-15 执行）

**环境**：`glm-4-flash` @ `https://open.bigmodel.cn/api/paas/v4`（本次实测时的配置）；工具集 = 4 个 `bill.*` + 系统提示。临时脚本跑完即删。

| 用例 | 模型产出 | 判定 |
|---|---|---|
| "把刚才那笔打车改成50" | `bill_recent_list(limit=1)` | ✅ 先查后改（符合设计：先 observation 再定位） |
| "删掉昨天那笔奶茶" | `bill_recent_list(limit=1)` | ✅ 先定位 |
| "记一下午饭56元" | `bill_add(amount=56, category=餐饮, consume_date=2021-08-30)` | ✅ 意图对（日期需兜底，见下） |
| "把昨天那笔奶茶改成20块" | `bill_recent_list(limit=5)` | ✅ 先定位 |
| **第二轮（observation 回填）** | 收到 `{bills:[{id:137,...}]}` 后产出 `bill_update(id=137, amount=50.0)` | ✅ **闭环成立** |

**结论**：① 兼容层**未**丢弃 `tools` 字段（返回原生 `tool_calls`）；② 模型能在"先查后改"上自发形成两步决策；③ **多轮 observation 消费正常** —— 目标消解闭环可落地。
**但**：该结果有前提 —— **必须给系统提示 + 工具集必须完整**（见修正 3）。

### 5.2 实测暴露的 3 条设计修正（已回写本文与 `09`）

| # | 实测现象 | 修正 |
|---|---|---|
| 1 | 模型自由传 `limit`（`1/1/5`）——传 1 时窗口过小，**可能漏掉真正的目标** | `bill.recent_list` 的 `limit` 由**服务端 clamp** 到 `[RECENT_BILL_WINDOW, RECENT_BILL_MAX]`（§4.2.4） |
| 2 | 对"午饭56元"（无时间线索），模型**编出 `2021-08-30`** | **确定性日期兜底不可删**：现有 `_fix_date`（无时间线索一律取今天，`agents/bill_agent/nodes.py:128-131`）必须保留——**强模型同样会编日期**，修正了"换强模型后兜底可简化"的想当然 |
| 3 | 第一版探针（无系统提示）触发率仅 1/3，且模型在**没有 `bill_add` 工具时回答"已记录"**（谎报成功） | ① bill_agent 提示词必须写明"涉及账单操作必须先调工具，**不得在未调用工具时声称已完成**"；② **写操作是否成功只能以工具返回值（`ok`）为准，绝不由模型文本决定**（§8.2 红线 3 的强化） |

### 5.3 ⚠️ 环境发现（P0-a 验证产物，非本里程碑引入）

本机 Windows **注册表系统代理**（Internet 选项）指向 `127.0.0.1:7892`；该代理未启动时 `requests` 默认走它 → **外部 LLM 调用全部失败**（`ProxyError: Unable to connect to proxy`）。
`modelService/providers/openai_compat.py` 的 `generate` 使用裸 `requests.post`（不建 Session、不设 `trust_env`），因此**生产链路同样受此影响**。
**处置（二选一，均属本里程碑之外）**：① 运行前启动代理软件；② 给外部 Provider 增加"绕过代理"可配置开关（`trust_env=False`），使无代理环境也能直连。**用户决策：走"显式直连"**——Provider 侧**固定 `trust_env=False`**（不加配置开关，避免过度设计），把网络行为从"看系统心情"变成确定行为。**已实施**：`modelService/providers/openai_compat.py` 建模块级 `_SESSION = requests.Session()` 且 `trust_env=False`，请求改走 `_SESSION.post`；并补回归用例 `test_external_provider_disables_system_proxy`（防后续重构改回裸 `requests.post`）。**代价（已知取舍）**：若将来部署环境**必须**经代理出网，需在该处显式传 `proxies`。

| 组件 | 类型 | 职责 |
|---|---|---|
| 「我的账单」面板 | `gr.HTML` | 按月 `<details>` 折叠（动态月份数天然支持）；行含：序号 · 消费日期 · 品类 · 金额 · 内容（`remark`）· 记账时间 · `id`（小字） |
| 目标选择器 | `gr.Radio` | 选项 = 「#3 · 09-13 · 交通 · 35.00 元 · 昨天打车35元」，与面板序号一致 |
| 「修改选中」/「删除选中」 | `gr.Button` | **只写输入框**：`gr.update(value="把 {描述} 改成")` / `"删除 {描述}"`，用户可编辑后再发送 |
| 「刷新账单」 + 自动刷新 | `gr.Button` + `respond` 追加 output | 每轮对话后刷新（改删/记账即时可见） |

- **红线**：按钮只产生自然语言，写操作仍走 `orchestrator → bill_agent` 单通道，保留 RBAC / 审计 / 对账 / 二次确认 / 习惯重算全链路。
- 对比：预算面板可直写 `user_config`（配置写入，无派生数据与对账义务，`webUI/app.py:174-177`）；账单是**业务事实**，两者不同待遇。
- **两个时间维度同时展示**（关键）：`consume_time` 是用户口述日期（无时间线索一律兜底为今天，`agents/bill_agent/nodes.py:128-131`），`create_time` 才是"刚才那笔"的口径；面板按月折叠用前者，选择器按 `id DESC` 用后者。
- 取数口径与 `bill.recent_list` **共用同一实现**，防"UI 看到的"与"Agent 认知的"分叉。
- ★**设计修正（2026-09-15，用户反馈驱动）**：`RECENT_BILL_WINDOW`（3）是**"自然语言指代"的窗口**，
  **不该约束"UI 点选"**——点选 = **显式指定**（id 已确定），不存在指代歧义。
  故：① 面板**不再画"超出可操作窗口"的行**（不展示"看得见却动不了"的条目）；
  ② 选择器**列全面板条目**（不再截断到 3 条）；
  ③ 选择器选中值由「序号」改为 **`id`**——序号会因"中间又记了一笔"整体漂移，导致
  "用户点的是第 1 条、Agent 改的却是另一条"这类**改错账**事故（id 是持久标识，不会漂移）；
  ④ 于是输入框写的是 `"把 id=9 那笔改成 "`。
  面板展示条数由 `UI_BILL_PANEL_LIMIT` 控制，两者的分工为"展示上限 vs 指代窗口"。

> **★★修订（2026-09-16，第二轮用户反馈驱动）**：上面 ④ 原写"显式 id 时把取数上限**放宽到
> `RECENT_BILL_MAX`（20）**"——**该做法已被实测证伪并废弃**，改为下面三点：
> ① **显式主键不受任何窗口约束，按主键直取该行**（`bill_tools.get_bill_by_id` + 节点侧
>   `_fetch_bill_by_id`，**均不注册为工具**——§4.2.6 已定 `bill.get(id)` 不做，此处是节点内部定位读数）。
>   原因：`RECENT_BILL_MAX`（20）只是"比 3 大一点"，而面板取数上限已放宽到 200 —— 实测用户
>   从面板选中 `#245` 后发送删除指令，后端只拉 20 笔 → 目标落在窗口外 → 回答"没找到符合条件的账单"
>   （**面板里能选、Agent 说找不到**）。主键是无歧义指认；窗口约束的本意是防"自然语言指代"命中错行，
>   **不该限制显式指定**。
> ② **显式 id 的 `edit` 改走 P3a 确定性路径**（§4.7 按**输入形态**分流），不再交给 FC 自主循环：
>   实测 FC 路径下模型会把 `bill.update` 的 **tool_call 形态当正文输出**
>   （回复体为 `{"name":"bill.update","parameters":{…}}`）而**工具未真正执行、数据未改**——
>   点选路径必须"给定 id 即改该笔"，行为可预期、可验收。自然语言指代仍走 FC（自主定位范式不丢）。
> ③ **面板取数上限独立**为 `UI_BILL_FETCH_LIMIT`（200）+ `recent_bills_for_ui()`（与 `recent_bills`
>   同一 SQL/排序/投影，**不注册为工具** → 模型可见面与 `RECENT_BILL_MAX` 语义**原样不动**）；
>   面板同时改为**按天分页（每页 7 天）+ 上下翻页**，避免 20 行列表一次铺开。
