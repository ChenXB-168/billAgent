# 21 · 三层进程退出防御（M23 · D26）

> **状态**：✅ **已实施**（2026-10-09：P0–P4 全部落地；L1 **539 → 550 passed**、`contract_check` FAIL 0、lint 0；M23 专项 **11 passed**）
> **日期**：2026-10-09
> **触发**：拷打复盘时被问「你的项目有没有做 SIGTERM 优雅关闭」。逐层核查后确认一个**反直觉的结论**：
> **优雅关闭的\*实现\*是完整的（`startup/bootstrap.py::shutdown_system` 逻辑可复用、已测），
> 但触发路径只接了 2 条（UI 退出按钮 / Ctrl+C），而最标准的 `SIGTERM` 没接；
> 且"被强杀"这一场景 100% 无覆盖。**
>
> **结论先行** —— 把「进程退出」按**父进程是否还有机会执行 Python 代码**拆成三层：
>
> | 层 | 前提 | 机制 | 改造前 |
> |---|---|---|---|
> | **L1 触发层** | 有机会执行 + 已触发 | `shutdown_system()`（已有） | ⚠️ 只接了 UI 按钮 / Ctrl+C |
> | **L2 信号层** | 有机会执行 + 需 OS 通知 | 注册 `SIGTERM` handler | ❌ **缺失**（Python 默认直接退出，`finally` 不执行） |
> | **L3 内核层** | **没有任何机会**（强杀 / 崩溃） | Win `Job Object KILL_ON_JOB_CLOSE` / Linux `PR_SET_PDEATHSIG` | ❌ **缺失** |
>
> **关键洞察：L3 是唯一能覆盖「不给任何机会」的机制** —— 它由内核态保证，不依赖父进程执行任何代码。

## 一、需求说明（要改什么）

### 1.1 真实诉求

| # | 场景 | 期望行为 | 改造前实际 |
|---|---|---|---|
| **R1** | `kill -15 <pid>` / `docker stop` / 系统关机 | 3 个 MCP 常驻子进程**随之收敛** | ❌ **全项目 0 个 `signal.signal()` 注册** → Python 收到 `SIGTERM` 默认**直接终止**，**不抛异常、不执行 `finally`、不跑 `atexit`** → `main()` 的 `finally: shutdown()` **根本不执行** → 3 个子进程（8001/8002/8003）**全部变孤儿** |
| **R2** | `taskkill /F` / 进程崩溃 / 父进程被 SIGKILL | 同上 | ❌ **无任何机制** —— 连"有机会执行代码"都不成立 |
| **R3** | CLI 入口（`main.py` → `startup/chat_loop.py`）输入 `exit` | 优雅关闭 MCP 常驻服务 | ❌ **`run_chat` 完全没有关闭逻辑** —— `break` 后函数返回，`asyncio.run` 只取消协程（4 个 worker 能收敛），**但 3 个 `Popen` 子进程不会被杀** → 必然泄漏。目前靠**下次启动时 `_cleanup_stale_mcp_ports()` 事后清理**兜底 |
| **R4** | 文档与配置的自洽性 | 注释不得误导 | ⚠️ `utils/docker_compose.yml` 注释写「tini 转发信号 → `shutdown_system` 生效」，**因果链断裂**：tini 只保证信号**送达**，`shutdown_system` **依然不会被调用**（缺的是 handler，不是信号） |

### 1.2 本方案不做什么（范围边界）

- ❌ **不改** `shutdown_system()` 的既有实现（L1 逻辑已正确、已测，只补**触发入口**）
- ❌ **不改** M4 `sandbox.py` 的内存限制语义（`_JOB_OBJECT_LIMIT_PROCESS_MEMORY` 保持）
- ❌ **不改** M3 的常驻拓扑 / `SERVER_CMD_MAP` / 端口约定
- ❌ **不做** MCP server 的「优雅停机 HTTP 端点」（Windows `terminate()` 是 `TerminateProcess`、不给拦截机会；要真优雅需 server 侧加 `/shutdown` 端点 —— 属独立能力，登记为待办 T-1，见 §八）
- ❌ **不加** 新增环境变量配置项（PDEATHSIG 复用既有 `memory_mb<=0` 的沙箱总开关语义）

## 二、架构结论

### 2.1 为什么必须是三层 —— 缺任何一层都有明确反例

| 只有 L1 | 只有 L1+L2 | 三层齐备 |
|---|---|---|
| `taskkill /F` → **孤儿** | `taskkill /F` → **孤儿** | `taskkill /F` → ✅ 内核回收 |
| `kill -15` → **孤儿** | `kill -15` → ✅ 收敛 | ✅ 收敛 |
| UI 按钮 → ✅ | ✅ | ✅ |

**→ L3 不是「L2 的加强版」，而是覆盖 L2 **原理上无法覆盖**的场景**（父进程被剥夺执行权）。

### 2.2 为什么"注册信号 handler"不能替代 L3（★核心论证）

`SIGTERM` 与 `SIGKILL` 的区别决定了两层的分工：

| 机制 | `kill -15`（SIGTERM） | `kill -9`（SIGKILL）/ `TerminateProcess` / 崩溃 |
|---|---|---|
| Python 层可拦截 | ✅（注册 handler 后） | ❌ **内核直接回收，进程无从感知** |
| 能否执行清理代码 | ✅ | ❌ |
| **Job Object `KILL_ON_JOB_CLOSE`** | ✅ | ✅ **仍生效** |

**故：L2 与 L3 是\*互补\*而非\*替代\*关系** —— 任何试图"只做一层"的方案都有明确的可构造反例。

### 2.3 为什么 L3 在 Windows 上**几乎零成本**（★本方案的性价比论点）

`mcpGateway/sandbox.py` **已经**为每个 MCP 子进程创建了独立 Job Object：

```python
job = kernel32.CreateJobObjectW(None, f"mcp_sandbox_{proc.pid}")
info.BasicLimitInformation.LimitFlags = _JOB_OBJECT_LIMIT_PROCESS_MEMORY   # ← 当前只有这一个标志
```

**只需在 `LimitFlags` 上按位或一个常量**，即可获得"父进程死亡（任意方式）→ Job 句柄被 OS 回收 → Job 关闭 → Job 内进程被内核终止"。

且**现有设计恰好满足该标志的前提**：

| 前提 | `sandbox.py` 现状 |
|---|---|
| Job 句柄必须在父进程存活期**保持打开** | ✅ `_ACTIVE_JOBS[proc.pid] = job` **且刻意不 `CloseHandle`**（原注释：*"句柄随 bootstrap 进程生命周期自然回收"*） |
| 父进程**不在**该 Job 内 | ✅ `CreateJobObjectW` 建的是**新 Job**，父进程不属于它 |

> **注**：若 `AssignProcessToJobObject` 失败（父进程本身已在某 Job 中，如 IDE / shell 环境），
> 子进程**不受本方案保护** —— 此路径**既有行为即为"降级告警、不阻断启动"**，本方案不改变。

### 2.4 为什么 PDEATHSIG 挂在 `apply_process_limits()` 内部

`PR_SET_PDEATHSIG` 是**进程对自身的设置**，POSIX 下父进程**无法事后**给已启动的子进程施加 —— 必须**子进程自己调**。

而 `apply_process_limits()` 正是 3 个 MCP server `__main__` 的既有自调用钩子：

```python
# mcpGateway/sql_server/server_bill.py（同构：server_llm_base.py / server_llm_finance.py）
if __name__ == "__main__":
    from mcpGateway.sandbox import apply_process_limits
    apply_process_limits()          # ← PDEATHSIG 挂进这个函数内部，3 个 server 零改动获得
```

**→ 复用既有钩子，改动收敛在 `sandbox.py` 单文件，3 个 server 与调用方零改动。**

## 四、改造顺序（依赖关系）

```
第 0 步（常量先行）
  P0-1  _JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE
      └─ 验收：常量可 import

第 1 步（L3 内核层 —— 独立可验，且是唯一覆盖强杀的一层）
  P1-1  LimitFlags 加按位或
  P1-2  apply_parent_death_signal()（含竞态检查）
  P1-3  apply_process_limits 内调用（POSIX 分支）
  P1-4  __all__ 补导出
      └─ 验收：Win 下 Job 标志位含 0x2000；POSIX 下 prctl 被调用且父已死时不误挂；
              沙箱关闭（memory_mb<=0）时两者均跳过

第 2 步（L2 信号层）
  P2-1  _install_signal_handlers()（webUI main 开头）
  P2-2  chat_loop 的 try/finally 收尾
      └─ 验收：SIGTERM 触发 shutdown_system；CLI 输入 exit 后 MCP 进程被收敛

第 3 步（收口）
  P3-1  compose 注释修正
  P4-1  新增单测
  D1    回归：tests/unit 全量 + contract_check FAIL 0 + lint 0
  D2    文档回填：09 §3.9、设计/02 D26、设计/11 M23、08 §5.2、从零系列/11
```

**顺序原则**：

1. **L3 先于 L2** —— L3 覆盖范围**严格大于** L2（含 L2 无法覆盖的强杀），先补覆盖面最广的一层；
2. **L3 改动自包含** —— 全部收敛在 `sandbox.py` 单文件，可与 L2 独立验证、独立回滚；
3. **L2 必须"handler + CLI 收尾"同批** —— 只注册 handler 而不补 CLI 收尾，等于把 `main.py` 入口的泄漏原样留着。

## 六、风险点

| # | 风险 | 说明与对策 |
|---|---|---|
| **R-1** | **`KILL_ON_JOB_CLOSE` 误杀正常子进程** | 触发条件是"**Job 句柄全部关闭**"，而 `_ACTIVE_JOBS` 在父进程存活期**始终持有句柄** → 正常运行期**不可能触发**。仅父进程死亡时句柄被 OS 回收 |
| **R-2** | **PDEATHSIG 竞态**：设置时父进程**已死** | `prctl` 在父已死时**不会**触发 PDEATHSIG → server 会变孤儿。**对策**：设置后立即检查 `os.getppid()`，若为 `1`（已被 init 收养）则**主动退出** |
| **R-3** | **PDEATHSIG 在容器中语义变化** | 容器内 PID 1 若为 tini，父进程（bootstrap）退出后 server 的父变为 tini → PDEATHSIG **已正常触发**（bootstrap 死时即触发），无需额外处理 |
| **R-4** | **`prctl` 不可用**（musl / 非 Linux） | 用 `ctypes.CDLL(None)` 取符号；失败则**告警降级**，不阻断启动（贯彻"沙箱是加固不是故障点"） |
| **R-5** | **PDEATHSIG 触发 SIGTERM 打断正在进行的 SQL 写入** | ① SQLite WAL + 事务保证**不会写坏文件**；② 这是"父进程已死"的异常路径，**不留孤儿**优先于"跑完最后一条"；③ 目标信号选 `SIGTERM` 而非 `SIGKILL`，给 uvicorn 自行收尾机会 |
| **R-6** | **L1 与 L3 的执行顺序竞争** | 正常退出时 L1（`stop_mcp_servers` → `terminate()`）先执行并**清空 `MCP_SERVER_PROCESSES`**；L3 只在父进程**未走 L1** 时兜底。两者**互不干扰**（L3 由内核在父死时触发，此时 L1 已不可能执行） |
| **R-7** | **信号 handler 在非主线程注册抛错** | `signal.signal` 仅限主线程；`main()` 在主线程 ✅ 且用 `try/except (ValueError, OSError)` 包裹 |

| 场景 | 期望 |
