## 2. 安全

### 2.1 鉴权模型（现状：枚举 + 最小权限表）

| `finance_agent` | `BILL_READ` + `LLM_FINANCE` | 只读 + 专用模型 |

> ⚠️ **RBAC 现状权威声明（2026-09-04，M9 修订）**：上表与代码 `mcpGateway/rbac_config.py` `AGENT_PERMISSION_MAP` **逐字一致**，是 RBAC **现状唯一权威**。要点：**orchestrator 零写（+`FACT_READ`）；bill_agent 承接 `HABIT_WRITE`；price_agent 有 `BILL_READ`；finance_agent 无 `LLM_BASE`**。任何文档（含 `10` 手册 §5.2.5 / §5.6.4）与其冲突时以本表 + 代码为准。

```python
    required_perm = DBPerm.BILL_READ
else:
```

### 2.2 SQL 注入防护

| 机制 | 现状 | 代码位置 |
|---|---|---|
| **参数化查询** | ✅ 全程 `?` 占位 + `params` 列表 | `sql_mcp_base.py:45,50` → `db.query_sql(sql, params)` |
| **DDL 黑名单** | ✅ **11 项前缀**（`CREATE/DROP/ALTER/TRUNCATE/GRANT/RENAME`，★M4 补 `ATTACH/DETACH/VACUUM/PRAGMA/REINDEX`——挂外部库 / 整库重写 / 写类 pragma 与 DDL 同级危险）一律拒绝并审计 | `sql_validator.py` |
| **未知类型拒绝** | ✅ 非 select/insert/update/delete 一律拒绝 | `sql_mcp_base.py:25-27` |
| ⚠️ **类型判定方式** | **字符串前缀**（`sql.strip().upper().startswith(op)`） | `sql_validator.py:7-21` |

> **风险**：前缀判定对注释开头（如 `/* hint */ SELECT ...`）或换行开头会误判为 `unknown`（拒绝，安全侧失败）。
> 这是**可接受**的（误拒优于误放行），但 To-Be 应把类型判定下沉到 `ToolSpec`——
> `sql.read` / `sql.write` 两个工具**静态声明**操作类型，不再靠解析 SQL 字符串（`08` §6 ★Q1 已推荐拆分）。

### 2.5 工具沙箱（D8 · M4）——常驻化的进程隔离替代

> ✅ **M4 已完成（2026-09-03）**。
> 背景：M3 常驻化后，工具在**常驻 server 进程**内执行（短连接"一次一进程"的天然隔离消失），
> 一个死循环 / 爆内存工具会拖垮整个 server → 所有 Agent 一起挂（`03` §9.8.2 ④ 风险1）。
> 沙箱 = 三层防御，落地代码见 `mcpGateway/sandbox.py`（进程资源限制）/
> `executor.py`（工具级超时）/ `sql_validator.py`（危险操作白名单）。

**三层沙箱**：

| 层 | 机制 | 位置 | 兜底语义 |
|---|---|---|---|
| ① 工具级超时 | `ToolSpec.timeout` → 引擎 `asyncio.wait_for`（async 可取消） | `executor.py:_execute` | 死循环 / 挂死调用被拦；**CPU 失控在此层治理**（进程级不做 CPU 限制——常驻 server 的 CPU 是正常工作属性） |
| ② 进程资源限制 | Windows：bootstrap 给 3 个 server 挂 **Job Object**（进程内存硬上限，超限被 OS 终止）；POSIX：server 启动 **self-prison**（`RLIMIT_AS` / `RLIMIT_CORE=0`） | `sandbox.py` / `startup/bootstrap.py` / 3 个 server `__main__` | 爆内存被拦且**宿主进程（主编排）不受影响**；沙箱施加失败只告警、不阻断启动（加固非故障点） |
| ③ 危险操作白名单 | 三层：工具注册白名单（registry 显式注册 + `list_tools` 权限过滤）/ SQL 语句白名单（`sql_validator` 类型分类）/ 写权限（RBAC `required_perm`） | `registry.py` / `sql_validator.py` / `rbac_config.py` | 平台只有显式注册工具可被调用；DDL / 会话级 / 库级 SQL（`ATTACH`/`VACUUM`/`PRAGMA` 等）一律拒绝 |

**阈值（`config.py`，环境变量可配、≤0 = 关闭——M4 回滚要求）**：

| 配置 | 默认 | 依据 |
|---|---|---|
| `BILLAGENT_SANDBOX_MEMORY_MB` | 2048 | 单 server 常驻峰值约 200~400MB，留足余量 |
| `BILLAGENT_TOOL_TIMEOUT_SQL` | 30s | SQLite 本地库 + `busy_timeout` 5s，M3 实测单次调用 135ms |
| `BILLAGENT_TOOL_TIMEOUT_LLM` | 300s | 本地 1.8B 单次实测 189s；M3 消除冷启动后从 M1 的 900s 收紧 |

> **CPU 治理口径**：工具级 CPU 失控（死循环）由 ① 超时拦截（async 可取消）；
> 同步 CPU 死循环无法被线程取消，属进程级最后防线范畴——Windows 上 Job 内存超限即杀进程；
> POSIX 可对一次性执行场景（D8"代码执行用 subprocess + 受限工作目录"）显式传 `cpu_seconds`
> 设 `RLIMIT_CPU`，**常驻 server 不设**（会把正常长跑误杀）。

**验收（`tests/unit/test_sandbox.py`）**：async 死循环工具 0.2s 被拦且事件循环上其它任务照常完成；
同步阻塞工具超时返回且循环不被冻结；`timeout=0` 关闭护栏后慢工具正常返回；
爆内存子进程（96MB 限制 + 分配 256MB）被 OS 终止（Windows Job / POSIX rlimit 双路径）；
`ATTACH/DETACH/VACUUM/PRAGMA/REINDEX` 补入危险白名单。

## 3. 可观测

### 3.1 现状：只有日志，没有链路

| 项 | 现状 |
|---|---|
| 日志 | loguru，`logs/app.log`，按天轮转保留 7 天 |
| `run_id` / `trace_id` | ❌ **无** |
| span 计时 | ❌ 无 |
| 关键指标 | ❌ 无（工具耗时、任务耗时、失败率均无法统计） |

只能靠 print 与人工读日志。

### 3.2 目标：Tracer + span 树

> 职责与接入点已定稿于 `03_逻辑架构` §9.3；实施设计见 `08` 第 3 章。本文给**规范口径**。

**Trace 模型**：

| 概念 | 定义 |
|---|---|
| `run_id` | **一次用户请求**的唯一标识，贯穿全链路 |
| `span` | 一段有起止的工作单元（工具调用 / 节点执行 / 任务执行） |
| span 树 | `run_id` 下按调用嵌套形成的树 |

**接入点（仅 3 处，刻意保持最小）**（`03` §9.3）：

| # | 位置 | 产生 |
|---|---|---|
| 1 | 编排入口 | 建 `run_id`，开根 span |
| 2 | worker 执行 | 包 span（子 Agent 执行全过程） |
| 3 | `ToolRegistry.invoke` | 包 span（**工具耗时自动计时**） |

> 第 3 处接入是关键：工具调用收敛到 Registry 之后，**所有 MCP/本地调用自动获得计时与审计**，
> 无需在每个调用点手写——这是 D1 的**附带收益**（`03` §8.2 T1）。

**落盘**（✅ **D3 阶段1 已落地，2026-08-31**）：**SQLite `llm_call_stat` 表**——`utils/tracer.py.record_llm_call` 每 LLM 调用落一条（`agent_tag` / `model` / `channel` / token / `latency_ms` / 成败 / `error_type`，**永不抛异常**）。
- ⚠️ 早期"JSONL 文件（`logs/trace/{date}.jsonl`）+ exporter"方案**已废弃**（阶段1 定为 SQLite，理由见 `04` §3.3 与 `08` 第 3 章修订）；JSONL exporter 仅作为**阶段2 span 树持久化的预留选项**（`08` §6 Q8）。

### 3.3 关键指标建议

| 指标 | 口径 | 用途 |
|---|---|---|
| 请求总耗时 | 根 span 时长 | 用户体验基线 |
| 任务耗时分布 | 按 `agent_type` 聚合 span | 定位慢 Agent |
| 工具耗时 / 调用次数 | `ToolRegistry.invoke` span | **MCP 冷启动开销的可观测化**（现为 26~29s/次） |
| 失败率 | span 中 `success=false` 占比 | 回归门禁 |
| LLM 调用耗时 | 按 `agent_tag` 区分本地/外部 | 双通道效果对比 |

> **与评测的关系**：`09_评测体系设计` 的 L4 工程化需要这些指标做门禁；
> 本视图负责"**怎么采集**"，评测文档负责"**怎么用**"。

## 4. 容错

### 4.1 错误分类（建议统一口径）

| 类别 | 示例 | 处理策略 |
|---|---|---|
| **可重试错误** | 数据库锁冲突、网络抖动、超时 | 有限重试（≤3 次） |
| **不可重试错误** | 参数非法、SQL 语法错误、权限不足 | 立即失败，**不重试** |
| **副作用不可重试** | 记账写操作失败 | **不重投**（`retriable=0`，见 `04` §3.3） |
| **需人工介入** | 外部 API 配额耗尽、模型文件缺失 | 告警 + 降级 |

### 4.2 现有容错机制

| 机制 | 配置/实现 | 代码位置 |
|---|---|---|
| **A2A 等待超时** | `wait_result(timeout=240)`，与 `MODEL_TIMEOUT` 对齐 | `a2a_queue.py:99-116` |
| **本地模型超时** | `MODEL_TIMEOUT = 240s` | `config.py:49` |
| **外部模型超时** | `EXTERNAL_LLM_TIMEOUT = 300s`（可用环境变量覆盖） | `config.py:64` |
| **双通道回退** | 外部 LLM 失败 → 回退本地 Ollama | `03` §四 要点 4 |
| **启用推导** | `EXTERNAL_LLM_ENABLED = bool(base_url and api_key)`——留空即自动回退 | `config.py:66` |
| **数据库锁重试** | `database is locked` → `sleep(0.1)` 重试 3 次 | `utils/common.py:69-72` |
| **SQL 异常** | 捕获后回滚 + 审计 + 返回错误信息（不抛出） | `sql_mcp_base.py:57-60` |
| **JSON 解析** | 带自校验 + 重试的解析器 `parse_json_output` | `agentCore/parsers/json_parser.py` |

**超时值的关系**（易错点）：

```
wait_result(240s)  ≥  MODEL_TIMEOUT(240s)     ← 必须 ≥，否则编排器早于模型熔断
EXTERNAL_LLM_TIMEOUT(300s)                    ← 外部链路更慢，但受 wait_result 240s 约束
```

> ⚠️ **注意**：`EXTERNAL_LLM_TIMEOUT=300s` > `wait_result=240s`——
> 这意味着**外部 LLM 慢到 240~300s 之间时，编排器先超时**。这是**当前的一个不一致**，
> 影响：编排器判超时后任务仍可能在 worker 里继续跑（孤儿任务）。
> D2 落地后由 `task_state` 记录状态，可接受；当前建议**对齐为 240s** 或明确接受该行为。

### 4.3 目标：统一重试策略

| 规则 | 说明 |
|---|---|
| **非幂等不重试** | `retriable=0` 的任务（如记账写）失败即终态 |
| **重试上限 3 次** | 超上限置 `failed` |
| **崩溃恢复** | 启动扫描 `running` → 按 `retriable` 决定回 `submitted` 或 `failed`（`04` §3.1） |
| **超时即失败** | 不静默重试（避免用户重复等待） |

### 4.4 熔断与降级

| 场景 | 现状 | 目标 |
|---|---|---|
| 外部 LLM 连续失败 | 单次回退本地，**无熔断** | 建议：连续 N 次失败后短时直连本地（避免每次都等超时） |
| 本地模型不可用 | ❌ 无降级，直接失败 | 建议：明确报错（模型缺失属部署问题，见 `07_部署架构` §4 决策点 4） |
| 数据库锁死 | 重试 3 次后失败 | 保持；WAL 启用后冲突概率下降 |

```python
EXTERNAL_LLM_ENABLED = bool(EXTERNAL_LLM_BASE_URL and EXTERNAL_LLM_API_KEY)
```
