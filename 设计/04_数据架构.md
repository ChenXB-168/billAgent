## 1. 数据全景：六类存储，生命周期各不相同

> 它们的**生命周期差异**是 D2（状态丢失）、D5（会话态丢失）两条缺陷的共同根因——先看清这张表，后面的设计才有依据。
> **2026-08-30 更新**：新增第 6 类「用户文档库」（`userDocs/`，`01` §3.5 新需求）。

| # | 存储 | 内容 | 持久化 | 生命周期 | 进程重启后 | 代码位置 |
|---|---|---|---|---|---|---|

### 1.1 存储关系图

```
┌─ 持久化层（重启保留）────────────────────────────────────┐
│  bill.db（SQLite）  ← 事实的唯一来源（确定性计算只认这里）  │
│  long_consume_mem.pkl ← 长期记忆原文（FAISS 的数据源）      │
│  userDocs/*.txt|md   ← 用户文档库原文（唯一真相源，To-Be） │

└──────────────────────────────────────────────────────────┘
              ↑ 启动时加载                    ↓ 写入
┌─ 进程内（重启即失）──────────────────────────────────────┐
│  FAISS 索引（由 pkl 重建）                                 │

│  SESSION_MEM / SESSION_DRAFT_CACHE（短期记忆 + 草稿）       │
│  OrchState（每次 ainvoke 重建）                            │

```

### 1.2 进程内状态清单（D2 / D5 的风险面）

| 状态 | 结构 | 位置 | 丢失后果 |
|---|---|---|---|
| 任务队列 | `Dict[str, asyncio.Queue]` | `a2a_queue.py:8` | 队列中未消费任务**永久丢失** |
| 结果缓存 / 事件 | `_result_store` / `_result_events` | `a2a_queue.py:9-10` | 已完成任务的结果丢失，编排器超时 |
| 对话历史 | `SESSION_MEM: Dict[str, List]` | `short_memory.py:4` | 会话上下文归零（用户感觉"失忆"） |
| 账单草稿 | `SESSION_DRAFT_CACHE` | `short_memory.py:6` | 半成品草稿丢失（**当前行为**） |
| 编排状态 | `OrchState`（TypedDict） | `orchestrator/state.py:3` | 每次 `ainvoke` 重建（**设计如此**，不是缺陷） |

> ⚠️ **关键**：`OrchState` 每次 `ainvoke` 都会重建——**它无法承载跨轮次计数**（追问 3 轮上限）。
> 这正是 `03_逻辑架构` §8.2 **T9** 选择"会话级存储"而非 graph state 的原因。

### 2.4 新增表：`task_state`（D2 Durable Execution）

> 设计来源：`08_架构演进方案与决策记录` §2.3（已给出 DDL 与状态机），本文确认其**数据层归属**并补充约束。

```sql
CREATE TABLE IF NOT EXISTS task_state (
    task_id      TEXT PRIMARY KEY,      -- 自然幂等键（orchestrator 生成）
    session_id   TEXT NOT NULL,
    agent_id     TEXT NOT NULL,
    status       TEXT NOT NULL,         -- submitted|running|completed|failed|interrupted
    payload      TEXT,                  -- JSON：派发参数
    result       TEXT,                  -- JSON：执行结果
    retry_cnt    INTEGER DEFAULT 0,
    retriable    INTEGER DEFAULT 1,     -- 有副作用任务置 0（关键！见 §3.3）
    created_at   REAL,
    updated_at   REAL
);
CREATE INDEX IF NOT EXISTS idx_status  ON task_state(status, updated_at);
CREATE INDEX IF NOT EXISTS idx_session ON task_state(session_id);
```

## 3. 状态设计

### 3.1 任务状态机

```
                    ┌──────────── retry_cnt<3 且 retriable=1 ───────────┐
                    ▼                                                    │
  submitted ──(worker 领取)──→ running ──(成功)──→ completed             │
                                  │                                      │
                                  ├──(失败/超时)──→ failed ───────────────┘
                                  └──(进程退出)──→ interrupted ──(重启扫描)──→ submitted
```

| 状态 | 含义 | 终态 | 迁移条件 |
|---|---|---|---|
| `submitted` | 已入队待执行 | 否 | 派发时创建 / 重试回退 |
| `running` | worker 已领取 | 否 | worker `recv_task_blocking` 取到 |
| `completed` | 执行成功 | ✅ | 收到 result |
| `failed` | 失败且不可/不再重试 | ✅ | 失败且（`retry_cnt>=3` 或 `retriable=0`） |
| `interrupted` | 进程退出遗留 | 否 | 优雅关闭标记（`08` §6 Q7） |

**崩溃恢复**（挂 `bootstrap_all()`，与现有"无脑清空 A2A 队列"同位置）：

```python
def recover_orphans(self):
    """启动时扫描上次进程遗留的 running 任务"""
    rows = db.query("SELECT task_id, retriable, retry_cnt FROM task_state WHERE status='running'")
    for task_id, retriable, cnt in rows:
        if retriable and cnt < 3:
            db.execute("UPDATE task_state SET status='submitted', retry_cnt=? WHERE task_id=?", (cnt+1, task_id))
        else:
            db.execute("UPDATE task_state SET status='failed' WHERE task_id=?", (task_id,))
```

> 🔴 **2026-08-30 修订：跨进程原子性缺口（原设计遗漏）**
>
> **问题**：`task_state` 由**主进程**的 `TaskManager` 写，而 `bill` 的 INSERT 在 **MCP 子进程**执行
> （与 §4.1 的 `db_lock` 跨进程问题是同一个根因的两处表现）。
> 若崩溃发生在「**子进程已 commit 账单**」与「**主进程标记 completed**」之间，
> 恢复时走 `running → failed`，但**账其实已经记进去了** → **状态与事实相反**
> （用户被告知"记账失败"，实际账单已入库）。
>
> 且当前 `bill` 表**没有 `task_id` 字段** → 恢复时**无从对账**，无法确定到底记了没有。
>
> **方案（两步，均纳入 M5）**：
>

### 3.2 幂等键设计

| 场景 | 幂等键 | 机制 |
|---|---|---|
| **任务级** | `task_id`（orchestrator 生成） | `task_state.task_id` 主键 → 重复投递直接冲突，不重复执行 |
| **记账级（当前）** | 无 | ⚠️ 依赖"LLM 正确生成一条 insert"——**无去重保护** |
| **习惯累加** | `(month, category)` | upsert 累加（**重入会重复累加**，见 §2.3 提示） |

> **`task_id` 生成规则（2026-08-30 补齐）**：`f"t{int(time.time()*1000)}{secrets.token_hex(3)}"`——
> 毫秒时间戳 + 6 位随机十六进制（如 `t1725000000123a1b2c3d`）。满足：① 单用户量级全局唯一；② 含时间可排序；③ ~20 字符，写入 `bill.task_id` 列可读。
> 生成位置：orchestrator `dispatch_node` 派发时（`03` §9.8.4）。**子进程侧不需要复算**——崩溃对账时主进程按此 `task_id` 反查 `bill` 表即可（§3.1）。

> 🔴 **已知缺口（2026-08-30 明确定案）**：幂等键**只防"重投"，不防"重说"**。
>
> | 场景 | `task_id` 是否相同 | 幂等键能否拦住 |
> |---|---|---|
> | 自动重投（崩溃恢复 / 重试） | **相同** | ✅ 拦得住（`task_id` 主键冲突） |
> | **用户重发"记午饭56元"** | **不同**（每次派发生成新 `task_id`） | ❌ **拦不住 → 产生两条账单** |
>
> **决策：v1 接受该缺口，用「明确回执」缓解，不加模糊去重。** 理由：
> 1. 引入"N 秒内相同金额 + 品类即去重"的模糊逻辑，会**误拒**真实场景
>    （连续买两杯 56 元的午饭、两笔同金额消费）——**误拒比重复更糟**（用户会以为系统吞了账）；
> 2. 与改造前行为一致，**不是本次改造引入的回归**；
> 3. 缓解成本极低：记账成功后**必须回执金额 + 品类**（"已记账：餐饮 56 元"）——
>    真实重复多数源于"以为没成功"，看到回执就不会重发。
>
> **演进（P2，需产品决策）**：若实测"用户重发"导致重复记账频发，再考虑加**短窗口查重逻辑**（同一 `session_id` + 同摘要，如 5 分钟窗口内只记一条）。
> ⚠️ **口径澄清（2026-09-02，消除与 §3.1 的排期冲突假象）**：`bill.task_id` **列**本身已在 **M5** 随 §3.1 修订加上（§6.3 变更 1b，P0——它是崩溃对账的依据）；**P2 的仅是"利用该列做短窗口查重"这一层逻辑**，二者不同期，§3.1 修订（M5）与此并不冲突。

### 3.3 副作用记录：`retriable` 标志（本方案最关键的设计）

> **原则**：**非幂等操作不重试**。宁可失败告警，也不产生重复账单。

| 任务类型 | `retriable` | 理由 |
|---|---|---|
| `bill`（记账，**写操作**） | **0** | 重复执行 = 重复记账（金额错误，且用户可见） |
| `stat` / `price`（只读） | 1 | 重跑无害，结果一致 |
| `finance`（LLM 生成） | 1 | 重跑只影响文案，无副作用落库 |

> 这正是 `08` §2.3 ④「副作用保护」的落点：`bill` 任务失败后**不重投**，直接 `failed` + 告警，
> 由用户决定是否重新说一遍——**用交互成本换数据正确性**。

### 3.5 用户文档库存储设计（`userDocs/`，2026-08-30 新增需求）

**定位**：用户笔记是**文件系统的文件**，文件是**唯一真相源**；向量索引是**派生结构**（可由文件重建）——
与长期记忆（pkl 是真相源）同一设计哲学，但**文件系统比 pkl 更直观**（用户可直接增删改文件）。

#### 3.5.1 目录结构与格式扩展（解析器注册制）

```
userDocs/
├── *.txt / *.md          # v1 支持两种格式
├── _index.json           # 索引清单（元数据，非真相源，损坏可重建）
└── (未来) *.pdf / *.docx # 注册制扩展，不影响现有文件
```

```python
DOC_PARSERS: Dict[str, Callable[[Path], str]] = {
    ".txt": parse_txt,   # 读取原文
    ".md":  parse_md,    # 读取原文（保留标题为段落语义）
    # 未来注册 pdf/docx 解析器，一行接入，不破坏现有逻辑
}
```

> **格式扩展原则**：v1 只支持 **txt / md**（零额外依赖）；后续每加一种格式 = 注册一个解析器，
> **不改**目录结构 / 索引逻辑 / 检索接口。

#### 3.5.2 文件 → 向量对齐机制（核心：回答"用户增删文件后向量库怎么对齐"）

**原则**：**启动时全量对账，运行时增量对齐**——文件系统永远是对的，索引负责追上它。

| 时机 | 动作 | 说明 |
|---|---|---|
| **启动时** `load_user_docs()` | 扫描 `userDocs/` 全部文件 → 与 `_index.json` 对账：<br>**新增** → 解析 + embedding + add<br>**删除** → 从索引移除<br>**修改**（内容哈希变化，⚠️ 2026-09-02：**不用 mtime**——文件复制 / 时钟回拨 / 秒内多次修改会漏检，见 §3.5.2b 保险 1）→ 删旧加新 | 对账使索引与文件系统**必然一致**；即使 `_index.json` 丢失也能全量重建 |
| **运行时**（对话指令） | `doc:add` → 写文件 + 增量 embedding<br>`doc:delete` → 删文件 + 移除向量 | **只处理变更文件**，不做全量重建（1000 条上限下全量太重） |
| **索引损坏** | 删除 `_index.json` → 下次启动全量重建 | 文件系统兜底，**永不丢失**（参考 `load_rag_index()` L101"不存在/损坏/不匹配则重建"） |

**幂等键**：`doc_id = 文件相对路径`——同一文件只索引一次，重入不重复。

> 🔴 **2026-08-30 勘误与补全**（原设计有两处错误 + 三处缺失）：

**勘误 1 · FAISS 删除**：原文"`IndexFlatL2` 不支持单条删除"**是错的**——
`remove_ids()` 已实现（`faiss/swigfaiss.py:2810`，`requirements.txt` 锁 faiss-cpu≥1.7）。
**真正的坑**：删除会触发**压实重排**，其后向量整体前移 → 位置映射失效。
而现状 `rag_service.py:23` 正是用 `doc_list[idx]` **按位置取** → 删一个，**后面所有 doc_id 全错位**。

**勘误 2 · 落盘策略**：原文未明确索引是否落盘，与 §1「FAISS ❌ 内存」矛盾（§1 说的是**长期记忆**的 FAISS）。
**现明确：用户文档索引落盘**（与 `ragKnowledge` 现状一致，见 §1 第 2b 类）。

**对齐的三种操作（修正后）**：
| 操作 | 实现 |
|---|---|
| **添加** | 分块 → batch embedding → 追加 `IndexIDMap` + 更新 `_index.json` |
| **删除** | 用 **`IndexIDMap`**（FAISS 官方方案）让 `doc_id` 与**物理位置解耦** → `remove_ids([doc_id])` 不影响其它条目 |
| **修改** | `remove_ids(doc_id)` + 重新 embed 添加（先删后加） |

#### 3.5.2b 增量对账的 4 道保险（**不重嵌的前提**）

> 落盘 + 增量能省掉"每次启动全量重嵌"（1000 篇 × 逐条 embedding = 数十秒~分钟级），
> 但会引入索引与文件漂移的风险，必须用 4 道保险兜住。

| # | 保险 | 防什么 | 实现 |
|---|---|---|---|
| 1 | **内容哈希判变更** | mtime 不可靠（文件复制 / 时钟回拨 / 秒内多次修改会漏检） | 用 **md5(文件内容)** 而非 mtime；1000 篇几 MB，算哈希仅几十 ms |
| 2 | **模型版本校验** | 🔴 **换 embedding 模型后旧向量全部失效**（`doc_list.pkl` 无模型信息，检测不到 → 检索结果全错） | 索引元数据记 `model_name` + `dim`；**不匹配 → 全量重建** |
| 3 | **`IndexIDMap`** | 删除的压实重排导致 doc_id 错位 | doc_id 与物理位置解耦 |
| 4 | **原子写 + 损坏重建** | 对账中途被 kill → 半更新 / bm25+faiss+doc_list 三文件不一致 | 写 tmp → `os.replace` 原子替换；索引损坏或版本不符 → 全量重建兜底 |

**已知取舍（接受）**：
- **运行期直接改文件不生效**：用户不走 `doc:add` 而直接编辑文件，索引要**下次启动**才更新（简单化，写清即可）。
- **超限边界**：启动对账若扫到 >1000 个文件 → 索引前 1000 个 + **明确告警**（不静默丢弃）。

**性能约束（必须同时做）**：
`embedding_loader.py:36` 是**逐条 encode、无 batch、无 `to_thread`**——在事件循环里会冻结 4 个 worker。
改为 **batch encode + `to_thread` 卸载**（对齐 `orchestrator/nodes.py:494` 的既有做法）。

> | 主进程 | `orchestrator/nodes.py:490,511,522,609,629`（9 处直连） | `db_lock` #1 |
> | MCP 子进程 | `sql_mcp_base.py:43` | `db_lock` #2 |
>
> → **跨进程写根本无互斥**，当前只是"调用频率低 + `sleep(0.1)` 重试"碰巧没暴露。
>
> ⚠️ **改常驻 HTTP 后依然无效**：常驻只是"不再频繁启停"，**server 仍是独立进程**，进程边界未变
> （除非把 server 内联进主进程——但那会彻底失去进程隔离，见 `02` D8）。
>
> **结论**：跨进程互斥**只能靠 SQLite 自身的锁**（WAL + `busy_timeout`）；`db_lock` 只管进程内协程。
> 这是 **M3.5 WAL 必须独立排期**的根本原因（`08` §5.2）。

### 4.2 SQLite 写互斥（WAL）—— ✅ **M3.5 已落地（2026-09-03）**

| 项 | 落地前（截至 2026-09-02） | ✅ **落地后（2026-09-03，M3.5）** |
|---|---|---|
| `journal_mode` | 默认（delete），未显式设置（`utils/common.py:34` 仅 `check_same_thread=False`） | **WAL**：`DatabaseCRUD.__init__` 增 `PRAGMA journal_mode=WAL`；实测 `journal_mode=wal` |
| `busy_timeout` | 未设置，靠 `sleep(0.1)` 重试 3 次（`utils/common.py:69-72`） | **5000ms**：`PRAGMA busy_timeout=5000`；同步 `sleep(0.1)` 重试已删除（C 层等待吸收竞争，见 §4.3 阻塞修正落地注） |
| 目的 | — | ① 跨进程写**无** `db_lock` 保护（§4.1 勘误）→ 只能靠 SQLite 层互斥；<br>② WAL 让"读不阻塞写、写不阻塞读"，是并行派发（M6）的前提 |
| 代价 | — | 多 `-wal` / `-shm` 两个文件，`07` 备份策略已覆盖 |

> **结论（已修订）**：原文"与 `03` §9.8.3 同期实施、不需单独排期"**不成立**——
> `03` §9.8.3 拆的是 `client.py` 的 `self._lock`（**传输层**锁，解决 MCP 调用串行），
> 本节要解决的是 **`db_lock` 跨进程失效**（**数据层**），**两者不是同一件事**，且后者**无阶段承接**。
> 故独立为 **M3.5**，排在 M3（MCP 常驻化）之后、**M6（并行派发）之前**——**先并行再补锁 = 边撞车边修路**。

### 4.3 并发写策略 —— ✅ **M3.5 已落地（2026-09-03）**

> 承接 §4.1 勘误：`db_lock` 只管**进程内**协程，**跨进程**必须靠 SQLite 层。

| 层 | 策略 | ✅ M3.5 落地（2026-09-03） |
|---|---|---|
| **进程内** | `db_lock` 从"包住全部 DB 访问"降级为**只包住写事务**；读操作并发（WAL 下读无需锁） | ✅ 主进程（`nodes.py`）：4 处纯读去锁（`_load_recent_habits` / `_sum_month_bills` / `_query_city_avg_price` / `_sum_month_bills_by_category`）、写保留锁且写后读移出锁外；⚠️ **server 子进程（`sql_mcp_base.py`）保留 db_lock**——其经 `anyio.to_thread` 线程池访问**单连接**，锁是线程安全必需（单连接无法真并发读，去锁反而引入线程并发碰连接风险；真读并发需连接池，不在 M3.5 范围） |
| **跨进程（关键）** | 启用 **WAL** + `busy_timeout=5000`，由 SQLite 自身保证写互斥——这是**唯一**有效的跨进程防线 | ✅ 实测：双独立进程并发各写 80 行，`ok=80 / ok=80`，**零 `database is locked`** |
| **阻塞修正** | `time.sleep(0.1)`（**同步阻塞**，会冻结事件循环与 4 个 worker）→ ⚠️ **同步函数内不能 `await`**：正确改法是 `asyncio.to_thread(execute_sql, ...)` 卸载到线程池，或把**调用方**改异步后再 `await asyncio.sleep` | ✅ **落地为直接删除**（`execute_sql` / `batch_add_city_price` 两处，比 to_thread 更简）：WAL + busy_timeout 后 SQLite 在 C 层等待吸收锁竞争，`sleep(0.1)` 重试既冗余又同步阻塞事件循环，故去掉、直接重试（每次由 busy_timeout 兜底） |
| 业务 | 写操作仍串行（单库写是 SQLite 的物理约束）；**读多写少**是本项目特征，收益主要来自"读读并发 + 读写不互斥" |
| 幂等 | 写操作必须带 `task_id` 幂等键（§3.2）；⚠️ 幂等键**只防重投、不防重说**——用户重发"记午饭56元"会生成新 `task_id`，仍产生两条账单（**已知缺口**，见 §7 决策点） |

### 5.3 工具调用契约（To-Be：`ToolSpec` / `ToolResult`）

> 详见 `08_架构演进方案与决策记录` §1.4（工具统一模型），此处只给数据视角的字段。

| 结构 | 关键字段 |

> ✅ **这套模式是对的，后续 schema 变更必须沿用**，不要引入 Alembic 等迁移框架（单机单用户，与"零依赖"红线冲突）。

### 6.2 schema 变更策略

1. **向后兼容优先**：新增列必须带 DEFAULT 或允许 NULL，禁止直接改列类型
2. **检测式迁移**：`PRAGMA table_info` 判断列是否存在，幂等执行
3. **破坏性变更**：走"建新表 → 拷贝 → 换名"（参考 `migrate_bill_table`）
4. **备份**：变更前拷贝 `bill.db`（现有 `bill.db.bak_20260816` 即为此前手工备份）
