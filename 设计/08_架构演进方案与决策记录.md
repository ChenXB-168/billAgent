## 第 1 章 D1 工具接入平台方案（统一模型 + 注册 / 发现 / 执行引擎 / 协议适配）

> **本章为详细设计稿（建议，可照图施工）**。D1 的目标不是"加个注册中心"，而是建成**工具接入平台**，
> 结构为：**工具统一模型（底座）+ 注册 → 发现 → 执行引擎 → 协议适配（四层）**。
> 每一块都给出完整数据结构、接口签名、流程与错误处理（见 1.4–1.8）。
>
> **贯穿本章的核心洞察**：
> **MCP 只是众多可接入协议中的一种。** 连接模式（短连接 / 长连接 / 连接池）是协议适配器内部的私事，
> 上层与业务代码完全无感知——这正是"MCP 只是一个需要接入的协议"在工程上的落地形态。

### 1.1 目标与验收标准

| 项 | 内容 |
|---|---|
| 目标 | 把"工具"从**散落的协议调用**升级为**统一接入平台**：一处注册、统一发现、统一执行、统一治理 |
| 验收 | ① 新增工具**只写注册代码**，不改 `client.py` / RBAC / 审计 / 调用方<br>② `list_tools(agent_id)` 返回权限过滤后的 schema，可直接喂给 LLM function calling<br>③ 所有调用自动带：鉴权、参数校验、超时、审计、耗时、可观测打点<br>④ 现有 **~18 处生产调用 + ~40 处测试 patch 零改动** |

### 1.2 现状盘点（本轮实测）

| 项 | 现状 | 实证 |
|---|---|---|
| MCP 工具 | 3 个：`exec_sql` / `llm_chat` / `finance_chat` | `client.py` L23-27 |
| 业务工具雏形 | **12 个 skill**（3 本地 + 9 MCP 封装，带参数校验 + `_std_response`），但目前是 LEGACY，只服务 `offline_debug` / `agentCore` | `agentCore/skills.py` |
| **生产调用点** | **约 18 处**（stat 2 / price 2 / orch 3 / finance 1 / bill 2 / skills 8） | 全项目搜索 |
| **测试 patch 点** | **约 40 处**，形如 `@patch("agents.stat_agent.nodes.mcp_client.call_bill_sql")` | `tests/unit/*` |
| 权限模型 | 静态 `agent → [Enum]` 映射（最小权限原则，设计良好） | `rbac_config.py` L17-43 |

> （`@patch("...nodes.mcp_client.call_bill_sql")`）。
> 一旦改动调用形态，这 40 处全部失效。**兼容层因此是必选项，不是可选项**（见 1.9）。

### 1.3 五块总览：统一模型（底座）+ 四层

```
┌─ 业务层 ─────────────────────────────────────────────────────────┐
│  agents/*/nodes.py   ·   agentCore/skills.py                     │
│  调用：registry.invoke(...) 或 mcp_client.*（兼容层）             │
└─────────────────────────┬────────────────────────────────────────┘
┌─ ★工具统一模型（底座，贯穿四层）─────────────────────────────────┐
│  ToolSpec（元数据）· InvokeContext（入参）· ToolResult（返回）    │
│  ToolError（错误分类）── 所有协议的工具在平台眼里是同一种东西      │
└─────────────────────────┬────────────────────────────────────────┘
┌─ ① 注册层 Registry ──────────────────────────────────────────────┐
│  register / register_adapter / tool 装饰器 / 启动装配            │
│  ★fail-fast：注册时校验一切不一致，启动即报错                    │
└─────────────────────────┬────────────────────────────────────────┘
┌─ ② 发现层 Discovery ─────────────────────────────────────────────┐
│  list_tools(agent_id) · to_openai_schema · to_mcp_schema         │
│  verify_schemas（离线自检防漂移）→ 解锁 D7 与 LLM 自主选工具       │
└─────────────────────────┬────────────────────────────────────────┘
┌─ ③ 执行引擎 ExecutionEngine ─────────────────────────────────────┐
│  ①解析 ②鉴权 ③参数校验 ④前置审计 ⑤执行(超时) ⑥重试 ⑦结果         │
│  ⑧后置审计 ⑨可观测打点；横切：幂等保护 · 熔断 · 降级              │
└─────────────────────────┬────────────────────────────────────────┘
┌─ ④ 协议适配层 Adapters ──────────────────────────────────────────┐
│  MCPAdapter（★长短连接是其私事）· LocalAdapter · HTTPAdapter(预留) │
└──────────────────────────────────────────────────────────────────┘
```

> **统一模型是底座，不是另一层**：四层（注册/发现/执行/适配）共享同一套
> 元数据、入参、返回、错误定义。它的存在让"新增一个协议"和"新增一个工具"
> 都不需要改任何一层——这就是工具接入平台的核心价值。

### 1.4 ① 工具统一模型（底座，详细设计）

> **文件**：`mcpGateway/tool_model.py`（新增，~90 行）
> **职责**：把"工具"在平台里的**所有形态**统一成四件套——
> 元数据（是什么）· 入参（带什么）· 返回（得什么）· 错误（错在哪）。
> **硬规则：任何一层都不允许出现"MCP 特判"或"本地特判"**——统一模型不存在，平台就不成立。

```python
# mcpGateway/tool_model.py（新增，~90 行）
"""工具统一模型：元数据 / 入参 / 返回 / 错误，四件套。"""
from dataclasses import dataclass, field
from enum import Enum
from typing import Any
from mcpGateway.rbac_config import DBPerm, LLMPerm   # ★复用现有权限枚举，不重复造


# ════════ ① 元数据：一个工具"是什么" ════════
@dataclass(frozen=True)
class ToolSpec:
    name: str                        # 全局唯一，点分命名："sql.read" / "bill.parse"
    description: str                 # ★给 LLM 看的，直接决定它选不选这个工具
    params_schema: dict              # JSON Schema（同时驱动"参数校验"与"LLM 可见性"）
    version: str = "1.0"
    result_schema: dict | None = None          # 可选：返回结构声明（供结果校验）
    required_perm: Enum | None = None          # DBPerm.BILL_READ / LLMPerm.LLM_FINANCE / None
    side_effect: bool = False        # 写副作用 → 引擎前置审计；★且永不自动重试（D2 防重复记账）
    auditable: bool = True           # ★2026-08-30 新增：是否记审计（默认记），llm.chat 设 False 以对齐现状
    idempotent: bool = True          # 结果是否确定（不参与重试闸门判定，见 §1.7 修正）
    timeout: float = 120.0           # 单次调用超时（秒）
    max_retry: int = 0               # 自动重试上限（仅 idempotent=True 时生效）
    protocol: str = "local"          # "mcp" / "local" / "http"（需已注册对应适配器）
    binding: dict = field(default_factory=dict)
    #   mcp:   {"server_key": "sql_bill", "tool": "exec_sql"}
    #   local: {"func": <callable>, "to_thread": True}
    tags: tuple[str, ...] = ()       # 能力标签，如 ("bill", "rag")，发现层可按标签过滤
    hidden: bool = False             # True → 不出现在 list_tools（内部工具，不暴露给 LLM）

    def to_llm_schema(self) -> dict:
        """导出为 OpenAI function-calling 的单工具描述"""
        return {"name": self.name, "description": self.description,
                "parameters": self.params_schema}


# ════════ ② 入参：一次调用"带什么" ════════
@dataclass(frozen=True)
class InvokeContext:
    """引擎注入的上下文。★不进 params_schema——工具契约只描述业务参数，
    agent_id/trace_id/session_id 由引擎透传，不污染校验与 LLM 描述。"""
    agent_id: str
    trace_id: str | None = None
    session_id: str | None = None


# ════════ ③ 返回：一次调用"得什么" ════════
@dataclass
class ToolResult:
    ok: bool
    data: Any = None
    error: "ToolError | None" = None
    attempts: int = 1                # 实际尝试次数（含重试）
    cost_ms: float = 0.0
    trace_id: str | None = None

    def unwrap(self) -> Any:
        """★兼容旧语义：成功返回 data；失败抛底层异常（兼容层/旧调用点使用）"""
        if not self.ok:
            err = self.error
            raise err.origin if err and err.origin else err
        return self.data


# ════════ ④ 错误：平台层统一分类 ════════
class ToolErrorKind(Enum):
    NOT_FOUND = "not_found"          # 工具不存在
    PERMISSION = "permission"        # 无权限（RBAC 拒绝）
    VALIDATION = "validation"        # 参数不符合 params_schema
    TIMEOUT = "timeout"              # 超过 spec.timeout
    CONNECTION = "connection"        # 连接类故障（唯一可重试 kind）
    REMOTE = "remote"                # 远端业务错误（MCP server 明确返回错误）
    INTERNAL = "internal"            # 适配器/引擎内部错误


@dataclass(frozen=True)
class ToolError(Exception):
    kind: ToolErrorKind
    message: str
    origin: Exception | None = None
    tool_name: str | None = None
    retriable: bool = False          # 是否可自动重试（由 kind 与 spec.side_effect 共同决定，§1.7 修正：与 idempotent 无关）
```

**设计要点**：

| 决策 | 理由 |
|---|---|
| `required_perm` 复用 `DBPerm`/`LLMPerm` | 权限表 `AGENT_PERMISSION_MAP` 是当前设计得最好的一块，**零改动** |
| `InvokeContext` 与 `params_schema` 分离 | agent_id/trace_id 是"谁在调用"而非"调用什么"，混在一起会污染工具契约和 LLM 描述 |
| `ToolResult.unwrap()` | 保持旧调用点"成功得值、失败抛异常"的语义，兼容层不必改调用形态 |
| `ToolErrorKind` 7 分类 | 是重试策略、可观测、降级的**统一判据**，散落的 `except Exception` 全部收口 |

### 1.5 ② 注册层（详细设计）

> **文件**：`mcpGateway/registry.py`（新增，~110 行）
> **职责**：工具的**唯一真相源**。注册时 **fail-fast**——一切不一致都在启动时报出，
> 绝不让坏工具带到运行时。

```python
# mcpGateway/registry.py（新增，~110 行）
class ToolRegistry:
    """注册层 + 发现层。执行由 ExecutionEngine 负责（本类持有其引用）。"""

    def __init__(self):
        self._specs: dict[str, ToolSpec] = {}
        self._adapters: dict[str, ProtocolAdapter] = {}
        self._engine: "ExecutionEngine | None" = None

    # ─────────────── 注册 API ───────────────
    def register(self, spec: ToolSpec) -> None:
        """注册一个工具。★fail-fast：校验不通过 / 重复注册 → 启动即报错"""
        self._validate_spec(spec)
        if spec.name in self._specs:
            raise ValueError(f"工具重复注册: {spec.name}")
        self._specs[spec.name] = spec

    def register_adapter(self, protocol: str, adapter: "ProtocolAdapter") -> None:
        if protocol in self._adapters:
            raise ValueError(f"协议适配器重复注册: {protocol}")
        self._adapters[protocol] = adapter

    def tool(self, *, name=None, description, schema, **kw):
        """装饰器：本地函数一行注册成工具。用法：
            @registry.tool(name="calc.premium", description="计算保费", schema={...})
            def calc_premium(...): ..."""
        def deco(fn):
            to_thread = kw.pop("to_thread", True)
            self.register(ToolSpec(
                name=name or fn.__name__, description=description,
                params_schema=schema, protocol="local",
                binding={"func": fn, "to_thread": to_thread}, **kw))
            return fn
        return deco

    def unregister(self, name: str) -> None:
        """热卸载（Skills 动态加载/卸载用，见 D7）"""
        self._specs.pop(name, None)

    def _validate_spec(self, spec: ToolSpec) -> None:
        """★fail-fast：注册时的全部校验集中在这里"""
        if not spec.name or not spec.description or not spec.params_schema:
            raise ValueError(f"工具[{spec.name}] 缺少必填字段")
        if spec.protocol not in self._adapters:
            raise ValueError(f"工具[{spec.name}] 的协议[{spec.protocol}]未注册适配器")
        if spec.protocol == "mcp" and not (
                spec.binding.get("server_key") and spec.binding.get("tool")):
            raise ValueError(f"工具[{spec.name}] mcp 绑定缺 server_key/tool")
        if spec.protocol == "local" and "func" not in spec.binding:
            raise ValueError(f"工具[{spec.name}] local 绑定缺 func")

    def bind_engine(self, engine: "ExecutionEngine") -> None:
        self._engine = engine

    # ─────────────── 统一执行入口（门面）───────────────
    async def invoke(self, name: str, args: dict, *, agent_id: str,
                     trace_id=None, session_id=None) -> ToolResult:
        """业务代码只认识这一个入口。内部委托给 ExecutionEngine"""
        if self._engine is None:
            raise RuntimeError("ExecutionEngine 未绑定")
        return await self._engine.invoke(name, args, agent_id=agent_id,
                                         trace_id=trace_id, session_id=session_id)
```

### 1.6 ③ 发现层（详细设计）

> **文件**：`mcpGateway/registry.py`（与注册层同文件，~40 行）
> **职责**：让"这个 Agent 能用哪些工具"成为**可查询、可导出、可自检**的一等公民。

```python
    # ─────────────── 发现 API ───────────────
    def get(self, name: str) -> ToolSpec:
        return self._specs.get(name)

    def all(self) -> list[ToolSpec]:
        return list(self._specs.values())

    def has(self, name: str) -> bool:
        return name in self._specs

    def list_tools(self, agent_id: str) -> list[ToolSpec]:
        """★权限过滤即发现过滤。过滤流程：
           ① hidden=True 的内部工具不暴露
           ② required_perm=None → 公开工具，放行
           ③ required_perm ∈ get_agent_permission(agent_id) → 放行"""
        perms = set(get_agent_permission(agent_id))
        return [s for s in self._specs.values()
                if not s.hidden and (s.required_perm is None or s.required_perm in perms)]

    def to_openai_schema(self, agent_id: str, tags: tuple[str, ...] | None = None) -> list[dict]:
        """导出为 OpenAI/Ollama function-calling 格式（LLM 自主选工具的输入）"""
        return [{"type": "function", "function": s.to_llm_schema()}
                for s in self.list_tools(agent_id)
                if not tags or set(tags) & set(s.tags)]

    def to_mcp_schema(self, agent_id: str) -> list[dict]:
        """导出为 MCP 工具列表格式（调试 / 网关转发用）"""
        return [{"name": s.name, "description": s.description, "inputSchema": s.params_schema}
                for s in self.list_tools(agent_id)]

    async def verify_schemas(self) -> dict[str, list[str]]:
        """离线自检：对比本地注册的工具契约与 MCP 远端 tools/list 是否漂移。
        ★不进启动路径（MCP 子进程启动慢），作为 CI / 手动命令执行。"""
        report: dict[str, list[str]] = {}
        for spec in self._specs.values():
            if spec.protocol != "mcp":
                continue
            adapter = self._adapters["mcp"]
            remote = {t["name"]: t for t in await adapter.list_remote_tools()}
            want = spec.binding["tool"]
            if want not in remote:
                report.setdefault(spec.name, []).append(f"远端缺少工具: {want}")
            elif _schema_diff(spec.params_schema, remote[want].get("inputSchema")):
                report.setdefault(spec.name, []).append("schema 与远端不一致")
        return report
```

**战略价值**：`to_openai_schema` 是 **D7（Skills 渐进式披露）与 LLM 自主选工具的地基**——
没有它，"让模型自己选工具"无从谈起，而这正是当前架构缺失的关键能力。

### 1.7 ④ 执行引擎（详细设计，**当前全缺的能力都在这层**）

> **文件**：`mcpGateway/executor.py`（新增，~110 行）
> **职责**：把散落各处的治理逻辑收拢成**一条固定的 9 步流水线**。
> 现状对照——这些能力现在要么没有、要么散落在调用点手写：

| 能力 | 现状 | 执行引擎收拢后 |
|---|---|---|
| 鉴权 | `client.py` 按 SQL 前缀粗判 | 统一按 `ToolSpec.required_perm` 静态判定 |
| 参数校验 | skills.py 手写 if | JSON Schema 统一校验 |
| 超时 | 仅握手超时，调用无超时 | 统一 `asyncio.wait_for(spec.timeout)` |
| 重试 | 硬编码 2 次，仅连接异常 | 按 kind + **幂等性** 决策（见决策表） |
| 审计 | 各调用点手写，易漏 | **引擎内自动，不可能漏** |
| 可观测 | 无 | **引擎内打点，D3 的天然挂载点** |

```python
# mcpGateway/executor.py（新增，~110 行）
class ExecutionEngine:
    def __init__(self, registry: ToolRegistry, audit=None, tracer=None):
        self._reg = registry
        self._audit = audit or write_audit_log   # 默认接现有审计
        self._tracer = tracer                    # D3 挂载点，可为 None

    async def invoke(self, name, args, *, agent_id, trace_id=None,
                     session_id=None) -> ToolResult:
        # ── ① 解析 ──
        spec = self._reg.get(name)
        if spec is None:
            return ToolResult(ok=False, error=ToolError(
                ToolErrorKind.NOT_FOUND, f"工具不存在: {name}"))
        # ── ② 鉴权 ──
        perms = set(get_agent_permission(agent_id))
        if spec.required_perm and spec.required_perm not in perms:
            return ToolResult(ok=False, error=ToolError(
                ToolErrorKind.PERMISSION,
                f"Agent[{agent_id}] 无 {spec.required_perm.value} 权限"))
        # ── ③ 参数校验（JSON Schema）──
        if err := _validate_params(spec.params_schema, args):
            return ToolResult(ok=False, error=ToolError(
                ToolErrorKind.VALIDATION, f"参数校验失败: {err}", tool_name=name))

        ctx = InvokeContext(agent_id=agent_id, trace_id=trace_id, session_id=session_id)
        # ── ④ 前置审计（仅副作用工具，避免读操作刷屏）──
        t0 = time.perf_counter()
        if spec.auditable and spec.side_effect:
            self._audit(agent_id, name, str(args), False)

        # ── ⑤⑥ 执行 + 重试 ──
        result = await self._execute(spec, args, ctx, t0)

        # ── ⑧ 后置审计（★全量：读操作也审）──
        if spec.auditable:
            self._audit(agent_id, name, str(args), result.ok)
        # ── ⑨ 可观测打点（D3 挂载点）──
        if self._tracer:
            self._tracer.span(tool=name, agent=agent_id, ok=result.ok,
                              cost_ms=result.cost_ms, trace_id=trace_id)
        return result

    async def _execute(self, spec, args, ctx, t0) -> ToolResult:
        adapter = self._reg._adapters[spec.protocol]
        last_err = None
        for attempt in range(spec.max_retry + 1):
            try:
                out = await asyncio.wait_for(        # 统一超时
                    adapter.invoke(spec, args, ctx), timeout=spec.timeout)
                return ToolResult(ok=True, data=out, attempts=attempt + 1,
                                  cost_ms=(time.perf_counter() - t0) * 1000,
                                  trace_id=ctx.trace_id)
            except asyncio.TimeoutError:
                last_err = ToolError(ToolErrorKind.TIMEOUT,
                                     f"工具[{spec.name}] 超时 {spec.timeout}s",
                                     retriable=not spec.side_effect)   # §1.7 修正：由 side_effect 决定
            except ToolError as e:
                last_err = e
            except CONNECTION_EXC as e:
                last_err = ToolError(ToolErrorKind.CONNECTION, str(e),
                                     origin=e, retriable=not spec.side_effect)   # §1.7 修正
            except Exception as e:                   # 兜底：内部错误，不重试
                last_err = ToolError(ToolErrorKind.INTERNAL, str(e),
                                     origin=e, tool_name=spec.name)
            # ★重试决策：不可重试 → 立即终止（idempotent 不参与闸门，§1.7 修正）
            if not last_err.retriable:
                break
            await asyncio.sleep(min(2 ** attempt, 5))    # 指数退避 1,2,4,5,5...
        return ToolResult(ok=False, error=last_err,
                          attempts=spec.max_retry + 1,
                          cost_ms=(time.perf_counter() - t0) * 1000,
                          trace_id=ctx.trace_id)
```

**错误 → 重试决策表**（重试策略的唯一判据）：

| kind | 默认 retriable | 重试条件 | 理由 |
|---|---|---|---|
| `NOT_FOUND` / `PERMISSION` / `VALIDATION` | ✗ | 永不 | 重试结果必然相同 |
| `REMOTE` | ✗ | 永不 | 远端明确拒绝，重试无意义 |
| `INTERNAL` | ✗ | 永不 | 代码缺陷，重试只会掩盖问题 |
| `TIMEOUT` | `not spec.side_effect` | **仅无副作用工具** | 超时不代表未执行，写操作重试 = 可能重复写 |
| `CONNECTION` | `not spec.side_effect` | **仅无副作用工具** | 连接断了可重连，但写操作无法确认是否已提交 |

> 🔴 **2026-08-30 修正（动工前核对发现）**：原表用 `spec.idempotent` 做重试闸门 **会误伤 `llm.chat`**——
> LLM 调用 `side_effect=False`（重试无害）但 `idempotent=False`（结果不确定），按原表连接异常**不重试**，
> 而现状 `client.py` L62 的 `MAX_CONNECT_RETRY=2` **连接异常会重试 2 次** → **M1 反而降级了现状**。
> **根因**：`idempotent` 被混用为两种语义——「结果是否确定」与「重试是否安全」。
> **修正**：重试安全性由 **`side_effect`** 决定（有无副作用 = 重演是否造成脏数据），
> `idempotent` 回归「结果是否确定」的本义。**结果**：
> `sql.write`（side_effect=True）永不重试 —— D2 防重复记账目标**不受影响**；
> `llm.chat`（side_effect=False）连接异常可重试 —— 与现状一致。

> **与 D2 的衔接（★）**：`side_effect=True` 的写工具（如 `sql.write`）设 `idempotent=False`，
> 引擎层**永不自动重试**——从机制上杜绝"崩溃重投导致重复记账"，比业务层事后打补丁可靠。

**降级与熔断（P3，接口预留给 D2）**：

```
每工具一个断路器：连续 N 次 CONNECTION 失败 → 打开
  → 后续 invoke 直接短路返回（不发起真实调用）
  → 每 30s 半开探测一次，成功则闭合
fallback 配置：可选指定降级工具或默认值（如统计失败 → 返回空报表）
```

### 1.8 ⑤ 协议适配层（详细设计）

> **文件**：`mcpGateway/adapters.py`（新增，~70 行）
> **职责**：把"怎么连上去、怎么传参、怎么收回来"这类协议细节**隔离在平台最底层**。

```python
# mcpGateway/adapters.py（新增，~70 行）
class ProtocolAdapter(ABC):
    protocol: str = ""

    @abstractmethod
    async def invoke(self, spec: ToolSpec, args: dict, ctx: InvokeContext) -> Any: ...
    @abstractmethod
    async def list_remote_tools(self) -> list[dict]: ...   # 供 verify_schemas 自检


class MCPAdapter(ProtocolAdapter):
    """MCP 协议适配器。
    ★★ 连接模式（短连接 / 长连接 / 连接池 / 进程复用）是这里的内部实现细节，
       上层、ToolSpec、调用方全部无感知——这正是「MCP 只是一个需接入的协议」。
       当前实现 = 复用现有 MCPClient（短连接 + 自动重连 + 120s 握手超时）。
       将来换长连接 / 换 HTTP / 换 gRPC，只改这一个类，四层零改动。"""
    protocol = "mcp"

    def __init__(self, client: "MCPClient"):
        self._client = client                 # 复用现有客户端，不重写

    async def invoke(self, spec, args, ctx):
        payload = dict(args)
        # ★agent_id 由引擎注入，不进 params_schema（理由见下方「agent_id 归属」）
        if spec.binding.get("inject_agent_id", True):
            payload["agent_id"] = ctx.agent_id
        try:
            return await self._client._call_server(
                spec.binding["server_key"], spec.binding["tool"], payload)
        except ToolError:
            raise
        except CONNECTION_EXC as e:
            raise ToolError(ToolErrorKind.CONNECTION, str(e), origin=e) from e
        except Exception as e:
            raise ToolError(ToolErrorKind.REMOTE, str(e), origin=e) from e

    async def list_remote_tools(self):
        ...   # 拉一次 tools/list（子进程启动慢，仅 verify_schemas 离线自检时调用）


class LocalAdapter(ProtocolAdapter):
    """本地函数适配器：同步函数默认 to_thread 卸载，避免阻塞事件循环。"""
    protocol = "local"

    async def invoke(self, spec, args, ctx):
        fn = spec.binding["func"]
        if spec.binding.get("to_thread", True) and not inspect.iscoroutinefunction(fn):
            return await asyncio.to_thread(fn, **args)
        return await fn(**args)

    async def list_remote_tools(self):
        return []      # 本地函数无远程定义，verify_schemas 自动跳过
```

**这一层对 E3 的意义**：MCP 长连接/短连接的取舍，从此**降级为 MCPAdapter 内部的一个实现选择**，
不再影响任何架构决策——也不应该再出现在主干路线图的讨论里（见《项目执行架构》第 9 章 E3）。

### 1.14 动工时补充的实现约束（2026-08-30，M1 落地实录）

> 以下 4 条是 M1 动工时核对真实代码发现的、原设计**未覆盖**的实现级约束。
> 它们不改变架构，但**不处理就无法落地**（或会静默退步）。

| # | 问题 | 处置 |
|---|---|---|
| **① 嵌套重试放大** | `client.py::_call_server` **自带** `MAX_CONNECT_RETRY=2` 次连接重试。若引擎再设 `max_retry>0`，实际尝试次数变成 `(1+max_retry)×2` 的**乘数效应**，故障期会把延迟与负载成倍放大 | P0 工具统一 `max_retry=0`，重试仍由底层负责 → **行为与改造前完全一致**；M3 常驻化后底层重试可移除，届时再启用引擎层重试 |
| **② 写操作必须关闭底层重试** | 底层重试对所有工具一视同仁；`sql.write` 若在"INSERT 已落库但连接随后断开"时被重试 → **重复记账**（D2 要防的核心场景，原设计只在引擎层防了，没防住底层） | 给 `_call_server` 加 `max_retry` 可选参数（`None`=沿用默认，`0`=一次即止），由 `MCPAdapter` 对 `side_effect=True` 的工具传 `0` |
| **③ 异常类型必须映射回原生类型** | `ToolResult.unwrap()` 若一律抛 `ToolError`，会破坏现有契约——`call_bill_sql` / `call_llm_finance` 无权限时**原本抛 `PermissionError`**，且 `tests/integration/test_mcp_gateway.py` 有 2 处 `pytest.raises(PermissionError)` 断言 | `unwrap()` 按 kind 映射原生异常：PERMISSION→`PermissionError`、VALIDATION→`ValueError`、TIMEOUT→`TimeoutError`、CONNECTION→`ConnectionError`、REMOTE→抛底层原始异常；并用 `__cause__` 保留原始异常 |
| **④ `ToolError` 不能用 frozen dataclass** | 设计原稿用 `@dataclass(frozen=True) class ToolError(Exception)`：dataclass 生成的 `__init__` **不调用** `super().__init__(message)`，导致 `Exception.args` 为空 → `str(e)` 返回**空字符串**，错误信息在日志与异常冒泡中全部丢失 | 手写 `__init__` 并调用 `super().__init__(message)` |

**导入环的破法**（§1.11 依赖图中 `registry → adapters → client → registry` 实为环路）：

- `adapters.py` 对 `MCPClient` 仅做 `if TYPE_CHECKING:` 导入，实例由装配注入；
- 平台装配改为**惰性单例** `get_registry()`——首次访问时才执行 `_build_platform()`
  （函数内延迟导入 `client` / `executor`），既破环，又保证"不跑 `bootstrap_all()` 也能用"
  （集成测试直接调 `mcp_client.*` 时自动完成装配）。

**`agent_id` 注入的参数名映射**：`inject_agent_id` 支持三种取值——
`True`（注入为 `agent_id`，默认）/ `"agent_tag"`（注入为远端指定参数名，`llm_chat` 侧叫 `agent_tag`，
用于差异化推理参数）/ `False`（不注入）。

## 第 2 章 D2 Durable Execution 方案

### 2.1 目标与验收标准

| 项 | 内容 |
|---|---|
| 目标 | 任务状态持久化、崩溃可恢复、重复投递不产生副作用 |
| 验收 | ① `kill -9` 后重启，残留 running 任务被扫描并按策略恢复<br>② 优雅关闭（`shutdown_system`）时在途任务状态被记录，而非静默 cancel<br>③ 同一 `task_id` 重复投递不产生重复业务写入 |

### 2.2 现状的两个天然挂载点

```python

# 关闭：现在是直接 cancel，在途任务零状态 → 改为"标记 interrupted"
startup/bootstrap.py L174:  task.cancel()
```

### 2.3 方案设计（主推：SQLite 状态机 + 幂等 + 副作用保护）

**① 存储：独立 `database/task_state.db`**

```sql
CREATE TABLE IF NOT EXISTS task_state (
    task_id      TEXT PRIMARY KEY,      -- 自然幂等键（orchestrator 生成）
    session_id   TEXT NOT NULL,
    agent_id     TEXT NOT NULL,
    status       TEXT NOT NULL,         -- submitted|running|completed|failed|interrupted
    payload      TEXT,                  -- JSON
    result       TEXT,
    retry_cnt    INTEGER DEFAULT 0,
    retriable    INTEGER DEFAULT 1,     -- 有副作用任务置 0
    created_at   REAL,
    updated_at   REAL
);
CREATE INDEX IF NOT EXISTS idx_status ON task_state(status, updated_at);
CREATE INDEX IF NOT EXISTS idx_session ON task_state(session_id);
```

**② 状态机**

```
                    ┌──────────── retry_cnt<3 且 retriable=1 ───────────┐
                    ▼                                                    │
  submitted ──(worker 领取)──→ running ──(成功)──→ completed             │
                                  │                                      │
                                  ├──(失败/超时)──→ failed ───────────────┘
                                  └──(进程退出)──→ interrupted ──(重启扫描)──→ submitted
```

**③ 崩溃恢复（挂在 `bootstrap_all()` L148）**

```python
def recover_orphans(self):
    """启动时扫描上次进程遗留的 running 任务"""
    rows = db.query("SELECT task_id, retriable, retry_cnt FROM task_state WHERE status='running'")
    for task_id, retriable, cnt in rows:
        if retriable and cnt < 3:
            db.execute("UPDATE task_state SET status='submitted', retry_cnt=? WHERE task_id=?",
                       (cnt + 1, task_id))
        else:
            db.execute("UPDATE task_state SET status='failed' WHERE task_id=?", (task_id,))
    return len(rows)
```

**④ 副作用保护（本方案最关键的设计）**

由于 **worker 串行 + 任务有写副作用**（`bill_add` 会记账），崩溃恢复重投可能导致**重复记账**：

```python
# 方案：retriable 标记 + 业务幂等键
RETRIABLE_TASKS = {"stat", "price", "finance"}   # 只读/可重算 → 允许重投
NON_RETRIABLE   = {"bill"}                        # 写操作 → 禁止自动重投，转 failed 并告警
```

> **这是本方案最需要你确认的地方**：记账类任务的恢复策略，是"禁止重投 + 人工/用户确认"，还是"业务层加幂等键（如 `hash(user_id+amount+raw_text+分钟级时间窗)` 去重）"？见 Q6。

> ⚠️ **2026-09-02 对齐标注**：上方「③ 崩溃恢复 + ④ retriable 标记」为 **D2 v1 方案**。`04` §3.1 修订（2026-08-30）已**拍板升级**：`bill` 表加 `task_id` 列（可空），恢复时**按 `task_id` 反查 `bill` 对账**（有记录→`completed`；无记录→按 `retriable` 决定重投或 `failed`），两步均纳入 **M5**。**开工以 `04` §3.1 修订版为准**；本段 v1 保留其价值（`NON_RETRIABLE={"bill"}` 的保守精神在对账方案中延续为"无记录才可重投"）。恢复代码中的 `agent` 字段名以 `task_state` DDL 的 `agent_id` 为准。

### 3.2 方案设计（落地：轻量 Tracer + SQLite `llm_call_stat`；JSONL exporter 预留）

> ✅ **阶段1 已落地（2026-08-31），两处修订**：
> 1. **落点修正**：`coreModules/tracer.py` → **`utils/tracer.py`**（`coreModules` 为 M13 待退役目录；`03` §8.1 本就定 `utils/tracer.py`，此处原稿与 `03` 不一致，以 `03` 为准）。

```python
# utils/tracer.py（新增，~50 行；⚠️ 2026-09-02 核对现役代码：落点 utils/tracer.py，非 coreModules/tracer.py）
@dataclass
class Span:
    run_id: str                    # 一次用户请求唯一，贯穿 orchestrator → worker → MCP
    span_id: str
    parent_id: str | None
    name: str                      # plan_node / bill_agent / mcp.exec_sql / llm.chat
    start: float
    end: float | None = None
    tokens_in: int = 0
    tokens_out: int = 0
    status: str = "ok"             # ok / error
    meta: dict = field(default_factory=dict)

class Tracer:
    @asynccontextmanager
    async def span(self, name, *, parent=None, **meta): ...   # 自动计时、异常标记 status=error
    def dump(self, run_id) -> list[Span]: ...                 # 导出 span 树

```

**接入点仅 3 处**（改动极小）：

| 位置 | 动作 |

**与评测联动**（补上飞轮闭环的关键一环）：L3 用例失败时自动 `tracer.dump(run_id)` 落盘，评测报告里附带 span 树路径。

### 4.1 目标与验收标准

| 项 | 内容 |

### 4.2 现状问题回顾（**已按真实代码校正**）

> ⚠️ **勘误**：早期分析把总线描述成"单队列混装所有会话"，与真实代码不符。实际结构是
> `self._task_queues: Dict[str, asyncio.Queue]`（**每个 agent 一个独立队列**，L8），队列内混装**该 agent** 的所有会话。
> **缺陷依然存在，但形态与严重性须按下述重新界定。**

**真实存在两条消费路径，问题各不相同**：

```python
# L8：按 agent 分队列 —— 不是全局单队列
self._task_queues: Dict[str, asyncio.Queue] = defaultdict(asyncio.Queue)

# ── 路径①：worker 常驻消费（recv_task_blocking, L58-87）──
#    调用方 bootstrap.py L36/60/86/109 只传 agent_name，session_id=None
while True:
    try:
        msg = queue.get_nowait()          # 非阻塞取
    except asyncio.QueueEmpty:
        await asyncio.sleep(0.1)          # ★问题1：定时轮询
        continue
    if session_id is None or msg["session_id"] == session_id:
        return msg                        # session_id=None → 直接短路返回
    queue.put_nowait(msg)                 # 回插（worker 路径永不触发）
    await asyncio.sleep(0.1)

# ── 路径②：测试/业务调用（recv_task, L35-56，传了 session_id）──
#    队首消息 session 不匹配 → 回插队尾 → sleep 0.1 → 重试
#    ★问题2：O(n) 回插扫描（队内并发会话越多，取出单条消息的尝试次数越多）

# ── L89-96：target_agent 是死参数（此判断成立）──
def send_result(self, target_agent: str, session_id: str, task_id: str, result: Any):
    self._result_store[task_id] = result      # target_agent 未被使用
```

**三个问题的准确定性**：

| # | 问题 | 性质 | 严重性 | 说明 |
|---|---|---|---|---|
| 1 | `get_nowait() + sleep(0.1)` 轮询 | **定时轮询**，不是忙等自旋 | **中** | `await asyncio.sleep()` 会让出控制权，**不占 CPU、不卡其他协程**；真实代价是最坏 **100ms 投递延迟** + 空闲时每秒 10 次无谓唤醒 |
| 2 | 回插队尾做 session 匹配 | O(n) 扫描 | **中（仅路径②）** | worker 路径不触发（`session_id is None` 短路）；仅 `recv_task(sid)` 触发，测试 `test_a2a_session_isolation` 依赖此语义 |
| 3 | `send_result.target_agent` 死参数 | 设计缺陷 | 低 | 判断不变 |

> **严重性修正**：D4 早期被描述为"多会话并发最先崩的地方"。按真实代码，**不存在 O(n²) 退化、不存在 CPU 空转**，
> D4 应由"P0 崩溃风险"下调为 **"P1 延迟与优雅性"** —— 它**该改**，但**不会最先崩**。
> 当前架构最先崩的是 **D5（会话态全局 dict 无上限无 TTL）** 与 **worker 串行导致的吞吐天花板**。

**硬约束（C2）**：worker 调用 `recv_task_blocking(agent_name)` **不传 session_id**，即"消费该 agent 的所有会话"。→ **不能**改成"每 session 一个队列 + 一一对应 worker"。

### 4.3 方案设计（主推：签名不变，内部按 session 分流 + Queue 事件驱动）

**核心思路**：对外 `send_task` / `recv_task_blocking` / `wait_result` **签名与语义完全不变**，只重构内部数据结构。

```python
class A2AMessageBus:
    def __init__(self):
        # 旧：self._task_queues: Dict[agent_id, Queue]  ← 每 agent 一队列，队内混装所有 session
        # 新：
        self._session_queues: Dict[Tuple[str, str], asyncio.Queue] = defaultdict(asyncio.Queue)
        self._ready_sessions: Dict[str, asyncio.Queue] = defaultdict(asyncio.Queue)  # 就绪的 session 索引
        # 注：不引入 asyncio.Event —— asyncio.Queue.get() 内部即 Future 事件驱动，
        #     无需手写 clear()/wait() 配对（少一处竞态隐患）

    def send_task(self, target_agent, session_id, task_id, task_data):
        key = (target_agent, session_id)
        self._session_queues[key].put_nowait({"session_id": session_id,
                                              "task_id": task_id, "task_data": task_data})
        self._ready_sessions[target_agent].put_nowait(session_id)   # 登记就绪 session

    async def recv_task_blocking(self, agent_id, session_id=None):
        # 等待一律用 await q.get()：asyncio.Queue 内部即 Future 事件驱动，
        # 队列空 → 协程挂起；入队 → 事件循环精确唤醒。零轮询、零延迟、零手写 Event
        if session_id is None:
            # worker 模式：从就绪索引取一个 session（O(1)，无扫描无回插）
            ready_sid = await self._ready_sessions[agent_id].get()
            return self._session_queues[(agent_id, ready_sid)].get_nowait()
        else:
            # 指定 session：直接定位（O(1)），队列空则挂起等待
            return await self._session_queues[(agent_id, session_id)].get()
```

> **`recv_task`（带超时版，L35-56）同步简化**：同样的 per-session 队列 + `asyncio.wait_for(q.get(), max_wait)`，
> 超时分支原样保留 → 现有超时测试 `test_a2a_recv_timeout` 无需改动。

**效果对比**：

| 维度 | 现状 | 改造后 |
|---|---|---|
| **空闲唤醒** | 每秒 10 次定时轮询（无论有无消息） | **Event 等待，仅在有消息时唤醒** |
| **投递延迟** | 最坏 **100ms**（消息在 sleep 期间到达，要等这一觉睡完） | **≈0**，入队即刻唤醒消费者 |
| 空闲 CPU | 极低（`await sleep` 会让出，非空转） | 零 |
| session 匹配 | 路径② O(N) 回插扫描（N = 队内并发会话数） | **O(1)** 直接定位 |
| 消息顺序 | 回插导致跨会话取出顺序不稳定 | 按 session 保序 |
| 对外签名 | — | **完全兼容，worker 代码零改动** |

> **收益重排序（修正后）**：本改造的**首要收益是消除 100ms 投递延迟与空闲轮询**，
> 其次是路径②的 O(n) 匹配。**不再是"消除 CPU 空转"**——因为现状本就没有 CPU 空转。
> 若仅想拿延迟收益，可用 4.5 的方案 B（改动更小）。

**背压（可选）**：`_session_queues` 改为有界队列（`maxsize=100`），满时 `send_task` 抛 `BusFullError` 由 orchestrator 降级（见 Q13）。

**M12 ContextManager 接口**（⭐ **2026-08-30 补齐**；新增 `agents/context_manager.py`）

> ⚠️ **落地核对（2026-09-04）**：以下为设计雏形，落地以代码为准——① `build_context` 返回 `ContextResult{layers, per_layer_tokens, truncated}`：因调用方 system/user **分传** `call_llm_base(sys, usr)` 且模板分列变量，`final_text` 改为按层返回、由调用方回填各自模板；② `task_results` 支持 `list[(text, protected)]`，受保护块（确定性底稿）不截（R9 落点）；③ overflow 枚举收敛为 `fixed / reduce_top_k / truncate / keep_tail`（原 `truncate_tail / drop / summarize` 由 keep_tail/截尾承担、摘要后置）；④ 窗口换算默认 `context_window − output_reserve`（4096−1024），M14 `Capabilities.context_window` 落地后接管。

```python
@dataclass
class Budget:
    layer: str      # system / long_memory / user_docs / task_results / history
    max_tokens: int
    overflow: str   # fixed(不可截) / truncate_tail / drop / summarize / reduce_top_k

class ContextManager:
    def build_context(self, *, system, long_memory, user_docs, task_results, history) -> ContextResult:
        """分层 token 化 → 超预算按 overflow 策略处理 → 返回 {final_text, per_layer_tokens}"""
    def truncate_text(self, text, max_tokens, mode="tail") -> str
```

预算数值（**M12 时按所选 LLM 的 context 窗口换算**，下表为 8k 窗口示例）：

| 层 | 预算（8k 示例） | overflow | 可截 |
|---|---|---|---|
| system | 固定 ~400 | — | ❌ **不可截** |
| 长期记忆 | 20% ~1600 | 降 top_k | ✅ |
| **用户资料** | 25% ~2000 | 降 top_k（**最低保留 1 段**） | ✅ |
| 任务结果 | 30% ~2400 | 重排后截断 | ⚠️ 底稿部分**不可截** |
| 对话历史 | 25% ~2000 | 滑窗 + 摘要（调 `llm_base`） | ✅ |

## 第 7 章 M1 技术债修复设计（T4 配置分层 / T5 重试分类）

> 本章为 `01_需求与约束.md` §8.1 技术待办 **T4 / T5** 的实施级设计。
> 性质：M1 里程碑实测暴露的**技术债**，粒度小于 D1–D4 架构级决策，独立成章、不混入第 6 章决策清单。
> 两处根因同源——**可观测缺失导致的隐性缺陷**（见 `02` D3 章节「M1 实战补课」）。
> 设计原则：**先把所有风险铺在纸面上再动手**，宁可方案保守，不留返工隐患。

### 7.1 T4 · 模型参数按后端分层

#### 7.1.1 缺陷根因（为什么改）

`config/config.py` 的 `BASE_LLM_OPTIONS` / `AGENT_LLM_CONFIG` 全部是 **Ollama 本地参数**（`num_predict` / `num_ctx` / `top_k` / `repeat_penalty` 均为 Ollama 专属），而 `modelService/llm_loader.py` 的 `external_llm_call` 用**隐式白名单转译**：`num_predict → max_tokens`（L191-192）。

问题本质：`num_predict`（本地"预测多少 token"的**软约束**）与 `max_tokens`（外部"输出**硬上限**，**含 reasoning 消耗**）语义不同。M1 实测 `num_predict=400` 透传后，hy3 推理模型的 reasoning 吃满预算，`message.content` 返回空串，触发空 content 重试 3 次白烧 token。

#### 7.1.2 三条设计原则

1. **源头分层**：参数在 `config.py` 就分好本地层/外部层，**不在 `llm_loader` 里做隐式转译**（转译 = 隐式语义转换，易漏、易错、难审计、难追溯）。
2. **防御性白名单**：两个入口各认各的白名单，跨端参数（`num_predict` 进外部、`max_tokens` 进本地）**忽略并告警**（符合 R10「禁止静默失败」），而非转译、也非报错崩溃。
3. **语义相同的参数不重复分层**：`temperature` 两端语义一致（都是随机性）可复用；**只有 `num_predict` vs `max_tokens` 这类语义不同的参数才分层**——避免为"为了分层而分层"制造重复配置。

#### 7.1.3 配置结构（`config/config.py`）

```python
# 本地 Ollama 参数层（现有 BASE_LLM_OPTIONS / AGENT_LLM_CONFIG 保留不动，零破坏）

# 外部 OpenAI 兼容参数层（新增）
EXTERNAL_BASE_LLM_OPTIONS = {
    "temperature": 0.3,
    "max_tokens": 4096,   # 推理模型：reasoning + 正文预算（M1 实测 400 会被 reasoning 挤空 content）
}
AGENT_EXTERNAL_LLM_CONFIG = {
    "orchestrator_agent": {"max_tokens": 4096},
    "finance_agent": {"max_tokens": 4096},
}
```

#### 7.1.4 路由分层（`mcpGateway/server_llm_base.py`）

```python
if use_external:
    # T4：外部层参数与本地层源头分离，禁止混传
    agent_opts = AGENT_EXTERNAL_LLM_CONFIG.get(agent_tag) or EXTERNAL_BASE_LLM_OPTIONS
    return external_llm_call(..., agent_custom_options=agent_opts, ...)
else:
    agent_opts = AGENT_LLM_CONFIG.get(agent_tag) or {}
    return ollama_base_call(..., agent_custom_options=agent_opts, ...)
```

#### 7.1.5 白名单（`modelService/llm_loader.py`）

```python
EXTERNAL_OPTION_WHITELIST = {"temperature", "max_tokens"}   # 外部只认这两个
LOCAL_OPTION_WHITELIST = {"temperature", "num_predict", "num_ctx",
                          "top_p", "top_k", "repeat_penalty", "stop"}  # 本地只认 Ollama 参数
```

- `external_llm_call`：删除 `num_predict → max_tokens` 转译，改为只透传白名单内参数；`max_tokens` 兜底值从**硬编码 4096** 提升为读 `EXTERNAL_BASE_LLM_OPTIONS`。
- `ollama_base_call`：`final_options.update(agent_custom_options)` 前先用本地白名单过滤，防止外部参数（`max_tokens`）误入 payload。
- 跨端参数被过滤时，用 `logger.warning` 打一条（不静默、不阻断）。

### 7.2 T5 · 重试先分类 + 兜底必有测试

#### 7.2.1 缺陷根因（为什么改）

现状存在**三层重试嵌套**，但**请求层 HTTP 失败（402/401/400/5xx/429/Timeout）完全无分类、一律直接 return**：

1. `agents/price_agent/nodes.py` 外层 `for retry_times in range(2)`（包住 `parse_json_output`）
2. `agentCore/parsers/json_parser.py` `parse_json_output` 内 `while attempt <= max_self_retry`（模型格式/缺字段自修正）
3. `modelService/llm_loader.py` `external_llm_call` 内 `MAX_EMPTY_RETRY=3`（空 content）

问题：**可重试**的瞬时失败（5xx/429/连接错误）不重试 → 链路脆弱；而**不可重试**的确定性失败（402 配额）一旦未来"无脑加重试"就会白烧钱。此外 `force_bill` 兜底死代码已于 2026-08-31 修复（`prune_tasks_by_heuristics` 移除提前 return），且 M4 阶段已补全 14+ 条兜底单测（`test_prune_*`）——满足 R10「兜底必有测试」。

#### 7.2.2 三条设计原则

1. **重试前分类**：可重试（瞬时/服务端/限流/连接/空 content）vs 不可重试（鉴权/配额/参数/权限/超时），后者严格短路。
2. **统一预算池**：请求层所有可重试场景**共用一个 attempt 预算**，把原"空 content 单独 3 次"与新增"HTTP 瞬时错误重试"合并进同一池，**避免 `3×3=9` 的叠加放大**（这是最容易返工的点）。
3. **本地免费链路不主动重试**：本地 Ollama 不烧钱但单次 189s（极慢），重试价值低、延迟灾难，保持快速失败，靠外层 `parse_json_output` 兜底。

#### 7.2.3 重试分类矩阵（仅 `external_llm_call` 请求层）

| 失败类型 | 判定 | 分类 | 处理 |
|---|---|---|---|
| 429 限流 | `status==429` | ✅ 可重试 | 退避重试（占预算池） |
| 5xx 服务端 | `500/502/503/504` | ✅ 可重试 | 退避重试（占预算池） |
| 连接错误 | `requests.ConnectionError` | ✅ 可重试 | 退避重试（占预算池） |
| 空 content | 请求成功但 content 空 | ✅ 可重试 | 重试（占预算池，沿用现有） |
| 401/402/400/403/404 | 确定性失败 | ❌ 不可重试 | **立即短路** return（不烧钱） |
| Timeout | `requests.Timeout` | ❌ 不重试 | 直接 return（300s 已足够长，重试价值低、代价高） |
| 其他异常 | 未知 | ❌ 不重试 | 直接 return（不赌未知异常可重试） |

#### 7.2.4 实现（`modelService/llm_loader.py`）

```python
RETRYABLE_HTTP_STATUS = {429, 500, 502, 503, 504}
NON_RETRYABLE_HTTP_STATUS = {400, 401, 402, 403, 404}
MAX_REQUEST_ATTEMPTS = 3        # 统一预算池（含首次）
RETRY_BACKOFF_BASE = 1.0        # 指数退避基数（秒）

for attempt in range(MAX_REQUEST_ATTEMPTS):
    try:
        resp = requests.post(...); resp.raise_for_status()
        content = ...; text = content.strip()
        if text:
            record(success); return text
        record(EMPTY_CONTENT)      # 空 content：占池重试
    except requests.Timeout:
        record(Timeout); return FINANCE_ERROR(...)      # 不重试
    except requests.HTTPError as e:
        status = e.response.status_code
        record(HTTPError)
        if status in NON_RETRYABLE_HTTP_STATUS:
            return FINANCE_ERROR(...)                   # 立即短路
        # RETRYABLE_HTTP_STATUS → 落池重试
    except requests.ConnectionError:
        record(ConnectionError)                          # 落池重试
    except Exception as e:
        record(type(e)); return FINANCE_ERROR(...)      # 未知不重试
    if attempt < MAX_REQUEST_ATTEMPTS - 1:
        time.sleep(RETRY_BACKOFF_BASE * (2 ** attempt))
return FINANCE_ERROR("重试耗尽")
```

`ollama_base_call` 维持现状（快速失败，不加重试），设计理由见 7.2.2 原则 3。

#### 7.2.5 重试嵌套预算核算（防放大）

| 层 | 次数 | 说明 |
|---|---|---|
| price_agent 外层 retry | 2 | 业务级兜底（捕获 `parse_json_output` 所有异常） |
| `parse_json_output` 自修正 | 4（`max_self_retry=3`） | 模型格式/缺字段自修正 |
| `external_llm_call` 请求层 | 3（统一池） | 空 content + 5xx + 429 + 连接错误共享 |

- 单次 `llm_call` 最坏仍 **3 次**（改造前后不变——HTTP 重试并入原空 content 池，**不是额外叠加**）。
- 整链最坏 `2 × 4 × 3 = 24` 次（仅 price），与现状一致，**无额外放大**。
- 不可重试（402/401）在最内层**立即短路**，不会进入外层重试的放大路径。

## 第 8 章 模型接入层（ChatModel harness）——「换模型就崩」的结构性修复

> 本章为「换模型就崩」问题在**设计层**的根治方案，对应 `02` **D17**、`03` **T11**、`11` **M14**。
> 性质：**架构级新增模块**（粒度大于第 7 章的 T4/T5 技术债修复），独立成章。
> 与第 7 章的关系：**第 7 章是"止血"（堵转译 bug、加白名单、加重试分类），本章是"根治"（把模型接入从"两个平级入口打补丁"升级为标准 harness 分层）**。
> 判据一句话：**该加模型适配层，但职责是「隔离 + 契约 + 路由」，不是「翻译/转译」**——`num_predict→max_tokens` 的隐式转译正是踩坑根源。

### 8.0 定位与设计判据（为什么这样设计）

**先回答"要不要加适配层、加什么样的适配层"**（落定 `03` T11）：

| 问题 | 结论 | 依据 |
|---|---|---|
| 要不要加模型适配层？ | **要加** | 现状 `llm_loader.py` 是 `ollama_base_call` / `external_llm_call` **两个平级入口**，各自做白名单过滤 + 重试 + 埋点，**没有统一抽象**；换后端 = 在三处散落的 if/else 里猜参数，语义正确性靠"程序员记得"而非"结构保证" |
| 加什么样的适配层？ | **隔离 + 契约 + 路由**（标准 harness），**不是翻译/转译** | `num_predict`（本地"预测多少 token"软约束）与 `max_tokens`（外部"输出硬上限，含 reasoning"）**语义不同**；隐式转译 = 隐式语义转换，易漏、易错、难审计。适配层的职责是让"换后端"变成"换一个 Provider + 声明一份 Capabilities"，而不是"在一堆换算里猜参数" |
| 适配层不做什么？ | ❌ **不做** `num_predict↔max_tokens` 互转；❌ 不做"万能参数字典"跨端透传 | 跨端参数只做**过滤 + 告警**（R10 不静默）；语义相同的参数（`temperature`）才归一复用 |

**核心设计原则（五条）**：

1. **统一抽象**：业务层（`server_llm_base` / `server_llm_finance` 及以上）只认 `ChatModel.generate()`，**不再感知"本地还是外部"**。
2. **能力契约**：`Capabilities` 显式声明「支持哪些参数 / 是否 reasoning 模型 / 窗口多大」——**适配行为由契约定义，不由调用点临场判断**。
3. **参数适配 = 归一（同义）+ 过滤告警（异义），绝不转译**。
4. **路由集中**：单一 `ModelRouter.resolve(agent_tag)` 决定走哪个 Provider，三个开关（`EXTERNAL_LLM_ENABLED` / `FORCE_EXTERNAL_LLM` / `DISABLE_LOCAL_LLM`）**只在一处判断**。
5. **可观测统一**：单一埋点入口，消除 `_record_local_usage` / `_record_external_usage` 两份重复 helper。

### 8.1 缺陷根因（「换模型就崩」的完整因果链）

> 现状代码证据：`config/config.py`（`BASE_LLM_OPTIONS.num_predict=1000`、`AGENT_LLM_CONFIG` 各 agent `num_predict=2048`、`EXTERNAL_BASE_LLM_OPTIONS.max_tokens=4096`）+ `modelService/llm_loader.py`（两平级入口 + 白名单 + 重试 + 双埋点）。

**因果链（五环）**：

```
① 参数只有一套（Ollama 语义：num_predict）
      ↓ 换外部模型时被"隐式转译"
② num_predict=400 → max_tokens=400（语义已错位：软约束变硬上限）
      ↓ 外部是 reasoning 模型（先 thinking 再 content，共享 max_tokens 预算）
③ reasoning 吃满 400 预算 → message.content 为空串
      ↓ 下游 parse_json_output 解析失败
④ 空 content 被当作"可重试" → 重试 3 次，每次都重新烧 token
      ↓ 无统一可观测，故障只能靠"重跑 + 加 print"定位
⑤ 换模型 = 崩 + 白烧钱 + 定位难
```

**根因定性**：不是"某个参数写错了"，而是**模型接入层缺失**——两个后端被硬编码成两个平级函数，**能力差异（参数语义、reasoning 预算、上下文窗口）没有成为一等公民**，散落在注释和 if/else 里。

### 8.3 ① 能力契约 `Capabilities`

```python
# modelService/chat_model.py（新增，~40 行）

@dataclass(frozen=True)
class Capabilities:
    """能力契约：一个后端的"参数边界 + 推理特性"显式声明。
    适配行为完全由本契约决定——这是"隔离"的结构化落点，不是靠注释/if-else 记忆。"""
    backend: str                      # "ollama" | "openai-compat"
    supported_params: frozenset[str]  # 本后端认识的参数名（契约边界，越界即过滤+告警）
    reasoning: bool                   # 是否推理模型（reasoning 与 content 共享 max_tokens 预算）
    context_window: int               # 上下文窗口 token 数（喂 D6 ContextManager 预算表）
    streaming: bool = False
```

**契约语义（三条铁律）**：

1. **`supported_params` 是参数边界**：Provider 只认自己 `supported_params` 内的参数；跨端参数（`num_predict` 进外部、`max_tokens` 进本地）**过滤 + `logger.warning`**（R10 不静默），**绝不转译、绝不静默丢弃**。
2. **`reasoning=True` 时，输出预算必须覆盖 thinking + content**：`max_tokens` 是**硬上限且含 reasoning 消耗**；契约要求 reasoning 后端在预算过小时告警（见 8.5），从结构上杜绝"reasoning 吃满、content 为空"。
3. **`context_window` 供 D6 复用**：`ContextManager` 的分层预算表（`08` §5.2 M12）当前用"8k 示例"，接入 `Capabilities.context_window` 后按**实际所选后端窗口**换算，而非写死。

### 8.4 ② `ChatModel` 抽象 + `ChatResult` / `ChatError`

```python
# modelService/chat_model.py（续）

@dataclass
class ChatResult:
    text: str
    model: str
    prompt_tokens: int = 0
    completion_tokens: int = 0
    reasoning_tokens: int = 0     # 推理模型的思考消耗（非推理模型恒为 0）
    total_tokens: int = 0
    latency_ms: int = 0
    channel: str = ""             # "local" | "external"

class ChatError(Exception):
    """统一错误类型：retryable 决定是否进入重试预算池（T5 分类的结构化落点）。"""
    def __init__(self, message: str, *, retryable: bool, error_type: str):
        super().__init__(message)
        self.retryable = retryable
        self.error_type = error_type   # "HTTP_429" / "HTTP_401" / "Timeout" / "EMPTY_CONTENT" / ...

class ChatModel(ABC):
    @property
    @abstractmethod
    def capabilities(self) -> Capabilities: ...

    @abstractmethod
    def generate(self, *, system: str, user: str,
                 options: dict, agent_tag: str) -> ChatResult:
        """统一入口。options 为已归一参数；实现方内部按 capabilities 过滤越界参数。"""
```

**关键不变量**：`generate()` 只返回 `ChatResult` 或抛 `ChatError`——**不再返回 `"FINANCE_ERROR: ..."` 字符串**（现状用字符串承载错误，业务层要 `startswith` 判断，脆弱）。错误语义由 `ChatError.error_type` 结构化承载，业务层按类型分支；字符串化留给最外层兼容层（见 8.9）。

```python
# modelService/providers/openai_compat.py（新增，~110 行）
class OpenAICompatProvider(ChatModel):
    def __init__(self, model: str, *, reasoning: bool = True, context_window: int = 8192):
        self._model = model
        self.capabilities = Capabilities(
            backend="openai-compat",
            supported_params=frozenset({"temperature", "max_tokens"}),
            reasoning=reasoning,
            context_window=context_window,
        )
    def generate(self, *, system, user, options, agent_tag):
        opts = _filter(options, self.capabilities.supported_params)
        # ★reasoning 预算告警：reasoning=True 且 max_tokens < 预算下限 → logger.warning
        #   （reasoning 与 content 共享预算，过小会被 thinking 挤空 content，R10 不静默）
        # ★重试分类（T5）：可重试(429/5xx/连接/空content)占池重试；不可重试(401/402/400/403/404/Timeout/未知)短路
        # 成功 → ChatResult(channel="external", reasoning_tokens=completion_tokens_details.reasoning_tokens, ...)
```

**Provider 职责边界（防越界）**：

| Provider | 只做什么 | 明确不做 |
|---|---|---|
| 任一 Provider | 把**已归一参数**组装成**本后端请求体** → 发请求 → 把**本后端响应**归一成 `ChatResult` | ❌ 不决定"走哪个后端"（路由在 Router）<br>❌ 不做跨端参数转译（越界即过滤告警）<br>❌ 不处理 fallback（在 Router） |

### 8.6 ④ 路由 `ModelRouter`

```python
# modelService/router.py（新增，~90 行）
class ModelRouter:
    def __init__(self, local: ChatModel, external: ChatModel):
        self._local = local
        self._external = external

    def resolve(self, agent_tag: str) -> tuple[ChatModel, dict]:
        """开关集中判断，替代现状散落在 server_llm_* 的 if/else。"""
        if DISABLE_LOCAL_LLM:            # 硬开关：封死本地，走本地即判为路由缺陷
            return self._external, AGENT_EXTERNAL_LLM_CONFIG.get(agent_tag) or EXTERNAL_BASE_LLM_OPTIONS
        if FORCE_EXTERNAL_LLM and EXTERNAL_LLM_ENABLED:   # 联调开关：全走外部
            return self._external, AGENT_EXTERNAL_LLM_CONFIG.get(agent_tag) or EXTERNAL_BASE_LLM_OPTIONS
        if EXTERNAL_LLM_ENABLED and agent_tag in EXTERNAL_LLM_AGENTS:  # 默认：仅主调度走外部
            return self._external, AGENT_EXTERNAL_LLM_CONFIG.get(agent_tag) or EXTERNAL_BASE_LLM_OPTIONS
        return self._local, AGENT_LLM_CONFIG.get(agent_tag) or {}   # 本地基线（不配 API 也能跑，R1/C7）

    def generate(self, *, system, user, agent_tag, options=None) -> ChatResult:
        model, opts = self.resolve(agent_tag)

```

**路由决策表（开关 → 后端，替代散落判断）**：

| 优先级 | 开关组合 | 后端 | 说明 |
|---|---|---|---|
| 1 | `DISABLE_LOCAL_LLM=1` | 外部 | 走到本地 = 路由缺陷，**立即抛错**暴露问题（`config.py` L86 语义不变） |
| 2 | `FORCE_EXTERNAL_LLM=1` 且 `EXTERNAL_LLM_ENABLED` | 外部 | 联调/测试期全量走强模型 |
| 3 | `EXTERNAL_LLM_ENABLED` 且 `agent_tag ∈ EXTERNAL_LLM_AGENTS` | 外部 | 默认：主调度 + finance 走外部 |
| 4 | 其余 | 本地 | 本地 1.8B 兜底，保证「不配 API 也能跑全流程」（`01` §7） |

### 8.7 ⑤ 重试 + fallback（统一预算池，杜绝嵌套放大）

> 承接第 7 章 T5 的分类矩阵，本章把重试**收口到 Router 层**，而非留在各 Provider 内重复实现。

| 失败类型 | 分类 | 处理 | 位置 |
|---|---|---|---|
| 429 / 5xx / 连接错误 / 空 content | ✅ 可重试 | 退避重试（**共用一个 attempt 预算池**，默认 3 次） | Router |
| 401 / 402 / 400 / 403 / 404 | ❌ 不可重试 | 立即短路（重试只烧钱） | Router |
| Timeout | ❌ 不重试 | 直接返回（外部 300s 已足够长，本地 189s 同样不重试） | Router |
| 未知异常 | ❌ 不重试 | 不赌未知可重试 | Router |

**fallback 策略（仅一处，Router 内）**：

- **外部失败 → 可选回退本地**：仅 `finance` 等「外部优先、本地兜底」的 agent 允许；`DISABLE_LOCAL_LLM=1` 时**禁止回退**（本地已被封死）。
- **本地失败 → 不回退外部**：本地是"免费基线"，本地失败通常意味着 Ollama 服务本身异常，回退外部不能解决根因，且会引入意外计费。
- **每次尝试都单独埋点**：重试是**真实计费**的，只有逐次记账才能回答"这一轮为什么烧了这么多 token"（第 7 章已落，本章收口为 Router 统一行为）。

### 8.8 ⑥ 可观测统一（消除双份埋点）

现状 `llm_loader.py` 有 `_record_local_usage` / `_record_external_usage` 两份 helper，逻辑高度重复。harness 统一为**单一埋点入口**：

```python
# Router.generate 末尾统一调用（成功/失败/每次重试都记）
from utils.tracer import record_llm_call
record_llm_call(
    agent_tag=agent_tag or "unknown",
    model=result.model,
    channel=result.channel,              # "local" | "external"（由 Provider 填）
    prompt_tokens=result.prompt_tokens,
    completion_tokens=result.completion_tokens,
    reasoning_tokens=result.reasoning_tokens,   # 推理模型思考消耗，非推理恒 0
    total_tokens=result.total_tokens,
    latency_ms=result.latency_ms,
    success=isinstance(result, ChatResult),
    error_type=None or err.error_type,
)
```

**铁律不变**（`03` §9.3.1 支撑层）：可观测失败**不得阻断主链路**——埋点自身吞掉一切异常，最坏只是统计缺失。

| # | 风险 | 应对 | 是否可接受 |
|---|---|---|---|
