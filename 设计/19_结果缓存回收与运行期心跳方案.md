## 二、架构结论

### 2.1 T-2：为什么**不能**改成"无等待者即丢弃"（★核心论证）

最直觉的修法是"`send_result` 时若没有等待者就直接丢"。**它有竞态，会引入新 bug**：

```
时序：
  dispatch_node:  create_task(tid) → send_task(tid) ──┐ 投递后 worker 即刻可被唤醒
                                                       │
  【竞态窗口】worker 可能在 wait_result 建 Event 之前就回传                ← ★危险区
  具体触发路径：track() 开头 `if not self.mark_running(task_id)` →
               任务已被取消 → **立即 `_notify_result`**（同步快速，不等子图）
                                                       │
  wait_result_node: ────────────────────────────────── → wait_result(tid) 建 Event
```

若"无等待者即丢弃"，则**上面这条合法路径的结果会被丢掉** → 编排器白白等满 240s → **回归**。

**→ 故采用「显式放弃标记」**：只在"`wait_result` 超时"这一**明确**路径上登记 `_abandoned`，
`send_result` 命中标记才丢弃。**正常路径语义零变更**（含"结果先到、等待后至"的既有语义）。

```
_result_events 中无 tid  ──→  可能是"还没等到"（正常）或"已放弃"（异常）  ← 不可区分
_abandoned 中有 tid      ──→  确定是"编排器已超时放弃"                   ← 可区分 ✓
```

### 2.2 T-4：看门狗为什么**只告警、不摘除通道**

| 若做自动摘除 | 后果 |
|---|---|
| 摘除后新任务怎么办？ | 需定义"拒投"语义 → 与 M20 的背压拒绝**语义重叠**、要统一 |
| 何时恢复？ | 需引入"重探 + 半开"状态机（circuit breaker），复杂度显著上升 |
| 误判风险 | 一次探活抖动就摘除通道 → **比"不摘"更危险** |

**→ 第一步只把"可观测"补齐**（这正是 D3 可观测缺口的延伸），摘除/自愈作为独立能力另立。

## 四、改造顺序（依赖关系）

```
第 0 步（配置与状态先行）
  P0-1  config 加 MCP_HEALTH_INTERVAL
  P0-2  _ABANDONED_MAX
  P0-3  __init__ 加 _abandoned
      └─ 验收：常量可 import；实例含 _abandoned

第 1 步（T-2：结果回收——自包含，可独立验证）
  P1-1  send_result 命中标记即丢弃
  P1-2  _remember_abandoned（有界）
  P1-3  wait_result 超时登记
  P1-4  clear_all 同清理
      └─ 验收：超时后回传不入 store/events；正常路径零回归；"结果先到"语义保持

第 2 步（T-4：运行期心跳）
  P2-1  _mcp_health_watchdog
  P2-2  bootstrap_all 同批挂载（退出由 shutdown_system 一并 cancel）
      └─ 验收：interval<=0 / stdio 回退即返回；探活失败出 WARNING；恢复出 INFO

第 3 步（收口）
  D1  回归：`tests/unit` 全量 + `contract_check` FAIL 0 + lint 0
  D2  文档回填：`09`（§3.4 / §3.8）、`设计/02` D23/D24、`设计/11` M21
```

**顺序原则**：
1. **配置/状态先行**（第 0 步）——两步都依赖；
2. **T-2 先于 T-4** —— T-2 是**缺陷修复**（有明确 bug 与验收），T-4 是能力新增，先修 bug；
3. **T-2 必须"丢弃 + 登记 + 清理"同批** —— 只改 `send_result` 而不登记 `_abandoned`，等于把所有"结果先到"场景误杀。

## 六、风险点

| # | 风险 | 说明与对策 |
|---|---|---|
| **R-1** | **`_abandoned` 误丢正常结果** | 仅在 `wait_result` **超时**路径登记；且有测试锁定"正常路径零回归"与"结果先到仍可取" |
| **R-2** | **`_abandoned` 自身泄漏** | 容量有界（`_ABANDONED_MAX`），达上限按插入序淘汰最旧；误淘汰的后果仅"恢复原泄漏行为"，不影响正确性 |
| **R-3** | **看门狗探活开销** | 每次探活 = 建 HTTP 连接 + MCP `initialize` 握手；间隔默认 60s（3 个服务 ≈ 每分钟 3 次握手），可接受；`<=0` 可关 |
| **R-4** | **看门狗自身成为故障源** | 全部异常内部吞掉（探活异常按失败计），循环内不抛；且随 `WORKER_TASKS` 被 cancel 收敛 |
| **R-5** | **stdin/stdio 回退模式下无服务可探** | 看门狗开头即判 `MCP_STDIO_FALLBACK` 直接返回 |
| **R-6** | **只告警不摘除 → 故障仍会持续** | **有意为之**：第一步只补"可见性"（见 §2.2）；摘除/自愈作为独立能力另立 |

## 七、验收标准（实施后）

| 场景 | 期望 |
|---|---|
| `wait_result` 超时后 worker 回传 | 结果**被丢弃**：`_result_store` / `_result_events` 均无该 tid；标记被消费；出 WARNING |
| 正常等待中 worker 回传 | **零回归**：结果可取回，`_abandoned` 无该 tid |
| 结果先到、等待后至 | **语义保持**：`wait_result` 仍能取到（不允许改为"无等待者即丢弃"） |
| 连续大量放弃 | `_abandoned` 长度**封顶** `_ABANDONED_MAX` |
| `clear_all()` | `_abandoned` 一并清空 |
| `MCP_HEALTH_INTERVAL <= 0` | 看门狗**立即返回**（可回滚） |
| `MCP_STDIO_FALLBACK=1` | 看门狗**立即返回** |
| 运行中某 MCP 服务挂掉 | **≤1 个探测周期**内打出 WARNING（含 server_key 与连续失败次数） |
| 服务恢复 | 打出 INFO"已恢复"（连续失败计数归零） |
| 回归 | M21 专项 **9 passed**；`tests/unit` 全量通过；`contract_check` **FAIL 0**；lint 0 |
