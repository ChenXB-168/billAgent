# 13 · 多笔账与多次统计改造方案（梳理稿，未实施）

> **状态**：📋 **方案梳理（仅设计，未改任何代码）**
> **日期**：2026-09-19
> **触发**：用户提出"一次输入多笔账 / 模糊统计需拆多个操作该怎么办、该由谁拆"
> **结论先行**：**拆分责任应落在子 Agent（领域专家）内部，而非主 Agent；`task_plan` / `agent_result_cache` 保持"每类型一条"不变。**

---

## 一、需求说明（要改什么）

### 1.1 两条真实诉求

| # | 用户输入示例 | 期望行为 | 现状 |
|---|---|---|---|
| **R1** | "记午饭30，记打车20" | **落两笔账**（餐饮30 / 交通20） | ❌ **只落一笔**（30 或 20，另一笔丢失） |
| **R2** | "这个月跟上个月比，花得多了还是少了" | 一次给出**两个时间窗**的对比统计 | ❌ 只能算**一个** filter（IR 只装得下一个时间段） |

### 1.2 用户已明确的设计原则

1. **`finance` 汇总【所有】上游信息**再给建议 —— 不是只取某一条。（用户原话："肯定两个都拿啊，finance 是最终汇总所有信息，然后给出分析建议的。"）
2. **`finance` 同轮至多一条**；`bill` / `stat` / `price` 的"多次"由**子 Agent 内部**承接，不由主 Agent 展开成多条任务。

### 1.3 本方案不做什么（范围边界）

- ❌ **不改** `task_plan` 的数据结构（仍为 `Dict[任务类型名, 任务信息]`）
- ❌ **不改** `agent_result_cache` 的键（仍为 `agent_type`）
- ❌ **不改** 编排层的 `dispatch` / `wait_result` / `_merge_deps` / `_has_cycle` / `collect`
- ❌ **不改** `TASK_CONTEXT_DEPS` 依赖表

> **理由**：让"领域内的多次操作"下移到子 Agent 内部后，主 Agent 每类型只需一条"领域诉求"，编排层无需任何改动 —— 这是风险面最小的路径（见 §五对比）。

---

## 二、架构结论（拆分责任归属）

```
主 Agent（orchestrator.plan_node）
    颗粒度 = 【领域】：bill / stat / price / finance 各一条"领域诉求"
         │  A2A 派发（每类型一条，payload 携带整句原文）
         ▼
子 Agent（领域专家）
    颗粒度 = 【领域内的原子操作】：自主分解为多次抽取 / 多次 SQL / 多次 INSERT
```

**关键判断（回答"该由谁拆"）**：

- **子 Agent 不需要新增"意图识别"层** —— 它**已经有了**：
  `stat_agent.parse_query_node` 就是一层 LLM 意图识别（自然语言 → 查询 IR）。
- 真正的缺口**不是"缺意图识别"，而是"意图识别的产物装不下"**：
  `stat` 的 IR 里 `agg_ops` **本来就是数组**（支持一次执行多项统计），
  但 **`filter` 只有一个**，所有算子共享它 —— 于是"两个时间窗"无处安放。
- 同理 `bill` 侧：提示词已写"多条独立消费，输出多条独立JSON"，但**输出 schema 与执行代码都是单笔**。

> 一句话：**能力缺口在"数据结构的表达力"，不在"智能程度"。**

## 四、改造顺序（依赖关系）

```
第 0 步（前置，独立可验证）
  P1  修 _try_loads_merged 浅合并      ← 不做这步，后面全部白做
      └─ 验收：单测直接喂两笔 JSON，断言返回两笔而非一笔

第 1 步（R1 主链路，用户可感知，优先级最高）
  B1  提示词 schema 改数组
  P2  解析器支持数组返回
  P3  必填校验适配数组
  B2  抽取段改遍历
  B3  金额兜底逐笔
  B4  类目/日期逐笔
  B5  落库改循环 + 事务
  B6  习惯重算确认
  └─ 验收：e2e「记午饭30，记打车20」→ bill 表恰好 +2 行，金额/类目各自正确

第 2 步（R2 stat 多组，改动最大、最独立）
  S1 → S2 → S3 → S4 → S6 → S7 → S8
  （S5 几乎不动）
  └─ 验收：e2e「本月跟上月比」→ 两个时间窗数据都在，且渲染不糊

第 3 步（收口）
  B7  FC 路径同步
  D1  回归：tests/unit 全量 + contract_check + 相关 e2e
  D2  回填 设计/11 验收记录
```

**顺序原则**：
1. **先 parser（P1/P2/P3）**——它是 R1/R2 的公共底座，且是当前"静默丢数据"的真凶；
2. **再 R1**（bill 多笔）——用户可感知、范围可控；
3. **后 R2**（stat 多组）——改动面最大（`merge_stat_data` 几乎重写）；
4. **最后收口**（FC 路径 + 回归 + 文档）。
