## 1. 设计原则（红线）

> **需求与约束的完整内容在 `01_需求与约束.md`**：产品定位、功能矩阵、五条原始需求、
> 边界（不做什么）、非功能需求、约束 R1–R10 与 C1–C7。
>
> 本节只保留**架构层面的设计红线**——需求落到架构时不可违背的项。

### 1.1 架构红线（来源 `10_模块契约手册.md` §0.3）

1. Agent 之间**不直接调用函数**，一律通过 A2A 总线异步通信；
2. Agent **不直接访问数据库与 LLM**，一律通过 MCP 网关转发；
3. **业务能力沉淀在 `coreModules`**，Agent 只做编排与状态流转；
4. **记忆分长短两层**：短期随会话、长期跨会话；
5. **prompts 与代码分离**，提示词外置在 `prompts/`。

**核心设计要点**（来源 `03_逻辑架构.md` §四）：

6. **确定性优先**：统计/物价/预警事实全部由纯 SQL/数值计算产生，LLM 只负责"表达"；
7. **方案 C 防幻觉**：数字白名单校验 → 修正重试 1 次 → 回退本地确定性渲染；
8. **本地基线可交付**：不配任何 API 也能完整运行；
9. **双通道回退**：finance 外部 LLM 失败自动回退本地。

## 2. 架构视图框架（六视图）

| 视图 | 名称 | 回答的问题 | 对应文档 |

> **视图 ≠ 编号**（避免混淆）：
> - **编号** = **阅读顺序**（为什么要按这个顺序读，见 §4）
> - **视图** = **架构视角**（这份文档在回答架构的哪一类问题）
>
> 二者不必一一对应：例如视图 0 有 `01`（要什么）+ `02`（现在有什么问题）两份；
> 视图 4 有 `06`（横切能力）+ `09`（评测，质量视角）；`08` 是决策文档，不属任何视图。

> **关于"数据流"的归属**（易混点）：
> - **模块间传什么**（数据契约）→ 属于**视图 1**（接口设计的一部分）
> - **数据存哪、状态怎么管**（数据存储）→ 属于**视图 2**（数据架构）
>
> 二者不可混为一谈：前者跟着模块走，后者跟着存储走。

## 4. 阅读顺序 = 设计依赖顺序（为什么编号这么排）

> **编号不是随意排的**：它同时是**阅读顺序**与**设计依赖顺序**——
> 后一份文档的输入，来自前一份文档的输出。顺着编号读，不会遇到"看不懂，因为缺前置"。

### 4.1 每一步"为什么必须在这一步"

| 编号 | 阶段 | 必须在这一步的理由 | 依赖的前置产出 |
|---|---|---|---|
| `01` | 需求 | 约束决定可选空间——如 C1（协程非进程）直接否定"跨进程恢复"方案 | — |
| `02` | 现状与缺陷 | 先知道"现在有什么问题"，才知道"该改什么"；判断"什么算缺陷"需先有需求边界 | 需求与边界 |
| `03` | 逻辑架构 | 后面所有设计都在回答"**哪个模块**"的问题 | 约束清单 + 缺陷清单 |
| `04` | 数据架构 | 不知道有哪些模块，就不知道"**谁的数据、存在哪**" | 模块清单 + 接口契约 |
| `05` | 执行架构 | 并发边界取决于**模块怎么交互**、数据怎么流转 | 模块划分 + 数据流 |
| `06` | 横切能力 | 打点位置、安全边界、容错策略都长在 `03`–`05` 的产物上 | `03`–`05` 全部 |
| `07` | 部署架构 | 部署形态取决于运行时结构与外部依赖 | `03`–`06` 全部 |
| `08` | 演进方案 | "怎么改"依赖"改成什么样"；决策点来自方案对比 | `03` 目标架构 + `02` 缺陷 |
| `09` | 评测体系 | 评测需要"什么算对"的定义，否则无法设通过线 | `01` + `03` |

### 4.2 重要补充：**不是纯瀑布，As-Is 分析会回冲**

```
   现状分析（持续）──────────────────────────────┐
        ↓                                         │
   0 → 1 → 2 → 3 → 4 → 5                         │
        ↑                                         │
        └────────── 发现新问题，回头修订 ←────────┘
```

实例：《`05_执行架构.md`》发现"**名义 4 worker、实际并发度 1**"（`dispatch_node` 只取就绪列表首项并阻塞等待）。
这是 As-Is 分析，但它反过来说明：**并发优化是模块级改造**（要改 `dispatch_node` 的调度逻辑），不是调参数——因此它会修订视图 1 的模块设计。

> **结论**：现状分析随时可做、且应早做；但**目标设计（To-Be）必须按 1→2→3→4→5 的顺序推进**。

### 5.4 设计文档质量门禁（每份文档写作 / 修订时对照 · 2026-09-03 新增）

> **为什么不是"每份文档开头放总则"**：把设计总则全文复制进每份文档 = 制造 N 份漂移源，反而违反下方门禁 2 自身。
> 真正防 bug 的是把同一组**可判定要求**作为门禁，让"断言无证据 / 成对只写一侧 / 状态不清 / 重复漂移"在**写作期**就暴露。
> 心法：与 `10` §0.5 契约完备三问同构（`10`:160-164）——读者看完本文应能答出：① 本文管什么、不重复谁；② 每个论断凭什么信；③ 改它影响谁、它依赖谁。

| # | 门禁 | 判定标准（不满足即不过） | 防的 bug | 依据 / 先例 |
|---|---|---|---|---|
| 1 | **身份与归属** | 头部含编号 / 一句话职责 / 所属视图 / 实证基线 / 更新日期；30 秒能说清"本文管什么、不管什么" | 职责漂移、权威处难找 | `00` §3.1；`01`:6-10；`04`:10-12 |
| 2 | **只引用不复制** | 每个事实只有一个权威家；跨文档内容一律写 `` `编号` §章节 `` 引用，不抄正文 | 双份维护、旧版残留 | `00`:100-104；`00`:213-221 |
| 3 | **现状断言带代码位置** | 每条"现状 X"附 `` `文件:行` ``（如 `bootstrap.py` L162-164）；无实证的现状一律标"待核" | 文档说与代码不符 | `01`:224-232（C1-C7 实证列） |
| 4 | **设计断言带引用或三态** | To-Be / 方案：要么引上游定稿处（如 `03` §9.8.1），要么标 ⚠️ 待确认并登记本文「待确认决策点」 | 未拍板当已拍板施工 | `05`:1035（「建议稿·待审核」）；`04` §7 |
| 5 | **成对两端互登** | client↔server、生产入口↔测试入口、代码↔文档等成对处，**两端都**登记连接列 | 改 A 漏 B（M3 五坑主力） | `10`:86-88（连接列必填）；`10`:985-986（坑 6/7） |
| 6 | **运行时假设先补约束** | 设计依赖"程序此刻怎么跑"（协程/进程/生命周期）→ 先登记 `01` C 表或本文约束区，再继续设计 | 跨协程 / 生命周期假设 bug | `01`:226（C1 否定跨进程方案）；`00`:153 |
| 7 | **行号引用标实证日** | 引用代码行号处标注实证日期；代码改动后回查更新（防行号漂移） | 行号断言静默失效 | `00`:221；`10` §8.2 |
| 8 | **修订留痕 + 同步** | 每次改动记修订记录（日期/版本/改动点/**同步了哪些文档**）；文档状态变化同步 `00` §5.1/§5.2 | 文档间静默失同步 | `10`:997-1001（v2.2–v2.4 跨文档同步）；`00`:225-239 |

> 用法：**新文档立项前、旧文档每次实质修订后**逐项对照；任何一项不通过，先修文档再进入下一步。
