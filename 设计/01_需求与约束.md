## 1. 一句话定位

> **billAgent 是一个「单用户的对话式个人消费管家」：
> 用自然语言记账，系统自动归类、统计、比价、给建议，并在预算异常时主动提醒——
> 且所有数字 100% 来自确定性计算，不靠模型编。**

**三条价值主张**：

| # | 主张 | 用户感受到什么 |
|---|---|---|
| 1 | **记账零摩擦** | 说一句"记午饭56元"就完成，不用打开 App 填表单 |
| 2 | **主动提醒** | 不只是记账本——花超了、快花超了、花得不值，它会**主动告诉你** |
| 3 | **数字可信** | 金额、占比、溢价率全由 SQL/数值计算产出，LLM 只负责"表达"（方案 C 防幻觉） |

## 2. 用户与场景

| 项 | 内容 |
|---|---|
| **目标用户** | **单个个人用户**（系统无 `user_id`、无登录、无多租户——见 §5 边界） |
| **使用场景** | ① 日常消费后随手记一笔；② 随时问"花了多少 / 贵不贵 / 怎么省" |
| **交互方式** | 自然语言对话：WebUI（`127.0.0.1:7860`）或 CLI（`python startup/main.py`） |
| **运行环境** | **本机单机**：Python + SQLite + 本地 Ollama 1.8B（外部 LLM 可选） |
| **数据规模** | 个人量级（月几十至几百笔），非海量数据场景 |

## 3. 核心功能

### 3.1 能力矩阵（4 大能力 + 1 组配置）

| # | 能力 | 意图 / 子类型 | 用户说什么 | 系统做什么 | 数字来源 |
|---|---|---|---|---|---|
| 1 | **记账** | `bill:add` | "记午饭56元" | LLM 结构化提取（金额/品类/时间/备注）→ 规则校验 → 入库 → 沉淀习惯 → **触发预警链** | 数值全确定性 |
| 2 | **改账** | `bill:edit` | "把刚才那笔改成60" | 定位 → 更新 | 同上 |
| 3 | **删账** | `bill:delete` | "删掉刚才那笔" | 定位 → 删除 | 同上 |
| 4 | **统计** | `stat:query` | "这个月花了多少" / "查7月开销" | SQL 取数 → 汇总 + 同比环比 → 文本渲染 | **纯 SQL，零 LLM** |
| 5 | **比价** | `price:query` | "打车贵不贵" / "咖啡比市场价高吗" | 本城均价 → **同级城市兜底** → 溢价四档 | **纯数值计算** |
| 6 | **理财分析** | `finance:analyse` | "给我点省钱建议" / "够不够撑到月底" | 确定性注入（目标/统计/物价/近 3 月习惯/历史记忆）+ 规则事实底稿 + **用户资料检索（可选，§3.5）** → LLM 生成建议（白名单校验；用户资料标注来源、不进白名单） | 事实确定性，表达 LLM；用户资料仅供参考 |
| 7 | **配置** | （隐含能力） | "设置月预算3000" / "我在北京" / "我要节俭" | 写入 `user_config`：城市 / 月预算 / 消费模式 / 品类预算 / 提醒偏好 | — |
| 8 | **知识管理** | `doc:add` / `doc:delete` / `doc:list` | "记下：我们那香蕉8块一斤" / "删掉那条笔记" / "我的笔记有哪些" | 写文件 → 索引对齐；删文件 → 索引对齐；列目录 | —（存用户原文，非事实数字） |

> **多意图**：一句话可含多个意图（"记午饭56元，再看看这个月花了多少"）→ 拆成任务 DAG，按依赖调度。

### 3.2 端到端示例：记一笔午餐

```
用户："记午饭56元"
  │
  ├─① 意图识别      orchestrator → bill:add
  │
  ├─② 结构化提取    bill_agent：LLM 抽取 {金额:56, 品类:餐饮, 备注:午饭} → 业务规则校验
  │
  ├─③ 入库 + 沉淀    bill 表 INSERT（RBAC + 审计）→ monthly_habit 习惯累加
  │
  ├─④ 预警链（★核心价值，纯确定性计算，零 LLM）
  │     L1 单笔溢价：本市餐饮均价对比 → 四档（偏低/正常/偏高/过高），仅偏高/过高才提示
  │     L2 品类进度：餐饮额度（用户设定 > 历史月均 > 城市估算）→ 进度与剩余
  │     L3 总量预警：月预算四档（over/warn/reward/ok）→ 超支则点名主因品类 + 给每日额度
  │
  └─⑤ 表达           LLM 按汇总提示词生成回复（数字只能引用上述事实，白名单校验）
        ↓
  "记账成功✅ 已记餐饮56元… 本月预算剩余…"
```

### 3.3 预警规则（需求 1–4 的落地形态）

| 档 | 触发条件 | 行为 |
|---|---|---|
| **reward 犒劳** | `0 < 已用比例 ≤ 0.5` | 提示可以适当犒劳（**月首无消费不触发**，避免刚开月就劝消费） |
| **ok** | `0.5 < 比例 < 0.8` | **不打扰**，正常汇总 |
| **warn 预警** | `0.8 ≤ 比例 < 1.0` | 预警 + 给出每日建议额度 |
| **over 超支** | `比例 ≥ 1.0` | 超支预警 + **点名主因品类** |

**单笔溢价四档**：`< -15%` 偏低 ｜ `±15%` 正常 ｜ `≤ 40%` 偏高 ｜ `> 40%` 过高
→ **仅"偏高/过高"才在回复中呈现**；本城无均价 → 同级城市兜底；仍无 → **跳过不打扰**。

### 3.4 多轮追问策略（2026-08-29 拍板；2026-10-08 修订）

**规则**：信息不全时向用户追问，**最多 3 轮**；若第 3 轮仍未得到符合格式要求的信息，**直接放弃并报错**。

| 项 | 规则 |
|---|---|
| **追问上限** | **3 轮** |
| **超限行为** | **放弃执行 + 报错**（不再追问，也不静默跳过） |
| **提示语** | **"信息不全，执行失败，请重新来"** |
| **放弃时的副作用** | **清空该会话的半成品草稿**（`bill_add` / `bill_edit` / `bill_delete`），防止脏数据带入下一次记账 |
| **触发条件①（子 Agent · 领域级）** | 子 Agent 返回 `success=False, error="need_more_info"`，并携带 `data["prompt"]` 作为追问文案 |
| **触发条件②（主 Agent · 参数级）** | **2026-10-08 新增**：`plan_node` 检出必需参数缺失（`missing` 非空）或意图超出四基元范围（`scope_check=out_of_scope`）→ **不派发**，直接回 `final_reply` 追问 / 引导 |

> **⭐ 两类追问的分工（2026-10-08 修订）**：
>
> | 类型 | 判断者 | 依据 | 何时触发 |
> |---|---|---|---|
> | **参数级**（比价缺金额、记账缺品类） | **主 Agent** | 契约表（`config/agent_contracts.json`） | **派发前**——不派发，**省一次 LLM 调用** |
> | **领域级**（"吃了顿好的"无法归类） | **子 Agent** | 领域提示词 + 代码正则 | 派发后——保留为**硬兜底** |
>
> **分工理由**：主 Agent 掌握**契约级知识**（"比价需要金额"），可写进 schema 提前判定；
> 子 Agent 掌握**领域级知识**（"这句话在业务上算不算一笔可分类消费"），主 Agent 装不下。
> **软判断（主 Agent / LLM）负责体验，硬判断（子 Agent / 代码）负责正确性**，两者互补而不替代
> —— 故**子 Agent 的 `need_more_info` 通道保留不删**。
>
> **共同约束**：两类追问**共用同一个 3 轮上限**（`ASK_ROUND_LIMIT`）与清草稿副作用——
> 主 Agent 追问须经"预规划追问 key"计入（见 `设计/14` §3.4），否则会形成"主 Agent 无限追问"的新死循环。
>
> **派发策略**：**全 barrier** —— 一轮内任一任务缺参即整轮不派发，追问完毕后（用户补充）下一轮重新规划派发
> （2026-10-08 用户拍板；**不做**部分派发，**不做** deps 感知追问）。
>
> 方案依据：`设计/14_意图层能力补齐与追问上移方案.md`；契约 `设计_从零系列/09` §2.14；里程碑 **M16**（缺陷 D18）。

> **⚠️ 与现状的差距（需改造）**：
> 当前**没有追问轮次上限**——`dispatch_round` 是**调度轮次**（防任务 DAG 死循环，上限 20），
> 且**每次新用户输入即重置为 0**，它**不是**追问轮次。因此当前实际行为是**无限追问**。
>
> 追问计数需落在**会话级**（`ShortSessionMemory` 的 `SESSION_DRAFT_CACHE` 是天然落点），
> 而非 graph state——后者每次 `ainvoke` 都会重建。
> 详见 `02_现状盘点与缺陷分析.md`；实现方案归入 `04_数据架构.md`（已建，§3.4 会话态）。

### 3.5 用户文档库（User Documents，2026-08-30 新增需求）

**定位**：用户自己的笔记，作为**个性化知识库**，供理财分析（finance）检索参考。
它是"用户告诉系统的**生活场景知识**"——`city_price` 表覆盖不到的**细分地区 / 品类**（如"某年某月 X 镇香蕉多少钱一斤"、本地省钱策略），由用户笔记补齐。

| 项 | 规则 |
|---|---|
| **存储** | 独立文件夹 `userDocs/`，**文件系统是唯一真相源**（`04_数据架构` §1 存储全景第 6 类） |
| **格式** | v1 支持 **txt / md**；解析器**注册制**，架构可扩展（pdf / docx 后续按需增加，不破坏现有设计） |
| **上限** | **1000 条文档**（超出明确提示，不静默丢弃） |
| **增删改** | 用户直接操作文件夹，或对话指令（"记下…" / "删掉那条笔记"）→ **索引自动对齐**（`04` §3.5 文件-向量对齐机制） |
| **检索使用** | finance 分析时检索 top_k 片段 → 注入 prompt，**标注为「用户资料」** |
| **冲突优先级** | **确定性事实永远赢**；用户资料与确定性事实冲突时，**必须向用户说明差异**，最终由用户参考判断 |
| **数字语义** | 用户资料中的数字**不参与白名单校验**（非确定性层产出），但**允许 finance 引用并做简单计算/对比**（如"按你记的香蕉 8 元/斤，这次 5 元/斤算便宜"） |
| **与 price_agent 的分工** | **price_agent 只处理 `city_price` 表内的城市/品类**，不做个性化；用户个性化价格知识一律交给 finance 整合（finance 可能用更强模型） |

**为什么这么分工（简单化原则，v1 不做）**：
- ❌ 不做"用户价格入库 → price_agent 读取"（那会污染全局比价基线）
- ❌ 不做 `city_price` 个性化覆盖
- ✅ 用户生活价格知识**全部走 finance 的 RAG 检索**——用户文档是参考输入，不是事实源

> **与 Q6 的关系**：Q6 拍板的"文本不承载事实数字"**依然成立**（用户文档数字不进白名单）；
> 本需求是**在其上新增**"用户文档可作参考输入"。详见 `01` §8 Q6（已修订）。

| 5 | "主 Agent 识别意图（记账 vs 简短提醒 vs 全面分析），多子 Agent。" | ⚠️ **架构要求，非产品需求** | 4 类意图 + 5 个 Agent（1 编排 + 4 专职） | ✅ 已实现 |

> ### ⚠️ 关于第 5 条，值得单独说
>
> **它不是用户需求，而是实现手段。** 用户真正要的是"**能听懂我说的话、并把事做对**"——
> 至于用 1 个 Agent 还是 5 个 Agent，用户并不关心。

>
> **启示**：后续新增需求时，先问一句"这是用户要的，还是我们实现它的方式？"

## 5. 边界：明确「不做什么」

> **这份"不做清单"比功能清单更重要**——需求之所以越补越散，往往是因为边界没立住。
> 以下均有**代码级证据**，不是猜测。

| 不做 | 代码级证据 |
|---|---|
| ❌ **多用户 / 登录 / 权限体系** | `bill`、`user_config` 表**均无 user_id**，全局单用户配置 |
| ❌ **记录收入** | `bill` 表 `CHECK(amount > 0)`，建表注释明写"**仅存支出正数**"；代码已明确拒绝（`nodes.py` L901："收入类内容不予入账，本系统仅支持支出记账"） |
| ❌ **自定义消费品类** | 五分类（餐饮/交通/住宿/购物/娱乐）**硬编码为 CHECK 约束**，改品类须改表结构 |
| ❌ **年度预算** | **只做月预算**。`user_config.budget_type` 的 `year` 选项为历史遗留且**未实现**（预警链只处理月），已列入清理清单 |
| ❌ **移动端 / 多端同步** | 单机 SQLite，无服务端 |
| ❌ **接入银行 / 支付流水** | 全靠手动对话记账，无任何自动导入 |
| ❌ **图表可视化** | 回复为纯文本；WebUI 是对话界面，无图表 |
| ❌ **跨会话复杂状态** | 短期记忆在**进程内**（重启即失）；长期记忆仅沉淀"月×品类"习惯 |

> **用法**：后续任何新增需求，先问——**它是否要打破这里的某一条？**
> 若是，那是产品升级（需改数据模型），不是"补个需求"。

## 6. 非功能需求

| 类别 | 要求 | 实现保障 |
|---|---|---|
| **数字准确性**<br>（最高优先级） | 回复中的金额/占比/溢价率**必须 100% 来自确定性计算** | 确定性事实底稿（先定事实、再生成文案）+ **方案 C 三层防护**：数字白名单 → 修正重试 1 次 → 回退本地确定性渲染 |
| ~~**本地可用性**~~ | ~~不配任何 API 也能完整跑通全流程~~ → **⚠️ 已废止（2026-10-09 · M22）**：**必须配外部 API**，未配即启动报错（见 R5） | 外部强模型（deepseek-chat）为**唯一形态**；本地 Provider 保留但**默认封死** |
| ~~**零成本默认路径**~~ | ~~默认免费；外部 LLM 仅为可选增强~~ → **⚠️ 已废止（2026-10-09 · M22）**：默认路径即**外部 API**（有成本） | `EXTERNAL_LLM_ENABLED` 由 base_url + api_key 推导；未配 → `ModelRouter.resolve` 抛 `RuntimeError` |
| **容错** | 外部模型失败不崩、有兜底 | ★M22：**单通道**（本地已弃用）——失败走 M19 终止语义（明确报错，不静默降级）+ 确定性渲染兜底；`EXTERNAL_LLM_TIMEOUT=60s` 防挂起 |
| **可验证** | 工程质量可量化、可回归 | L1 单元/集成 + L2 检索评测 + L3 回答质量（12 用例；本地 **12/12 均分 10.0**，混元 hy3 **12/12 均分 9.83**） |
| **性能** | 用户可接受即可（**非实时系统**）；★M22 收紧超时链：**工具 60s < 任务 120s < 编排器等待 150s** | 外部强模型**秒级**响应（原"本地 1.8B 秒级"表述有误，实测单次 189s）；**MCP 子进程启动 26~29s 为已知瓶颈**（M3 已消除运行期冷启动），见 `05_执行架构.md` |
| **可观测性**<br>（2026-08-31 新增） | **每次 LLM 调用必须采集 token / 耗时 / 成败，并可归因到 agent（`agent_tag`）**——用于成本核算与故障定位 | D3 Tracer（`utils/tracer.py` → `llm_call_stat` 表）；**可观测失败不阻断主链路**（铁律）；**禁止静默降级**——任何回退/兜底必须打 WARNING + 计数 |

## 7. 约束

约束分两类：**需求派生的（R）** 是产品的内在要求；**现状技术的（C）** 是当前实现带来的限制，改造时必须面对。

### 7.1 需求派生约束（R1–R9）

| # | 约束 | 来自 |
|---|---|---|
| **R1** | 单用户、单机、SQLite | §2 用户与场景 |
| **R2** | 品类固定五分类 | §5 边界 |
| **R3** | 只记支出、不记收入 | §5 边界 |
| **R4** | 数字必须确定性（不得由 LLM 产出） | §6 最高优先级 |
| ~~**R5**~~ | ~~必须本地可跑（零 API 也能用）~~ → **⚠️ 已废止（2026-10-09 · M22）**：本地通道**彻底弃用**，改为**必须配置外部 API**；未配时 `ModelRouter.resolve` 启动即抛 `RuntimeError`（快速失败，不静默降级）。代码与 Provider 保留（`BILLAGENT_DISABLE_LOCAL_LLM=0` 可临时恢复），属**软弃用**。 | §6 / `设计/20` |
| **R6** | 预警不得打扰（无异常不提示） | §3.3 边界处理 |
| **R7** | **预算周期仅"月"**（不做年度预算） | §8 Q4 决策 |
| **R8** | **信息不全最多追问 3 轮，超限即放弃并报错** | §8 Q5 决策 / §3.4 |
| **R9** | **用户文档库仅作参考，不参与数字白名单；确定性事实永远优先，冲突必须向用户说明** | §3.5 用户文档库（2026-08-30） |
| **R10** | **禁止静默失败**：任何降级 / 回退 / 兜底必须打 WARNING 并计数；每次 LLM 调用必须采集 token / 耗时 / 成败（**可观测前置**，不排到最后） | §6 可观测性 / M1 实战踩坑（2026-08-31） |

> **R1–R3、R7 已在 §8 经决策确认，属"锁定项"**：
> 任何突破它们的改动都属于**产品升级**，必须先回到本文修订需求基线，而不是直接改代码。

### 7.2 现状技术约束（C1–C7）

> 这些是**当前实现的既有事实**，决定了任何改造方案的可选空间。

| # | 约束 | 实证 | 对设计的影响 |
|---|---|---|---|
| **C1** | **Worker 是进程内 asyncio 协程**，非独立进程 | `startup/bootstrap.py` L162-164 | "持久化"不等于"跨进程恢复"；并发改造不能引入多进程语义 |
| **C2** | **Worker 消费不传 session_id** | `bootstrap.py` L36/60/86/109 | 总线改造**不能**改成"每 session 一队列"，必须保留 agent 级消费语义 |
| **C3** | **Worker 串行消费** | `bootstrap.py` L34-48 | 单 worker 一次只跑一个任务；重投必须防重复副作用 |
| **C4** | **数据库是 SQLite** | `database/bill.db` + 全局 `utils.common.db` | 持久化零新增依赖；但并发写需锁，状态机设计受限 |
| **C5** | **~40 处测试按名 patch** | `@patch("agents.*.nodes.mcp_client.call_bill_sql")` | 任何调用形态改动都会击穿测试 → **兼容层是必选项** |
| **C6** | **MCP 为 stdio 短连接** | `mcpGateway/client.py` L38-44 | 子进程启停开销大（模型加载 26~29s），握手超时 120s；工具调用是重操作 |
| **C7** | **单进程部署** | 无外部中间件 | 无分布式一致性问题；但也无水平扩展能力 |

## 8. 需求决策记录

> 还原需求时发现的模糊点，**已于 2026-08-29 全部拍板**。此处留档，作为后续架构设计的**硬性前提**。

| # | 决策项 | **结论** | 对架构的影响 |
|---|---|---|---|
| **Q1** | 要不要多用户？ | **不做 —— 维持单用户** | 所有表无需 `user_id`；无登录、无权限体系。架构大幅简化 |
| **Q2** | 要不要记收入？ | **不做 —— 维持仅记支出** | `CHECK(amount>0)` 保持；代码已有明确拒答（L901）。统计口径恒为"总支出"，无净结余概念 |
| **Q3** | 品类要不要可扩展？ | **不做 —— 维持五分类硬编码** | 不引入字典表；`city_price` / `monthly_habit` 的品类联动保持简单 |
| **Q4** | 年度预算支持吗？ | **不要 —— 只做月预算** | `budget_type` 的 `year` 属"声称支持但未实现"→ 列入清理清单（T1） |
| **Q5** | 追问几轮后放弃？ | **3 轮 —— 超限直接放弃并报错** | 提示语"信息不全，执行失败，请重新来"；需新增**会话级**追问计数（T2/T3） |
| **Q6** | 理财建议的事实来源走 RAG 吗？ | **分两层（2026-08-30 修订）**：<br>① **系统内置 10 条规则**（物价 / 阈值 / 占比）→ **清理**：本就属"参数/规则"性质，已被确定性层覆盖（`02` D16 已拍板移出），且**本就不该装在 RAG 里**；<br>② **用户文档库（`01` §3.5 新增需求）** → **走 RAG 检索**：用户笔记作为「**用户资料**」注入 finance，标注来源、**不参与白名单**（文本承载数字 ≠ 确定性事实，Q6 原论证仍成立）；冲突时**确定性事实永远优先**并向用户说明 | finance 防幻觉三件套（确定性事实底稿 + 白名单校验 + 历史记忆注入）**不变**；用户资料是**补充参考**，不是事实源；实施设计见 `03` §9.9 与 `04` §3.5 |

> **这六条都是"收缩型"决策**——明确不做，比明确要做更有价值。
> 它们共同把系统锁定在"**单用户 · 仅支出 · 五分类 · 月预算**"的简洁模型上，
> 后续架构设计可以放心地不做多租户抽象、不做字典表、不做周期泛化、不为 RAG 建链路。
