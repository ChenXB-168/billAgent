# 09 · 评测体系设计（视图 4 · 质量）

> 面向「记账理财多 Agent 系统」的评测体系设计文档。
> 回答三个问题：**测什么**、**怎么测**、**为什么这样测**。
> 本文档既是现有评测资产的说明书，也是待补全部分（工程化层）的构建规范。L1 三层测试、L2 检索评测、L3 回答质量评测（含数据正确性硬校验）均已落地并产出基线。

---

## 0. 文档定位

本项目是一个多 Agent 记账理财系统：orchestrator 负责意图规划，通过 A2A 进程内队列把子任务派发给 bill / stat / price / finance 四个子 Agent，底层依赖本地 1.8B LLM、长期记忆库、用户文档库（`userDocs/`，用户资料参考）与 SQLite 账单库（确定性事实）。

这是一个 **LLM 驱动、非确定性、多模块耦合** 的系统。这类项目的工程质量无法用"能跑通"来证明，必须用一套可复现、可量化、可对比的评测体系来证明。本文档描述这套体系。

### 评测体系要守护的三类东西

| 守护对象 | 破坏风险 | 评测手段 |
|---|---|---|
| 系统正确性（流程不崩、数据不丢） | 图控制流错误、超时、异常未兜底 | L1 确定性测试 |
| 子系统能力（检索找得对、找得全） | embedding 退化、索引漂移、阈值失效 | L2 检索质量评测 |
| Agent 回答质量（意图对、参数准、不幻觉） | 小模型语义误判、字段缺失、凭空编造 | L3 回答质量评测 |
| 可持续演进（改一行不崩一片） | 回归、指标退化无人察觉 | L4 工程化（CI/报告/存档） |

## 1. 为什么要构建评测体系

### 1.1 动机：LLM 输出是非确定性的

传统系统的测试是"输入确定 → 输出确定"，断言可以写死。但本系统的核心链路里，**输出由 1.8B 本地模型实时生成**，同一条输入每次输出都可能不同。实测中遇到的真实问题包括：

- JSON 键名被插入空格（`"operate_sub_type"` → `"operate sub type"`），标准 `json.loads` 直接抛异常；
- 一次输出多个顶层对象并列，需要拆分合并；
- `name` 字段塞入用户原话或测试标记，而不是任务描述；
- 规划阶段漏掉用户明确要求的任务（如"存账单"），或脑补出用户没提的任务；
- 金额幻觉：原文 `45元`，模型输出 `200元`；甚至把 `-30元` 的负号丢掉当成正数；
- 语义误判：把"发奖金 5000 元"当支出记账，把"物价对比"判成统计。

这些问题的共同点：**代码本身没写错，是上游模型输出不可信**。没有评测体系时，这类问题只能在每次人工跑 e2e 时靠肉眼发现，且无法量化"到底修没修好、修好了多少"。

### 1.2 实证：评测驱动根因修复

本次迭代以"全量跑测试 → 失败 → 定位根因 → 修复 → 回归"循环推进，最终挖出并修复 11 个独立根因（如 e2e 全超时实为 A2A worker 未启动、stat 崩溃实为 LangGraph 静态边吞掉 `Command(goto=...)`、SQL SUM 空结果 `float(None)` 崩溃等）。

这条实证链说明评测体系的真正价值不只是"证明正确"，而是 **为根因定位提供快速反馈回路**：全量用例 → 失败用例即最小复现 → 日志定位 → 修复 → 回归验证。

### 1.3 设计五原则

1. **确定性优先**：能用代码断言解决的（流程、数据结构、指标计算）绝不用人眼或大模型判断。
2. **可复现**：固定种子数据（`evaluation/seed_memory_data.py`）、固定运行链路（`_dbg_run_pytest.py`），同一环境下结果可重放。
3. **防漂移**：评测集里的期望值直接引用数据源原文（GT 引用 `seed_memory_data.MOCK_SUMMARIES` / `rag_builder.RAW_KNOWLEDGE` 元素），数据源改动时评测能立刻暴露"seed 与 eval 不同步"。
4. **分维度**：不同能力（意图、抽取、检索、格式）分开评测，问题出现时能定位到具体能力短板。
5. **可对比**：每次评测产出结构化报告，指标可跨版本对比，证明"改动让指标涨还是跌"。

## 2. 评测体系总览

```
┌─────────────────────────────────────────────────────────┐
│  L1 确定性测试（tests/，pytest）                         │
│  unit(81) + integration(14) + e2e(16)                   │
│  守护：流程正确性 / 数据结构 / 全链路行为 / 数据库正确性 │
├─────────────────────────────────────────────────────────┤
│  L2 检索质量评测（evaluation/，离线脚本）                │
│  hit@k / recall@k / MRR@k                               │
│  守护：RAG 知识库与长期记忆的召回能力                    │
├─────────────────────────────────────────────────────────┤
│  L3 Agent 回答质量评测（evaluation/，已实现）            │
│  rubric 五维评分(10分) + db_accuracy 数据正确性硬校验    │
│  守护：意图 / 参数 / 业务语义 / 格式 / 无幻觉 / 落库真相 │
├─────────────────────────────────────────────────────────┤
│  L4 工程化（待补全，本文档 §6 给出规范）                 │
│  CI 自动执行 / 报告存档 / 趋势对比 / 失败分类            │
└─────────────────────────────────────────────────────────┘
```

各层职责严格分离：L1 回答"系统对不对"（含数据层"库里对没对"），L2 回答"知识找得准不准"，L3 回答"回答质量高不高 + 落库真不真"，L4 保证前三层可持续运转。

**关键洞察**：L3 原本只评"回复文本"，存在盲区——模型说"记账成功"不等于数据库真的写对了。本次补充 `db_accuracy` 数据正确性硬校验（§5.6）与 integration 数据层测试（§3.3），首次抓到"回复满分但落库金额错误"的真实缺陷（§5.7）。

## 3. L1 确定性测试层

### 3.1 三层结构与职责边界

| 层 | 目录 | 用例数 | 职责 | 关键依赖 |
|---|---|---|---|---|
| 单元测试 | `tests/unit/` | 81 | 单函数/单模块逻辑：JSON 解析容错、任务规划启发式、各 Agent 节点、A2A 总线、记忆存取、RBAC | 无需 MCP，可离线 |
| 集成测试 | `tests/integration/` | 14 | 模块间协作：MCP gateway 协议、记忆 Agent 集成（含 worker）、会话记忆持久化、**账单数据库正确性**（写读回环/统计 SQL/CHECK 约束） | 需 LLM MCP |
| 端到端测试 | `tests/e2e/` | 16 | 完整链路：用户输入 → orchestrator 规划 → A2A 派发 → 子 Agent → 汇总回复 | 需 LLM MCP + 4 个 A2A worker |

### 3.3 数据正确性测试（B 方案：`tests/integration/test_bill_db_integrity.py`）

unit 层把 `call_bill_sql` mock 成字符串 `"成功"`、e2e 只断言回复文本，两者都无法回答"**数据库真的写对/算对了吗**"。本文件直连真实 `bill.db`（走 MCP sql_bill 网关，4 条用例，不依赖 LLM，28s 跑完）：

| 用例 | 验证内容 | 为什么重要 |
|---|---|---|
| `test_write_read_roundtrip` | INSERT 66.6/餐饮 → 查回金额/类别/日期一致 | 写读回环是最低限度的一致性保证 |
| `test_stat_sum_and_group_accuracy` | seed 10/20/30 → SUM=60、COUNT=3、分类聚合精确 | 统计回复里的数字依赖这些 SQL，SQL 错则一切统计皆错 |
| `test_check_rejects_negative_amount` | INSERT -5 → 被拒且不落库 | 负数金额入账是数据毒瘤 |
| `test_check_rejects_bad_category` | INSERT 非法类别 → 被拒且不落库 | 五分类约束是业务规则的物理实现 |

**该测试首次运行时 2/4 失败，暴露真实缺陷**：`bill.db` 里的 `bill` 表是旧版本创建的，**没有 CHECK 约束**（`CREATE TABLE IF NOT EXISTS` 不会升级已有表），负数金额、非法类别可直接入库。已通过 `database/init_db.py::migrate_bill_table()`（建带约束新表 → 清理违规数据 → 复制 → 换名，幂等）修复，修复后 4/4 通过。**这是"数据正确性测试发现 L1 文本断言永远发现不了的问题"的实证。**

**为什么分三层**：单层全量 e2e 的问题是一旦失败无法快速归因（是规划错、还是派发错、还是子 Agent 错？）。三层递进把失败范围逐层缩小：unit 保证"零件对"，integration 保证"接口对"，e2e 保证"整机对"。本次修复实践中，e2e 红 → 下沉写 unit 最小复现（如 `_dbg_stat_flow.py` 复现 goto 被忽略）→ 修完 unit 绿再回 e2e，归因成本显著下降。

### 3.2 断言设计逻辑

e2e 断言刻意**不只断言 pass/fail，而是断言"业务语义"**。以 `tests/e2e/test_single_task.py` 为例：

```python
# 记账：必须回执"记账成功" + 正确分类"餐饮"
assert "记账成功" in result["final_reply"]
assert "餐饮" in result["final_reply"]

# 统计：必须回执"月度消费统计" + 有"总支出"数据
assert "月度消费统计" in result["final_reply"]
assert "总支出" in result["final_reply"]
```

**为什么这样断言**：`final_reply` 是 LLM 生成的自由文本，无法断言全文相等。改为断言"关键业务语义词"，既校验了流程走到了正确分支（"记账成功"只在 bill_agent 成功入库后产生），又校验了内容质量（分类正确才可能出现"餐饮"）。同时这些关键词是**产品文案**（与 UI 一致），断言它们等于校验了用户可感知的结果。

### 3.4 e2e 评测集：覆盖维度清单

| 文件 | 用例 | 覆盖维度 |
|---|---|---|
| `test_single_task.py` | 单记账 / 单统计 / 单物价 / 单理财 | 四类基础能力 |
| `test_mixed_task.py` | 记账+统计 / 记账+理财 / 四任务全场景 | 多任务规划、依赖顺序、数据联动（统计读到新账单） |
| `test_boundary_case.py` | 无记账指令只分析 / 收入内容拦截 / 空输入不崩 / 多轮上下文引用 | 边界与对抗输入 |
| `test_a2a_full.py` | A2A 收发 / 会话隔离 / 超时 / 并发 / bill 集成 | 通信基座正确性 |

边界用例的设计逻辑体现了评测对"业务规则"的守护：

- `发奖金5000元` 必须**不**出现"记账成功"——收入拦截规则（`INCOME_KEYWORDS`）是可被打破的业务红线，必须用负向断言锁死；
- `哈哈哈随便聊聊` 必须返回非空字符串——系统对外不可崩溃是底线；
- 多轮用例把**上下文记忆**作为一等公民评测，防止"第二轮无法引用第一轮"的退化。

### 3.5 运行链路与工程细节

```
_dbg_run_pytest.py（UTF-8 输出包装，规避 PowerShell 中文乱码）
  └─ subprocess: venv python -X utf8 -m pytest <路径> -v --capture=no
       ├─ tests/conftest.py [session autouse]
       │    └─ 启动 mcpGateway/server_llm_base.py 子进程（LLM MCP，1.8B ollama），sleep 4s 就绪
       ├─ tests/unit / tests/integration / tests/e2e
       └─ tests/e2e/conftest.py [function autouse]
            ├─ a2a_bus.clear_all() 清队列
            ├─ 启动 _bill/_stat/_price/_finance_agent_worker 四个常驻 worker
            └─ 用例结束 cancel + gather
输出 → <路径>.log → read_file 回读
```

两个关键工程决策及原因：

1. **e2e 必须启动 4 个 A2A worker**（`tests/e2e/conftest.py`）：orchestrator 异步把子任务 push 进 `asyncio.Queue`，无人消费则 240s 超时。这是历史上 e2e 全红的首个根因，也是"评测环境本身必须正确"的教训——**评测体系不仅要测被测系统，还要防评测环境自身的错误**。
2. **LLM MCP 用 session 级 fixture 全局复用**：模型加载一次约数秒，逐用例启动会让 16 个 e2e 用例时长不可接受；session 级保证全部用例共享一个 LLM 实例，同时隔离单用例状态。

## 4. L2 检索质量评测层

### 4.1 为什么需要独立一层

系统回答质量的上限取决于检索质量：price_agent 判断物价贵不贵靠 `city_price` 确定性基准价表（白名单数据，非 RAG），plan 阶段的历史消费洞察靠长期记忆库（FAISS 语义检索）。**检索是子系统的内部能力，e2e 只能看到"最终回答对不对"，无法回答"是检索错了还是生成错了"**。因此单独建层，用信息检索标准指标（hit@k / recall@k / MRR@k）离线评测，无需 LLM 在线。

### 4.2 指标定义与"为什么选这三个"

| 指标 | 计算方式 | 回答的问题 |
|---|---|---|
| hit@k 命中率 | top-k 中是否出现期望结果 | "用户问得对，能不能问到东西"（最基本的可用性） |
| recall@k 召回率 | 多个期望结果中被找回的比例 | "该给的知识给全了没有"（多意图查询不丢信息） |
| MRR@k 平均倒数排名 | 首个命中位置倒数的均值 | "排得准不准"（答案是靠前还是要翻很久） |

三者缺一不可：只测 hit 会漏掉"找不全"；只测 recall 会漏掉"排序差"。本项目的 `evaluation/rag_recall_eval.py` 与 `memory_recall_eval.py` 按此三指标输出，每个指标还分 k=1/3/5 三档，刻画"深度"与"质量"的权衡。

### 4.3 评测集设计：防漂移与不可评估降级

- **GT 引用原文，不手抄**：期望结果直接 `import` 数据源元素（如 `from evaluation.seed_memory_data import MOCK_SUMMARIES as M`，期望项写 `M[0]`）。数据源增删改时，评测集自动感知，不会出现"期望值和真实数据悄悄不一致"的静默漂移。
- **不可评估降级**：期望项若不在当前索引（如向量生成失败被丢弃），标为"不可评估"，**不参与**指标计算，避免污染正确性度量；同时打印警告强制暴露同步问题。
- **查询保留口语化**：评测查询直接使用用户原始语句（如"哪个月份餐饮花的多"），不过度改写，如实反映真实检索难度。

### 4.4 输出规范：可定位问题

评测脚本输出三段式：**逐查询明细**（每条查询的命中标记与 top1 结果）→ **汇总指标**（三指标 × k 档位表格）→ **定位清单**（k=5 仍不命中的查询，标注"建议重点检查"）。

**为什么输出定位清单**：指标只能告诉你"变差了"，定位清单告诉你"差在哪几条查询上"，把评测从"打分工具"升级为"调试工具"，与 §1.2 的根因修复回路衔接。

## 5. L3 Agent 回答质量评测层（已实现：`evaluation/agent_answer_eval.py`）

> 当前状态：**已实现并产出基线**。评测集 12 条用例（单任务×4 / 多任务×3 / 边界×4 / 对抗×1），五维规则评分 + `db_accuracy` 数据正确性硬校验。文本维度基线：10/12 通过（83.3%），平均 9.33/10。`db_accuracy` 上线后 `single_bill_001` 因"回复满分但落库金额错误"降级为 FAIL（见 §5.7）。本节先讲评分规范（原补全规范），再讲本次新增的数据正确性校验。

### 5.1 为什么 pass/fail 不够

e2e 断言 `"记账成功" in final_reply` 只能区分"过了/没过"。但两个都过的回答质量可能天差地别：

- 回答 A："记账成功。金额 45 元，分类：购物。"（完整、准确）
- 回答 B："记账成功。"（关键参数丢失）

LLM 系统的评测必须**分维度打分**，量化这种差异，才能指导优化（prompt 迭代、容错增强、模型替换）的方向与幅度。

### 5.2 Rubric：五维评分表

针对记账理财业务定制，每维 0-2 分，满分 10 分：

| 维度 | 权重 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|---|
| 意图正确性 | 高 | 该记的没记 / 收入被记账 / 任务被漏规划 | 任务规划了但类型错（如 stat 判成 finance） | 完全正确 |
| 参数抽取 | 高 | 金额/类别/日期缺失或错误 | 部分正确（如金额对、类别错） | 全部正确且与原文一致 |
| 业务语义 | 高 | 金额幻觉（非原文数字）/ 统计结果虚构 | 数据真实但表述含糊 | 数据真实、来源可溯 |
| 格式完整 | 中 | 空回复 / 半截 JSON / 纯报错 | 有内容但缺关键信息（如无分类） | 完整回执含全部关键项 |
| 无幻觉 | 高 | 编造不存在的消费/金额/知识 | 轻微过界（如脑补用户没提的建议但无害） | 无任何编造 |

**权重说明**：意图、参数、语义、幻觉都是"高"，因为任何一个出错都意味着用户得到的是**错误信息**（比没信息更糟）；格式是"中"，因为格式问题至少可被用户发现。

### 5.3 评分方式：规则打分 + LLM-as-a-Judge

| 方式 | 适用维度 | 实现 |
|---|---|---|
| 规则打分 | 参数抽取、业务语义（金额）、无幻觉 | 用代码从 `final_reply` 正则抽取金额/关键词，与 GT 标注的期望金额比对。**确定性优先原则**，能用正则就不用模型 |
| LLM-as-a-Judge | 意图正确性、表述质量等开放式维度 | 把「用户输入 + 期望行为 + final_reply + rubric」发给大模型，要求按 rubric 输出 JSON 分数 |

**为什么混合**：规则打分可复现、零成本，适合"有明确对错"的维度（金额对不对）；意图与表述属于开放判断，只能交给 Judge。但 Judge 本身也是 LLM，会引入二次不确定性——因此**规则能判的绝不用 Judge**，且 Judge 输出需约束为严格 JSON 以利校验。

### 5.4 评测集规范（建议 JSON 结构）

```json
{
  "case_id": "single_bill_001",
  "category": "单任务/多任务/边界/对抗",
  "user_input": "晚饭38元帮我记一下",
  "expected": {
    "intent": "bill",
    "params": {"amount": 38.0, "category": "餐饮"},
    "must_contain": ["记账成功"],
    "must_not_contain": ["失败"],
    "no_hallucination": true
  },
  "skip_if_model": []  // 已知模型能力外的用例，显式声明而非静默跳过
}
```

**为什么必须写 `must_not_contain` 和 `no_hallucination`**：正样本只断言"该有的有"，负样本断言"不该有的没有"才能锁死红线（收入拦截、金额幻觉、报错泄露）。

### 5.5 报告输出规范

每次评测产出：

1. `eval_report_YYYYMMDD.json`：逐用例五维得分 + 总分 + 失败详情；
2. 控制台汇总：`通过率 / 各维平均分 / 最弱维度 Top3 用例`；
3. 定位清单：得分 ≤ 阈值的用例及其失败维度。

**为什么存档 JSON**：为 L4 的趋势对比提供数据源；面试展示时可直接给出"1.8B 模型下，通过容错增强将意图正确率从 X% 提升到 Y%"的量化证据链。

### 5.6 数据正确性硬校验（db_accuracy，A 方案）

**为什么必须加这一层**：五维 rubric 评的是"回复文本"，但记账系统最核心的真相在数据库里。"记账成功"四个字背后可能没有数据、或者数据是错的。本层让评测脚本直查真实 `bill.db`，把"文本对"与"数据对"解耦验证。

**三种校验类型**（写进每条用例的 `expected.db_verify`）：

| 类型 | 判定 | 对 pass 的影响 |
|---|---|---|
| `record`（记账写入） | 按 `[测试标记]` 查 `SELECT amount, category FROM bill WHERE remark LIKE '%标记%'`，金额/类别与期望一致（0 分：查不到记录 / 1 分：部分偏差 / 2 分：全对） | **硬校验**：不过则 FAIL |
| `no_record`（预期不写库） | 运行前快照 `MAX(id)`，运行后对比，预期不写库却新增记录 → 0 分 | **硬校验**：不过则 FAIL |
| `stat_sum`（统计一致性） | 抽取回复中的总支出数字，与 `SELECT SUM(amount) FROM bill WHERE 本月` 比对（软校验：DB 共享、历史数据不可控，只记录不阻断） | 软校验：仅记录 |

**设计决策**：
- `db_accuracy` 为**独立字段，不并入 10 分制**——保持与旧基线报告可比，同时让 pass 判定多一道门槛（`pass = 文本分≥8 且无红线且 DB 硬校验通过`）；
- 硬校验用 `[测试标记]` 定位自己写入的记录，**互不干扰、可精确归因**；
- 评测结束统一 `DELETE FROM bill WHERE remark LIKE '%测试标记%'` 清理，防止污染后续统计口径；
- `no_record` 用 `MAX(id)` 快照而非依赖标记，因为该场景预期"根本不该写"，标记不会存在；
- 每条用例跑完立即增量落盘，DB 校验异常也兜底为 0 分并记录 detail，不因校验器自身故障误判 pass。

### 5.7 数据正确性校验首轮实证（抓到 L3 文本层抓不到的问题）

抽样 3 条用例验证三种校验类型全部生效，并**立即抓到真实缺陷**：

| 用例 | 文本评分 | db_accuracy | 结论 |
|---|---|---|---|
| `single_bill_001` | 10/10（回复满分） | **1/2** | 回复"记账成功"，但落库金额是 **25.0 而非期望 38.0**——"文本对、数据错"实锤，且此前基线（仅文本断言）判定为 PASS |
| `single_stat_002` | 10/10 | 1/2（软） | 回复报总支出 32.0，DB 本月实际 SUM=238.0——统计数字疑似模型虚构，软校验记录偏差 |
| `boundary_no_record_cmd_008` | 7/10 | 2/2 | 本次未误记账（快照对比通过），失败纯属回复维度 |

同时 integration 数据层测试（§3.3）发现 `bill` 表缺失 CHECK 约束并已修复。**这验证了 A+B 方案的不可替代性：只评文本时 `single_bill_001` 是 PASS，加上数据校验后暴露为"回复满分但落库金额错误"，是求职叙事里最有说服力的"评测驱动修复"证据。**

## 8. 已知局限与演进方向

1. **L3 已落地，但基线暴露的真实缺陷未修**：`single_bill_001` 落库金额 25.0 vs 期望 38.0（金额抽取不稳）、`boundary_no_record_cmd_008` 偶发误记账（1.8B 对"花了X"脑补记账意图）、打车 30 元→餐饮的类别误判。下一步按评测定位修业务层，修完跑增量回归，形成"评测驱动修复"闭环。
2. **e2e 依赖真实模型**：1.8B 输出有随机性，个别用例存在"偶发红"风险。演进方向：引入固定 seed / 温度 0 配置 / 对统计类用例增加重试语义（重新跑一次而不是直接判负）。
3. **检索评测集规模偏小**：RAG 评测集约 13 组查询，记忆评测集约 10 组，覆盖面够演示但不够工程。演进：扩充到 50+ 并加入多意图、模糊语义、近义词干扰用例。
4. **无覆盖率门禁**：容错启发式代码缺少覆盖率硬约束。演进：对 §6 所列高价值模块设置 `--cov-fail-under`。
5. **LLM-as-a-Judge 的二次不确定性**：演进：双 Judge 投票或与规则打分交叉验证。
6. **统计数字一致性是软校验**：`stat_sum` 因 DB 共享、历史数据不可控只能"尽力比对"。演进：stat 用例改用独立 seed 库（跑前清空/快照重建），把软校验升级为硬校验——这也是统计准确性最终形态。
