# 14 · 意图层能力补齐与追问上移方案（梳理稿，未实施）

> **状态**：✅ **已实施**（2026-10-08：P0–P6 全部落地；L1 **463 → 480 passed**、`contract_check` FAIL 0）
> **日期**：2026-10-08
> **触发**：用户提出"我表达得比较模糊时，会直接规划失效、识别不到我想要的意图"
> **结论先行**：**在主 Agent 的 `plan_node` 内补齐「动作空间」——把追问 / 澄清 / 兜底从「失败后的兜底」升级为「与执行平级的一等动作」，由 `scope_check` / `confidence` / `missing` 三个状态信号驱动策略；①\~④ 全部落在 `plan_node` 一处，`task_plan` 结构与子 Agent 入参契约零改动。**

## 一、需求说明（要改什么）

### 1.1 三条真实诉求

| # | 用户输入示例 | 期望行为 | 现状 |
|---|---|---|---|
| **R1** | "我打算去KTV，选什么价位合适" | 识别为**消费决策咨询 / 或澄清**，不应硬跑比价 | ❌ **命中 `CONSUME_NOUNS` 里的 "KTV" → 判为"消费陈述" → 放行补 `price` → 缺金额 → 失败**，汇总层还可能编出"无法获取当地物价信息" |
| **R2** | "记午饭"（缺金额） | **主 Agent 提前追问**，不派发子 Agent | ❌ 先派发 `bill_agent` → 子 Agent 调 LLM 抽取 → 才发现缺金额 → 返回 `need_more_info`（**多烧 1\~2 次 LLM 调用/追问轮**） |
| **R3** | "帮我弄一下" / "那个怎么办" | 判明超出四基元范围 → 给**引导式兜底**（能力清单 + 示例） | ❌ 无"域外"判定，靠 `_is_consume_statement` 等关键词反推；兜底文案是固定单句，信息量少 |

### 1.2 用户已明确的设计原则（2026-10-08 拍板）

1. **四基元约束**：`bill` / `stat` / `price` / `finance` 是消费场景的**四个基本组成**，能覆盖大部分场景——**不新增意图类目**，改为加深映射能力。
2. **不做部分派发** —— 一轮内若有任一任务缺参，整轮不派发。
3. **不做 deps 感知追问状态** —— 依赖表 `TASK_CONTEXT_DEPS` 保持静态。
4. **追问完毕之后再派发**（全 barrier 策略）：追问 → 用户补充 → 下一轮重新规划派发。
5. **子 Agent 契约不变**：仍下发 `raw_segments: List[str]`，子 Agent 代码一行不动。

### 1.3 本方案不做什么（范围边界）

- ❌ **不改** `task_plan` 的数据结构（仍为 `Dict[任务类型名, 任务信息]`，`agents/orchestrator/nodes.py:1452-1459`）
- ❌ **不改** 子 Agent 的 `State` 与入参（`raw_segments` 类型与字段名不变）
- ❌ **不改** `dispatch_node` / `wait_result_node` / `_merge_deps` / `_has_cycle` / `collect_node`
- ❌ **不改** `TASK_CONTEXT_DEPS` 依赖表（`nodes.py:96`）
- ❌ **不做** 部分派发（完备任务先跑 + 缺参任务单独追问）
- ❌ **不做** Function Calling 化（`raw_segments` → 结构化参数，见 §2.3 讨论）
- ❌ **不做** 在意图层新增领域判断（如"吃了顿好的算不算一笔可分类餐饮消费"——那是子 Agent 的领域知识）

> **理由**：上述"不做"项的共同点是——**它们都会改「意图层 ↔ 下游」的契约**。
> 本方案的全部改动落在**契约之前**（`task_plan` 产生之前），因此影响面自然收敛在 `plan_node` 内（见 §五）。

## 二、架构结论

### 2.1 根因：动作空间里缺了 `ask`

```
【现状的隐式动作空间】≈ { execute(tasks), 失败兜底 }

    面对模糊输入 → 系统只有两条路：
        ① 硬猜一个任务去 execute（KTV 案例就是这条）
        ② 猜不出 → 走固定 block_tip 兜底
    → 没有"我主动决定先问"这个动作
```

**关键判断**：R1 的失败**不是"分类不准"**，而是：

- `_is_consume_statement`（`nodes.py:383-408`）的判据是「无记账指令 +（含金额 或 含消费实体词）」——
  **它分不清「已发生的消费」与「未发生的计划/咨询」**（`"KTV"` 在 `CONSUME_NOUNS` 中，`"打算"` / `"合适"` 不在任何排除表里）。
- 且系统**没有"域外检测"（OOD）环节** —— 关键词能判断"属于哪类"，但判断不了"在不在能力范围内"，因为**关键词没有语境**。

> **一句话**：**能力缺口在「动作空间的表达力」，不在「分类器的精度」。**

### 2.2 业界建模对照（设计依据）

| 业界建模概念 | 形式化表述 | 本方案落点 |
|---|---|---|
| **POMDP 的 Ask Action** | 动作空间含 `ask(slot)`，与 `execute` 平级 | 三分支中的"缺参 → 追问" |
| **DST（对话状态跟踪）** | 维护槽位填充状态 | 输出 `missing` |
| **Belief State** | 意图的概率分布 | 输出 `confidence` |
| **OOD Detection** | in-domain 二分类（独立研究领域） | 输出 `scope_check` |
| **Dialogue Policy** | 状态 → 动作的策略函数 | `plan_node` 的三段判定 |
| **Grounded Generation** | 生成必须 grounded 在事实 | 归一化"不新增事实"铁律 |

> 依据：任务型对话领域以 POMDP 为经典建模（Young et al., 2013）；OOD 检测为独立子领域
> （Zheng et al., IEEE/ACM TASLP 2020；arXiv 2609.00961 / 2108.12229）。

### 2.3 决策流水线（本方案的执行模型）

```
                    用户输入 + 会话历史
                            │
              ┌─────────────▼─────────────┐
              │  plan_node 单次 LLM 调用   │
              │  （一次性产出：状态 + 策略）│
              └─────────────┬─────────────┘
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
   scope_check=?       missing=?          confidence=?
        │                   │                   │
   out_of_scope         非空               < 阈值
        │                   │                   │
        ▼                   ▼                   ▼
   ┌─────────┐        ┌──────────┐       ┌──────────┐
   │ 动作①    │        │ 动作②     │       │ 动作③     │
   │ 引导兜底 │        │ 缺参追问  │       │ 候选澄清  │
   └────┬────┘        └────┬─────┘       └────┬─────┘
        │                  │                  │
        └──────────────────┴──────────────────┘
                            │
                   task_plan = {}  +  final_reply
                            │
                    goto collect_node（★ 不进编排）
                            │
              ─────────── 全部通过 ───────────
                            │
                    task_plan 非空
                            │
                    goto dispatch_node（编排，零改动）
```

**⭐ 关键**：动作 ①\~③ 的产出**全部是 `task_plan = {}`**，走 `final_reply` 旁路 ——
**`dispatch_node` 根本不会被调用**，这是"编排零改动"的结构性原因。

### 2.4 归一化（Query Rewriting）的定位与边界

**做**：口语 → 紧凑槽位表达（指代消解 / 术语对齐 / 时间归一），写入 `raw_segments` 的**内容**。

```
"那打车花了80块呢"  →  raw_segments = ["打车 交通 80元 是否偏高"]
（结构不变，仍是 List[str]；子 Agent 读取方式不变）
```

**❌ 不做**：**补出用户没说的"事实"**（金额 / 品类 / 城市）。

> **铁律（与 §3.5 参数落地校验配套）**：归一化只允许「重述 + 对齐」，**禁止新增事实**。
> 写进 `raw_segments` 的**数值型实体必须能在用户原文回溯到依据**；找不到 → 不写入 → 若因此缺必需参数 → 转动作②追问。

**⭐ 与 FC 范式的关系**：本方案的槽位表达本质是"文本化 Schema"。
将来若做 FC 化，只需把「文本槽位」换成「JSON 参数」——**改写逻辑可直接复用**，故本方案是通往 FC 的桥梁而非弯路。

### 3.3 `plan_node` 三分支（核心改动）

**插入位置**：`nodes.py:1385-1405`（现"顶层准入拦截分支"区域），**替代**现有的
`pre_check_pass → _is_force_bill → _is_consume_statement` 判定链。

| # | 分支 | 触发条件 | 动作 | 落点 |
|---|---|---|---|---|
| B1 | **OOD 兜底** | `scope_check == "out_of_scope"` | 回 Rich Fallback（能力清单 + 用法示例），`task_plan={}` | `nodes.py:1391` 之前 |
| B2 | **缺参追问** | `missing` 非空（**全 barrier**：任一任务缺参即整轮追问） | 回追问话术（优先用 `clarify_options`），`task_plan={}` | `nodes.py:1391` 之前 |
| B3 | **低置信澄清** | `confidence < INTENT_CONFIDENCE_THRESHOLD` | 回候选式澄清，`task_plan={}` | `nodes.py:1391` 之前 |

**判定优先级（自上而下，命中即返回）**：

```
① scope_check == out_of_scope        → B1（最优先：域外优先于一切）
② _is_force_bill(user_text)          → 放行（保留现有硬判断，防 OOD 误伤明确记账）
③ missing 非空                       → B2
④ confidence < 阈值                  → B3
⑤ 其余                               → 走原逻辑（prune → 封装 → dispatch）
```

> **⭐ 保留 `_is_force_bill` 的理由**：它是**代码级硬判断**（正则 + 词表），
> 与 LLM 的**软判断**（`scope_check`）互补。**软判断负责体验，硬判断负责正确性** ——
> 用户明确说"记打车35元"时，不应因模型偶发 `out_of_scope` 而拦下。
>
> **`_is_consume_statement` 的处置**：**降级为兜底**（不再作为主判据），
> 但**不删除** —— 它的两个放行语义（记账指令明确 / 纯消费陈述）仍需在
> `pre_check_pass=false` 的旧路径下兜底。见 §六 R-3。

## 四、改造顺序（依赖关系）

```
第 0 步（前置，独立可验证）
  C5  建 config/agent_contracts.json（契约表）
      └─ 验收：单测断言四基元 required 读取正确；bill 的 edit/delete 例外生效

第 1 步（最小闭环：解 R1 + R2，用户可感知）
  C1  schema_example 增 5 字段 + ignore_missing_keys 同步
  C2  解析 + 类型兜底
  C3  提示词 Schema 契约
  C6  新增两个配置常量
  B2  missing 非空 → 追问（全 barrier）
  B1  scope_check → OOD 兜底
  C7  _ask_round_key 扩展（预规划 key）
  └─ 验收：e2e「我打算去KTV，选什么价位合适」→ **不派发**、回追问（非失败）；
           e2e「记午饭」→ **不派发**、直接追问；KTV 回归用例通过

第 2 步（能力补强：解 R3 + 防编造）
  C4  提示词 4 类示例
  B3  confidence → 澄清
  C9  _verify_grounding 参数落地校验
  C10 金额补全降级为兜底
  └─ 验收：模糊口语归一化后派发成功；缺事实时给候选；归一化不产生原文没有的数字

第 3 步（收口）
  D1  回归：tests/unit 全量 + contract_check + 相关 e2e
  D2  回填 设计/11 §3 M16 验收记录；契约回写 设计_从零系列/09 §2.14
```

**顺序原则**：

1. **先契约表**（第 0 步）——它是 `missing` 判定的唯一依据，不先定则后续无法判"缺什么"；
2. **再最小闭环**（第 1 步）——OOD + 缺参追问直接解掉用户提的两条诉求，范围可控；
3. **后能力补强**（第 2 步）——归一化与置信度涉及提示词大改，独立排期；
4. **最后收口**——回归 + 契约回写。

### 6.1 实测反馈与修复（2026-10-08 用户真机验证）

**输入**：`我想买个去唱歌，预算花多少钱合适`
**首版输出**：`信息不全，请补充：price 缺金额（如「记 午饭 35」/「火锅 120 贵不贵」）`

**判定**：**追问机制本身生效了**（未硬跑比价任务，走了缺参分支）——M16 的核心目标达成；
但话术与语义存在三个缺陷，已修复两个、登记一个：

| # | 缺陷 | 性质 | 处置 |
|---|---|---|---|
| 1 | 话术暴露**内部任务名** `price`（用户看不懂） | 话术缺陷 | ✅ 已修：新增 `_TASK_LABEL` 中文标签（比价/记账/统计/消费分析），并加测试锁定「不得泄露内部名」 |
| 2 | 兜底示例写死无关场景（「记 午饭 35」），且**模型未输出 `clarify_options`** | 提示词缺陷 | ✅ 已修：提示词明确「缺参时**必须**给贴题候选」，并禁止承诺系统不具备的能力 |
| 3 | **语义错位**：用户问"该花多少"（预算咨询），系统问"你花了多少"（比价需金额） | **能力缺口** | ⏳ **登记为 M17 候选**（见下） |

**缺陷 3 的根因**：`price_agent` 的定位是**比价器**（需要"一笔已发生消费的金额"算溢价率，
前置拦截"无金额数字"直接失败），**不支持"无金额 → 返回品类均价参考"**。
故"预算多少合适"这类**无具体消费的价位咨询**，在现有四基元内**无对应能力**，
M16 只能做**优雅引导**，无法直接作答。

**M17 候选（建议）**：`price_agent` 增设分支——当**有品类、无金额**时，
查 `city_price` 取该品类本地均价，返回"该品类本地均价约 X 元"（不做溢价率判断）+ 引导补金额。
**收益**：把高频需求「我想去唱歌，预算多少合适」从"追问"升级为"直接给参考价位"；
**成本**：仅 `price_agent` 内部加分支，**入参契约不变**（不违反 `设计/14` §十 P-5）。
