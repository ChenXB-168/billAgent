# 第 1 部分 · Runtime 与架构

## Q1-1　Agent runtime 是怎么跑起来的？

**启动链路**（`startup/bootstrap.py` · `bootstrap_all()`）：

```
数据库连通校验 → 加载个人笔记索引 → 拉起 3 个 MCP 常驻服务（8001/8002/8003）
+ 健康检查 → 清理残留任务 → 崩溃恢复对账 → 注册 Agent 与 worker
```

**运行形态**：主进程单进程多协程 —— **1 个编排器协程 + 4 个常驻 worker 协程**（bill / stat / price / finance），彼此经 A2A 消息总线按 agent 分队列通信，**事件驱动唤醒、无轮询**。

**一次请求的链路**：

```
入口（CLI / Gradio）
  → 编排器 plan_node 规划（意图识别 → task_plan）
  → dispatch_node 按依赖 DAG 派发
  → worker 经 ToolRegistry 调工具
  → wait_result_node 收结果
  → collect_node 汇总 + 确定性预警 + 表达
```

**依据**：`README.md` §6

## Q1-2　为什么是「1 编排 + 4 子 Agent」，而不是一个大 Agent？

> 两个极端都不行：**提示词越大、意图边界越模糊，模型越容易漏任务或脑补任务**；而每个意图一个 Agent 又会让通信拓扑随数量膨胀。
>
> 1+4 换来的是**职责内聚、失败隔离、可单独替换与测试**。

**依据**：`README.md` §6

## Q1-3　子 Agent 为什么用协程，不用进程？

> 主进程不做重计算——推理在外部 API 或本地 Ollama，**IO 等待为主**，协程足以覆盖。进程化反而带来 IPC、状态序列化与数倍内存开销。

**依据**：`README.md` §11

**反向加分**：如果被追问"什么时候该进程化"——当 Agent 需要执行不可信代码、或单机算力不够时，才该拆进程。我的沙箱设计里已经预留了这个演进路径。

## Q1-4　任务之间的依赖关系怎么确定？LLM 在这里面做什么决策？

> 依赖表是 **「LLM 输出的 deps」∪「静态依赖表」** 取并集，再裁剪到本批任务内。
>
> 关键是一条**安全不变式**：**LLM 只能增加依赖、不能删除静态表依赖**。因为如果模型错误地说"统计不依赖记账"，就会导致本该串行执行的任务并行跑——统计拿不到刚记的账，结果就是错的。
>
> 如果 LLM 给出的依赖**成环**，会回退到纯静态表并**继续执行**，而不是终止。

**依据**：`agents/orchestrator/nodes.py` 的 `_merge_deps` / `_collect_llm_deps` / `_has_cycle`；对应测试 `tests/unit/test_orchestrator_parallel.py:154`（`test_merge_deps_static_cannot_be_removed`）与 `:190`（`test_plan_node_ring_from_llm_deps_falls_back`）

## Q1-5　一句话里有多笔记账怎么办？会不会派发多条任务？

> **只派发一条 `bill` 任务。**
>
> 这是我特意划的一条颗粒度分工线：**编排层按「任务类型」规划（每种类型至多一条），同一领域内的多次操作下沉到子 Agent 内部承接**。
>
> "记午饭30，记打车20" → 编排层只派一条 `bill`，子 Agent 内部按 `items` 逐笔抽取和兜底，最后用**单条多值 INSERT** 一次落库（原子：要么两笔都成、要么都不成）。
>
> 好处：编排层不必为"多次"展开成多个任务，`dispatch` / `wait_result` / 依赖图 / 环检测**全部无需改动**，而表达力完整保留。

**依据**：`README.md` §6「颗粒度分工」

# 第 2 部分 · 工具的定义与调用

## Q2-1　工具是怎么定义的？

> 统一契约 `ToolSpec`——**一处声明元数据**，就带上了：`params_schema` / `required_perm` / `protocol` / `timeout` / `max_retry` / `side_effect` / `auditable`。
>
> 工具被建模成**可管理资产**，而不是散落在各处的调用点。

**依据**：`mcpGateway/tool_model.py`

## Q2-2　工具调用的完整链路是什么？

`ToolRegistry.invoke(name, args, agent_id)` → `ExecutionEngine` 的 **9 步流水线**（`mcpGateway/executor.py`）：

```
①解析 ②鉴权 ③参数校验 ④前置审计 ⑤执行 ⑥重试 ⑦结果 ⑧后置审计 ⑨可观测打点
```

**协议差异（local / mcp）全部由 adapter 承担**，引擎内**零 MCP 特判**——这是"工具接入平台"能成立的前提。

**✅ 主动抛**：`executor.py` 顶部有一张「改造前 vs 收拢后」的对照表，这是讲"架构演进"的好素材：

| 能力 | 原本状态 | 收拢后 |
|---|---|---|
| 鉴权 | client.py 按 SQL 前缀粗判 | 按 `ToolSpec.required_perm` 静态判定 |
| 参数校验 | skills.py 手写 if | JSON Schema 统一校验 |
| 超时 | 仅握手超时，调用无超时 | 统一 `asyncio.wait_for(spec.timeout)` |
| 重试 | 硬编码 2 次，仅连接异常 | 按错误类型 + **副作用**决策 |
| 审计 | 各调用点手写，易漏 | 引擎内自动，不可能漏 |
| 可观测 | 无 | 引擎内打点 |

## Q2-3　参数怎么校验？非法参数怎么处理？

> 用 **JSON Schema（Draft7Validator）** 按 `ToolSpec.params_schema` 校验。
>
> 有一个刻意的设计：**只回传「按错误路径字典序排序后的第一条」错误**，而不是全部。原因是 JSON Schema 的全量错误列表**调用方和大模型都消化不了**——给 LLM 一堆错误反而干扰它修正；只给最靠前的一条更利于定位。
>
> 校验失败**不抛异常**，而是返回 `ToolErrorKind.VALIDATION`，在 FC 循环里以 observation 形式回填给模型，让模型自己修正（改参数 / 换目标 / 转追问）。

**依据**：`mcpGateway/executor.py:33` 的 `_validate_params`、`:129-133`

## Q2-4　编排器为什么不能直连数据库？

> 权限设计上，**编排器只有只读权限、零写权限**。读事实必须走工具层（`fact_tools`），写操作只可能发生在有职责的子 Agent 内。
>
> 这样做的收益是**从架构上消除越权写**——不是靠 review 保证，是"能力层面就不可能"。

**依据**：`mcpGateway/rbac_config.py` 的 `AGENT_PERMISSION_MAP`（编排器只有 `LLM_BASE` + `FACT_READ`）；`README.md` §7.2

# 第 3 部分 · Function Calling 与失败处理（面试主战场）

## Q3-1　Function Calling 场景里，模型选错工具怎么办？

**四道护栏，缺一不可**（`agents/bill_agent/nodes.py` · `_execute_fc`）：

| # | 护栏 | 做法 |
|---|---|---|
| ① | **可见面裁剪** | 工具清单由 `operate_sub_type` 经 tags 过滤得到——"改着改着顺手删了"在**能力层面**即不可能 |
| ② | **有界** | 最多 `FC_MAX_TURNS` 轮，达上限转追问（防无限试探） |
| ③ | **写幂等闸门** | 单次任务内**同一写工具只允许成功一次**，重复调用立即拦截并终止（防模型重复调 `bill.add` 造成重复记账） |
| ④ | **失败即 observation** | 工具报错回填给模型而非抛出，连续失败自然走到熔断转追问 |

**依据**：`agents/bill_agent/nodes.py:868-875`

## Q3-2　模型谎报成功怎么办？（✅ 主动抛，很能打动面试官）

> 循环的终态出口 `_fc_finalize` 里，**判定成功的唯一依据是「写工具真的成功过」**（`write_result` 非空）——**绝不允许凭模型文本报成功**。
>
> 因为实测过：**模型在没有对应工具时会回答"已记录"**，这是谎报成功。如果这里信了模型文本，用户会以为账改了，其实没改。

**依据**：`agents/bill_agent/nodes.py:792-800`（红线 7）

## Q3-3　为什么删除操作不走 Function Calling？（✅ 主动抛）

> **删除不受 FC 开关影响，永远走确定性路径。**
>
> 原因：删除**不可逆**，契约要求「先确认后删」；而如果交给模型自主循环，**模型会跳过确认直接调 `bill.delete`**——真库被删，用户没机会反悔。
>
> 这是"**安全优先，不可逆操作不给模型自主权**"的取舍。edit 是可逆的、且需要模型在候选里自主定位，所以保留 FC 路径。

**依据**：`agents/bill_agent/nodes.py:349-354`

## Q3-4　还有哪种情况会强制走确定性路径？

> **显式 id 的情况**。如果用户是点 UI 选中的（比如"把 id=515 那笔改成 60"），目标已由主键唯一确定，**不需要也不该**再交给模型自主定位。
>
> 为什么：FC 路径下模型会把 `bill.update` 的 tool_call 形态当**正文**输出（`{"name":"bill.update","parameters":{…}}`），**工具并未真正执行**——用户看到一段 JSON，而数据没改。确定性路径"给定 id 即改该笔"，行为可预期、可验收。

**依据**：`agents/bill_agent/nodes.py:339-348`

## Q3-5　调用失败怎么重试或降级？

**错误四分类**（`mcpGateway/executor.py` · `_execute`）：

| 异常 | 分类 | 是否重试 |
|---|---|---|
| `asyncio.TimeoutError` | TIMEOUT | 读工具可重试 |
| `ToolError` | 原样保留 | 看其 `retriable` 标记 |
| `CONNECTION_EXC` | CONNECTION | 读工具可重试 |
| 其他 Exception | INTERNAL | **不重试** |

**重试策略**：

- **有写副作用的工具永不自动重试**（机制层面防重复记账）；
- 指数退避 `min(2^attempt, 5)` → 1s / 2s / 4s / 5s / 5s…
- **已达上限不再 sleep**——否则最后一次失败会白等退避时长（M4 实测过这个坑）；
- `timeout <= 0` 表示**显式关闭超时**（支持按工具配置关闭）。

**依据**：`mcpGateway/executor.py:178-251`

## Q3-6　为什么按「副作用」而不是「幂等性」决定重试？（✅ 主动抛）

> 我最初想按**幂等性**判断，后来改成按 `spec.side_effect`。
>
> 理由：**幂等性需要业务语义判断，容易写错**；而"有没有写副作用"是工具元数据里的**静态声明**——在机制层面就杜绝了重复记账，不依赖每次业务判断是否准确。

**依据**：`mcpGateway/executor.py:232-244` 注释「★重试安全性由『副作用』决定，而非『幂等性』」

## Q3-7　有个 Python 层面的坑你可能想听（✅ 极加分）

> 异常捕获的**顺序是敏感的**：Python 3.11+ 的 `TimeoutError` 是 `OSError` 的子类，所以 **`asyncio.TimeoutError` 必须排在 `CONNECTION_EXC`（含 `OSError`）之前**，否则超时会被误判成连接故障。

**依据**：`mcpGateway/executor.py:223-224` 注释

## Q3-8　降级路径是什么样的？

**三层降级**（`设计/12` §4.7）：

```
FC 自主循环（P3b）→ 确定性驱动（P3a）→ 追问
```

- `BILL_FC_ENABLED=0` 时退回 P3a，**功能不丢**；
- 两条路径**共用同一批工具、同一份落库语义**，所以切换开关**不改变数据行为**；
- FC 通道异常（如 `call_llm_fc` 抛错）**不向图外抛**，一律转追问——把"通道坏了"如实告知用户。

**依据**：`agents/bill_agent/nodes.py:336-338`、`:899-901`

# 第 4 部分 · 记忆系统

## Q4-1　记忆是怎么设计的？

| 层 | 实现 | 位置 |
|---|---|---|
| **短期** | 进程内 dict：会话历史 + 草稿缓存 + 追问计数 | `memory/short_memory.py` |
| **长期** | FAISS `IndexFlatL2` + 原文落盘（pkl）+ **月度消费习惯语义摘要** + **12 个月滚动裁剪** + **双路混合检索**（向量 0.6 / 关键词 0.4，时间表达强信号加权） | `memory/long_memory.py` |
| **知识库** | 个人笔记库作为 RAG **唯一入口**，向量不可用时自动降级 BM25 | `memory/user_docs.py` |

## Q4-2　长期记忆怎么防止膨胀？

> **12 个月滚动裁剪**——只保留最近 12 个月的语义摘要，超出的裁掉。不做的话索引会无限增长。

**依据**：`memory/long_memory.py`；`腾讯PCG_SSP冲击可行性分析.md` §2.1

## Q4-3　向量检索不可用怎么办？

> **自动降级 BM25**，不中断服务。检索是"增强能力"，不该成为单点。

**依据**：`README.md` §11、§12

## Q4-4　记忆系统的启动性能做过优化吗？（✅ 主动抛）

> 做过一次**惰性加载重构**。原来 `import` 模块时会立即加载 embedding 模型（首次约 10s），拖慢启动。
>
> 拆成两步后：**读文本是纯 IO（毫秒级）**，**向量索引只在真正写/查向量时才触发模型加载一次并常驻**——纯记账或关键词检索路径不拖慢启动。

**依据**：`memory/long_memory.py:41-44`（2026-09-05 重构）

## Q4-5　短期记忆的边界在哪？

> 会话态在**进程内存**，重启即丢。这是明确的已知边界，跨进程方案（如 Redis + TTL）是后续演进方向。
>
> 另外追问有**轮次上限 3 轮**，达上限直接放弃并报错，不再追问——避免用户被无限追问。

**依据**：`README.md` §12；`BILLAGENT_ASK_ROUND_LIMIT=3`（`.env.example`）

# 第 5 部分 · 可靠性与 Durable Execution

## Q5-1　任务执行到一半服务重启怎么办？（新题必考）

> 我实现了一套基于 SQLite 的任务状态机：
>
> ```
> submitted → running → completed / failed / interrupted
> ```
>
> **关键设计是 `interrupted` 不作为终态**：进程启动时按 `task_id` 对账分流——业务表里已有记录 → 判定为 `completed`（**注意不是 failed**）；没有记录 → 回到 `submitted` 等待重投。
>
> 而且**只对有写副作用的 Agent 执行对账**（`SIDE_EFFECT_AGENTS`），避免无意义的全量扫描。
>
> 实测 `kill -9` 后重启可以恢复，重复投递不会重复记账。

**依据**：`README.md` §7.3、§8；`startup/task_manager.py`

## Q5-2　「执行完成」和「业务成功」是一回事吗？

> **不是，我明确做了区分**。`completed` 的判据是「worker 未抛异常」，不是"业务成功"——正常的业务拒绝（比如收入不入账）也算 `completed`，成败由 `result` 字段承载。
>
> 如果混为一谈，统计口径就错了。

**依据**：`README.md` §7.3 注 2；`startup/task_manager.py`

## Q5-3　`submitted` 状态为什么需要单独处理？

> `submitted` 是**数据库状态**，而 worker 只认**内存队列**——中间必须经过 `resubmit_submitted()` 重投，这一步在原始状态图里容易漏。
>
> 崩溃在「账单已写、状态未改」这一瞬间也不会重复记账：重启对账时发现 `bill` 表已有该 `task_id` 的记录，直接判定完成。

**依据**：`README.md` §7.3 注 1、注 4；`startup/task_manager.py`

## Q5-4　防幻觉怎么做的？

**三层防护**（`README.md` §7.1）：

```
汇总确定性事实（SQL / 数值计算）
  → 生成「数字白名单」
  → 提示词约束：只准引用白名单内的数字
  → LLM 生成表达文案
  → 抽取回复中的数字与白名单逐项比对
      ├ 全部命中 → 通过
      ├ 出现白名单外数字 → 第二层：修正重试 1 次
      └ 仍违规 → 第三层：回退本地确定性渲染（丢弃模型文案）
```

**底线是：绝不让模型编造的数字出现在用户面前。**

## Q5-5　白名单怎么实现？有没有误杀问题？（✅ 主动抛，很能体现细节功力）

> 白名单工具在 `utils/number_whitelist.py`，抽取数字时分三步：
>
> 1. **先剔除日期串**——避免 `2026-07-15` 被拆成 2026 / 07 / 15 三个假数字；
> 2. **再剔除列举序号**——`1.` `2、` 这种，但要限 1-2 位且后继非数字，**避免误伤小数 `1.5` 和金额**；
> 3. 最后正则匹配带可选负号与百分号的数字。
>
> 比对时容差 0.5，且判定是「**全量包含**」语义——只要有一个数字落不进白名单就整体不通过。
>
> **踩过一个真实的坑**：最初剔除序号的规则只处理**行首**序号，结果单行内 `1.…2.…` 这种列举序号漏网，被白名单闸门**误判为幻觉数字**，导致本该通过的回复被拦。修复后把剔除逻辑放宽到**句子边界**。

**依据**：`utils/number_whitelist.py:8-9`（修复历史）、`:14-19`（三个正则）、`:46-63`

## Q5-6　白名单有没有覆盖不到的边界？

> 有，我明确划了边界：**个人笔记里的数字是"用户陈述"而非"系统事实"**，不进白名单，引用时标注来源；与事实冲突时以事实为准并显式说明。

**依据**：`README.md` §7.1 边界说明

# 第 6 部分 · 安全防线

## Q6-1　权限体系怎么设计的？

四级权限枚举（`mcpGateway/rbac_config.py`）：

| 枚举 | 值 | 说明 |
|---|---|---|
| `DBPerm` | `bill:read` / `bill:write` | SQL 通道按 SQL 类型校验 |
| `LLMPerm` | `llm_base` / `llm_finance` | **通道级最小权限隔离**：两个 MCP 服务各校各的 |
| `FactPerm` | `fact:read` | 编排器取数"走正门"，替代裸连 DB |
| `HabitPerm` | `habit:read` / `habit:write` | 写权限下沉给 `bill_agent`（记账成功后顺手沉淀习惯） |

**编排器**只有 `LLM_BASE` + `FACT_READ`，**零写权限**。

**依据**：`mcpGateway/rbac_config.py` 的 `AGENT_PERMISSION_MAP`

## Q6-2　沙箱是怎么做的？（这题答好很加分）

> 我做的是**进程级资源限制的跨平台双轨实现**：
>
> - **Windows**：进程无法自我限制内存（没有 POSIX 的 `resource` 模块），所以由**父进程用 Job Object** 给子进程挂硬上限（`JOB_OBJECT_LIMIT_PROCESS_MEMORY`），超限直接被操作系统终止；
> - **POSIX**：无法事后约束已启动的子进程，所以 server 进程启动时 **self-prison**（`resource.setrlimit`），3 个 server 的 `__main__` 各调一次。
>
> **为什么必须做**：M3 常驻化之后失去了"短连接一次一进程"的天然隔离——**一个失控工具（爆内存 / 死循环）会拖垮整个 server，所有 Agent 一起挂**。
>
> **定位是"加固而非故障点"**：所有施加动作失败只告警、不阻断启动，可用性优先。

**依据**：`mcpGateway/sandbox.py:1-30`

## Q6-3　沙箱为什么不对 CPU 时间做进程级限制？（✅ 主动抛，体现思考深度）

> 因为**常驻 server 的 CPU 占用是正常工作属性**（uvicorn 并发服务），设 `RLIMIT_CPU` 会把正常长跑的 server 误杀。
>
> CPU 失控改由**引擎层工具级超时**承担（`ToolSpec.timeout`，async 可取消）——**分层治理：进程级管内存，调用级管时间**。

**依据**：`mcpGateway/sandbox.py:26-29`

## Q6-4　沙箱有覆盖不到的边界吗？

> 有，我明确记录了：**stdio 回滚模式**下 server 是由 `client.py` 按需 Popen 拉起的，**不经 bootstrap** → 不挂 Job Object。
>
> 该模式只用于联调排障，生产主路径是常驻 HTTP（沙箱生效）。

**依据**：`mcpGateway/sandbox.py:22-24`

# 第 8 部分 · 踩坑与架构演进

## Q8-1　你项目里最有价值的一次性能优化是什么？

> **消息总线从轮询改事件驱动。**
>
> 改造前是 `get_nowait() + sleep(0.1)` 轮询：消息到达后**平均要多等 50ms** 才被取走，空闲时还每秒空转 36 次。
>
> 改成 `await queue.get()` 后：消息到达即被唤醒，**零等待、零空转**。
>
> 我写了基准脚本做 A/B 对照（`bench/bench_a2a_latency.py`），300 次样本、同步往返 + 随机到达时刻：**P95 从 94.9ms 降到 0.10ms（约 954 倍）**，且 P50 47.6ms / P95 94.9ms / 平均 50.4ms 三个指标都与「100ms 轮询 + 均匀分布」的理论值（50 / 95 / 50 ms）吻合。

**依据**：`bench/bench_a2a_latency.py`、`README.md` §8

## Q8-2　改事件驱动时踩过什么坑？

> 踩过两个：
>
> **① 不能把不匹配的消息放回队尾。** 会话不匹配的消息如果放回主队尾，`await queue.get()` 会**立刻再取到同一条**，退化成 **100% CPU 忙循环**。改成旁路暂存（`_parked`）后解决。
>
> **② `asyncio.Queue` 跨事件循环复用会抛错。** `clear_all()` 原本是逐个 `get_nowait` 清空，但 Queue 在首次 `await get()` 时会**绑定所属 event loop**，跨 loop 复用会抛 `is bound to a different event loop`。改成直接**重建队列字典**——重建后的队列全新且未绑定任何 loop，测试与重启场景都安全。

**依据**：`mcpGateway/a2a_queue.py:43-45`（坑①）、`:75-79`（坑②）

## Q8-3　三项并发改造的顺序能颠倒吗？

> **不能，有严格先后依赖**：总线去轮询 → MCP 常驻化并拆全局锁 → 派发批量化。
>
> 因为**并发派发的收益必须建立在常驻与拆锁之后**，否则收益为零——如果 MCP 还是每次冷启动 26~29s，并行派发只会让多个任务同时等冷启动。

**依据**：`README.md` §7.5

## Q8-4　架构演进中最大的教训是什么？

> **可观测属于前置需求，不是后置优化。**
>
> 早期我是"零可观测"开发，结果参数语义不兼容、死代码、重试不分层这些问题**长期没有暴露**。后来加了 Tracer（`run_id` + span 树自动埋点）才看得见。
>
> 由此还定了另一条规矩：**任何兜底都必须告警 + 计数，禁止静默失败**。

**依据**：`README.md` §7.4

## Q8-5　MCP 从短连接改成常驻，是为什么？

> stdio 短连接**每次调用都要冷启动 26~29 秒**——这是不可接受的开销。改成常驻 HTTP 后，就绪时间约 6 秒**只付一次**，端到端耗时从 76.6s 降到 58.5s（**-24%**）。
>
> 但我保留了 `BILLAGENT_MCP_STDIO=1` 的**回滚开关**——架构改动必须留退路。

**依据**：`README.md` §8、§11；`.env.example` 的 `BILLAGENT_MCP_STDIO`

# 第 9 部分 · 高频追问（必须准备）

## Q9-1　「你这个是 workflow 还是 agent？」

> 我的设计哲学是「**代码锁框架，LLM 定内容**」——规划、表达交给 LLM，执行、校验、熔断交给代码。
>
> 对记账这种**高容错成本**的场景，确定性优先是对的：账错了用户会直接不信任这个产品。但我并不是"没有自主性"——编排层的**任务依赖是 LLM 决策的**，只要模型删不掉静态依赖；在编辑类任务里，**改哪一条、改成什么，也是模型在裁剪过的工具可见面内自主决策的**。
>
> 如果要服务开放域任务，我会把路由也改成 LLM 自主决策——这正是我把工具全部注册到 `ToolRegistry` 的原因。

**依据**：`README.md` §6、§7；`agents/bill_agent/nodes.py:336-343`

## Q9-2　「你做过微调吗？」（诚实回答）

> **没有实际落地微调。** 我试过本地小模型路线——用 Ollama 加载 1.8B 的模型，但实测在意图识别这类需要稳定结构化输出的环节做不了：JSON 输出不稳定，单次推理最长 189 秒，e2e 4 条用例跑了 36 分钟。
>
> 所以我**把编排和 Agent 的推理切到了外部大模型 API（智谱 GLM-4-Flash）**，本地小模型降为**可选离线 / 兜底通道**——不配任何 API 仍能跑通全流程。
>
> 我的判断是：**当前阶段工程可靠性比模型侧更重要**，所以我把精力投在了 Durable Execution、防幻觉、评测这些地方。模型侧（LoRA / 量化推理）是我明确的下一步。

**依据**：`README.md` 开篇、§6、§12

## Q9-3　「为什么不做 LLM 全自主决策？」

> 因为我的场景**容错成本高**。记账是"错了就有真实损失"的场景——幻觉一个数字，用户就对整个系统失去信任。
>
> 所以我把确定性放在执行层，把自主性留在决策层。**但我也不是全确定性**：任务依赖、编辑目标都是模型决定的。
>
> 更本质的原因是：**Agent 的瓶颈不在"能不能自主"，而在"自主之后靠不靠得住"**。我的项目就是在回答后半个问题。

## Q9-4　「你工作做驱动，为什么想做 Agent？」（必问）

> 我的职业主线一直是「用软件把需要专业判断的流程自动化」。
>
> 起点在本科：做电磁器件设计时，流程是先用仿真软件把设计跑通、再投硬件生产。我当时意识到这个流程可以被软件替代，甚至做到自动优化。硕士团队试过用神经网络做天线的全软件化设计，但方案停在中间态——因为**模型只会算，不会按工程流程办事**。
>
> 我们当时卡住的判断是：要让软件做硬件设计，它得先理解硬件设计的真实流程。**放到今天看，那就是要给 Agent 配一个领域 Skill。** 所以我去普联，想从生产制造侧把硬件设计的实际流程搞明白。
>
> 今年 Agent 技术成熟之后我对上了——它恰好是我一直在找的方案：Planning 拆解流程、Tool Use 调专业能力、Memory 维持上下文，再叠加工程化约束保证可靠。所以我做了这个项目，想亲手把那条链路走通。

## Q9-5　「这个项目最大的不足是什么？」（诚实版，主动说反而加分）

> 三个，我列得很清楚：
>
> 1. **单机单用户**——没有用户体系和服务端，数据在本地文件系统，没有真实并发压力；
> 2. **会话态在进程内存**——重启即丢，跨进程方案（Redis + TTL）是明确的演进方向；
> 3. **模型侧零落地**——微调、量化推理都没做，目前是纯应用层。
>
> 另外**影响力为零**——项目刚完成架构收口，开源和评测基线重建还在进行中。

**依据**：`README.md` §12；`项目现状评估.md` §4.1

## Q9-6　「这个项目能迁移到别的场景吗？」

> 能，它的核心能力是**领域无关**的：
>
> | 我做的 | 可迁移到 |
> |---|---|
> | 消费意图识别 | 内容 / 聊天意图识别 |
> | 月度消费习惯长期记忆 | 用户兴趣画像长期记忆 |
> | 账单数据管道 | 社交内容管道 |
> | 多 Agent 记账任务编排 | 内容审核 / 群运营 / 客服编排 |
>
> 我选记账是因为它**能单机完整闭环**，方便把工程和评测做扎实。领域可以换，能力是通用的。
