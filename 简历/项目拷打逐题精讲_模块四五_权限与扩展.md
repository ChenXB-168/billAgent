## Q13 · 权限机制 vs 约定

> **⭐ 这节的 L2 是最容易被"问穿"的一刀**，但**你恰好有一个别人没有的答案**。

### L1｜只有记账 Agent 能写账单——怎么阻止其他 Agent 写？ ✅

**答**：**工具层按 `required_perm` 静态鉴权**，在引擎的 9 步流水线第 ② 步执行。

**★权限画像（有测试锁定）**：

| Agent | 可见工具 | 关键差异 |
|---|---|---|
| **`orchestrator_agent`** | 仅编排相关 | **零写权限** |
| **`bill_agent`** | `bill.add` / `bill.delete` / `bill.update` / `sql.write` / `habit.upsert` … | **★ 唯一有 `sql.write`** |
| **`stat_agent`** | `bill.recent_list` / `llm.chat` / `sql.read` | **只读** |
| **`price_agent`** | 类似 stat | **只读** |
| **`finance_agent`** | `bill.recent_list` / **`llm.finance`** / `sql.read` | **只读 + 专用模型**（**无 `llm.chat`**） |

**★代码依据**：`tests/unit/test_tool_platform.py` 的 `test_list_tools_filters_by_permission` —— **每种权限画像的可见工具清单被完整断言，改动即测试红。**

**★知识点：「权限过滤即发现过滤」**

**这是他设计里一个很干净的点**：**没有权限的工具，模型根本看不到** —— 不是"看到了但调不动"，而是**在 `list_tools` 阶段就被剔除**。

```python
def list_tools(self, agent_id):
    return [s for s in self._specs
            if s.required_perm is None or s.required_perm in get_agent_permission(agent_id)]
```

**答法**：

> 分两层：
> **① 发现层**：`list_tools(agent_id)` 只返回**该 Agent 有权限的工具** —— 也就是**模型根本看不到它没权限的工具**；
> **② 执行层**：即使绕过发现层直接调，引擎在鉴权步骤会按 `ToolSpec.required_perm` 静态判定，**不通过就拒绝**。
>
> **权限画像是完整的**：`bill_agent` 是**唯一持有 `sql.write` 的**；`stat`/`price` 只有 `sql.read`；**`finance_agent` 更特殊——它只有 `llm.finance`，连通用的 `llm.chat` 都没有**。
>
> **而且这套画像是被测试锁定的**：`test_list_tools_filters_by_permission` 对每个 Agent 的可见清单做完整断言，**任何权限被改宽都会立刻测试红。**

### L2｜统计 Worker 代码里直接 `sqlite3.connect().execute('INSERT INTO bill...')` 能拦住吗？ ❌

**答**：**拦不住。** —— **但你有别人没有的补偿手段。**

**★先说清楚为什么拦不住**：

```python
# 如果 stat_agent 的代码里写了这段 —— 我的权限系统拦不住
import sqlite3
sqlite3.connect("bill.db").execute("INSERT INTO bill (...) VALUES (...)")   # ✗ 绕过网关
```

**原因**：**同进程内的 Python 代码可以绕过任何"逻辑层"的约束** —— 因为**权限检查是我自己写的代码，同进程的其它代码当然可以不走它。**

**★但我有这个**：

| 补偿手段 | 说明 |
|---|---|
| **源码级静态扫描测试** | 扫描源码，**出现越权写操作即测试红** |
| **`test_webui_source_contains_no_bill_write_calls`** | 扫描 `webUI/app.py` / `bill_panel.py`，**禁止出现账单写操作** |
| **契约漂移检测** | `test_contract_check.py` 对比设计文档与代码符号 |

**★答法（完整版，这段话要背）**：

> **拦不住。** 同进程内没有强制访问控制 —— **这是我这套权限模型的明确边界**：它是**逻辑层隔离**，不是 OS 级的机制强制。
>
> **但我用另一种方式守这条线**：**源码级静态扫描测试**。比如 `test_webui_source_contains_no_bill_write_calls` 会**扫描 `app.py` 和 `bill_panel.py` 的源码**，一旦出现账单写操作**测试直接失败**。
>
> **所以我的红线不是靠"人工 review 保证"，是靠 CI 拦住的。** 这个区别很重要：**review 会漏，但测试不会。**
>
> **如果将来要真正的强制隔离**，路径是**把 Worker 拆成独立进程 + 各自持有受限的数据库账号** —— 这样权限由**操作系统和数据库**强制，而不是我的代码。
> **代价是丢掉"零 IPC 开销"**（现在的 worker 和编排器在同进程、共享内存），**所以当前规模下没有做。**

**★知识点：为什么"同进程 = 无强制隔离"是根本性的**

**强制访问控制（MAC）需要"主体"和"客体"分属不同的保护域**：

| 隔离级别 | 谁能强制 | 代价 |
|---|---|---|
| **同进程（函数级）** | **只能靠代码自觉** ✗ | 0 |
| **同进程（进程内沙箱）** | 语言级沙箱（如 PyPy sandbox） | 大、受限 |
| **多进程** | **OS（不同 uid / 能力集）** ✓ | IPC 开销 |
| **多容器 / 多机** | **OS + 网络策略** ✓✓ | 部署复杂度 |

**他的选择是同进程** —— **代价是"逻辑隔离"，收益是"零 IPC 开销 + 简单"**。

**★知识点②：为什么"静态扫描"是个有效的补偿**

**它把"运行时的不可控"变成了"构建时的可控"**：

```
运行时：代码可能绕过网关（拦不住）
构建时：源码里出现越权写 → 测试红 → CI 拦住 → 代码进不了主干 ✓
```

**⚠️ 但要说清它的边界**：

> **静态扫描能防"写出来的越权代码"，防不了"动态构造的"**（比如 `eval("sqlite3.connect(...)")`）。
> **所以它是"工程约束"不是"安全机制"** —— 对个人项目的场景足够（防自己写错），**但如果是多租户系统，必须用进程隔离。**

### L3｜你的权限隔离是逻辑层约定还是机制层强制？ ❌

**答**：**逻辑层约定**（诚实）。

**答法见 L2** —— **关键是主动说出"这是约定"+"我有什么补偿"+"机制化要付什么代价"。**

**★知识点：三种隔离强度的对照表（可以直接给面试官）**

| 强度 | 机制 | 能否绕过 | 他的现状 |
|---|---|---|---|
| **① 文档约定** | 写在规范里 | **随时可以** | — |
| **② 代码约定**（他在这里） | 网关鉴权 + 静态扫描 | **能绕过，但会被测试拦住** | ✅ |
| **③ 进程隔离** | OS 权限（不同 uid） | **绕不过** | ✗ |
| **④ 数据层隔离** | 数据库账号权限（GRANT） | **绕不过** | ✗ |

**答法**：

> **逻辑层约定。** 更准确说是"**代码约定 + 静态扫描兜底**" —— 排在下面这张表的第 ② 档：
>
> | 强度 | 机制 | 能否绕过 |
> |---|---|---|
> | ① 文档约定 | 规范 | 随时可以 |
> | **② 代码约定（我在这）** | **网关鉴权 + 静态扫描测试** | **能绕过，但 CI 会拦住** |
> | ③ 进程隔离 | OS 权限 | 绕不过 |
> | ④ 数据库账号 | GRANT | 绕不过 |
>
> **我知道它不在最强档。** 但要升到 ③④ 档，**前提是拆进程** —— 那会丢掉现在的"零 IPC 开销"，**对单机个人项目来说不划算**。

### L4｜如果以后把 Worker 拆到独立进程——你的权限模型还能工作吗？ ✅

**答**：**能，而且会更强。**

**★答法**：

> **能，而且会更彻底。**
>
> 因为我的权限模型**核心是 `ToolSpec.required_perm` + 网关鉴权**，这套东西**不依赖进程模型** —— 工具调用本来就走网关（`executor.py` 的 9 步流水线），**拆进程后网关还是那个网关**。
>
> **而拆进程会额外带来两层强化**：
> ① **进程隔离**：worker 之间**不能再直接读写对方内存**，必须走消息总线（**这本来就是我的设计**）；
> ② **★ 数据库账号隔离**：每个 worker 进程可以**用不同的 SQLite 连接配置**，甚至（换 PostgreSQL 后）**用不同的数据库账号** —— **这样越权写会在数据库层被拒绝，而不是靠我的代码拦。**
>
> **所以拆进程对我来说是"补齐短板"，不是"推倒重来"。** 我的架构本来就是"进程边界清晰"的（4 个 worker + 3 个 MCP 服务），**只差把 worker 也搬出去**。

**★知识点：为什么"网关模式"天然适合拆进程**

**因为网关已经把"调用入口"收敛成一个点了**：

```
现在：worker 协程 → 网关（同进程函数）→ MCP / 本地工具
拆分：worker 进程 → 网关（IPC / RPC）  → MCP / 本地工具
                    ↑ 只是传输方式变了，接口不变
```

**对比**：如果权限检查**散在每个 worker 里**（没有网关），拆进程时要改 N 处。**收敛到一个点之后，拆进程只改网关的传输层。**

### L5｜记账 Worker 自己被攻破（比如代码注入）怎么办？权限模型还有效吗？ ❌

**答**：**无效**（诚实的答案）。

**★答法**：

> **在同一个进程内，代码注入是"上帝视角"** —— 它可以**直接改 `AGENT_PERMISSION_MAP`**、直接连数据库、甚至直接改内存里的任务状态。**这种情况下我的权限模型完全失效。**
>
> **所以答案是"防不住"，但我能说清"什么情况下会防不住"+"要防住需要什么"**：
>
> **要防住代码注入，必须在"被注入的东西"之外建立信任边界**：
> ① **进程隔离** —— 被注入的进程**只能用自己那份受限凭证**去连数据库；
> ② **数据库账号** —— 即使进程被完全控制，**它能做的也只有这个账号被 GRANT 的事**；
> ③ **沙箱** —— 限制系统调用（我的项目里对**工具层**做了沙箱，**但没有对 Agent 代码做**）。
>
> **我的项目里其实有一个相关实践**：**工具执行有超时 + 内存上限的沙箱**（`test_sandbox.py` 验过"死循环工具被拦、爆内存工具被 OS 杀、服务本身存活"）。**但那是对"工具"的防护，不是对"Agent 代码"的防护。**

**★知识点：信任边界（Trust Boundary）的概念**

**信任边界之外的东西不能相信**：

```
同一进程内：所有代码共享同一个信任域 → 一处被攻破 = 全部沦陷
跨进程：    每个进程是独立信任域 → 攻破一个只影响一个
```

**"代码注入"这个问题的答案永远是"看信任边界画在哪"。**

**★顺便：他在工具层做了沙箱** —— 这是个可讲的点：

| 防护对象 | 机制 | 测试 |
|---|---|---|
| **工具执行** | 超时（`asyncio.wait_for`）+ 内存上限（Job Object） | `test_sandbox.py` 6 用例 |

### L6｜你做了操作审计吗？谁在什么时候调了什么工具——有日志吗？ ✅✅

**答**：**做了，而且在引擎层自动执行**（业务代码零介入）。

**★知识点：审计的"自动 vs 手写"是分水岭**

| 做法 | 问题 |
|---|---|
| **各调用点手写审计** | **必然漏**（新增工具时忘了写、异常路径跳过） |
| **引擎层自动审计**（他用的） | **不可能漏** ✓ |

**★代码依据**：`ToolSpec.auditable` 是**元数据声明**，引擎按它决定要不要审：

```python
auditable: bool = True           # 是否记审计日志，默认 True
# llm.chat 设 False 以对齐现状（现状不审 LLM）
```

**★审计落日志**：`memory/user_docs.py` 里的 `AUDIT_LOG_PATH`（格式 `时间 | 级别 | 模块 | 操作 | 明细`）✓

**答法**：

> 做了。**而且不是在调用点手写，是在工具引擎里自动做的** —— 这是关键区别。
>
> **我的 `ToolSpec` 有个 `auditable` 元数据**，引擎在执行前后按它决定要不要写审计。**所以业务代码完全不用管审计** —— 新增一个工具，只要声明 `auditable=True`，审计自动生效。
>
> **为什么强调"自动"**：**手写审计必然会漏** —— 新增工具时忘了写、异常路径跳过了、或者某个人觉得"这个不用审"。**把它放到引擎层，这些漏洞都不存在。**
>
> **另外我明确知道审计的边界**：**审计是"事后追溯"，不是"事前阻止"** —— 它能告诉你"谁在什么时候做了什么"，**但不能阻止它发生**。阻止是鉴权的职责。**两者是互补的。**

## Q14 · 工具网关

> **⭐ 这是你的强项区** —— `executor.py` 的 9 步流水线是硬货，
> **而且代码里有"改造前 vs 收拢后"的对照表**，是现成的面试素材。

### L1｜网关是独立进程还是同进程函数？Worker 能绕过吗？ ⚠️

**答**：**同进程函数**；**理论上能绕过，但实际不会**。

**★答法（诚实 + 说清为什么不绕）**：

> **同进程的函数层，不是独立服务。** 所以**理论上 worker 可以绕过它直接调工具** —— **但我的 worker 拿不到工具函数本身**。
>
> **机制是这样**：worker 执行子图时，**图里的工具调用走的是 `mcp_client` / 本地工具注册表**，**而不是直接 import 某个函数**。**工具函数被封在 `binding` 里**，只有引擎能拿到。
>
> **所以"绕过"意味着"自己重写一份工具实现"** —— 那已经不是绕过了，是另一套代码。
>
> **如果拆成独立进程（网关服务化）**，绕过就变成"网络可达性"问题，**那才是真正的强制边界**。

**★知识点：同进程"包一层函数"和"独立网关"的区别**

| | 同进程函数层 | 独立网关服务 |
|---|---|---|
| **调用开销** | **几乎为 0** | IPC / RPC 开销 |
| **能否绕过** | **理论上能**（但要有替代实现） | **不能**（除非有网络凭证） |
| **可观测** | 进程内埋点 | **独立可监控** |
| **适用** | 单机 ✓ | 多服务 |

**他的选择是同进程** —— **对单机场景是对的**（收益是零开销，成本是"非强制"）。

### L2｜网关做了什么？参数校验？权限判断？耗时统计？链路追踪？ ✅✅

**答**：**9 步流水线，全做了。**

**★9 步流水线**（`mcpGateway/executor.py`）：

```
① 解析工具名 → ToolSpec
② 鉴权（按 required_perm 静态判定）
③ 参数校验（JSON Schema）
④ 前置审计（auditable=True 时）
⑤ 执行（适配器分发：local / mcp / http）
⑥ 重试决策（按 side_effect + 错误分类）
⑦ 结果处理
⑧ 后置审计
⑨ 可观测打点（trace_span）
```

**★而且有"改造前 vs 收拢后"的对照表**（`executor.py` 开头注释）：

| 能力 | 原本状态 | 收拢后 |
|---|---|---|
| **鉴权** | `client.py` 按 SQL 前缀粗判 | 统一按 `ToolSpec.required_perm` 静态判定 |
| **参数校验** | `skills.py` 手写 if | JSON Schema 统一校验 |
| **超时** | 仅握手超时，调用无超时 | 统一 `asyncio.wait_for(spec.timeout)` |
| **重试** | 硬编码 2 次，仅连接异常 | **按 kind + 副作用决策** |
| **审计** | 各调用点手写，易漏 | **引擎内自动，不可能漏** |
| **可观测** | 无 | 引擎内打点（天然挂载点） |

**★知识点：这张表本身就是最好的答案**

**它回答了"网关到底做了什么"** —— 而且**每一项都对比了"原本怎样"**：

```
原本：鉴权靠 SQL 前缀粗判 → 现在：按权限枚举静态判定
原本：参数校验各写各的   → 现在：JSON Schema 统一
原本：调用无超时        → 现在：统一 wait_for
原本：重试硬编码 2 次    → 现在：按副作用决策
原本：审计手写易漏      → 现在：引擎自动
原本：无可观测          → 现在：引擎打点
```

**答法**：

> **9 个步骤，基本覆盖了工具调用需要的一切治理**：解析、鉴权、参数校验、前置审计、执行、重试决策、结果处理、后置审计、可观测打点。
>
> **我想强调的不是"我做了 9 件事"，而是"这些问题原本散在各处"**：
> 鉴权原来是在 `client.py` 里**按 SQL 前缀粗判的**（`SELECT` 开头就当读、`INSERT` 开头就当写）——这明显不可靠；
> 参数校验原来是**各 skills 里手写 `if`**；
> 调用**根本没有超时**；重试是**硬编码 2 次、只对连接异常生效**；审计是**各调用点手写、必然漏**。
>
> **收拢到引擎后，这些能力变成"自动的"** —— 新增工具不用管鉴权校验审计，**只要声明元数据**。

### L4｜MCP 服务返回 500——网关怎么处理？重试？降级？超时设的多少？ ✅✅

**答**：**错误四分类 + 按副作用决定重试 + 超时按工具类型配置。**

**★错误分类**：

| 类别 | 是否重试 | 理由 |
|---|---|---|
| **TIMEOUT** | ✅（读工具） | 可能只是慢 |
| **CONNECTION** | ✅（读工具） | 可能只是暂时不可达 |
| **VALIDATION** | ❌ | **参数错了，重试多少次都一样** |
| **INTERNAL**（500） | ❌ | **可能已经执行了一部分** |

**★超时按工具类型配**（`ToolSpec.timeout`）：

| 工具类型 | 超时 | 理由 |
|---|---|---|
| **SQL 工具** | 30 s | 数据库操作应该快 |
| **LLM 工具** | **300 s** | **本地 CPU 推理可能很慢** |
| 默认 | 120 s | — |

**★退避策略**：指数退避 `min(2^attempt, 5)`

**答法**：

> 分三层：
>
> **① 错误分类**：我把错误分成四类 —— **超时、连接失败、参数校验失败、服务内部错误**。
> **② 重试决策**：**只有前两类且工具是"读操作"时才重试**；参数错误重试没意义；**内部错误（500）不重试，因为它可能已经执行了一部分**。
> **③ 超时按类型配**：SQL 工具 30 秒，**LLM 工具 300 秒** —— 因为本地 CPU 推理可能很慢，**用统一超时会把正常调用误杀**。
>
> **退避用的是指数退避**：`min(2^attempt, 5)` 秒，**封顶 5 秒**避免等太久。

**★知识点：为什么"500 不重试"是对的**

**HTTP 500 只说明"服务端出错了"，不说明"操作没生效"**：

```
场景：INSERT 语句执行成功 → 返回结果时服务崩了 → 客户端收到 500
如果重试：INSERT 再执行一次 → 重复写入 ✗
```

**这就是为什么"重试的前提是幂等"** —— 而**写操作不幂等**，所以**不重试**。

### L5｜网关本身挂了——Worker 还能调工具吗？有降级方案吗？ ⚠️

**答**：**网关是函数层，不是独立服务，"网关挂了"这个故障域不存在** —— **但如果网关代码抛异常，工具调用会失败。**

**★答法（先纠正问题的前提 + 再说真实的风险）**：

> **网关在我的实现里是函数层，不是独立服务** —— 所以**不存在"网关进程挂了"这个故障域**。
>
> **但真实的风险是"网关内部抛异常"**：如果没有兜住，**整个工具调用链会断**。
>
> **我的处理是分层兜底**：
> ① **网关内部**：9 步流水线的每一步都有异常处理，**校验失败返回结构化错误而不是抛异常**；
> ② **调用方**：编排器和子 Agent 对工具失败有**降级路径** —— 比如 `stat_agent` 的 SQL 失败会转成 `success=False` 的结果，**主流程继续**；
> ③ **Tracer 层**：可观测打点**自身异常永不阻断主链路**（有专门的测试锁定：`test_tracer_never_blocks_pipeline`）。
>
> **所以我的原则是"可观测和治理层不许成为单点故障"** —— 治理失败不应该让业务失败。

**★知识点：横切关注点（Cross-cutting Concern）的可用性设计**

**治理层（鉴权/审计/追踪）是"横切"在所有调用上的** —— **它一旦不可用，影响面是 100%。**

| 设计选择 | 影响 |
|---|---|
| **治理失败 → 阻断业务** | **治理层成为单点故障** ✗ |
| **治理失败 → 降级继续 + 告警** | 业务不受影响 ✓ |

**他的原则是后者** —— 代码里多处能印证："习惯沉淀静默失败（不阻断记账）"、"Tracer 自身异常不阻断主链路"、"校验异常跳过直发"。

### L6｜写操作不自动重试——为什么？因为会重复写入？那读操作重试吗？ ✅✅

**答**：**按"副作用"而非"幂等性"判定；写工具永不自动重试，读工具可重试。**

**★代码依据**：

```python
side_effect: bool = False        # 写副作用 → 前置审计 + ★永不自动重试（D2 防重复记账）
idempotent: bool = True          # 结果是否确定（语义标注，★不参与重试闸门判定）
```

**★注意这里有一个很细的设计**：**`idempotent` 存在，但刻意不参与重试判定。**

**★为什么用 `side_effect` 而不是 `idempotent`**（这是个可以深挖的点）：

| | `idempotent`（幂等） | `side_effect`（副作用） |
|---|---|---|
| **定义** | 执行多次结果相同 | **执行会对系统产生改变** |
| **判定重试** | **理论上更精确** | **保守但安全** |
| **风险** | **推理错一次就出事** | 少重试几次，**只是慢** |

**答法**：

> **写操作永不自动重试** —— 因为**重试可能导致重复写入**。
>
> **判定依据是 `side_effect` 而不是 `idempotent`**，这一点我想说明：
> 我的 `ToolSpec` 里**两个字段都有**，但**重试只按 `side_effect` 判定，`idempotent` 不参与**。
>
> **为什么**：**"幂等"是需要在脑子里推理的** —— 比如"`UPDATE ... SET amount=? WHERE id=?` 是幂等的吗？" 答案是"**看情况**"（如果中间有别的 UPDATE 改过 id，就不幂等了）。**推理错一次就是重复写账。**
>
> **而 `side_effect` 是个保守的粗粒度标记**："这个工具会不会改数据？" —— **不确定就标 True，不重试只是慢，不会错。**
>
> **所以我的规则是**：**用"会不会改数据"这个保守判据来换安全**，而不是用"是否幂等"这个精确但易错的判据。

**★知识点：这是"宁可少做不可做错"在重试策略上的体现**

**和他整个项目的一贯取舍一致**：

```
"不可逆操作宁可失败也不误做"
  ├─ 写任务默认不重投（retriable=0）
  ├─ 写工具永不自动重试（side_effect=True）
  ├─ 无写成功绝不报成功（FC 循环红线）
  └─ 删除必须二次确认
```

**这四条是同一个原则的四个实例** —— **能说出这个统一原则，比罗列四条规则强得多。**

## Q15 · 防幻觉的边界

### L1｜"约50块"怎么处理？正则提取到 50，SQL 算出来 49.5，在不在白名单？ ⚠️

**答**：**不在** —— **白名单是精确匹配，没有容差。**

**★代码依据**：`utils/number_whitelist.py`

```python
def extract_numbers(text) -> set[float]:
    """三步：剔日期 → 剔列举序号 → 正则匹配数字"""
```
**比对是集合成员判断（精确相等），不做范围匹配。**

**⚠️ 所以 `50` vs `49.5` 会被判为幻觉** —— 即使它们语义上接近。

**★知识点：这里是"精确匹配"还是"容差匹配"的权衡**

| 方案 | 优点 | 缺点 |
|---|---|---|
| **精确匹配**（他用的） | **不可能放过真幻觉** ✓ | **可能误杀"约50"这类合理表述** ✗ |
| **容差匹配** | 减少误杀 | **容差多大？谁定？** → 引入新的主观性 |

**答法（诚实 + 说清这个选择的两面）**：

> **不在白名单** —— 我的白名单是**精确匹配，没有容差**。
>
> **"约50块"提取到 50，SQL 是 49.5 → 判为幻觉 → 触发修正重试。**
>
> **我知道这会误杀**：模型说"约50块"其实是个**合理的四舍五入表述**，不应该被判幻觉。
>
> **但我仍然选了精确匹配，理由是**：**容差匹配需要定"容差多少"，而这个阈值是主观的** —— 定 0.5 还是 1？金额 1000 和 100 应该用同一个容差吗？**一旦引入阈值，就引入了"什么算幻觉"的模糊地带。**
>
> **我选择的是"宁可误杀、不可放过"**，因为**误杀的代价是"多一次重试"**，而**放过的代价是"用户看到一个假数字"**。
>
> **改进方向**：如果要减少误杀，可以**在 prompt 里明确要求"不得四舍五入、必须引用精确值"** —— **用约束模型输出代替放宽校验**。

**★知识点：这个"用 prompt 约束代替放宽校验"的思路很关键**

**防幻觉有两条路**：

```
① 放宽校验（容忍"约50"）→ 但校验就变弱了 ✗
② 约束输出（要求说"49.5"）→ 校验保持严格 ✓
```

**他选了 ②** —— **这是"把问题推到上游"的典型思路**（和"金额全部由 SQL 产出、模型只做语言组织"是同一个原则）。

### L2｜白名单是精确匹配还是范围匹配？范围多少？谁定的？ ✅

**答**：**精确匹配，没有范围。**

**★知识点：`_DATE_RE` 和 `_ORDER_RE` 这两个预处理很有意思**

**抽取数字前要先剔除两类"假数字"**：

```python
# ① 日期："2026-07-15" 会被拆成 2026 / 07 / 15 三个假数字
_DATE_RE = re.compile(r"\d{4}[-/年]\d{1,2}[-/月]\d{1,2}日?|...")

# ② 列举序号："1." "2、" 会被提取成数字
_ORDER_RE = re.compile(r"(?m)(?:^|(?<=[。；;：:！？\s]))\s*\d{1,2}[.)、](?=\s*[^\d\s])")
```

**★注意 `_ORDER_RE` 的两个细节**：

| 细节 | 作用 |
|---|---|
| **限定 1-2 位** | **不误伤金额**（`123元` 不会被当序号） |
| **后继非数字** | **不误伤小数**（`1.5` 的 `1.` 不被当序号） |

**答法**：

> **精确匹配，没有范围。**
>
> **但抽取这步有两个容易踩的坑，我专门处理了**：
> ① **日期**："2026-07-15" 如果不先剔除，会被拆成 **2026、07、15 三个假数字**，全部进入白名单；
> ② **列举序号**：模型输出"1. xxx 2. xxx"时，`1` 和 `2` 会被当数字提取 —— 而这些**不是业务数字**。
>
> **第二个坑的处理有个细节**：我把序号正则限定为"**1-2 位 + 后继非数字**"，就是为了**不误伤小数（`1.5`）和大额金额**。

**★知识点：抽取型校验的"假阳性"问题**

**任何"从文本抽特征"的方案都要先处理"表述噪音"**：

| 噪音类型 | 例子 | 处理 |
|---|---|---|
| **格式混淆** | 日期被拆成数字 | **先剔除日期模式** |
| **结构性标记** | 序号、列表符号 | **按位置+长度约束剔除** |
| **单位后缀** | "50元" vs "50%" | 保留（都是数字，语义靠上下文） |

### L3｜模型输出中文数字（"五十"）覆盖了吗？ ❌

**答**：**没覆盖，这是已知盲区。**

**★知识点：为什么这是个真问题**

```python
_NUM_RE = re.compile(r"-?\d+(?:\.\d+)?(?:%|％)?")     # ← 只匹配阿拉伯数字
```

**所以模型只要用中文数字，就能绕过白名单**：

```
模型输出："这笔消费大概五十元"    → 白名单提取到 0 个数字 → 校验通过 ✗
```

**⚠️ 风险等级**：中等（**因为模型输出以阿拉伯数字为主**，但不排除偶发）。

**答法（诚实 + 说清风险 + 给出补法）**：

> **没覆盖，这是已知漏检。** 我的数字抽取只用正则匹配阿拉伯数字，**中文数字（"五十""一百二"）不会被识别为待校验数字**。
>
> **风险是**：**模型可以用中文数字绕过白名单校验** —— 虽然当前模型输出以阿拉伯数字为主，**但这个口子是真实存在的**。
>
> **补法是**：**加一层中文数字归一化**（"五十" → 50、"一百二" → 120），把归一化后的数字并入白名单集合。**中文数字解析规则明确、不难做**，我把它排在"还没做"的清单里。
>
> **另外我想说明为什么这个漏检在实践里没暴露**：**因为我的 prompt 明确要求"引用精确数值"**，而且**素材本身是 SQL 产出的阿拉伯数字** —— 模型大部分情况下是**复制素材里的数字**，而不是自己转换。**但"大部分情况"不等于"覆盖"，这是缺口。**

**★知识点：白名单的"完整性"取决于"抽取能力"**

**白名单的强度 = 抽取的覆盖率**：

```
抽取覆盖率 100% → 白名单不可能漏
抽取覆盖率 80%  → 20% 的数字形态可以绕过 ✗
```

**所以"白名单"这件事的本质是"你能把模型可能输出的所有数字形态都抽出来吗"** —— 阿拉伯数字、中文数字、百分比、带单位的、带千分位的……

**他的抽取覆盖了"阿拉伯数字 + 百分号"，漏了"中文数字"。**

### L4｜模型输出"五十多"——提取到 50 还是 51？范围匹配能覆盖吗？ ❌

**答**：**都提取不到**（因为中文数字不识别）。

**★答法（承接 L3 + 说清"模糊表述"的处理原则）**：

> **都提取不到** —— 因为中文数字根本不进抽取流程。
>
> **而且即使我做了中文数字归一化，"五十多"仍然是个难题**：它**既不是 50 也不是 51**，而是一个**区间**。
>
> **这类"模糊量词"的处理原则是**：**要么归一化到一个点值，要么直接判为"不可校验表述"并拒绝。**
>
> **我倾向后者** —— **因为"五十多"本身就不该出现在我的输出里**：我的 prompt 要求**引用精确数值**，用户看到的应该是"49.5 元"这种可溯源的值，**而不是"五十多"**。
>
> **所以正确的解法不是"让白名单支持模糊匹配"，而是"约束模型不要输出模糊表述"** —— **校验层放宽是治标，约束输出才是治本。**

**★知识点：这一层又回到"防幻觉的两条路"**

```
治标：放宽校验（支持"五十多"）→ 校验能力被削弱
治本：约束输出（要求精确值）  → 从源头消除模糊表述 ✓
```

**能连贯地说出"治标 vs 治本"，说明你理解这类问题的解法层次。**

### L5｜如果模型输出完全不在白名单里——你拒绝后怎么处理？重试？降级到人工？ ✅✅

**答**：**三层降级：修正重试 1 次 → 仍违规则回退本地确定性渲染。**

**★代码逻辑**（`collect_node` 的汇总路径）：

```python
if EXTERNAL_LLM_ENABLED:
    # ① 生成回复
    # ② 过白名单闸门
    #    越界 → ③ 修正重试一次（把越界数字告诉模型，让它改）
    #    仍越界 → ④ 回退 _render_local_final()（确定性渲染，不经过模型）
else:
    # 本地模式直接确定性渲染
    final = _render_local_final(text_blocks, alert_facts, remind_pref)
```

**★三层降级**：

| 层 | 动作 | 结果 |
|---|---|---|
| **① 首次生成** | LLM 按汇总提示词生成 | 大部分情况通过 ✓ |
| **② 修正重试** | **把越界数字反馈给模型，要求重写一次** | 多数能修正 |
| **③ 回退渲染** | **完全不走模型**，用确定性模板拼接 | **100% 安全** ✓ |

**答法（★这段是 Q15 的核心，要讲清"为什么三层"）**：

> **三层降级，而且第三层是"彻底不用模型"**：
>
> **① 首次生成**：LLM 按汇总提示词生成回复；
> **② 白名单校验**：抽取出回复里的所有数字，逐个和白名单比对；
> **③ 越界处理**：
> - **先修正重试一次** —— 我把越界数字反馈给模型，让它重写；
> - **仍越界 → 回退本地确定性渲染** —— **这层完全不经过模型**，用 SQL 结果直接拼模板。
>
> **为什么最后一层是"不用模型"而不是"再试一次"**：**因为如果模型连续两次都无法遵守约束，说明它不可靠** —— 这时候**再重试是浪费，直接降级到"不可能出错"的路径才是对的。**
>
> **而且这个降级是无缝的**：用户看到的是**同一份数据**（都来自 SQL），**只是表达方式从"模型组织"变成"模板渲染"** —— **数字的准确性完全一样。**

**★知识点：降级链设计的核心原则**

| 原则 | 说明 |
|---|---|
| **逐级降低"能力"** | 模型生成 → 修正重试 → 模板渲染 |
| **逐级提高"确定性"** | 越靠后越不可能出错 ✓ |
| **终点必须"零风险"** | 最后一层不能还依赖模型 ✓ |

**"终点零风险"是关键** —— 很多人的降级链最后一层还是"让模型再试一次"，**那等于没有降级。**

### L6｜金额全由 SQL 产出——那统计 Worker 做的"消费评估"结论是谁生成的？模型还是规则引擎？ ⚠️

**答**：**数字由 SQL 产出，结论文本由模型组织 —— 但结论里的数字必须过白名单。**

**★知识点：这是"事实与表达分离"的精确含义**

```
事实层（SQL / 数值计算）  →  数字、聚合、占比、预算进度
                              ↑ 100% 确定性
表达层（LLM）             →  语言组织、分析建议、结论陈述
                              ↑ 受白名单约束
```

**关键**：**模型可以"下结论"，但结论里引用的每个数字都必须来自事实层。**

**★答法（要讲清边界）**：

> **要区分"结论"和"结论里的数字"**：
>
> **数字全部来自事实层** —— 金额、汇总、占比、预算进度**都由 SQL 和数值计算产出**，模型**不参与数值生成**。
>
> **结论文本由模型组织** —— 比如"你这个月餐饮支出占比偏高，建议控制外卖频率"，**这句分析是模型写的**。
>
> **但"餐饮支出占比"这个数字必须来自事实层** —— 模型只能**引用**，不能**计算**。**而且引用错了会被白名单抓住。**
>
> **所以准确的说法是**：**模型负责"表达和判断"，不负责"计算和记忆"。** 它可以说"这笔消费偏高"，**但"偏高"的依据（溢价率 23%）必须是确定性计算出来的。**
>
> **还有一层保障**：**如果事实底稿是空的（比如没有预算数据），白名单也是空的，那么模型输出任何数字都会被拦截** —— 这保证了"没数据的时候模型不会编"。

**★知识点：这一条有个很妙的边界情况（可以主动讲）**

```python
# agents/finance_agent —— 事实底稿为空时的行为
test_no_whitelist_gate_when_fact_sheet_empty
```

**如果事实底稿为空，白名单也就是空的** —— 那么**模型输出的任何数字都会被判越界**。

**这是"默认安全"的设计**：**没数据 → 不允许说任何数字** ✓

## Q16 · 水平扩展路径

### L1｜支持 10 个用户同时用——Queue 换什么？SQLite 换什么？ ✅

**答**：**Queue → Redis 之类的外部消息队列；SQLite → PostgreSQL。**

**★答法（要给"为什么"，不只是"换什么"）**：

> **两处要换，原因不同**：
>
> **① `asyncio.Queue` → Redis Stream / RabbitMQ**
> **原因**：`asyncio.Queue` 是**进程内内存队列**，**跨进程、跨机器都不可见**。多用户意味着大概率要**多实例部署**，那时候 worker 和编排器可能不在同一个进程里。
>
> **② SQLite → PostgreSQL**
> **原因**：SQLite 是**文件级锁 + 单写者**（我的 WAL 只解决了"读不阻塞写"，**写与写仍然互斥**）。**多用户并发写会撞锁** —— 我的 `busy_timeout=5000` 能把等待变成 5 秒，**但 10 个用户并发写时，这个等待会明显拖慢响应**。
>
> **其他不用改**：编排逻辑、工具网关、子 Agent 业务逻辑、检索层 —— **这些都不依赖存储实现**。

**★知识点：单机架构扩展到多机的"三个必换"**

| 组件 | 单机实现 | 分布式替代 | 为什么必须换 |
|---|---|---|---|
| **消息队列** | `asyncio.Queue` | Redis / RabbitMQ | **进程内内存** |
| **状态存储** | SQLite | PostgreSQL | **单写者 + 文件锁** |
| **会话状态** | 进程内 dict | Redis | **多实例不共享** |

**答法（补上第三个）**：

> **还有一处要换：会话记忆**。我现在用**进程内 dict**存会话历史、草稿、追问计数 —— **多实例部署时这些不共享**，用户第二次请求打到另一个实例就丢上下文了。**所以会话态要外置到 Redis。**

**⚠️ 主动补上第三个，会显得你"想全了"。**

### L2｜`asyncio.Queue` 换 Redis Stream 要改多少代码？接口兼容吗？ ⚠️

**答**：**替换面可控，因为 `a2a_bus` 是独立模块，接口很少。**

**★`a2a_queue.py` 的对外接口**：

```python
send_task(target_agent, session_id, task_id, task_data)   # 派发
recv_task_blocking(agent_id, session_id)                  # worker 接收
recv_task(agent_id, session_id, max_wait)                 # 测试接收
send_result(task_id, result)                              # 回传结果
wait_result(task_id, timeout)                             # 等结果
clear_all()                                               # 清空
```

**答法（诚实 + 给出判断依据）**：

> **接口很窄，只有 6 个方法**，而且**都很薄**（本质是 `put` / `get`）。
>
> **替换面的判断依据**：**如果接口窄且语义简单，换实现的成本就低。** 我的接口没有暴露任何"队列内部结构" —— **调用方只关心"投递"和"接收"，不关心底层是 `asyncio.Queue` 还是 Redis。**
>
> **但有两个地方要改设计**：
> ① **`wait_result` 现在是 `asyncio.Event` 唤醒** —— 换成 Redis 后要变成**轮询或 Pub/Sub + 回调**；
> ② **`recv_task_blocking` 的"无限阻塞"语义** —— Redis 侧要用 `BLPOP` 或 Stream 的 `XREAD BLOCK` 实现。
>
> **所以"改多少代码"取决于"接口的语义有多薄"** —— 我的接口比较薄，**主要工作量在适配层，不在业务层。**

**★知识点：这个回答展示的是"可替换性的判断标准"**

**可替换性取决于两个因素**：

| 因素 | 好 | 差 |
|---|---|---|
| **接口宽度** | **窄（方法少）** | 宽（暴露很多方法） |
| **抽象泄漏** | **无（不暴露实现细节）** | 有（返回 `asyncio.Queue` 对象等） |

**"能不能说出判断标准"**，比"我估 200 行"更有价值 —— **因为估算会错，标准不会。**

### L3｜SQLite 换 PostgreSQL——SQL 要重写吗？用了 ORM 还是裸写？ ⚠️

**答**：**裸写 SQL**（无 ORM）。

**★知识点：裸写 SQL 的"换库成本"分析**

| 部分 | 兼容性 | 说明 |
|---|---|---|
| **标准 SQL（SELECT/INSERT/UPDATE/DELETE）** | ✅ **基本兼容** | 他的绝大多数 SQL 是这类 |
| **`PRAGMA journal_mode=WAL`** | ❌ **SQLite 专有** | PostgreSQL 是 MVCC，不需要 |
| **`PRAGMA busy_timeout`** | ❌ 专有 | PostgreSQL 用 `statement_timeout` |
| **`INSERT OR IGNORE`** | ❌ 专有 | PostgreSQL 用 `ON CONFLICT DO NOTHING` |
| **`?` 占位符** | ❌ | PostgreSQL 用 `%s`（psycopg） |
| **`CREATE TABLE` 的 DDL** | ⚠️ 部分兼容 | 类型名有差异（`TEXT` / `AUTOINCREMENT`） |

**答法**：

> **裸写 SQL，没有 ORM。**
>
> **换库成本分三块**：
> ① **DML（增删改查）** —— **大部分是标准 SQL，基本不用改**；
> ② **SQLite 专有语法** —— **要改的集中在这里**：`PRAGMA journal_mode` / `busy_timeout`（PostgreSQL 用 MVCC，不需要）、`INSERT OR IGNORE`（→ `ON CONFLICT DO NOTHING`）、参数占位符 `?`（→ `%s`）、`AUTOINCREMENT`（→ `SERIAL` / `IDENTITY`）；
> ③ **DDL** —— CREATE TABLE 要重写。
>
> **这些改动集中在 `utils/common.py` 和 `database/init_db.py` 两个文件** —— 因为我把数据库访问**收敛在一个 `DatabaseCRUD` 类里**，**没有散在各处**。

**★知识点：为什么"没有 ORM"在这里反而是好事**

| | ORM | **裸写 SQL（他）** |
|---|---|---|
| **换库** | 通常更平滑 | **要改专有语法** ✗ |
| **性能可控性** | 差（不知生成什么 SQL） | **完全可控** ✓ |
| **调试** | 难（要开 SQL 日志） | **一眼看到 SQL** ✓ |
| **本项目** | — | **应用小、SQL 简单 → 裸写够用** ✓ |

**"没有 ORM"不是缺点** —— **在 SQL 简单、性能敏感、且要防 SQL 注入（他用参数化）的场景下，裸写是合理的。**

### L4｜Worker 跑在多个进程里——Queue 通信怎么跨进程？ ✅

**答**：**换成外部 broker（Redis）后，跨进程就是它的原生能力。**

**★答法**：

> **现在 worker 和编排器在同进程**（用内存队列），**所以不存在跨进程通信**。
>
> **拆成多进程后，跨进程通信由外部 broker 承担** —— Redis 的 Pub/Sub 或 Stream 本来就是**为跨进程/跨机设计的**。
>
> **关键是我的架构里"跨进程"不是新问题**：**我现在的 3 个 MCP 服务已经是独立子进程**了，**它们和主进程的通信走的是 HTTP**（不是内存）。**所以我很清楚"跨进程通信"需要什么** —— 需要**序列化 + 传输层 + 超时/重试**。
>
> **换到 worker 上，就是把"内存队列"换成"Redis 队列"，其余逻辑（序列化格式、超时、重试）我都有现成实现。**

**★知识点：他其实已经有一个"跨进程通信"的实例**

```
主进程 ←── HTTP ──→ 3 个 MCP server 子进程
        ↑ 这是真实的跨进程通信（不是内存共享）
```

**这一点很有说服力** —— **他不是"没做过跨进程"，而是"已经在一部分链路上做了"。**

### L5｜Orchestrator 也要多实例吗？多 Orchestrator 怎么协调？ ⚠️

**答**：**如果要做高可用，是要的；协调要靠"无状态 + 任务租约"。**

**★知识点：编排器的"有状态"和"无状态"部分**

| 部分 | 状态 | 多实例难点 |
|---|---|---|
| **编排逻辑（图执行）** | **无状态**（每次从 `init_state` 开始） | ✅ 天然可水平扩 |
| **任务分配** | **有状态**（谁派发谁等待） | ⚠️ **要靠幂等 + 租约** |
| **会话记忆** | **有状态**（进程内 dict） | ❌ **必须外置** |

**答法**：

> **编排器本身是无状态的** —— 每次请求都是从 `init_state` 建一张新图、跑完就结束。**所以水平扩没有问题。**
>
> **难点在两处**：
> ① **会话记忆要外置**（现在是进程内 dict，多实例不共享）；
> ② **任务分配要防重复** —— **如果两个编排器同时扫到同一批 `submitted` 任务，会各投一遍。**
>
> **后者的解法就是"租约"**：`task_state` 加 `owner` + `lease_expire_at`，**派发前先抢租约，抢到才能投。**
>
> **另外有个天然的保护**：**我的 `task_id` 是幂等键** —— 即使重复投递，`INSERT OR IGNORE` 保证**不会建两次单**。**但"不会建两次单"不等于"不会执行两次"**（因为队列里可能有两条消息），**所以租约还是必须的。**

**★知识点：幂等键能防"重复建单"，防不了"重复投递"**

```
两个编排器同时投递同一 task_id：
  → task_state：INSERT OR IGNORE 只建一条 ✓
  → 但队列里进了两条消息 → worker 会消费两次 ✗
```

**这个区分很重要** —— **幂等键不是万能的，它只覆盖"状态层"，不覆盖"消息层"。**

### L6｜如果以后要跨机器部署——你架构里哪些组件需要重写？ ✅

**答**：**三个组件，其余不动。**

| 组件 | 现状 | 跨机器后 |
|---|---|---|
| **消息总线** | 进程内 `asyncio.Queue` | **Redis / RabbitMQ** |
| **状态存储** | SQLite 文件 | **PostgreSQL** |
| **会话状态** | 进程内 dict | **Redis** |
| 编排逻辑 | LangGraph 图 | **不变** ✓ |
| 工具网关 | 进程内函数 | **可不变**（或服务化） |
| 子 Agent 业务 | 各子图 | **不变** ✓ |
| 检索层 | BM25 + FAISS（本地索引） | **可能要拆成独立服务** ⚠️ |

**★答法**：

> **三个必换**：消息总线（→ Redis）、状态存储（→ PostgreSQL）、会话状态（→ Redis）。
>
> **三个不动**：编排逻辑、工具网关、子 Agent 业务逻辑 —— **因为它们都不依赖"本地内存"或"本地文件"。**
>
> **还有一个要评估的**：**检索层**。我现在用的是**本地 FAISS 索引**（进程内），**多实例时每个实例都要加载一份索引** —— 这会浪费内存、也可能索引不一致。**如果要跨机器，检索应该抽成独立服务，或者用外部的向量数据库。**
>
> **⚠️ 但要提醒一点**：**跨机器后延迟模型完全变了** —— 现在是**内存操作（纳秒级）**，跨机器是**网络调用（毫秒级）**。**我现在的"并行派发"收益计算是基于内存队列的，跨机后要重新评估。**

**★知识点：最后一个提醒很关键**

**"跨机器"不只是"换个实现"，而是"换了整个成本模型"**：

| | 单机 | 跨机器 |
|---|---|---|
| **延迟** | 纳秒~微秒 | **毫秒** |
| **失败模式** | 进程崩 | **网络分区、超时、乱序** |
| **一致性** | 内存可见 | **需要显式同步** |

**"跨机器会改变延迟模型"这句话，说明你不只是"知道要换什么"，而是"知道换了之后整套权衡都要重做"。**

## Q17 · 新功能接入成本

### L1｜加第 5 个 Worker——改配置文件还是改 Orchestrator 代码？ ✅✅

**答**：**注册 Agent + 配依赖表，不动编排器代码。**

**★知识点：他的"可扩展性"具体体现在哪**

```python
# startup/bootstrap.py —— 注册只需加一行
AGENT_GRAPH = {
    "orchestrator_agent": orchestrator_graph,
    "bill_agent": bill_agent_graph,
    "stat_agent": stat_agent_graph,
    "price_agent": price_agent_graph,
    "finance_agent": finance_agent_graph,
    # ★加第 5 个：这里加一行 + 写一个 worker 协程
}
```

**答法（要说得具体）**：

> **编排器代码不用改**，改三处：
> ① **注册 Agent 图**（`AGENT_GRAPH` 加一行）；
> ② **加一个 worker 协程**（`_xxx_agent_worker`，4 个现有 worker 是同一个模板）；
> ③ **在依赖表里声明新任务的依赖**（比如"导出"依赖"统计"）。
>
> **编排器的 `dispatch` / `wait` / `collect` 三个节点完全不用动** —— 它们**按 `task_plan` 的依赖关系通用地工作**，**不针对具体 Agent 写逻辑**。
>
> **而且权限也是数据驱动的**：新 Agent 只要在权限映射表里声明它需要哪些权限，**鉴权自动生效**。

**★知识点：这是"配置驱动扩展"的实证**

**判断一个架构是否"可扩展"的标准**：**加新功能要不要改核心代码。**

| 改动类型 | 加第 5 个 Agent |
|---|---|
| **核心逻辑**（编排器） | ❌ **不用改** ✓ |
| **注册**（Agent 表） | ✅ 加一行 |
| **依赖声明**（依赖表） | ✅ 加一条 |
| **权限声明**（权限表） | ✅ 加一条 |
| **业务实现**（新 Agent 的图 + worker） | ✅ 这是真正的开发工作 |

**答法可以补一句免责**：

> **但我要说清"不用改核心代码"的边界**：**新增 Agent 的业务逻辑当然要自己写**（那是开发工作），**我说的是"不用改编排器"** —— **编排器不知道有几个 Agent、也不关心它们是什么，它只按 `task_plan` 的依赖关系调度。**

### L2｜依赖关系硬编码还是可配置？ ✅✅

**答**：**静态依赖表（数据）+ LLM 动态补充（只能加不能删）。**

**★这是个很硬的设计，要讲清**：

```python
# ① 静态依赖表：硬编码的基准（数据，不是 if-else）
#    比如 stat 依赖 bill（先记账才能统计）
#
# ② LLM 可以在 plan 时补充依赖
#
# ③ ★安全不变式：LLM 只能【加】依赖，不能【删】
```

**★测试锁定了这条不变式**：

```
test_merge_deps_static_cannot_be_removed    # 🔴 安全不变式：LLM 只能加依赖不能删
test_merge_deps_union_and_prune             # 静态表 ∪ LLM deps 并裁剪
test_plan_node_ring_from_llm_deps_falls_back # 🔴 LLM deps 成环 → 回退静态表继续执行（非终止）
```

**答法（★这段很有说服力）**：

> **两者结合：静态依赖表是基准，LLM 可以动态补充。**
>
> **关键在设计上我做了一个"单向"的约束**：
> - **LLM 可以【加】依赖** —— 比如用户说"记完账告诉我这个月花了多少"，LLM 会加上"统计依赖记账"；
> - **LLM 不能【删】静态表里的依赖** —— **因为我写进静态表的是"业务上不可能变"的约束**（比如记账必须先于统计）。
>
> **为什么这个方向很重要**：**依赖少会导致"数据还没准备好就执行"**（比如统计先于记账跑，查到的是旧数据）；**依赖多只是"慢一点"，不会出错**。
>
> **所以方向是"允许加、禁止删"** —— 往安全的方向偏。
>
> **而且我对 LLM 的输出做了两道防御**：
> ① **成环检测** —— 如果 LLM 加的依赖形成了环，**回退到纯静态表**（不是终止执行）；
> ② **无效引用丢弃** —— 引用了不存在的任务、或自依赖，直接丢掉。

**★知识点：这是一个"LLM + 确定性规则"协作的经典模式**

```
LLM 负责：理解语义（"记完账告诉我花了多少" → stat 依赖 bill）
规则负责：守住底线（不能删依赖、不能成环）
```

**这个模式的名字可以叫「LLM 提议 + 规则裁决」** —— **LLM 有自由度，但最终决策权在确定性规则手里。**

---

### L3｜新 Worker 的工具接入走适配器吗？还是直接写？ ✅✅

**答**：**走适配器 + 元数据声明，不写胶水代码。**

**★答法（呼应 Q14 的 9 步流水线）**：

> **走适配器，而且新工具只需要"声明元数据"，不写任何治理代码。**
>
> 具体说，新增一个工具是三步：
> ① **写业务函数**（真正的逻辑）；
> ② **声明 `ToolSpec`** —— 名字、参数 schema、**需要什么权限（`required_perm`）**、**有没有副作用（`side_effect`）**、超时、走哪个协议（`protocol`）；
> ③ **注册**。
>
> **然后鉴权、参数校验、审计、超时、重试、打点全部自动生效** —— 因为它们在引擎的 9 步流水线里，**不在工具代码里**。
>
> **协议也只需注册一个适配器**：`protocol` 字段取值 `local` / `mcp` / `http`，**新增一种协议就是实现一个适配器类并注册**，**调用方完全无感**。

**★知识点：这个设计的正式名字叫「声明式接入」**

| | 命令式 | **声明式（他）** |
|---|---|---|
| **新增工具** | 写业务 + **写鉴权 + 写校验 + 写审计 + 写重试** | **写业务 + 声明元数据** |
| **漏写风险** | **高**（很容易忘某一项） | **低**（漏了就没有该能力，但不会静默错） |
| **一致性** | 靠人保证 | **引擎保证** |

**答法可以补一句**：

> **这个设计最直接的好处是"不可能漏"** —— 比如新增工具时，**我不可能"忘了写鉴权"**，因为**鉴权不在工具代码里**，引擎每次都做。
>
> **而如果按老的做法（每个工具自己写鉴权）**，新增 10 个工具就有 10 次"忘记写"的机会。

### L4｜加新功能从开发到上线你估多久？ ⚠️

**答**：**要给一个"分解后"的估算，而不是拍一个数。**

**★分解**：

| 步骤 | 耗时 | 说明 |
|---|---|---|
| **写子 Agent 图**（节点 + 提示词） | 1~2 天 | 主要工作量 |
| **注册 + 依赖 + 权限声明** | **30 分钟** | 框架支撑的部分 |
| **补测试** | 半天 | 参照现有 Agent 的测试模板 |
| **联调** | 半天 | — |
| **合计** | **约 2~3 天** | 取决于业务复杂度 |

**答法**：

> **取决于业务复杂度，但框架部分基本免费。**
>
> **以"加一个导出 Agent"为例，我估算 2~3 天**：
> - **真正的开发量在"子 Agent 图"**（节点设计 + 提示词）—— **1~2 天**；
> - **框架接入部分很快**：注册 Agent、声明依赖、声明权限，**加起来 30 分钟**；
> - **补测试半天**（有现成的 Agent 测试模板可以套）；
> - **联调半天**。
>
> **对比一下"如果没有这层框架"**：我要**改编排器的 dispatch / collect 逻辑来支持新任务类型、手写鉴权和参数校验、再手写审计** —— **这些加起来可能比业务逻辑还多。**
>
> **所以"框架的价值"就在于：新增功能的成本，从"框架改动 + 业务开发"变成了"只算业务开发"。**

**★知识点：估算要给"分解"而不是给"数字"**

| 回答 | 面试官判断 |
|---|---|
| "大概一周吧" | **怎么来的？** ✗ |
| **"2~3 天。其中业务 1~2 天、框架接入 30 分钟、测试半天"** | **他知道时间花在哪** ✅ |

### L5｜如果新 Worker 需要访问已有 Worker 的数据——怎么拿？走 Orchestrator 还是直接访问？ ✅

**答**：**走编排器（经网关），不直接访问。**

**★代码依据**：`finance_agent` 就是这种模式 —— 它的 `init_state` 里带着上游结果：

```python
# startup/bootstrap.py — _finance_agent_worker
init_state = {
    ...
    "bill_result": msg["task_data"].get("bill_result"),
    "stat_result": msg["task_data"].get("stat_result"),
    "price_result": msg["task_data"].get("price_result"),
    "habit_data": msg["task_data"].get("habit_data"),
    "user_docs": msg["task_data"].get("user_docs", []),
}
```

**答法**：

> **走编排器，不直接访问。**
>
> **现有的例子就是 `finance_agent`**：它需要账单、统计、物价的结果，**这些数据不是它自己去查的，而是编排器在派发时打包进 `task_data` 下发的。**
>
> **为什么不让它直接查**：
> ① **权限**：`finance_agent` 只有 `BILL_READ`（只读），**它自己的权限画像是受限的**；
> ② **一致性**：直接查会拿到**当前最新**的数据，而编排器下发的是**同一波次的一致快照** —— **如果几个任务之间数据不一致，分析结论就不可靠**；
> ③ **依赖表达**：通过 `task_plan` 的依赖关系，**"我需要 stat 的结果"这件事是显式声明的**，编排器据此保证**顺序正确**。
>
> **代价是"编排器要负责取数和打包"**（`_build_task_data` 里逐个取），**收益是"数据一致 + 权限清晰 + 顺序有保证"。**

**★知识点：这是"数据传递" vs "数据共享"的选择**

| | 数据共享（各自查） | **数据传递（他）** |
|---|---|---|
| **一致性** | ❌ 可能读到不同时刻的数据 | ✅ **同一快照** |
| **权限** | ❌ 每个 Agent 都要有读权限 | ✅ **只有编排器要** |
| **耦合** | ❌ 下游要知道上游的存储 | ✅ **只依赖 `task_data` 契约** |
| **性能** | ✅ 省一次传递 | ❌ 要打包传递 |

**"用传递代替共享"和 Go 的设计哲学一致** —— **在可靠性和一致性要求高的场景，这是更稳的选择。**

## Q18 · MCP 服务可用性

### L1｜3 个 MCP 常驻服务有一个挂了——系统怎么办？ ✅

**答**：**该通道的工具调用失败 → 任务失败 → 转追问或报错；不影响其他通道。**

**★答法**：

> **故障是隔离在"通道"级别的**。比如 `sql_bill` 挂了：
> - **所有 SQL 工具调用失败** → 依赖它的任务（记账 / 统计）失败；
> - **LLM 通道不受影响** → `price` / `finance` 走 LLM 的部分正常；
> - **失败的任务**按 `side_effect` 决定重投或告警（写任务不重投）。
>
> **但有一个缺口我要如实说**：**运行时没有持续的健康检查** —— 我的健康检查**只在启动期**做（每 1 秒探活一次、最多 120 次）。**服务在运行中挂掉，我要等"调用失败"才知道。**
>
> **改进方向**：加一个**后台心跳协程**，定期探活，**探到不可用就主动摘掉该通道、并触发告警**。

**★知识点：健康检查的两个位置**

| 位置 | 他有没有 |
|---|---|
| **启动期检查** | ✅ **有**（每 1s 探活，最多 120 次，超时抛 `RuntimeError`） |
| **运行时持续检查** | ❌ **没有** |

**"运行时没有持续检查"是个真实的缺口** —— 但**如实说出来 + 说清补法**，比硬说"有监控"强。

---

### L2｜Orchestrator 能感知吗？怎么感知？ ✅

**答**：**启动期能（探活 + 握手）；运行期只能通过"调用失败"感知。**

**★代码依据**：`_probe_mcp_server`

```python
async def _probe_mcp_server(server_key: str) -> bool:
    url = f"http://{MCP_HOST}:{MCP_SERVER_PORTS[server_key]}{MCP_HTTP_PATH}"
    try:
        async with ...:
            await session.initialize()     # ★完成一次 MCP initialize 握手
        return True
    except Exception:
        return False
```

**★答法（说清"探活方式"的严谨性）**：

> **启动期的探活是很严的**：不是简单 ping 一下端口，而是**建立连接 + 完成一次真正的 MCP `initialize` 握手** —— **握手成功才算就绪。**
>
> **为什么不能只 ping 端口**：**端口通不代表服务可用** —— 进程可能起来了但还在加载模型、或者 MCP 协议栈没初始化好。**用 `initialize` 握手，等于"确认它真的能接 MCP 请求"。**
>
> **另外我还处理了两个边界**：
> ① **进程提前退出** → 立刻 `raise`（不用等满 120 秒）；
> ② **120 秒还没就绪** → `raise RuntimeError`，**启动失败**（而不是带着坏依赖继续跑）。
>
> **运行期的感知我说实话：只靠"调用失败"** —— 这是缺口。

**★知识点：健康检查的"深度"分级**

| 深度 | 检查内容 | 能发现 |
|---|---|---|
| **L1 端口探测** | TCP 能连 | 进程在不在 |
| **L2 HTTP 探测** | 返回 200 | Web 服务活着 |
| **★ L3 协议握手（他用的）** | **完成 `initialize`** | **业务真的可用** ✓ |
| **L4 业务探测** | 调一个真实业务接口 | 依赖都好 ✓✓ |

**他做到了 L3** —— **比大多数实现都严。**

---

### L3｜挂了之后重试几次？退避策略？ ✅

**答**：**指数退避 `min(2^attempt, 5)` 秒；次数按工具的 `max_retry` 配置。**

**★答法**：

> **退避用的是指数退避，封顶 5 秒**：`min(2^attempt, 5)` —— 也就是 2 秒、4 秒、5 秒、5 秒……
>
> **封顶很重要**：不加封顶的话，重试间隔会指数膨胀（8s、16s、32s...），**用户等待时间会失控**。
>
> **重试次数不是全局统一的，而是每个工具自己配 `max_retry`** —— 因为**不同工具的"重试价值"不同**：读一个缓存可以多试几次，**写账单最好一次也不试**。

**★知识点：为什么要封顶**

```
不封顶：1s → 2s → 4s → 8s → 16s → 32s → 64s ...  → 用户等到崩溃 ✗
封顶 5s：1s → 2s → 4s → 5s → 5s → 5s → ...        → 可控 ✓
```

**"封顶"体现的是"对用户等待时间的尊重"** —— 这个细节能说出来，说明想过真实体验。

### L4｜如果这个 MCP 是记账必需工具——降级方案是什么？ ❌

**答**：**没有降级方案 —— 记账必需工具挂了就是失败，不能降级。**

**★这里要讲清"什么能降级、什么不能"**：

| 能力 | 能否降级 | 降级方式 |
|---|---|---|
| **检索（向量路挂）** | ✅ **能** | **降级 BM25**（他实现了） |
| **模型汇总（LLM 挂）** | ✅ **能** | **回退模板渲染**（他实现了） |
| **记账（SQL 挂）** | ❌ **不能** | **无降级，如实报错** |

**答法**：

> **记账没有降级方案 —— 这是刻意的。**
>
> **区分一下我的两类降级**：
> - **检索可以降级**：向量路不可用时走纯 BM25，**因为有"另一条能达成目标的路径"**；
> - **模型汇总可以降级**：LLM 不可用时回退模板渲染，**照样能产出正确数字**；
> - **但记账不行**：**记账是"写操作"，它没有替代路径** —— 数据库连不上，就是写不进去。
>
> **这时候如果"降级"，只能是降级到"先存本地待补"之类** —— **但这会引入新的复杂度和不一致风险**（本地队列和数据库怎么对账？）。
>
> **所以我选择"如实报错"** —— 用户看到"记账失败，请稍后重试"，**而不是"看起来成功了但实际没记"。**
>
> **这和我整个项目的原则一致：不可逆操作，宁可失败也不误做。**

**★知识点：这个回答把"有没有降级"变成了"该不该降级"的讨论**

```
能降级的前提：存在"另一条能达成目标的路径"
不能降级的情况：目标本身就依赖那个组件
```

**"记账依赖数据库"** —— **没有数据库就没有记账，不存在替代路径。** **这时候"降级"是幻觉。**

### L5｜MCP 服务启动慢（冷启动 26s）——Orchestrator 派发时服务还没 ready 怎么办？ ✅

**答**：**启动期已经等它 ready 了，所以不存在这个问题。**

**★启动序列**：

```
③ 拉起 3 个 MCP 常驻服务 + 健康检查   ← ★这一步阻塞等待，直到全部就绪
④ 清空队列 + 崩溃恢复
⑤ 启动 worker
```

**答法**：

> **不存在这个问题** —— 因为**启动序列里，MCP 服务就绪是第 3 步，而 worker 是第 5 步才启动。**
>
> **也就是说：能接受任务的 worker 开始跑的时候，MCP 服务已经全部握手成功了。**
>
> **而且我对"没就绪"的处理是"启动失败"而不是"带病启动"**：
> - **进程提前退出** → 立刻报错；
> - **120 秒还没就绪** → `raise RuntimeError`。
>
> **所以我宁可"启动失败"，也不会出现"服务起来了但工具调不通"的中间状态。**

**★知识点：这是"启动顺序"作为依赖保证手段**

```
用启动顺序表达依赖：
  MCP 就绪  →（必须先）→  worker 启动
```

**比"启动后检测再重试"简单得多** —— **因为它把"运行时的竞态"变成了"启动时的顺序"。**

**⚠️ 但代价要说清**：

> **代价是"启动慢"** —— 要等 3 个服务都就绪（最多 120 秒）。**但这是"一次性成本"，换的是"运行期不用处理未就绪状态"。** 冷启动 26~29 秒的优化就是在这个背景下做的。

### L6｜你有 MCP 服务的健康检查吗？多久检测一次？ ✅

**答**：**有，启动期每 1 秒一次，最多 120 次。**

**★代码依据**：

```python
# 健康检查：120s 内每 1s 探活一次
for _ in range(120):
    if proc.poll() is not None:
        raise RuntimeError(f"[M3] {key} 常驻服务启动失败，退出码 {proc.returncode}")
    if await _probe_mcp_server(key):
        logger.info(f"[M3] {key} 常驻服务就绪：...")
        break
    await asyncio.sleep(1)
else:
    raise RuntimeError(f"[M3] {key} 常驻服务健康检查超时（120s）")
```

**答法（精确回答"多久一次"）**：

> **启动期：每 1 秒探活一次，最多 120 次（总预算 120 秒）。**
>
> **探活方式**是**建连接 + 完成 MCP `initialize` 握手**，不是简单 ping 端口。
>
> **两个提前退出条件**：
> ① **进程已退出** → 立刻报错，不用等满 120 秒；
> ② **握手成功** → 立刻 `break`，不用等满。
>
> **但我要如实说运行期的缺口**：**启动后没有持续的健康检查** —— **服务在运行中挂掉，我只能通过"调用失败"发现。** 补法是加一个后台心跳协程定期探活。

**★知识点：`for...else` 的用法**

```python
for _ in range(120):
    if ready:
        break
else:
    raise RuntimeError("超时")     # ← 只有循环正常结束（没 break）才执行
```

**这个 `for...else` 用得很地道** —— **它精确表达了"试了 120 次都没成功才报错"**，比用一个标志位变量更清晰。
