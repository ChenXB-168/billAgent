# 拷打逐题精讲 · 模块六：选型对比

> **本节特点**：这些是"送分题也是送命题" —— **答得好显得有技术视野，答得差显得"跟着教程走"。**
> **关键原则**：**说清"我评估过、为什么不适合我的场景"，而不是"不知道还有别的"。**

---

## Q19 · 为什么不用 AutoGen / CrewAI

### L1｜AutoGen 天然支持多 Agent 对话协商——你评估过吗？ ✅

**答**：**评估过，它的核心是"对话协商"模式。**

**★知识点：AutoGen 的范式**

| 特征 | AutoGen |
|---|---|
| **协作方式** | **Agent 之间自由对话**（多轮消息往来） |
| **终止条件** | 由对话内容决定（可能由某个 Agent 说"完成"） |
| **适合场景** | **探索式问题**（头脑风暴、代码协作、辩论） |
| **不适合** | **确定性流程**（每步都要可预测） |

**答法**：

> **评估过。AutoGen 的核心范式是"多 Agent 自由对话"** —— Agent 之间多轮往来，通过对话推进任务。
>
> **它的优势在"探索式问题"**：比如几个 Agent 从不同角度分析一个问题、互相质疑和补充。**但我的场景恰恰是它的反面**：
>
> **记账是"容错成本高 + 流程确定"的场景**：
> - **用户说"记午饭30"** —— 我需要的是**准确写进数据库**，不是"几个 Agent 讨论这笔账该不该记"；
> - **Agent 之间的多轮对话会引入不确定性**（聊到第几轮结束？谁来判定完成？），**而我的每个环节都必须可预测、可测试**。
>
> **所以我选的是 Orchestrator-Worker 模式**：**规划权收在编排器手里，子 Agent 只负责执行分配到的任务** —— **用确定性换可靠性。**

**★知识点：这个回答的关键是"说清场景差异"，不是"贬低 AutoGen"**

| ❌ 差的回答 | ✅ 好的回答 |
|---|---|
| "AutoGen 不太好用" | **"它的范式是对话协商，我的场景需要确定性流程"** |
| "我场景简单不需要" | **"我的场景容错成本高，协商会引入不确定性"** |

---

### L2｜你的场景为什么不适合对话协商模式？ ✅

**答**：**三个理由：容错成本、可测性、延迟。**

| 维度 | 对话协商 | **他的场景要求** |
|---|---|---|
| **容错** | 聊错了可以"再聊一轮"修正 | **记账错了就是脏数据** ✗ |
| **可测性** | **对话轨迹难复现**（同样的输入可能走不同轮次） | **每个节点要能单测** ✓ |
| **延迟** | 多轮往返，**延迟成倍增加** | **用户等不起** |
| **可观测** | 一轮对话里发生了什么很难归因 | **要能按任务追踪耗时** ✓ |

**答法（把"延迟"和"可测性"讲出来，因为这两点最实在）**：

> **三个理由**：
>
> **① 容错成本高**：**对话协商的机制是"聊错了再聊一轮"** —— 这在头脑风暴里没问题，**但记账场景里，一句"我记了"如果是错的，用户账上就多了一笔假数据。**
>
> **② 可测性差**：**对话轨迹很难复现** —— 同样的输入，Agent 可能聊 2 轮也可能聊 5 轮，**测试没法写断言**。**而我的每个节点都有单测，因为流程是确定的。**
>
> **③ 延迟成倍增加**：**对话协商是多轮 LLM 调用**，每轮都有网络往返 + 推理时间。**我现在的端到端已经是数十秒（大头是 LLM），再乘几轮用户等不起。**

**★知识点：延迟这一点特别有说服力**

**因为它不是"理念之争"，而是"实测过的成本"** —— **他做过端到端基测，知道 LLM 调用是主要耗时**，所以**"多轮对话 = 延迟翻几倍"是个可量化的判断。**

### L3｜如果以后要加"Agent 之间互相讨论"的能力——你的架构能加吗？ ⚠️

**答**：**能，而且不需要改架构。**

**★答法**：

> **能，因为我的消息总线支持任意拓扑。**
>
> 现在的拓扑是**星型**（编排器 ↔ 各子 Agent），**但总线本身不限制拓扑** —— 它只是"按 agent 名分队列 + 按 task_id 索引结果"。
>
> **要加"讨论"，只需要**：
> ① **加一个协调子图**（比如 `debate_agent`），它的图里有"多轮往来"的逻辑；
> ② **在依赖表里声明它需要哪几个 Agent 的输入**（比如 finance 和 stat 的观点）；
> ③ **其余不动** —— 编排器照常派发，把它当成一个普通任务。
>
> **换句话说：对话协商可以作为一个"子 Agent 内部的实现细节"** —— **我不排斥这种模式，只是不把它用在主流程上。**

**★知识点：这个回答的层次感**

**它把"选型"从"二选一"变成了"分层选择"**：

```
主流程（编排）：确定性 Orchestrator-Worker ✓
子任务内部（可选）：如果需要，可以用对话协商 ✓
```

**"我不排斥它，只是不用在主流程上"** —— 这比"我不用 AutoGen"成熟得多。

---

### L4｜CrewAI 有角色扮演和任务委派——你看过吗？ ⚠️

**答**：**了解过它的范式（角色 + 任务委派）。**

**★知识点：CrewAI 的范式**

| 特征 | CrewAI |
|---|---|
| **抽象** | **Agent 有"角色"**（role / goal / backstory） |
| **协作** | **任务委派**（Task 分给 Agent） |
| **适合** | **角色分工明确、任务可枚举的场景** |

**答法（诚实 + 说清差异）**：

> **了解过它的范式**：Agent 有明确角色（角色 / 目标 / 背景故事），任务在 Agent 之间委派。
>
> **它和我的设计其实有相似之处**（都是"分工"），**但差异在两处**：
>
> **① "角色设定" vs "能力边界"**：CrewAI 用**提示词**定义角色（"你是一个财务专家"），**而我的隔离是"能力层面"的** —— 我的记账 Agent 有 `sql.write`、统计 Agent 只有 `sql.read`，**这不是"提示词说它是个记账员"，而是"它真的只能写账单这一类操作"**。
>
> **② 委派 vs 依赖驱动**：CrewAI 的委派**由 Agent 决定**（"这个任务我干不了，交给别人"）；**我的派发由编排器按依赖图决定** —— **是确定性的，不依赖 Agent 的判断。**

**★知识点：这个回答很有价值，因为它把"看起来像的方案"讲出了本质差异**

**CrewAI 和他在形式上都是"多 Agent 分工"** —— **但一个靠"提示词+自主委派"，一个靠"权限约束+依赖调度"。**

**答法可以补一句**：

> **所以我的方案不是"CrewAI 的简化版"，而是"同一个问题（多 Agent 分工）的另一种解法"** —— **我选的是"把隔离做在能力层、把调度做在编排层"。**

### L5｜你选型 LangGraph 的核心原因是什么？是功能匹配还是学习成本低？ ✅

**答**：**功能匹配（显式控制流 + 状态契约）。**

**★答法（正面回答"功能匹配"，并说清"代价"）**：

> **功能匹配，不是学习成本。**
>
> **我用它的两个具体能力**：
> ① **显式控制流**：我的编排图是 `plan → dispatch → wait → dispatch` 的**循环结构**，而且跳转是**运行时动态决定的**（有任务就继续派、依赖不满足就收口）。**LangGraph 的 `Command(goto=...)` 直接表达这个，手写要一堆 `if/elif`**；
> ② **状态契约**：`TypedDict` 定义了节点间的状态契约，**加字段时结构是显式的**。手写 dict 的话，**谁往 state 里塞了什么、删了什么，不会有静态检查。**
>
> **但我也付了代价**：**框架把控制权收走了** —— 我想在"图执行期间"插入自定义调度逻辑就得绕开它。**这正是我后来把 Agent 通信做成外部总线的原因**：**图管一次请求内的编排，跨请求的调度我自己做。**

**★知识点：说代价比说优点更可信**

| 回答 | 面试官判断 |
|---|---|
| "LangGraph 功能强大、社区活跃" | **像宣传语** ✗ |
| **"我用它做编排骨架，但它的控制权收得太紧，所以我把 Agent 通信挪到外面自己做"** | **他真的用过、撞到过边界** ✅ |

## Q20 · 为什么不用 Celery / Redis Queue

### L1｜Celery 有持久化和重试、Worker 池、监控——你用 `asyncio.Queue` 的理由是什么？ ✅

**答**：**本质是"分布式任务队列"和"单机进程内调度"的差别。**

**★答法（要给"为什么不引入"的量化理由）**：

> **Celery 是分布式任务队列** —— 它需要 **broker（Redis/RabbitMQ）+ 序列化 + 独立的 worker 进程组**。**这些成本对我是纯开销**：
>
> | Celery 提供的 | 我的场景需要吗 |
> |---|---|
> | **跨机器任务分发** | ❌ **单机** |
> | **独立 worker 进程池** | ❌ **4 个协程就够** |
> | **序列化传输** | ❌ **同进程可以直接传对象** |
> | **持久化** | ⚠️ **我需要，但我用 `task_state` 表自己做了** |
> | **重试 / 监控** | ⚠️ **同上，自己做** |
>
> **所以真正的问题是**：**我需要的"持久化 + 重试"其实只有一小部分**，**而引入 Celery 的代价是"多一套部署依赖（broker）+ 全链路序列化"。**
>
> **更关键的是"认知负担"**：**我如果用了 Celery，我就不知道"任务为什么重投了"** —— 因为决策在框架里。**而我现在能精确控制"什么情况重投、什么情况不投"**（比如写任务永不重投）。

**★知识点：这个回答最有力的部分**

**"我不引入框架是为了保持控制"** —— 这与他的核心需求（**写任务绝不重复执行**）直接相关：

```
Celery 的重试策略：按配置重试 ← 我改不了它的内部决策
我的重试策略：按 side_effect 判定 ← 完全可控 ✓
```

---

### L2｜是部署简单？不需要分布式？还是没考虑过？ ✅

**答**：**都考虑过，主要原因是"不需要分布式 + 要保留对重试策略的控制"。**

**★答法（不要选一个，要说清权衡）**：

> **三个都成立，但权重不同**：
>
> **① 部署简单是"顺带的收益"** —— 我不需要额外起 broker，**但这本身不是主要理由**；
> **② 不需要分布式是"根本前提"** —— 单机单用户，**Celery 的核心价值我用不上**；
> **③ ★ 最主要的原因是"控制权"** —— **我的可靠性设计有一个核心约束：写任务绝不能自动重投。**
>
> **这个约束贯穿整个系统**（`retriable=0`、`side_effect=True` 不重试、对账判定）。**如果我用 Celery，它的重试逻辑是框架内部的** —— **我要么关掉重试（那它的价值就少了一半），要么接受"框架可能会重投我禁止重投的任务"。**
>
> **所以不是"没考虑过 Celery"，而是"考虑过，发现它的重试策略和我的安全约束冲突"。**

**★知识点：这是一个"看起来在讲框架，实际在讲设计原则"的回答**

**面试官问"为什么不用 X"，通常期待的是"性能/复杂度"的对比** —— **他给的答案是"安全性约束"，层次更高。**

### L3｜如果以后要跨机器——Queue 怎么迁移？ ✅

**答**：**见模块五 Q16-L1**（三个必换：消息总线 / 状态存储 / 会话态）。

**★补一句"迁移时机"**：

> **迁移的触发条件很明确**：**当"单进程消费不过来"或者"需要多实例容灾"时。**
>
> **在那之前不迁移的理由**：**跨机器会把"纳秒级内存操作"变成"毫秒级网络调用"** —— **我现在的并行派发收益是基于内存队列算的，换成网络后要重新评估。**

### L4｜Celery 的 retry + dead letter queue 你有等价实现吗？ ⚠️

**答**：**retry 有；dead letter queue 没有**（诚实）。

| 机制 | Celery | **他** |
|---|---|---|
| **retry** | ✅ 内置 | ✅ **`retry_cnt` + `retriable` + `MAX_RETRY=3`** |
| **dead letter queue** | ✅ 独立队列 | ❌ **失败任务留在表里，无独立队列** |
| **任务优先级** | ✅ 支持 | ❌ 无 |
| **定时任务** | ✅ beat | ❌ 无 |
| **可视化管理** | ✅ Flower | ❌ 无（但有 SQL 可查） |

**答法**：

> **retry 有等价实现**：`retry_cnt` 计数 + `retriable` 标记 + `MAX_RETRY=3` 上限，**而且比 Celery 更细**（按有无副作用分别处理）。
>
> **dead letter queue 没有** —— 我的失败任务是**留在 `task_state` 表里标 `failed`**，**没有独立的死信队列，也没有自动的"人工介入"入口**。
>
> **"没有死信队列"的实际影响是**：**失败任务不会被自动重试（好），但也不会被主动提醒（差）** —— **我只能通过日志告警知道有失败**。
>
> **补法**：**加一个 `failed` 任务的查询接口/界面**，或者接一个告警通知。**这属于"运维完善"，不影响正确性。**

**★知识点："没有"要说清"后果"和"严重程度"**

| 回答 | 判断 |
|---|---|
| "没有" | 信息量低 |
| **"没有。影响是"不会自动重试（好）但也不会提醒（差）"，属于运维完善，不影响正确性"** | **知道自己缺什么、缺的影响有多大** ✅ |

## Q21 · 为什么不用 FastAPI 做服务化

### L1｜做成 API 服务，架构能直接套吗？ ⚠️

**答**：**核心逻辑能套，但有三处必须先改。**

| 部分 | 能否直接套 | 要改什么 |
|---|---|---|
| **编排图** | ✅ 能 | 几乎不用改 |
| **工具网关** | ✅ 能 | 不用改 |
| **子 Agent** | ✅ 能 | 不用改 |
| **会话状态** | ❌ **必须外置** | 进程内 dict → Redis |
| **任务状态** | ⚠️ 要换 | SQLite → PostgreSQL（多 worker 并发写） |
| **长任务模式** | ❌ **必须改** | **现在是"阻塞到出结果"，要改成"提交 + 轮询/回调"** |

**答法**：

> **核心逻辑能套** —— 编排图、工具网关、子 Agent 都不依赖"单机"。
>
> **但三处必须先改**：
> ① **会话态外置**（现在是进程内 dict）；
> ② **任务存储换库**（SQLite 多 worker 并发写会撞锁）；
> ③ **★ 请求模型要改** —— **我现在是"提交后阻塞等到出结果"**（WebUI 用 `run_until_complete`），**服务化必须变成"提交任务 → 返回 task_id → 轮询 / 回调取结果"。**
>
> **第 ③ 点其实我的架构已经支持了** —— 因为**我本来就有 `task_id` + 状态表**，**只要把它暴露成 API 就行**，不用改内部逻辑。

**★知识点：第 ③ 点是关键洞察**

**"同步阻塞"和"异步任务"是两种请求模型**：

```
同步：POST /chat → 等到 LLM 跑完 → 返回结果   ← 他的现状（WebUI）
异步：POST /chat → 立刻返回 task_id           ← 服务化必须
      GET /task/{id} → 查状态和结果
```

**而他的架构里已经有 `task_id` 和状态表了** —— **服务化不是重写，是"把已有的内部能力暴露出去"。**

---

### L2｜Orchestrator 做成 endpoint？Worker 做成后台任务？ ⚠️

**答**：**对，而且要区分"请求生命周期"和"任务生命周期"。**

**★知识点：这两个生命周期的分离是关键**

```
请求生命周期：HTTP 连接建立 → 返回响应 → 连接关闭     （秒级）
任务生命周期：create_task → running → completed        （可能跨重启）
```

**答法**：

> **编排器做成 endpoint，但"worker 不能跟着请求走"** —— **这是关键。**
>
> **现在 worker 是常驻协程**（进程启动时就挂上了），**它们的存在不依赖任何请求**。**服务化后这一点不变** —— worker 还是常驻的（可能变成独立进程甚至独立服务）。
>
> **请求进来时**：编排器建图、派发任务、**然后等**；
> **但"等"的方式要变**：不能阻塞 HTTP 连接等 30 秒，**应该先把 `task_id` 返回给客户端，让它轮询。**
>
> **所以服务化后，`dispatch` 之后的流程和"请求"就解耦了** —— **任务在后台跑，客户端通过 `task_id` 查进度。** 这正好是我现在的状态表能支持的。

---

### L3｜用户请求进来后断开连接——任务还在跑吗？结果怎么拿回？ ⚠️

**答**：**任务会继续跑**（状态在表里），**但结果现在拿不回来** —— 这是缺口。

**★答法（这里要诚实，且能说清"为什么现在不行"）**：

> **任务会继续跑** —— 因为**它的生命周期不受请求影响**（状态在 `task_state` 表，worker 是常驻的）。
>
> **但结果拿不回来** —— 因为**我现在的设计是"阻塞等待 + 直接返回"**：编排器 `await wait_result(...)`，拿到结果后返回给调用方。**如果调用方断了，这个结果就没人接了。**
>
> **严格说，`task_state` 表里**有**结果**（`result` 列会写入），**但那是"子 Agent 的结果"，不是"最终汇总回复"** —— **最终回复是编排器在 `collect_node` 里生成的，只在内存里返回给调用方，没落库。**
>
> **所以要支持"断线后取回结果"，要补一步**：**把 `collect_node` 产出的 `final_reply` 也持久化**（按 `session_id` 或 `request_id` 存），这样客户端重连后能查到。

**★知识点：这个回答揭示了一个真实的架构缺口**

**"任务状态持久化了，但对话结果没有"** —— 这个不对称很容易被忽略，**但他能精确指出"哪部分是持久化的、哪部分不是"。**

**答法可以补一句**：

> **这个缺口很典型**：**我做了"任务级的 Durable"，但没做"会话级的 Durable"** —— 任务崩了能恢复，**但用户拿到的最终答复如果丢了就丢了。**

### L4｜你有做请求级别的超时控制吗？整个请求链路的 timeout 怎么设？ ⚠️

**答**：**有分层的超时，但没有"请求级总超时"。**

**★超时的分层**：

| 层 | 超时 | 位置 |
|---|---|---|
| **工具调用** | 按 `ToolSpec.timeout`（SQL 30s / LLM 300s） | 引擎 |
| **子任务等待** | **240 s**（对齐 `MODEL_TIMEOUT`） | `a2a_bus.wait_result` |
| **调度波次** | `MAX_DISPATCH_ROUND = 8`（**防死循环，不是超时**） | 编排图 |
| **请求级总超时** | ❌ **没有** | — |

**答法**：

> **有分层超时，但没有"请求级总超时"**：
>
> - **单次工具调用**：按工具类型配（SQL 30 秒、**LLM 300 秒**）；
> - **单个子任务等待**：**240 秒**（和模型超时对齐）；
> - **调度波次上限**：8 波（**这个不是超时，是防死循环**）。
>
> **缺的是"整个请求的总预算"** —— 现在理论上最坏情况是"8 波 × 240 秒"，**用户可能要等很久**。
>
> **补法**：**在编排入口设一个总预算**（比如 300 秒），超了就直接收口返回"处理超时"。**实现上是在 `run_scope` 外面套一层 `asyncio.wait_for`。**

**★知识点：为什么"分层超时"和"总超时"都要有**

```
分层超时：保证"单个环节不会无限等" ✓
总超时：  保证"用户不会无限等"     ← 他缺这个
```

**分层超时是"内部健康"，总超时是"用户体验"** —— **两者服务不同的目标。**

### L1b｜为什么是 4 个？不是 2 个或 8 个？ ⭐✅✅

**核心内容速记**：

### L2｜Worker 有独立身份吗？独立记忆吗？能拒绝任务吗？ ⚠️

| 追问 | 答 |
|---|---|
| **独立身份** | ✅ **有 `agent_id`**，是权限、工具可见面、审计的判定主体 |
| **独立记忆** | ⚠️ **部分** —— 各有独立的图状态（`init_state`），**但会话记忆是编排器统一管理下发的** |
| **能拒绝任务** | ✅ **能** —— 比如 `need_more_info`（追问分支）、收入不入账拦截 |

**★答法（第三点最有说服力）**：

> **有独立身份**：每个 Agent 有 `agent_id`，它是**权限判定、工具可见面过滤、审计记录**的主体 —— **同一个工具调用，换个 `agent_id` 就可能被拒绝。**
>
> **记忆方面**：**各 Agent 有独立的图状态**（`init_state` 是各自定义的），**但会话记忆是编排器统一管理、随任务下发的** —— **所以我不会说"每个 Agent 有独立记忆"，而是"有独立的工作状态，共享会话上下文"。**
>
> **能拒绝任务**：这一点很实际 —— **记账 Agent 在信息不全时会返回 `need_more_info`（转成对用户的追问）**，**在识别到"收入类内容"时会拒绝入账**。**这说明它有"不接受这个任务"的能力，不是无条件执行。**

**★知识点："能拒绝"是 Agent 自主性的一个标志**

**无条件执行的叫"函数"，能拒绝的叫"Agent"** —— **这是判定"是不是 Agent"的一个实用标准。**

### L3｜去掉 Queue 直接函数调用，用户感知到什么差别？ ❌

**答**：**功能上感知不到；差别在故障隔离与可恢复性。**

**★答法**：

> **功能上，用户感知不到差别** —— 都是"输入一句话，拿到回复"。
>
> **差别在这几处**：
>
> | | 直接函数调用 | **消息总线（他）** |
> |---|---|---|
> | **失败影响面** | **一个失败 = 整链失败** ✗ | **单任务失败可独立处理** ✓ |
> | **可重启恢复** | **做不到**（调用栈没持久化） | **能**（任务状态在表里）✓ |
> | **可独立重试** | 做不到 | **能**（读任务可重投）✓ |

> | **可观测** | 调用栈即上下文 | **每个任务有独立 task_id 可追踪** ✓ |
>
> **所以 Queue 的价值不在"能跑"，在"出事了怎么办"。** —— **这是我整个可靠性设计的基础**：**没有消息总线和任务表，`recover_orphans` 和幂等重投都无从谈起。**

### L4｜为什么叫多 Agent 不叫多 Worker 并发？ ❌❌

**★完整答案见**：`项目拷打应对与整改清单.md` 的 Q22 专答。

**核心内容速记**：

> **它们是同进程的协程，不是独立进程或服务** —— **这一点我如实说。**
>
> **我称它为"多 Agent"而不是"多 Worker"，因为每个子 Agent 具备三样独立的东西**：
> 1. **独立的工具可见面与权限**（仅记账 Agent 可写账单；理财 Agent 独享专属模型通道）
> 2. **独立的提示词与子图**（各自有 Plan/Execute/Verify 节点与自纠闭环，**不是同一个函数换参数**）
> 3. **独立的失败域**（一个失败转追问，不阻断其他任务）

> **如果要更严格地定义 Agent 需要进程隔离 + 自主规划，那我的实现介于"多 Agent"与"多 Worker 并发"之间。**

## Q24 · "已通过进程强杀验证"的诚实度

### L1~L4｜几次？什么信号？覆盖了哪些状态？SIGKILL 和断电一样吗？ ✅✅

**★完整答案见**：`崩溃恢复强杀验证记录.md`

**速记表**：

| 项 | 内容 |
|---|---|
| **信号** | **SIGKILL**（Windows 下等价 `TerminateProcess`） |
| **真实强杀** | **1 次**（轮询检测到 `running` 后立即杀，t≈30s 命中） |
| **构造中间态** | **4 个分支** |
| **覆盖** | 队列中 / 写任务执行中(账单已写) / 写任务执行中(未写) / 读任务执行中 / 真实 SIGKILL |
| **对账统计** | `{completed: 1, resubmitted: 1, failed: 1}` |

**★L4 的答法（SIGKILL vs 断电）**：

> **不一样，我只测了 SIGKILL。**
>
> **两者正好对应我的两个状态**：
> - **SIGTERM 可被捕获** → worker 收到后标 `interrupted`（**优雅关闭，重启后重投**）；
> - **SIGKILL 不可捕获** → 进程直接消失、状态停在 `running` → **靠重启对账处理**。
>
> **至于"断电"**：**它比 SIGKILL 更狠** —— SIGKILL 时操作系统和文件系统都完好，**断电可能丢 `fsync` 前的写、甚至损坏文件系统**。**我没测，也不打算测**（需要真机断电或虚拟化手段）。

**★★ 注意：这一项已经从"做不到"变成了"做完了"** —— M16 已实现。

**速记**：

| 层 | 状态 |
|---|---|
| **L1 停止等待** | ✅ **机制已具备**（任务继续跑完、结果落库） |
| **L2 停止派发** | ✅ **已实现**（`dispatch_node` 检查 `state["cancelled"]`） |
| **L3 中断执行** | ✅ **已实现**（`cancel_session` → `cancel()` 内层 runner Task） |
| **L4 撤销副作用** | ❌ **明确没做**（难点在业务语义） |

> **关键技术点是"区分两种中断"**：**我原来的 `interrupted` 状态（进程优雅关闭）重启后会重投任务，而用户取消绝不能重投** —— 否则用户点了停止，重启后又收到一条回复。**所以我把 `cancelled` 单独做成终态，不进恢复扫描。**
>
> **实现上踩过两个坑**：
> ① **worker 是常驻协程，直接 cancel 它会打死整条消费链路**（因为 `CancelledError` 不被 `except Exception` 捕获）—— 所以我把每个任务的执行**包成独立 Task**，取消只作用于它；
> ② **取消后必须主动回传结果** —— 子图被中断后 `reply_node` 不会执行，不代传的话**编排器会阻塞到 240 秒超时**才反应。
>
> **L4（撤销已产生的副作用）我没做**，难点不在技术、在业务语义 —— 并行任务里可能 A 已记账成功、B 还在跑，用户说停止时 **A 那笔账要不要撤？**

**★这一套讲下来覆盖**：状态机设计、协程取消语义、异常继承层级、补偿思维、边界认知。

**★知识点：为什么这个回答能站住**

**它把"没用的优化"重新定义为"有用的优化"** —— **而且论证是成立的**：

### L3｜CI 跑吗？ ✅✅

**答**：**跑，两个 job 并行。**

**★CI 配置**（`.github/workflows/ci.yml`）：

```yaml
on:
  push:
    branches: ['**']          # 任意分支
  pull_request:
  workflow_dispatch:          # 手动触发

jobs:
  contract:                   # Job 1：契约漂移检查（秒级，零依赖）

    steps:
      - run: pip install -r requirements-dev.txt
      - run: pytest tests/unit -q
```

**★设计亮点**：

> **CI 分成两个 job，这是刻意的**：
>
> **① 契约漂移检查单独成 job** —— 它**只用标准库、秒级完成、零安装成本**。**所以它最快给反馈**，而且**它 FAIL 说明"文档与代码漂移"，属于设计红线。**

**反馈速度决定开发体验**：

```
一个 job：装依赖(60s) + 契约检查(1s) + 单测(30s) = 91s 才反馈
两个 job：契约检查 5s 就反馈 ✓ ；单测并行跑
```

**"把快的检查单独拿出来"是 CI 设计的常见优化** —— 他能说清这个理由，说明**不是"配了个 CI 就完事"。**

### L5｜如果改了 Orchestrator 逻辑——怎么确认不影响 Worker？ ✅✅

**答**：**契约漂移检测 + 分层测试 + 静态断言。**

**★三重保障**：

| 保障 | 机制 |
|---|---|
| **① 契约漂移检测** | `test_contract_check.py` 核对**设计文档的接口符号/行号**与代码 —— **漂移即测试红** |
| **② 分层测试** | **worker 有独立单测**（`test_bill_agent` / `test_stat_agent` / ...），**改编排器不影响它们的测试** |
| **③ 静态断言** | 源码级扫描（如 `test_webui_source_contains_no_bill_write_calls`） |

**★答法（重点是"契约漂移检测"这个元测试）**：

> **三重保障**，其中最特别的是**契约漂移检测**：
>
> **它是一个"元测试"—— 测试的对象不是业务功能，是"文档与代码的一致性"。**
> 我的设计文档（`09_模块契约手册.md`）里写了接口符号和行号引用，**`test_contract_check.py` 会去代码里核对**：
> - 文档里的符号**必须存在于代码**（写了但代码删了 → 红）；
> - 文档里的**行号引用不得越界**（代码改了行号对不上 → 红）。
>
> **而且它有"负例"保证检测器真的有效**（`test_detects_missing_symbol` / `test_detects_stale_line_ref`）—— **防止"检查脚本空转、永远通过"。**
>
> **为什么这个重要**：**我改了编排器的一个接口，如果忘了更新文档，或者改了文档但代码没跟上** —— **这个测试会立刻红**。**"文档 ↔ 代码漂移"不再依赖人工 review 发现。**
>
> **另外"改编排器不影响 worker"这件事，是分层测试保证的**：**worker 有独立的测试文件**，**它们测的是"给一个 task_data，产出对不对"** —— **跟编排器怎么派发的无关。**

**★知识点："契约测试"和"单元测试"的区别**

| | 单元测试 | 契约测试（元测试） |
|---|---|---|
| **测什么** | 代码行为 | **文档与代码的一致性** |
| **失败意味着** | 逻辑错了 | **设计漂移了** |
| **他有没有** | ✅ | ✅✅ **有，且有负例自证** |

**"有负例自证"这一点很少见** —— **大多数人的"检查脚本"从来没有被验证过"真的能发现问题"。**

### L3｜链路追踪做了吗？一个请求从进到出经过哪些节点？ ✅✅

**答**：**做了，而且质量很高。**

**★实现细节**：

| 能力 | 实现 |
|---|---|
| **`run_id` 生成规则** | `r{毫秒}{hex3}` —— **与 `task_id` 同构** |
| **跨协程传递** | **`contextvars`**（asyncio 与线程池都安全） |
| **跨进程传递** | **`run_id` 随 `task_data` 下发给 worker**（因为 `contextvars` 不跨协程/进程） |
| **span 树落库** | `trace_span` 表（含 `parent_span_id`） |
| **可视化** | `utils/trace_view.py` 的 **ASCII 渲染** |
| **铁律** | **Tracer 自身异常永不阻断主链路**（有测试锁定） |

**★span 层级结构**：

```
orchestrator.run（root）
  ├── plan_node
  ├── dispatch_node
  │     └── bill_agent.run
  │           └── tool: sql.write
  ├── wait_result_node
  └── collect_node
```

**★答法（★这段讲清"跨协程/跨进程传递"这个难点）**：

> **做了完整的链路追踪，而且我想讲一个实现上的难点**：
>
> **追踪要解决的核心问题是"怎么把 `run_id` 传递到下游"**，而我有三种传递场景：
>
> | 场景 | 手段 |
> |---|---|
> | **同协程内** | `with run_scope(...)` 上下文管理器 |
> | **跨协程** | **`contextvars`**（**它对 asyncio 和线程池都安全**） |
> | **★ 跨进程/跨消息** | **`contextvars` 不管用** → **`run_id` 随 `task_data` 显式下发给 worker** |
>
> **第三种是难点**：**`contextvars` 不会自动跨"消息边界"** —— 我的子 Agent 是常驻 worker，**收到的是消息，不是被 `await` 调用的协程**。所以**我在 `dispatch_node` 里把当前 `run_id` 和 `parent_span_id` 塞进 `task_data`**，worker 拿到后**用 `run_scope(run_id=...)` 恢复上下文**。
>
> **这样一条用户请求的完整链路，就能被 `run_id` 串起来** —— 包括跨进程的部分。
>
> **另外有个"铁律"我一开始就定了**：**Tracer 自身的异常永不阻断主链路** —— **可观测是"帮助排障"的，不能成为"新的故障源"。** 有测试锁定这一条（`test_tracer_never_blocks_pipeline`）。

**★知识点：`contextvars` 的传播边界**

| 传播场景 | 自动吗 |
|---|---|
| **同协程 await 链** | ✅ **自动** |
| **`asyncio.create_task`** | ✅ **自动**（子任务复制上下文） |
| **`to_thread` 线程池** | ✅ **自动**（Python 3.x 复制上下文） |
| **★ 消息队列（跨边界）** | ❌ **不自动** ← **他的难点** |
| **跨进程** | ❌ 不自动 |

**"消息边界会切断 `contextvars`"是一个很容易被忽略的点** —— **他能识别出来并显式传递，说明真的踩过。**

### L4｜告警呢？失败了你知道还是用户告诉你？ ❌

**答**：**没有告警 —— 失败了我只能从日志里看到。**

**★答法（诚实 + 说清"哪些失败会被记录"）**：

> **没有告警，这是缺口。** 现在**失败了只能从日志里看到**（而且是我主动去查）。
>
> **但有一个细节值得说**：**我区分了"会告警的失败"和"静默的失败"**：
>
> | 失败类型 | 处理 | 理由 |
> |---|---|---|
> | **崩溃恢复发现遗留任务** | **`logger.warning`** ✓ | **需要人知道** |
> | **写任务未落库 → 判 failed** | **`logger.warning`** ✓ | **宁可告警也不重复记账** |
> | **习惯沉淀失败** | **静默**（不阻断记账） | **加固项，不该影响主流程** |
> | **Tracer 打点失败** | **静默**（不阻断主链路） | 同上 |
>
> **所以我的原则是"影响数据正确性的失败要告警，加固项的失败可以静默"** —— **这个区分是有意的。**
>
> **缺的是"告警通道"**：**warning 打进了日志，但没有推送到任何地方。** 补法是**接一个 webhook / 邮件通知**，或者**在启动时检查是否有遗留的 `failed` 任务并提示。**

**★知识点："哪些失败要告警"是个设计决策，不是全部都要**

```python
# 需要人介入的失败 → 告警
"崩溃对账：账单已落库 → 标记 completed（非 failed）"      → warning ✓
"未落库且不可重投 → failed"                            → warning ✓

# 加固项失败 → 静默（但记日志）
"习惯沉淀失败"                                        → 不阻断主流程 ✓
"Tracer 写库失败"                                     → 不阻断主链路 ✓
```

**这个区分的标准是：失败会不会导致"数据不正确或用户被误导"。** —— **能说清这个标准，比"我加了告警"有深度。**
