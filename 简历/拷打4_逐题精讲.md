## 面试官的评分模型

| 维度 | 权重 | 看什么 | 你说错一句话的代价 |
|---|---|---|---|
| **真实性**（做了没有） | 30% | 能否现场复现、指到文件行 | 一处造假 → 全盘归零 |
| **一致性**（说的=做的） | 20% | 简历 / README / 代码 / 复盘**四方对齐** | 数字打架 → 可信度崩 |
| **深度**（为什么这么做） | 20% | 因果链、边界、替代方案取舍 | 只会背概念 → 判定包装 |
| **工程性**（可维护/可观测） | 15% | 测试、日志、失败处理、整洁度 | 根目录堆垃圾 → 减分 |
| **诚实度**（知道边界） | 15% | 主动说"这块我没做" | 硬撑 → 直接淘汰 |

**📖 科普：为什么"一致性"占 20%，却比"真实性"更容易崩？**

因为**真实性**是一次性的（你做没做，看一眼就知道），而**一致性**是**全局的** —— 简历、README、复盘清单、代码注释，任何两处打架，面试官就会**重新验证你说的每一句话**。

你的项目已经踩过这个坑：整改清单说"取消能力缺失"、代码里 `cancel_session` 却完整实现。这类问题**不是技术不会，是文档追不上代码**。

## 0.5.0 项目头

**原文**（简历 `:13-15`）："…SQL 承担**全部**数值计算，模型**只**负责语义理解与语言组织…"

**【质疑】** 两个绝对词（"全部" / "只"）+ 一个矛盾（单机 vs 并发优化）。

### L2「SQL 承担全部数值计算」——真的吗？

**【真相】** ❌ **不准确**。实测有三处是 Python 计算：

| 计算 | 位置 | 谁算 |
|---|---|---|
| 比价溢价率 | `agents/orchestrator/nodes.py:34` 引入 `from coreModules.price_compare import calc_premium_evaluate` | **Python** |
| 预算档位 | `nodes.py:1217` `_calc_month_budget_status` | **Python** |
| 预警档位 | `nodes.py:1400` `_calc_alert_facts` | **Python** |

**【科普】** 这不是缺陷 —— **"谁算"不重要，"模型有没有参与算"才重要**。真正的红线是：**模型不参与任何数值计算**。所以：

- 账目事实（金额、汇总、占比）→ SQL ✅
- 派生指标（溢价率、档位）→ Python 确定性计算 ✅
- **共同点**：都是**确定性**的，都不经过模型

**【应答】**
> "我要修正措辞：不是'全部由 SQL'。**账目事实**确实全走 SQL；但**派生指标**（比价溢价率、预算档位、预警档位）是 Python 确定性计算的。
> 我真正的设计是'**模型不参与任何数值计算**' —— 这个说法更准。"

### L3「模型只负责语义理解」——真的吗？

**【真相】** ❌ **不准确**。代码里有大量**关键词启发式**参与决策：

| 启发式 | 位置 | 作用 |
|---|---|---|
| `AMOUNT_REGEX` | `nodes.py:205` | 金额提取/校验 |
| `prune_tasks_by_heuristics` | `nodes.py:656` | **剪枝** LLM 规划出的任务 |
| `repair_task_names` | `nodes.py:798` | **修正** LLM 返回的任务名 |
| `_is_consume_statement` | `nodes.py:385` | 判断"奶茶15块"是陈述还是记账 |

**【科普】** 这是**工业界标准做法**，不是遮掩。原因：LLM 输出是**概率性**的，会漏任务、会脑补任务；而启发式是**确定性**的，用来**兜底修正**。

**所以准确的分工是三层**：
```
模型（概率性规划）→ 启发式（确定性校验/剪枝/修正）→ 执行（确定性）
```

**【应答】**
> "模型负责'理解和表达'这个说法不准。准确的分工是：**模型做概率性规划，代码做确定性校验** ——
> 有 `AMOUNT_REGEX` 校验金额、`prune_tasks_by_heuristics` 剪掉不合理任务、`repair_task_names` 修正任务名。
> 这是**双保险**：模型负责覆盖面，代码负责兜底。"

### L4「单机运行」vs「并发优化」矛盾吗？

**【真相】** ❌ **不矛盾**，但简历没说清。

**【科普】** 「单机」指的是**部署形态**（一台机器、无服务端），「并发」指的是**执行模型**（同一请求内多个子任务并行）。两者是**不同维度**：

- 单机 ≠ 单线程：一台机器上仍可跑多协程
- 你的并发是**请求内并行**（`dispatch_node` 整波派发，`nodes.py:1967` 的 `BATCH_DISPATCH_ENABLED`），不是"多用户并发"

**【应答】**
> "不矛盾。'单机'是**部署形态**（无服务端、数据在本地），'并发'是**执行模型**（一句话里多个子任务并行执行）。
> 我优化的是后者，不是多用户并发。"

### L5「仅记账 Agent 具备写权限」——同进程怎么强制？

**【真相】** ⚠️ **拦不住**。

- `mcpGateway/rbac_config.py:66-94`：`get_agent_permission(agent_id)` 是**代码内静态映射**
- 权限校验在 `ToolSpec.required_perm`（引擎层）
- **但**：同进程内若有人直接 `sqlite3.connect().execute("INSERT INTO bill...")`，**完全绕过**

**【科普】** 这里要分清**两层**：

| 层 | 含义 | 你的实现 |
|---|---|---|
| **逻辑层约定** | 正常路径下，代码按约定调用，引擎校验权限 | ✅ 有 |
| **机制层强制** | OS / 进程级隔离，绕过不可能 | ❌ 没有 |

**Python 同进程内做不到机制层强制**（没有 OS 级访问控制）。要强制必须**拆进程 + 各自持受限 DB 账号**，代价是引入 IPC 与状态序列化开销。

**【应答】**
> "**拦不住。** 这套权限是**逻辑层约定**，不是 OS 级强制隔离 —— 同进程内绕过 `invoke` 直连数据库是可能的。
> 要真正的强制隔离，路径是**拆成独立进程 + 各自持受限数据库账号**，代价是丢掉零 IPC 开销，**当前规模下我没有做**。
> 但在**正常路径**上它是有效的：工具的 `required_perm` 在引擎层强制校验，越权调用直接拒绝。"

### L6「重试自动生效」——⚠️ **最狠一问**

**【真相】** ❌ **不成立，这是死代码**。

- `registry.py:449/457/469/478/496/570/578/586/594/602/611/683/693/701/709/718` —— **所有 16 个工具都是 `max_retry=0`**

**【科普】** 为什么不启用？

`registry.py:392-393`：**底层 `_call_server` 已自带 2 次连接重试**，外层再重试会**放大成乘数效应**（2×N 次）。所以引擎层 M1 阶段刻意不重试。

**这是合理的设计，但对外表述必须准确** —— 不能说"重试已生效"。

**【应答】**
> "这条我必须纠正：**引擎层的重试当前没有启用** —— 所有工具 `max_retry=0`，那段重试代码是**预留能力**，线上不执行。
> **重试实际发生在底层** `_call_server`（自带 2 次连接重试）。
> 原因是：外层再重试会和底层乘数叠加（2×N），所以引擎层刻意收口为 0。
> 简历里'重试自动生效'这个说法**不准确**，我已经改掉。"

**【应答】**

## 2.2 编排核心 / LangGraph

### Q22 · 编排图有条件边吗？★★★★★

**【真相】** ❌ **没有**。

`agents/orchestrator/graph.py` 全文：
```python

builder.add_edge("collect_node", END)
```
**只有 4 条 `add_edge`，无 `add_conditional_edges`**。

**【科普】** LangGraph 有两种表达分支的方式：
1. **`add_conditional_edges`**：在图**编译期**声明"从 A 出发，根据函数返回值去 B 或 C"
2. **`Command(goto=...)`**：在**节点内部运行时**动态决定目标

后者更灵活（分支逻辑和节点逻辑在一起），代价是**图的拓扑不再能从代码静态看出**。

**【应答】**
> "编排器**没有条件边**，分支全用 `Command(goto=...)` 表达。**条件边在子 Agent 里**（如 stat/finance 的 verify 重试）。
> 编排器用 LangGraph 的价值主要是：**StateGraph 的状态合并语义** + **5 张图统一心智模型**。
> **去掉它**，编排器核心逻辑能省几十行，但要自己实现状态合并和中断恢复。"

### Q23 · 用了 LangGraph 的 `Send` 吗？为什么自己写 Queue？★★★★★

**【科普】** `Send` 是 LangGraph 的**扇出原语**：一个节点可以动态发出 N 个并行分支，每个带独立 State。

**【真相】** ❌ 没用。理由（要能讲清）：

| 需求 | `Send` | 你的 Queue |
|---|---|---|
| 跨请求的任务生命周期 | ❌ 随图执行结束 | ✅ **独立于请求**（DB 持久化） |
| 崩溃后重投 | ❌ 不支持 | ✅ `resubmit_submitted` 从 DB 重投 |
| 用户取消在途任务 | ❌ 无入口 | ✅ `cancel_session` |
| 队列深度/背压 | ❌ 无 | ✅ `maxsize` + `queue_depth()` |

**【应答】**
> "`Send` 是**单图执行内**的扇出，生命周期随图结束。我的任务需要**跨进程重启**、**可取消**、**有背压** —— 这些 `Send` 都不管。
> 所以我用 `asyncio.Queue` + DB 状态机自己实现。"

### Q24 · Checkpointer 用了吗？

### Q101 · 重试真正落地怎么设计？★★★★★

**已知**：引擎层 `max_retry=0`（死代码）。

| 方案 | 代价 |
|---|---|
| A. **全局 retry budget**（整个请求共 N 次） | 简单，但一个坏工具会耗尽预算 |
| B. **每工具独立预算** | 精细，但要为每个工具配 |
| C. **预算 + 熔断 + 抖动** | 最稳，复杂度最高 |

**关键点**（要能答）：
1. **有副作用的工具永不重试** → 但**用户侧**怎么办？→ 靠**幂等键**（`task_id`）+ 用户可见的失败提示
2. **重试与幂等配合**：重试前必须确认操作幂等；写操作靠 `task_id`
3. **重试风暴**：熔断（连续失败 N 次停一段时间）+ 抖动（jitter 避免同时重试）
4. **怎么验证**：注入故障（mock 超时/5xx）跑集成测试

# 补充专章 · 优雅关机 / 进程退出防御（M23 / D26）

> **科普**：优雅关机（graceful shutdown）= 进程收到"要关了"的信号后，**不靠 OS 强杀**，自己有序地：① 停止接新任务 → ② 处理/中断在途任务 → ③ 落状态 → ④ 释放资源 → ⑤ 退出。
>
> **关键点**：Python 里 `SIGTERM`（`kill -15` / `docker stop`）的**默认行为是直接终止** —— **不抛异常、不执行 `finally`、不跑 `atexit`**（依据 `webUI/app.py:99-102`）。不处理就会**留下孤儿进程**。

**它和崩溃恢复是对偶面**：崩溃 = "来不及关"，优雅关闭 = "主动关"。共同构成**进程生命周期可靠性**。

### QJ2 · 你的优雅关机流程

**【真相】** `startup/bootstrap.py:491-512` `shutdown_system()`：

```python
SHUTDOWN_FLAG = True              # ① 停止接新任务
for task in WORKER_TASKS: task.cancel()   # ② 中断在途
await asyncio.gather(*WORKER_TASKS, return_exceptions=True)  # ③ 等收敛
await stop_mcp_servers()          # ④ 关 MCP 子进程
```

触发源：Ctrl+C / SIGTERM / 输入 exit / WebUI 退出。

### QJ3 · worker 卡在 `await queue.get()` 看不到 flag

**【真相】** ✅ 属实。`bootstrap.py:254/304/348/389` 是 `while not SHUTDOWN_FLAG`，**阻塞在 await 里看不到 flag**。

**真正的退出手段是 `task.cancel()`**（`:507-509`）—— flag 只是让循环**不再接新任务**。

### QJ4 · ⭐⭐ 没有 drain（置 flag 后立刻强断）★★★★★

**【真相】** ✅ 属实。`:506-509` 置 flag → **立即** cancel，无等待在途任务的步骤。

**且** `shutdown_system` docstring `:495` 说"让 worker **自然退出**" —— **与实际行为不符**（又一处文档↔行为漂移）。

**【应答】**
> "属实。我的'优雅关闭'实际是**'尽力断开'**，不是真 drain —— 置 flag 后立刻 cancel 在途任务。
> **为什么不先等在途**：记账任务很短（秒级），等待的收益小于快速退出的收益；且中断后靠 `interrupted` → 重启重投 + 对账兜底。
> **但要改的话**：先置 flag → 等在途任务 N 秒 → 超时再 cancel。这是 K8s `terminationGracePeriodSeconds` 下的标准做法。"

### QJ5 · ⭐ shutdown_system 没有超时兜底 ★★★★★

**【真相】** ✅ 属实，且**这是真 bug**。`bootstrap.py:509` `gather(...)` **无 timeout**。

**【科普】** `task.cancel()` **只在下一个 `await` 点生效**。若 worker 卡在**同步调用**（同步 DB/同步 LLM）里，**cancel 无效** → `gather` **永久挂死**、进程永不退出。

**【修法】**
```python
await asyncio.wait_for(
    asyncio.gather(*WORKER_TASKS, return_exceptions=True),
    timeout=N)
```
超时则记 WARNING 后继续走 `stop_mcp_servers()`。

### QJ6 · ⭐ SIGTERM 处理器真的测过吗？★★★★★

**【真相】** ✅ **只做了源码级断言**：`tests/unit/test_m23_exit_defense.py:203-220`
```python

```
小标题自标"③ L2：信号与 CLI 收尾（**源码级**）"。

**【科普】** **源码里有字符串 ≠ 运行时有效**。真正的验证是**实际 `kill -15` 一次**，看进程是否走了 `finally`、MCP 子进程是否清理干净。

**【应答】**
> "属实，**我没真跑过 `kill -15`**。测试只是断言源码里有 `signal.SIGTERM` 这个词。
> 理由当时是'导入链拉 gradio 实测要 8 秒' —— 这个理由**不充分**，应该放进 `tests/integration` 做慢测。这是我认的 gap。"
