# 崩溃恢复 · 强杀验证记录（M5）

> **用途**：应对「已通过进程强杀场景验证」这句简历描述的追问。
> **生成方式**：`_kill_test.py` 实跑，非手工构造结论。
> **验证时间**：2026-10-08
> **环境**：Windows / Python 3.11 / 真实系统（3 个 MCP 常驻服务 + 真实外部模型）

## 为什么这么设计（这是能讲出深度的地方）

**「账单已写、状态未更新」这个最危险的中间态，窗口只有毫秒级** —— 真实 `kill -9` 几乎不可能精确命中。

所以验证方案分两层：

```
① 真实 SIGKILL  → 证明"确实杀得进、且杀在任务执行中"，覆盖端到端的真实现场；
② 构造中间态    → 对每个对账分支做确定性覆盖（含窗口极窄的那一个）。
```

**两层结合 = 既有真实证据，又有对每个分支的确定覆盖。** 只做 ① 覆盖不全，只做 ② 没有真实现场。

## 场景 A · 真实 SIGKILL（杀在「任务已被 worker 领取、执行中」）

**方法**：子进程跑一次完整多任务请求；父进程轮询 `task_state`，一旦检测到 `running` 立即 `SIGKILL`。

**实跑输出**：

```
t=5s   尚无 running 任务，继续等…
t=10s  尚无 running 任务，继续等…
…
t=30s  检测到 1 个 running 任务 → 立即 SIGKILL
已发送 SIGKILL（pid=2612），返回码=1

强杀后 task_state 残留：
  t179147073341136  bill_agent  running

模拟重启（调用 bootstrap 同款 recover_orphans）：
  对账统计：{'completed': 0, 'resubmitted': 0, 'failed': 1}
  对账后状态：
  t179147073341136  bill_agent  failed
```

**结果解读**：

- 强杀精确命中 `running` 状态（**不是 submitted、也不是已结束**）；
- 该任务是 `bill_agent`（**有写副作用 → `retriable=0`，禁止盲重投**）；
- 重启对账查询 `bill` 表**未发现该 `task_id`** → 说明账单没写成 → **判 `failed`**；
- **这是刻意的保守选择：宁可告警让人介入，也不自动重投去冒"重复记账"的风险。**

---

## 场景 C · 崩溃在「账单已写、状态未更新」（★最关键）

**构造方法**：先往 `bill` 表写入一条带指定 `task_id` 的账单（模拟"已经写进去了"），再把 `task_state` 里同一 `task_id` 置为 `running`（模拟"状态还没来得及更新"），然后调用**真实的 `recover_orphans`**。

**实跑输出**：

```
构造完成：
  t-killtest-bill-written  running  retriable=0  running(bill, 账单已写)

调用 recover_orphans：
  [M5] 崩溃对账：task=t-killtest-bill-written 账单已落库 → 标记 completed（非 failed）

对账后：
  t-killtest-bill-written  completed  (期望 completed) ✅
```

**结果解读**：

- 对账逻辑**按 `task_id` 反查业务表**，发现账单已落库；
- 判定为 **`completed` 而非 `failed`、更不是重投** —— **账单不会写第二遍**；
- 源码注释里写明了这个判断的动机：*「不能标 failed，否则重启后『账已记』却因 `retriable=0` 被判 failed」*。

**这条是整套验证里最有价值的一条**，因为它覆盖的是**唯一会导致"重复记账"的路径**。

## 完整用例表

| # | 中间态 | `agent_id` | `retriable` | 账单是否已写 | 对账结果 | 语义 |
|---|---|---|---|---|---|---|
| B | `submitted`（队列中） | `stat_agent` | 1 | — | `submitted` | 重投 |
| **C** | `running` | `bill_agent` | **0** | **是** | **`completed`** | **判完成，不重复记账** |
| D | `running` | `bill_agent` | **0** | 否 | `failed` | 宁可告警不重复 |
| E | `running` | `stat_agent` | 1 | — | `submitted` | 安全重投 |
| A | 真实 SIGKILL | `bill_agent` | 0 | 否 | `failed` | 同 D |

**贯穿的一条规则**：
> **`retriable` 由「是否有写副作用」决定，不由「任务是否失败」决定。**
> 写任务（`bill_agent`）**永不自动重投**；读任务（`stat`/`price`/`finance`）可安全重投。

## 面试话术（被问「强杀验证怎么做的」时）

> 我做了两层验证，因为**最危险的那个中间态窗口太窄，真实强杀打不中**。
>
> **第一层是真实 SIGKILL**：起一个子进程跑完整请求，父进程轮询任务表，一检测到 `running` 就立刻强杀。实测在 t=30 秒左右命中，残留任务状态确实是 `running`——**证明杀进了执行中，不是杀在队列里或结束后**。重启后对账，这个 `bill_agent` 任务因为**账单没写成、且写任务不可重投**，被判 `failed`。
>
> **第二层是构造中间态**，因为有个状态真实强杀几乎打不中——**「账单已经写进库了，但状态还没来得及从 `running` 改成 `completed`」**，这个窗口只有毫秒级。我把它构造出来，然后调用**真实的 `recover_orphans`**，结果判成 `completed`：**因为对账是拿 `task_id` 去反查 `bill` 表，有记录就说明副作用已经发生了，绝不能重投——否则就是写两遍账。**
>
> **一共覆盖了 5 个分支**：队列中、写任务执行中（账单已写 / 未写）、读任务执行中、真实强杀。**对账统计是 `completed: 1 / resubmitted: 1 / failed: 1`，全部符合预期。**
>
> 验证脚本是自动化的，我保留了它——**跑一次就能复现**。
