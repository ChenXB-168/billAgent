## Q6 · 投递延迟 vs 端到端延迟

> **⭐ 这节是全项目最能体现「工程严谨性」的一节。** 因为面试官会用一个陷阱题试探你：
> **「`time.sleep(0.1)` 实际睡 100-110ms，你为什么测出 94.9ms？」**
> 这一刀的真实意图是抓"你根本没测，数字是编的"。**你有完整答案。**

### L1｜0.1ms 是投递延迟对吧？端到端你测了吗？ ✅

**答**：**两个都测了，而且我明确区分这两个指标。**

| 指标 | 数值 | 测量脚本 |
|---|---|---|
| **投递延迟**（消息入队 → 被 worker 取走） | P95 **94.9 ms → 0.10 ms** | `bench/bench_a2a_latency.py` |
| **端到端**（用户输入 → 拿到回复） | **数十秒量级** | `bench/bench_e2e.py` |

**★关键：这两个数字差两个数量级，但他从不混用** —— 简历上写的是「**投递延迟**」，不是「系统性能」。

| | 投递延迟 | 端到端 |
|---|---|---|

**投递延迟降 950 倍，端到端只降 24%** —— **这不是矛盾，这就是真实系统**：**代码层能优化的部分本来就只占一小块。**

**面试时这句话要说出来**：

> 投递延迟从 94.9ms 降到 0.1ms，**这不代表系统快了 950 倍**——端到端只降了约 24%。
> 因为**端到端的大头是 LLM 推理**，我这轮优化动的是"代码开销"那部分。
> **我在简历上写的是「投递延迟」而不是「系统性能」，就是这个原因。**

### L5｜94.9ms 那次是怎么测的？`time.sleep(0.1)` 实际睡眠在 CPython 里通常 100-110ms，你为什么是 94.9？ ⭐✅

**★ 这是全场最强的一刀，也是最强的回答。**

**答**（**必须讲满 2 分钟**）：

> **94.9ms 不是"sleep 的实际睡眠时长"，而是"端到端投递延迟的 P95"。**
>
> 我的基准脚本模拟的是**真实调度场景**：消息到达时刻相对 100ms 轮询周期**是随机的**（不是我掐着点 sleep）。所以延迟**均匀分布在 [0, 100ms]**：
>
> | | 理论值（均匀分布） | 实测值 |
> |---|---|---|
> | **P50** | 50 ms | **47.6 ms** |
> | **P95** | 95 ms | **94.9 ms** |
> | **均值** | 50 ms | **50.4 ms** |
>
> **三个指标都与理论值吻合**，说明**测量方法本身是对的**。
>
> **反过来说**：**如果我测出来是 100ms 或者 110ms，那才说明我测错了**——因为那意味着我把 `time.sleep` 的实际睡眠时长当成了延迟。

**★知识点①：为什么均匀分布的 P95 是 95ms**

设轮询周期 `T=100ms`，消息到达时刻在周期内**均匀随机**（0~T）：

- **等待时间** = 从到达时刻到下一个轮询点的距离
- **它也服从 `U(0, T)`** → 均值 `T/2 = 50ms`
- **P95** = 落在 95% 位置的值 = `0.95 × T = 95ms` ✓

**★知识点②：这个回答为什么强**

面试官问这题**不是想知道 94.9 怎么来的，是想确认"你有没有真的测"**。

| 如果回答 | 面试官的判断 |
|---|---|
| "我测的就是 94.9ms" | **在背简历，答不上来** ✗ |
| "可能是误差吧" | 不懂测量 ✗ |
| **"这是 P95 不是 sleep 时长；理论值 95ms，实测吻合；如果测出 100ms 才说明我错了"** | **他知道自己在测什么** ✅✅ |

**★知识点③：这个"反向论证"是点睛之笔**

**"如果我测出来是 100ms 那才说明我测错了"** —— 这句话证明：

1. **他知道理论值应该是多少**（不只是"我跑了个脚本"）
2. **他知道哪种结果是"错误信号"**（有验证意识）
3. **他的实测和理论互相印证**（不是单点数据）

**这一句话的价值，超过任何"我做了性能优化"的陈述。**

## Q7 · 性能优化的因果链

> **这节有真实缺口**：**没有 profile 数据支撑"三步顺序不可换"**。
> 但**缺口不在结论，在证据** —— 结论本身是对的。

### L1｜"三步顺序不可换"怎么证明的？有 profile 数据吗？ ❌

**答**：**没有 profile 数据，这是缺口**（诚实）。

**★但是——这个结论本身可以从机制上论证**：

**「为什么必须先事件驱动、再常驻、最后并行」的因果链**：

```
① 工具服务用 stdio 按需启动 → 每次调用要 Popen 一个 Python 进程（26~29 s 冷启动）
② 如果此时就做"并行派发"：
     stat 和 price 同时启动 → 两个 stdio 进程竞争 CPU
     → 两个都变慢，总耗时 ≈ ΣT 而不是 max(T)
     → 【并行收益被冷启动吃掉】
③ 所以必须先让服务常驻（消除冷启动），并行才有意义
```

**★知识点：这个论证的性质**

它是**机制推演（reasoning）**，不是**实测（measurement）**。

| | 机制推演 | 实测数据 |
|---|---|---|
| **可信度** | 中（逻辑对，但可能漏因素） | 高 |
| **面试评价** | "有判断力" | "有数据" |

**❌ 错误答法**：

> "我试过，先做并行没收益。" ← **如果他没试过，这就是编的**

**✅ 正确答法**：

> **我没有做 A/B 实测**，这是缺口。**但我可以从机制上说清为什么这个顺序不可换**：
>
> ① 冷启动是 26~29 秒，**每次工具调用都要付这个成本**；
> ② 如果此时做并行派发，**两个任务会同时竞争 stdio 进程启动**——两个都变慢，总耗时接近两者之和，**并行收益被冷启动吃掉**；
> ③ 所以**必须先让服务常驻，把"启动成本"这个变量消掉**，并行才能体现为 `max(T)` 而不是 `Σ(T)`。
>
> **如果我要把它变成实测**：用 `BILLAGENT_MCP_STDIO=1` 回滚开关跑一次"并行 + stdio"的对照组，对比耗时。**这个开关我留了，但没跑这个组合。**

**★知识点：为什么"我留了开关但没跑"是好答案**

**回滚开关的存在证明了**：
1. **他知道怎么做 A/B 对照**（说明有实验意识）
2. **他刻意保留了回滚能力**（工程习惯）
3. **只是没排到优先级**（诚实）

**比"我试过了"（可能编）和"没想过"（无意识）都好。**

### L2｜先并行再改事件驱动会怎样？你试过吗？ ❌

**答**：**没试过**。**但机制上看**：


| **LLM 推理** | 数秒~数十秒 | 部分（可并行） |

**所以他的三步顺序是对的**：**先把"串行成本"清掉，并行才有空间。**

### L5｜数据库改 WAL——你测过多协程并发写吗？遇到过 `database is locked` 吗？ ✅✅

**答**：**遇到过，而且做了完整处理 + 做了专门的实验验证。**

**★代码依据（三层都有）**：

```python
# ① utils/common.py —— WAL + busy_timeout
self.conn.execute("PRAGMA journal_mode=WAL")
self.conn.execute("PRAGMA busy_timeout=5000")

# ② execute_sql —— 锁冲突重试
except sqlite3.OperationalError as e:
    if "database is locked" in str(e) and i < retry - 1:
        continue                      # 重试（retry=3）

# ③ 注释写明了为什么不再 sleep
#   "busy_timeout=5000 已由 SQLite 在 C 层吸收锁竞争，不再需要 time.sleep(0.1)
#    （同步阻塞会冻结事件循环）"
```

**★而且他做了实验**：`_sqlite_wal_lab.py` 亲手验证 4 件事：

| 实验 | 结论 |
|---|---|
| ① 默认模式（delete）：写者持锁时读者读 | **被拒 → `database is locked`** |
| ② WAL 模式：同样场景 | **读者成功 → 读不阻塞写** |
| ③ WAL + 两个写者（timeout=0） | **后到的写者失败 → WAL 不解决写写互斥** |
| ④ WAL + 两个写者（timeout=5000） | **后到的写者等待后成功 → busy_timeout 的作用** |

**★知识点①：WAL 到底解决了什么**

| | 回滚日志模式（delete） | **WAL** |
|---|---|---|
| **写事务占什么锁** | **EXCLUSIVE**（连读也挡） | **不占 EXCLUSIVE** |
| **读写关系** | **写阻塞读** ✗ | **读不阻塞写、写不阻塞读** ✓ |
| **写写关系** | 互斥 | **仍然互斥**（SQLite 永远单写者） |

**这是最容易搞混的一点**：**WAL 解决的是"读写冲突"，不是"写写冲突"。**

**★知识点②：`busy_timeout` 是干什么的**

**它把"撞锁立即失败"变成"在 C 层等待重试"**：

```
timeout=0      → 撞锁立刻抛 database is locked
timeout=5000   → SQLite 在 C 层等待最多 5 秒，拿到锁就继续
```

**为什么他特意把 `time.sleep(0.1)` 删掉**（这个细节很能说事）：

> 早期是"捕获 locked → `sleep(0.1)` → 重试"。但 **`time.sleep` 是同步阻塞，会冻结整个事件循环**——本来只是想等锁，结果把其他协程全卡住了。
> 改成 `busy_timeout` 后，**等待发生在 SQLite 的 C 层，不占 Python 的事件循环**。

**★知识点③：为什么"进程内锁"和"跨进程锁"要分开处理**

代码注释里写得很清楚：

> `db_lock` 是【进程内】锁，跨进程（主进程 vs MCP server 子进程）写互斥**只能靠 SQLite 层兜底**。

| 层 | 机制 | 覆盖范围 |
|---|---|---|
| **进程内** | `asyncio.Lock`（`db_lock`） | 同一进程的协程之间 |
| **跨进程** | `busy_timeout` | 主进程 vs 3 个 MCP 子进程 |

**答法（完整版）**：

> 遇到过，而且我为此专门写了个实验脚本验证 SQLite 的锁行为。
>
> **三层处理**：
> ① **WAL 模式** —— 让读不阻塞写（这是我做并行派发的前提）；
> ② **`busy_timeout=5000`** —— 把"撞锁立即失败"变成"在 C 层等待"，**注意这个等待不占 Python 事件循环**；
> ③ **`database is locked` 重试（retry=3）** —— 兜底。
>
> **有个细节我想说**：早期我用的是"捕获 locked → `time.sleep(0.1)` → 重试"，后来删掉了 sleep——**因为 `time.sleep` 是同步阻塞，会冻结整个事件循环**，本来只是想等锁，结果把别的协程全卡住了。**改成 `busy_timeout` 后，等待发生在 SQLite 的 C 层。**
>
> **另外我明确知道 WAL 的边界**：**它解决的是读写冲突，写与写仍然互斥**——SQLite 永远是单写者。所以我做了**进程内 `db_lock`（协程级）+ 跨进程 `busy_timeout`** 的分层。

**⭐ 这个回答会让面试官明显提高评价** —— 因为**大多数人只会说"我开了 WAL"，说不出"WAL 不解决写写互斥"和"sleep 会冻结事件循环"**。

### L6｜"三步顺序不可换"——如果第一步只做了事件驱动但没改 HTTP 常驻，第二步并行派发有收益吗？为什么？ ⚠️

**答**：**几乎没有收益**。

**论证**：

```
只做①事件驱动（投递 50ms）+ 没做②常驻（冷启动 26~29s）
   → 并行派发两个任务
   → 两个都省下了 50ms 投递等待
   → 但各自仍要付 26~29s 冷启动，且两个同时启动会互相争 CPU
   → 总耗时 ≈ 26~29s+（甚至比串行更慢）
   → 【收益 ≈ 50ms，相对 26 秒可以忽略】
```

**★知识点：优化的"木桶效应"**

**优化收益由"最大瓶颈"决定**：

```
总耗时 = 投递等待(50ms) + 冷启动(27000ms) + 推理(T)
                    ↑ 这个占 99.8%
```

**先把 50ms 优化到 0.1ms，只影响 0.2%**；**而消掉 27 秒的冷启动，影响的是 99.8%。**

**所以"顺序不可换"的本质是：先消除主导项，再消除次要项。** —— **这是 Amdahl 定律的直观应用。**

## Q9 · 幂等性

### L1｜崩溃恢复后重派任务——如果 Worker 执行了一半，重派写两次，你怎么防？ ✅

**答**：**按 `task_id` 反查业务表对账，而不是无条件重投。**

**★完整的判定逻辑**（`recover_orphans`）：

```python
if agent_id in SIDE_EFFECT_AGENTS and self._bill_exists(bill_db, task_id):
    # → 账单已落库 → 副作用已发生 → 标 completed（绝不重投）
    UPDATE task_state SET status='completed' ...
elif retriable and cnt < MAX_RETRY:
    # → 没写过 + 可重投 → 标 submitted（安全重投）
else:
    # → 没写过 + 不可重投（写任务） → 标 failed（宁可告警）
```

**★知识点：为什么"对账"比"重试"更可靠**

| 方案 | 假设 | 风险 |
|---|---|---|
| **无条件重试** | "任务没成功" | **若实际成功了呢 → 重复写入** ✗ |
| **对账后重试** | **"先查清副作用发生没有"** | **需要业务知识（查哪张表）** ✓ |

**核心洞察**：**"重试"的前提是"能判断上一次有没有生效"** —— 而**这个判断需要业务语义**（账单在 `bill` 表、按 `task_id` 反查），**框架给不了**。

### L2｜你的任务有幂等键吗？是什么？任务 ID？用户指令哈希？ ✅

**答**：**`task_id`**（格式 `t{毫秒时间戳}{hex3}`）。

**★代码依据**：`task_state` 表的 `task_id` 是**主键**，建单用 `INSERT OR IGNORE`：

```sql
INSERT OR IGNORE INTO task_state (task_id, ...) VALUES (?, ...)
-- task_id 主键即幂等键 —— 重复投递同一 task_id 不会重复建单
```

**★知识点①：为什么用 `task_id` 而不是"用户指令哈希"**

| 方案 | 问题 |
|---|---|
| **用户指令哈希** | **用户真的想记两笔一样的时候（连续两杯咖啡）→ 会被误拦** ✗ |
| **`task_id`（每次请求新生成）** | **同一句话说两次 = 两个不同任务** ✓ |

**这点很关键**：**幂等键要区分"重复投递"和"真实重复操作"** —— **前者要拦，后者要放行。**

**★知识点②：`task_id` 的格式设计**

```
t + 毫秒时间戳 + 6 位随机十六进制
t179147073341136
```

| 特性 | 好处 |
|---|---|
| **含时间戳** | **可排序**（能按时间查任务） |
| **含随机位** | **同毫秒内不冲突** |
| **纯 ASCII + 定长前缀** | 便于日志检索 |

**而且它和 `run_id` 同构**（`r{ms}{hex3}`）—— **同一种生成策略，全局一致。**

### L3｜写操作前查重？还是数据库唯一索引？ ✅

**答**：**两条都用了，但用途不同**：

| 机制 | 位置 | 作用 |
|---|---|---|
| **主键幂等**（`INSERT OR IGNORE`） | `task_state.task_id` | **防重复建单** |
| **业务表反查**（`SELECT ... WHERE task_id=?`） | `recover_orphans` 时查 `bill` | **防重复执行** |
| **进程内串行**（`db_lock`） | `DatabaseCRUD` | 防协程间写冲突 |

**★知识点：为什么"任务表唯一"不够，还要查业务表**

**这两者的语义完全不同**：

```
task_state 有记录   →  只能说明"这个任务被创建过"
bill 表有记录       →  才能说明"这次记账真的生效了"
```

**崩溃可能发生在两者之间的任何一点**：

```
create_task（task_state 有） → worker 领取（running） → 写账单（bill 有） → 标 completed
                                                    ↑ 崩在这里
```

**崩在这个点时**：`task_state` 说 running、`bill` 说写过了 —— **只有查业务表才知道真相。**

**★知识点：为什么没给 `bill.task_id` 加 UNIQUE 索引**

**其实可以加，而且加了会更安全**（数据库层强制唯一）。**他没加**，原因可能是：

- **`task_id` 是可空列**（兼容历史数据），**SQLite 的 UNIQUE 允许多个 NULL**
- **加唯一约束要重建表**（SQLite 不支持 `ADD CONSTRAINT`）

**⚠️ 这是一个可以被追问的点**，准备好这个答案：

> `bill.task_id` **没加 UNIQUE 约束**。原因有两个：一是这个列是**后加的、可空的**（兼容历史数据），二是 **SQLite 加唯一约束要重建表**。
>
> **但代价是"防重复"依赖应用层对账，而不是数据库层强制。** 如果要加固，我会用 `CREATE UNIQUE INDEX ... WHERE task_id IS NOT NULL` —— 这样既兼容历史 NULL，又对新数据强制唯一。

**★知识点：SQLite 的部分索引（partial index）是个好工具**

```sql
CREATE UNIQUE INDEX idx_bill_task ON bill(task_id) WHERE task_id IS NOT NULL;
```

**它只约束"非 NULL 的行"** —— 完美匹配"历史数据没有 task_id、新数据必须有且唯一"的需求。

**"IGNORE" 的意思是"主键冲突时静默跳过"**，**不是"报错"** —— 这保证了**重复投递不会失败、也不会重复建单**。

### L4｜两套状态更新的顺序是什么？先更哪个？ ✅

**★他的状态流转顺序**（`task_state` 内的单表流转）：

**★关键：业务写入与状态更新的顺序**（这才是真问题）：

```python
# ① 先执行 INSERT INTO bill（业务副作用）
```

```
✓ 先写账单（产生"已发生"的证据）
✓ 再更新状态（记录"已完成"）
→ 崩在中间：有证据、无记录 → 可以查证据判断

✗ 先更新状态
✗ 再写账单

```

> 严格说，这个顺序**不是我用代码强制保证的**，是**图结构天然决定的**——账单写入在子图内部，状态更新在 `track()` 包裹层。**如果有人说"这表明顺序是偶然的"，我承认这个批评有道理**；但**结果是对的**，而且我会在未来的重构里把它变成显式约定。

### L5｜第一步成功第二步失败——中间态怎么处理？有补偿事务吗？ ✅

**答**：**没有补偿事务，但有"对账"** —— **对账是"事后判定"，补偿是"主动撤销"，两者不同。**

**★知识点：对账 vs 补偿**

| | 对账（他用的） | 补偿（他没做） |
|---|---|---|
| **时机** | **事后**（重启时） | 即时或事后 |
| **动作** | **判定"发生没有"** | **撤销已发生的** |
| **难度** | 中（需业务知识） | **高（需反向操作）** |
| **适用** | **插入型操作**（记账） | 需要"撤销"语义的操作 |

**为什么"插入型操作"不需要补偿**：

```
记账是"追加"语义 —— 写进去了就是写进去了，没有"未完成"的中间态
（不像转账，有"扣款成功但未到账"的中间态）
```

**答法**：

> **没有补偿事务，我用的是"对账"** —— 这两者解决不同的问题。
>
> **对账是事后判定**："这次副作用到底发生了没有？" → 有就判完成、没有就重投。
> **补偿是主动撤销**："把它撤回来"。
>
> **我的场景不需要补偿**，因为**记账是"追加"语义**——写进去就是写进去了，**不存在"扣了款但没到账"这种需要回滚的中间态**。
>
> **但 M16 用户取消时我明确说了不做补偿** —— 因为"用户取消"是"别再继续"，**不是"当作没发生"**。如果要做"撤销已记的账"，那是**补偿事务**，**需要反向操作 + 业务语义定义**（比如并行的 4 个任务里 A 成功了 B 还在跑，取消时 A 的账撤不撤？）。**这是两个不同的问题。**

**★知识点：什么操作需要补偿事务**

| 操作类型 | 中间态 | 需要补偿 |
|---|---|---|
| **插入**（记账） | 无（要么写了要么没写） | ❌ |
| **转账** | **扣款成功、到账未完成** | ✅ **必须** |
| **库存扣减** | 扣了但订单没生成 | ✅ |
| **多步编排** | 步骤 2 失败、步骤 1 已完成 | ✅ |

**他的记账是纯插入，所以对账足够。**

## Q11 · SQLite 并发与崩溃

> **⭐ 核实代码后这节要改写**：**他比我原先判断的深得多** ——
> **WAL + busy_timeout + 锁冲突重试三层都有，还写了实验脚本验证。**

### L1｜WAL 模式下 asyncio 多协程同时写——会锁吗？ ✅✅

**答**：**读不锁、写与写仍互斥。**

**★这是最容易被搞混的一点，你要答准**：

| | 回滚日志（delete） | **WAL** |
|---|---|---|
| **写事务持什么锁** | **EXCLUSIVE**（连读也挡） | **不占 EXCLUSIVE** |
| **读写互斥吗** | **是** ✗ | **否** ✓ |
| **写写互斥吗** | 是 | **★ 仍然是** ✓ |

**答法（主动说出边界，比只讲优点强）**：

> **WAL 解决的是"读写冲突"，不解决"写写冲突"。**
>
> 具体说：WAL 下**读走主库快照、写走 WAL 文件**，所以**读不阻塞写、写不阻塞读**；**但同一时刻仍然只能有一个写事务** —— SQLite 永远是单写者。
>
> **这一点我专门验证过**：我写了个脚本对比了 4 种组合：
> - 默认模式 + 写者持锁 → **读者被拒（`database is locked`）**
> - WAL + 同样场景 → **读者成功** ✓
> - WAL + 两个写者（`timeout=0`）→ **后到的失败** ✓（证明写写仍互斥）
> - WAL + 两个写者（`busy_timeout=5000`）→ **后到的等待后成功** ✓

**★知识点：为什么 WAL 能做到"读不阻塞写"**

```
回滚日志模式：
  写事务要改主库文件 → 必须占 EXCLUSIVE 锁 → 谁都别想读 ✗

WAL 模式：
  写事务只追加到 WAL 文件 → 主库不变 → 读者照常读主库快照 ✓
  提交时把 WAL 的变更"checkpoint"回主库（此时才需要独占）
```

---

### L2｜你遇到过 `database is locked` 吗？怎么解决的？ ✅✅

**答**：**遇到过，三层处理。**

| 层 | 机制 | 代码位置 |
|---|---|---|
| **① 日志模式** | `PRAGMA journal_mode=WAL` | `utils/common.py` |
| **② C 层等待** | `PRAGMA busy_timeout=5000` | 同上 |
| **③ 应用层重试** | 捕获 locked → 重试 3 次 | `execute_sql` |

**★有一个细节特别值得说**（代码注释里写明了）：

> **M3.5 后不再做同步 sleep** —— 锁竞争已由 `busy_timeout=5000` 在 SQLite C 层吸收等待，**`sleep` 只会冻结事件循环**。

**这是"知道自己在优化什么"的体现**：

```python
# ❌ 早期实现（会冻结事件循环）
except sqlite3.OperationalError as e:
    if "database is locked" in str(e):
        time.sleep(0.1)      # ← 同步阻塞！整个事件循环卡 100ms
        retry()

# ✅ 现在（等待在 C 层，不占 Python 事件循环）
PRAGMA busy_timeout=5000
```

**答法**：

> 遇到过。**三层处理**：WAL 让读不阻塞写；`busy_timeout=5000` 让 SQLite 在 C 层等待锁；`execute_sql` 还有 3 次重试兜底。
>
> **有一个细节我想说**：**早期我用的是"捕获 locked → `sleep(0.1)` → 重试"，后来把 sleep 删了。**
>
> **原因**：`time.sleep` 是**同步阻塞**，在协程里调用会**冻结整个事件循环** —— 本来只是想等锁，结果**把其他所有协程都卡住了 100ms**。改成 `busy_timeout` 后，**等待发生在 SQLite 的 C 层，Python 事件循环完全不受影响。**

**⭐ 这个回答的价值**：它证明**他知道"在哪等"比"等多久"更重要** —— 同样是等待，**在 C 层等和用 `time.sleep` 等，对事件循环的影响完全不同**。

**SQLite 的 WAL 设计其实比想象中稳健**：

| 崩溃时机 | 后果 |
|---|---|
| **写 WAL 文件时崩** | **未提交的变更丢弃**，已提交的仍在 WAL 里 → **恢复时自动重放** ✓ |
| **checkpoint 时崩** | WAL 文件完整、主库未更新 → 重启后**重新 checkpoint** ✓ |
| **极端情况**（WAL 文件部分写） | **可能损坏** → 需要 `PRAGMA integrity_check` 检测 |

**答法（诚实 + 给出正确做法 + 说清风险边界）**：

> **没做完整性校验，这是缺口。**
>

>
> **真正的风险在"WAL 文件本身写坏"**——这个概率低但存在。**补法是启动时跑 `PRAGMA integrity_check`**，发现问题就从备份恢复。

> **说到备份我得承认**：**我没有自动备份**，而**这块最容易踩的坑是"备份时漏掉 `-wal` / `-shm` 文件"** —— 只拷 `bill.db` 会丢掉最近的事务。**我的代码注释里标注了这一点**（`07 §5.1`），但**没有实现备份脚本**。

**★知识点：备份 SQLite 的正确方式**

```bash

cp bill.db backup/

# ✅ 正确方式一：拷全部三个文件
cp bill.db bill.db-wal bill.db-shm backup/

# ✅ 正确方式二（推荐）：用 SQLite 的在线备份 API
sqlite3 bill.db ".backup backup/bill.db"
```

**"备份要带上 `-wal`"这个坑，他代码注释里写了** —— **说明他知道，只是没做**。

### L7｜SIGKILL 和 SIGTERM 行为一样吗？你两种都测了？ ❌

**答**：**不一样，我测的是 SIGKILL（更强的那种）。**

**★知识点：两者的本质区别**

| 信号 | 能否被捕获 | 进程能做什么 | 他的处理 |
|---|---|---|---|
| **SIGTERM**（15） | ✅ **可以** | **能优雅关闭**（保存状态、清理资源） | `interrupted` 状态 ✓ |
| **SIGKILL**（9） | ❌ **不能** | **立即消失，没有任何清理机会** | **`running` 残留** → 靠对账恢复 ✓ |

**而"断电"又是第三种**：

| | 信号可达 | 文件系统状态 |
|---|---|---|
| **SIGKILL** | ❌ | **OS 仍在，文件系统正常**；未 `fsync` 的数据可能丢 |
| **断电** | — | **可能丢未落盘的写**，甚至文件系统损坏 |

**答法（诚实 + 说清覆盖边界）**：

> **不一样，我只测了 SIGKILL。**
>
> **两者的区别正好对应我的两个状态**：
> - **SIGTERM 可被捕获** → worker 收到后标 `interrupted`（**优雅关闭，重启后重投**）；
> - **SIGKILL 不可捕获** → 进程直接消失、状态停在 `running` → **靠重启对账处理**。
>
> **所以我需要 SIGKILL 这个场景** —— 它验证的是"最坏情况"。**SIGTERM 路径我有单元测试覆盖**（`test_track_cancelled_marks_interrupted`），**但没有做端到端的真实 SIGTERM 测试**，这是我明确知道的覆盖缺口。
>
> **至于"断电"**：它比 SIGKILL 更狠 —— **SIGKILL 时操作系统和文件系统都完好**，断电可能丢 `fsync` 前的写、甚至损坏文件系统。**我没测，也不打算测**（需要真机断电或虚拟化手段）。

**★知识点：为什么"我测了更难的那个"是好答案**

**SIGKILL 是 SIGTERM 的超集场景**（更暴力、更难处理）。**测了 SIGKILL 说明系统能扛住最坏情况**；但**"SIGTERM 没端到端测"仍是缺口**（因为优雅关闭路径是否真的会走到 `mark_interrupted`，只有单测保证）。

**★完整的启动序列**：

```
② 加载用户文档索引（userDocs/ 内容哈希对账）
③ 拉起 3 个 MCP 常驻服务 + 健康检查

⑤ recover_orphans()            ← ★扫描遗留 running/interrupted，定状态
⑥ resubmit_submitted()         ← ★把 submitted 重投进队列
```

**`submitted` 不进扫描是有讲究的**：**它是"声明可重投"的状态** —— `recover_orphans` 把该重投的改成 `submitted`，**再统一步骤重投**。**两阶段分离**，职责清楚。

### L3｜重派失败的任务你怎么处理？重试几次？最终失败怎么办？ ✅

**答**：**重试上限 3 次，超过标 `failed`，等人工介入。**

**★代码依据**：

```python
MAX_RETRY = 3
SIDE_EFFECT_AGENTS = {"bill_agent"}     # 有写副作用的 Agent

# recover_orphans 里：
if retriable and cnt < MAX_RETRY:
    # 重投 + retry_cnt + 1
else:
    # 标 failed
```

**★知识点：为什么"写任务"和"读任务"的重试策略完全不同**

| Agent | `retriable` | 崩溃后 | 理由 |
|---|---|---|---|
| **`bill_agent`（写）** | **0** | **不重投** | **重投可能写两遍账** ✗ |
| **`stat` / `price` / `finance`（读）** | **1** | **安全重投** | 无副作用，重跑无害 ✓ |

**而且写任务不是"直接失败"，而是先对账**：

```python
if agent_id in SIDE_EFFECT_AGENTS and self._bill_exists(bill_db, task_id):
    # 账单已写 → 判 completed（不是 failed！）
```

**答法**：

> **重试上限 3 次，超过标 `failed`。** 但更重要的是**写任务和读任务走的是不同路径**：
>
> **写任务（`bill_agent`）默认 `retriable=0`，不自动重投** —— 因为**重投的风险是"写两遍账"**，比"任务失败"严重得多。
>
> **但它也不是直接判失败**：**先按 `task_id` 查 `bill` 表** —— **有记录就判 `completed`**（说明上次其实成功了），**没记录才判 `failed`**。
>
> **读任务（统计 / 比价 / 理财）`retriable=1`，可以安全重投** —— 因为没有副作用，重跑一遍没有代价。
>
> **所以这条规则的本质是**：**`retriable` 由"有没有写副作用"决定，不由"任务是否失败"决定。**

**★知识点：`failed` 之后呢？**

**他的实现止步于"标 failed + 打告警日志"**：

```python

    logger.warning(f"[M5] 崩溃恢复完成：{stat}")
```

**生产上还应该**：告警通知 + 人工介入入口 + 失败任务的查询界面。**他明确说了"宁可告警也不重复记账"** —— **这是正确的取舍**（因为重复记账的代价 > 任务失败的代价）。

### L4｜对账时任务表锁吗？不锁的话扫描期间有新任务进来怎么办？ ✅

**答**：**启动时串行执行，此时没有任何任务在跑，所以不存在并发问题。**

**★知识点：为什么"启动期对账"天然安全**

```
bootstrap_all() 是同步阻塞的：
  ① clear_all() 清空队列
  ② recover_orphans() 对账
  ③ resubmit_submitted() 重投
  ④ 启动 worker  ← ★到这里才开始消费任务
```

**worker 是在第 ④ 步才启动的** —— **所以第 ②③ 步执行时没有任何消费者，不存在并发写。**

**答法**：

> **不需要锁，因为启动期是串行的、没有任何任务在跑。**
>
> 我的启动顺序是：**先清空队列 → 对账 → 重投 → 最后才启动 worker**。**worker 起来之前，对账已经完成了**，所以**不存在"扫描期间新任务进来"的情况。**
>
> **⚠️ 但有一个前提要说清楚**：这个安全性依赖于"**`bootstrap_all` 只被调用一次**"。如果重复调用，可能会出现"worker 已经在消费，又跑来对账"的情况 —— 所以我用的是**全局单例 `TaskManager`**，且 `bootstrap_all` 内部有幂等保护。

**★知识点：单例的作用**

```python
_MANAGER: "TaskManager | None" = None

def get_task_manager() -> TaskManager:
    global _MANAGER
    if _MANAGER is None:
        _MANAGER = TaskManager()
    return _MANAGER
```

**注释写明了为什么必须单例**：

> 编排器的任务建单与启动期 bootstrap 的恢复/重投**必须共用同一实例**，否则会各自持有独立连接与内存状态，**导致对账不一致**。
