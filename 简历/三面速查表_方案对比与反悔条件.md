# 三面速查表 · 方案对比与「反悔条件」

> **用途**：面试前 10 分钟扫一遍。每题按**同一套框架**答，不会漏、不会只给一个方案。
> **对应**：拷打 v5.0 的 Q100-Q113（前瞻型权衡 / 多方案对比）
> **原则**：答案**绑定你项目的真实实现**，不是通用模板 —— 这样才能讲到文件行号。

---

## 0. 通用框架（Q109 的模板，每题都套它）

```
① 列 3 个可行方案（★至少一个你没用的）
② 逐个说代价（成本 / 复杂度 / 风险）
③ 你选哪个、为什么
④ 什么条件下你会「反悔」（★三面最独特的考点）
```

**★ 自检**：**只能说出 1 个方案 = 你没做过横向调研**（这是三面最常挂人的地方）。

**应答开场白**（争取思考时间）：
> "我先说约束：现在规模是 X、约束是 Y。在这个约束下我列三个方案……"

## Q100 · SQLite 被逼到极限（50 家庭 / 日均 200 万写入 / 99.9% 可用；3 天）

| 方案 | 代价 |
|---|---|
| **A. PostgreSQL 主从** | 要自运维；裸写 SQL 需迁移（`database/init_db.py` 是 SQLite 方言） |
| **B. SQLite + 分片** | 分片键难选（按家庭？按时间？）；跨片查询要自己聚合 |
| **C. 托管 RDS**（你没用的） | 成本、云厂商绑定 |

**选 C**：3 天内**不可能**把 PG 运维好；托管能立刻拿到 99.9%。

**先动**：迁库 + 连接池 + 读写分离
**暂不做**：分片、多活、跨地域
**接受的风险**：云单点 + 成本

**反悔条件**：
1. 月成本超过自建的 3 倍
2. 写入量再涨 10 倍（分片更划算）
3. 合规要求数据不出本地

## Q101 · 重试真正落地（一周，把 `max_retry=0` 收拢）

| 方案 | 代价 |
|---|---|
| **A. 全局 retry budget**（整个请求共 N 次） | 简单；但一个坏工具会耗尽预算，饿死其他 |
| **B. 每工具独立预算** | 精细；但要为每个工具配，配置面大 |
| **C. 独立预算 + 熔断 + 抖动**（你没用的） | 最稳；复杂度最高 |

**选 B**（起步）→ 稳定后加 C。

**四个关键点（都要能答）**：

1. **有副作用的工具永不重试** → 那用户侧怎么办？→ **靠幂等键**（`task_id`，`task_manager.py:108`）+ 给用户可见的失败提示
2. **重试与幂等配合**：重试前必须确认操作幂等；写操作靠 `task_id`
3. **重试风暴**：熔断（连续失败 N 次停一段时间）+ 抖动（jitter 避免同时重试）
4. **怎么验证**：注入故障（mock 超时 / 5xx / 空响应）跑集成测试

**反悔条件**：若工具数超过 30 个（配置面爆炸）→ 改 A + 按 tag 分组。

## Q102 · 静态依赖表没了，完全靠模型规划，怎么保证无环？

**现状**：`_merge_deps`（`nodes.py:1047`）+ `_has_cycle`（`:1073` DFS 检测）+ 检测到环 → 终止（`nodes.py:1850`）。

| 方案 | 代价 |
|---|---|
| **A. 保留 DFS 环检测 + 终止** | 安全但直接失败，用户体验差 |
| **B. 检测到环就**降级为串行**（按模型给的顺序逐个执行）** | ✅ 不会失败，只是变慢 |
| **C. 拓扑排序 + 忽略回边** | 可能丢依赖 |

**选 B**：**退化而不失败** —— 记账场景"慢"比"失败"可接受得多。

**反悔条件**：若串行导致超时率 > 5% → 改回 A 并给用户明确报错。

## Q103 · 明天拆成独立服务，扇出怎么重做？

| 方案 | 代价 |
|---|---|
| **A. LangGraph `Send`** | ❌ **不适用** —— 生命周期随图结束，不能跨进程重启 / 取消 / 有背压 |
| **B. Redis Stream**（你没用的） | 要引入组件；但天然支持持久化 + 消费组 |
| **C. 保留自研 Queue，换成跨进程传输** | 改动最小，但要自己做序列化 |

**选 B**：跨进程后必须有**持久化队列**（否则进程一挂消息就丢，你现在的 `asyncio.Queue` 是内存的）。

**迁移期怎么保证不重复记账**：`task_id` 幂等（两个版本共存时，同一个 `task_id` 只会被执行一次）。

**反悔条件**：若消息量 < 1000/天（Redis 运维成本不划算）→ 退回 C。

## Q104 · "导出三年报表"来了，单事件循环撑不住

**怎么提前判断会撑不住**：它是 **CPU 密集 + 长时（分钟级）** —— 协作式 asyncio 遇到无 `await` 的 CPU 代码会**阻塞整个循环**。

| 方案 | 代价 |
|---|---|
| **A. `run_in_executor` 丢线程池** | 最小改动；但受 GIL 限制，CPU 密集仍只用 1 核 |
| **B. 独立 worker 进程** | ✅ 绕开 GIL；要 IPC |
| **C. 独立报表服务** | 最彻底；运维成本 |

**迁移路径**：A → B → C（**按这个顺序**，每步都可回退）。

**先动 A**（20 分钟），**B/C 等需求真来了再做**。

**反悔条件**：若报表是**一次性的** → A 就够，别过度设计。

## Q105 · 换更强 / 更弱的模型，架构哪里要改？

**耦合点**（要能指出来）：
- `plan_node`（`nodes.py:1522`）的意图识别与结构化输出
- 各子 Agent 的 JSON 解析容错

| 模型 | 要改什么 |
|---|---|
| **更强** | 启发式剪枝（`nodes.py:656`）可**放松**；但仍保留 —— 防极端情况 |
| **更弱** | 白名单 + 回退模板渲染要**加厚**（`number_whitelist.py`） |

**★ 换模型不换架构的关键**：**模型只出不进入"事实层"** —— 数值走 SQL/Python，模型只做理解与表达。这条守住了，换模型只影响"理解质量"，不影响"数据正确性"。

**反悔条件**：若换模型后首答正确率掉 > 15% → 说明耦合点在别处（要去查 prompt，不是改架构）。

## Q106 · 要真做可靠背压（现在只是"拒绝 + 等重启"）

**现状**：`send_task` 满时返回 `False`（`a2a_queue.py:168`），但 `task_manager.py:612` **没消费返回值**。

| 方案 | 代价 |
|---|---|
| **A. 消费返回值 + 记告警**（最小） | 5 分钟；但仍要等重启 |
| **B. 加**实时重投队列**（失败入队，稍后重试）** | ✅ 不用等重启；要防重复投递（靠 `task_id`） |
| **C. 限流 + 优先级队列** | 最完整；复杂度高 |

**选 A + B**（A 必做，B 视规模）。

**反悔条件**：若队列满的频率 < 1 次/天 → **只做 A**，别过度设计。

## Q107 · 权限要从"同进程约定"变"真隔离"

| 方案 | 代价 |
|---|---|
| **A. 拆进程 + 各自持受限 DB 账号** | ✅ **真隔离**；丢掉零 IPC 开销，要序列化 |
| **B. 独立服务 + 网关代理鉴权** | 更彻底；运维重 |
| **C. 维持现状（约定 + 测试）** | 零成本；**拦不住同进程绕过** |

**选 A**（当前规模下 B 过度）。

**怎么证明"真的隔离了"**：写一个**越权测试** —— 拆进程后，从 stat_agent 进程直连数据库写 bill，应该**失败**（账号无权限）。**这个测试现在跑不通，拆完能跑通**。

**反悔条件**：若 IPC 开销导致 P95 延迟涨 > 30% → 退回 C + 补 code review。

## Q108 · 接入公司内部真实工具生态

**能直接复用的**：
- 工具元数据声明 + 统一入口（`ToolSpec`）
- 引擎层横切（权限 / 校验 / 审计 / 超时）
- 适配器模式（`MCPAdapter` / `LocalAdapter`）

**要重做的**：
- **鉴权/配额/审计**要对接公司体系（现在是代码内静态映射）
- 协议适配（真实第三方 MCP 可能有 schema 差异）

**★ 诚实说**：**我没接过真实第三方 MCP**（3 个都是自建）—— 这是真实的经验缺口。

## Q110 · LangGraph / AutoGen / CrewAI / MetaGPT

| 框架 | 范式 |
|---|---|
| **LangGraph** | **图编排**（节点 + 边 + 状态）→ 你要**确定性流程** |
| **AutoGen** | **对话协商**（Agent 之间讨论） |
| **CrewAI** | **角色委派**（"公司"式分工） |
| **MetaGPT** | **软件公司**（SOP 流水线） |

**为什么不用 AutoGen**：记账**容错成本高** —— 不能让 Agent "商量着"改金额，要**确定性流水线**。

**诚实说**：**我没实际跑过 AutoGen**。

**反悔条件**：若要做"多方案讨论/评审"型场景（如投资建议的多视角辩论）→ LangGraph 不合适，该换 AutoGen。

## Q111 · 长记忆存储：FAISS / 向量库 / SQL+全文索引 ★（**优先准备这题**）

**因为它复用你已实测的素材**（`long_memory.py:223` 自承"最多约 60 条"），**最容易讲出深度**。

| 方案 | 60 条 | 10 万条 | 代价 |
|---|---|---|---|
| **FAISS**（当前） | ❌ **过重**（线性扫描更快） | ✅ | 索引不落盘、重启重建 |
| **SQL + FTS5 全文索引**（你没用的） | ✅ **最合适** | ⚠️ 语义弱 | 无语义召回 |
| **专用向量库**（Milvus/qdrant） | ❌ 运维重 | ✅ | 引入新组件 |

**诚实说**：60 条用 FAISS 是**杀鸡用牛刀**。我保留它是因为**笔记库也走 FAISS**，两处复用同一套检索栈 —— **用"一致性"换"最优性"**。

**反悔条件**：
1. 规模超 **1 万条**
2. 需要**跨进程共享索引**（FAISS 内存态做不到）
→ 换专用向量库

## Q112 · 防幻觉：白名单 / 约束解码 / 模板渲染 / 双模型交叉

| 方案 | 能防什么 | 代价 |
|---|---|---|
| **数字白名单**（你的） | ✅ 数值幻觉 | 只管数字；挡不住语义幻觉 |
| **约束解码**（你没用的） | ✅ 更底层 | 要模型侧支持（grammar/JSON schema） |
| **模板渲染**（你的兜底） | ✅ 完全确定性 | 文案生硬 |
| **双模型交叉校验** | ✅ 语义幻觉 | 成本翻倍、延迟翻倍 |

**为什么不叠加**：双模型交叉**成本翻倍**，而我的场景**数值幻觉是主要风险**（记账最怕数字错），白名单已覆盖。

**★ 明确边界**：白名单**防不住语义幻觉**（"本月省了不少"这种无数字的结论错误）—— 这是**我承认的边界**。

**反悔条件**：若用户投诉集中在**结论错误**（而非数字错误）→ 加双模型交叉。

## Q113 · 任务可靠性：DB 状态机 / Temporal / checkpointer / Celery

| 方案 | 特点 |
|---|---|
| **DB 状态机**（你的） | 简单可控；**无分布式协调** |
| **Temporal** | 完整（重试/补偿/长时/Saga）；**重**（要部署集群） |
| **LangGraph checkpointer** | 图状态快照；**粒度太细**（你只关心业务任务是否完成） |
| **Celery** | 成熟（重试/DLQ/监控）；要 broker |

**为什么不用 checkpointer**：我关心的是**业务任务的完成与否**（`task_state` 表），不是图的中间快照。图崩了重启按 `task_id` 对账即可。

**换 Temporal 的条件**：需要**跨服务编排** 或 **补偿事务（Saga）**。

# 附录 · 「反悔条件」汇总（三面最独特的考点）

> **为什么单独列**：面试官问"什么条件下你会反悔"，考的是**你有没有预设失败场景** —— 只说"我选 A"的人，会被判定为"没真正权衡过"。

| 题 | 反悔条件 |
|---|---|
| Q100 数据库 | 成本超 3 倍 / 写入再涨 10 倍 / 合规要求本地化 |
| Q101 重试 | 工具数 > 30（配置面爆炸）→ 改全局预算 |
| Q102 依赖环 | 串行导致超时率 > 5% → 改回"终止" |
| Q103 扇出 | 消息量 < 1000/天（Redis 不划算）→ 退回自研 Queue |
| Q104 报表 | 若报表是一次性的 → `run_in_executor` 就够，别过度设计 |
| Q105 换模型 | 首答正确率掉 > 15% → 问题在 prompt 不在架构 |
| Q106 背压 | 队列满频率 < 1 次/天 → 只做告警，不做实时重投 |
| Q107 权限隔离 | IPC 开销致 P95 涨 > 30% → 退回约定 + review |
| Q111 长记忆 | 规模 > 1 万条 或 需跨进程共享 → 换向量库 |
| Q112 防幻觉 | 投诉集中在结论错误 → 加双模型交叉 |
| Q113 可靠性 | 需跨服务编排 / 补偿事务 → 换 Temporal |

# 最后 · 三个「必背」的开场句

1. **被问方案对比时**："我先说约束：现在规模是 X、约束是 Y —— 在这个约束下列三个方案……"
2. **被问为什么这么设计时**："当时的判断是 A，代价是 B；**如果现在重做，我会在 C 处改** —— 因为……"
3. **被问到没做过的**："这个我没做过，我的思路是…… **但我没法给出实测数据，只能给推演** —— 这点我如实说明。"

**★ 第三句最重要** —— 三面考的从来不是"你全做过"，而是"**遇到没做过的，你怎么想**"。
