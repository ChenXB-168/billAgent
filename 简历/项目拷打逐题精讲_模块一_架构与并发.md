## Q1 · Worker 生命周期与资源管理

### L1｜Worker 是常驻协程还是每次任务新建？ ✅

**答**：**常驻协程**，进程启动时 `create_task` 创建一次，之后一直存活。

**代码依据**：`startup/bootstrap.py` — `bootstrap_all()` 末尾

```python
worker_coroutines = [
    _bill_agent_worker(), _stat_agent_worker(),
    _price_agent_worker(), _finance_agent_worker(),
]
# 逐个 create_task 挂起，保持常驻
```

**★知识点①：常驻 vs 每次新建的取舍**

| | 每次新建 | **常驻** |
|---|---|---|
| 创建开销 | 每次都付 | **只付一次** |
| 状态保持 | 做不到 | **可以（但他没用）** |
| 复杂度 | 低 | **要管生命周期 + 异常** |

**为什么他选常驻**：**因为启动开销贵**——子 Agent 的图编译、提示词加载、索引装载都要钱。**每次请求重建一次，代价远大于常驻。**

**★知识点②：asyncio 协程的"常驻"到底是什么**

它不是"后台线程"，而是**一个挂在事件循环上的 Task 对象**。它只在两种时刻占用 CPU：
1. **被唤醒执行**时（从 `await` 处恢复）
2. **被调度**时

**其余时间它只是内存里的一个对象**，事件循环不会去"轮询"它。

### L2｜退出条件是什么？谁触发？ ✅

**答**：**`SHUTDOWN_FLAG` 置位 → `while` 循环自然结束**。

**代码依据**：`startup/bootstrap.py`

```python
while not SHUTDOWN_FLAG:
    try:
        msg = await a2a_bus.recv_task_blocking(agent_name)
        ...
```

**触发方**：`shutdown_system()`（WebUI 的「退出系统」按钮 / 进程优雅关闭）

**★知识点：协程优雅退出的两种模式**

| 模式 | 做法 | 特点 |
|---|---|---|
| **标志位（poll）** | `while not FLAG` | **能跑完当前任务再退**；但卡在 `await` 时感知不到 |
| **`task.cancel()`（signal）** | 注入 `CancelledError` | **能打断 `await`**；但不保证清理 |

**他两者都用**：
- `SHUTDOWN_FLAG` 让循环**在处理完当前任务后**退出 ✓
- `task.cancel()` + `gather` 收敛处理**卡在 `await queue.get()`** 的情况 ✓

---

### L3｜如果 `while True` 没设退出条件怎么办？ ✅

**答**：**他有退出条件**（`while not SHUTDOWN_FLAG`）。

**★知识点：协程没有"强制终止"**

`task.cancel()` **不是杀进程**，它只是**向协程注入一个 `CancelledError`**：

```python
task.cancel()          # 只是"请求取消"
# 如果协程体里写了：
try:
    ...
except BaseException:  # 连 CancelledError 一起吞掉
    pass                # ← 那这个协程就永远取消不掉
```

**所以"能不能被取消"取决于被取消方的配合**。这也是为什么 `CancelledError` 继承 `BaseException` 而不是 `Exception`——**防止业务代码用 `except Exception` 顺手把它吞掉，导致取消失效**。

### L4｜Worker 处理完任务回到等待——占什么资源？4 个空转协程开销多大？ ✅

**答**：**几乎为零**。

**原因**：`await queue.get()` 会把协程**挂起并从就绪队列移除**，事件循环不再调度它。

**★知识点：`await` 挂起 ≠ 忙等**

| | 占 CPU | 占内存 |
|---|---|---|
| **`await queue.get()`（他用的）** | **0** | 几 KB（协程对象 + 栈） |
| **`while True: if not q.empty(): ...`（忙等）** | **100%** | — |

**他项目里专门为这件事做过优化**（README §8）：

> 原实现是 `get_nowait() + sleep(0.1)` 轮询 —— 空闲时 4 个 worker **每秒空转约 40 次唤醒**，改成 `await queue.get()` 后**空闲唤醒降为 0**。

**这个问题问的其实是"你知不知道自己有没有在空转"，他有实测数据（36 次/秒 → 0）。**

### L5｜Worker 异常没捕获——会传播到事件循环吗？做了全局 exception handler 吗？ ⚠️

**答**：
- **循环内有 `try/except Exception` 兜底** ✓（消费循环不会因单任务异常中断）
- **没有设置全局 `loop.set_exception_handler()`** ⚠️

**代码依据**：`startup/bootstrap.py`

```python
except Exception as e:
    logger.exception(f"[{agent_name}] 任务执行异常")
    await asyncio.sleep(0.5)          # 避免异常时疯狂空转
```

**★知识点①：`except Exception` 捕不住 `CancelledError`**

Python 异常层次：

```
BaseException
├── SystemExit
├── KeyboardInterrupt
├── asyncio.CancelledError     ← ★这里
└── Exception                  ← 业务异常都在这一支下面
    ├── ValueError
    ├── KeyError
    └── ...
```

**所以 `except Exception` 抓不到 `CancelledError`** —— 它会被"漏"过去，向上抛给事件循环。

**他在 M16 用户取消功能里正好踩到这个坑**（可以当面试素材讲）：

> 常驻 worker 的消费循环用 `except Exception` 兜异常，而 `CancelledError` 继承 `BaseException`、**不在捕获范围内**。所以我做用户取消时，如果直接 `cancel` worker 协程，**会把它整个打死**——于是改成把每个任务的执行包成**独立的内层 Task**，取消只作用于内层，**worker 循环照常继续**。

**★知识点②：`loop.set_exception_handler()`**

若协程里抛出的异常**既没被捕获、也不是 `CancelledError`**，事件循环会：
- **默认行为**：调默认异常处理器，**往 stderr 打一条日志**
- **不影响其它协程、不崩进程**（除非是 `SystemExit`）

**他没显式设置 handler** → **走默认行为即可**。面试时如实说："没设全局 handler，因为消费循环内部已经兜住业务异常，剩下的会让事件循环打日志——**但我明确知道 `CancelledError` 不在 `Exception` 分支里**，这也是我做取消功能时特别注意的点。"

**⚠️ 一句话兜底话术**：

> 全局 `set_exception_handler` 我没设。因为我的异常处理策略是"**就近兜底**"——消费循环包住单个任务，网关包住工具调用，Tracer 内部自己吞。**剩下漏到事件循环的，走默认打日志即可。** 但如果要上生产，我会加上全局 handler 做告警聚合。

### L6｜4 个 Worker 同时忙时第 5 个任务来了——排队还是拒绝？排多久？ ⚠️

**答**：**排队，队列无界，没有上限** ✗

**★知识点：asyncio.Queue 默认无界**

```python
asyncio.Queue()          # maxsize=0 → 无界
asyncio.Queue(maxsize=N) # 有界，put() 在满时会阻塞
```

**当前状态**：`a2a_queue.py` 里用 `defaultdict(asyncio.Queue)` —— **默认无界**。

**⚠️ 这是真实的架构缺口**（不是措辞问题）：

| 风险 | 说明 |
|---|---|
| **内存** | 任务对象持续堆积 → 内存上涨，**没有上限、没有告警** |
| **无背压** | 编排器不知道下游压力，会继续派发 |
| **无法感知** | 没有队列深度指标 |

**面试答法**（诚实 + 说清正确做法）：

> **没设 maxsize，这是当前版本的已知缺陷。** 单机单用户场景堆积风险低，但**上生产必须补**。
>
> 我会设 `maxsize` + **满时拒绝新请求**——注意**不是阻塞 `put()`**，因为 `put()` 阻塞会把编排器一起卡死（它自己也在事件循环里）。**同时暴露队列深度指标用于告警。**
>
> 当时优先做了崩溃恢复和幂等（**正确性问题**），背压属于**容量问题**，排在后面。

**★知识点：背压（Backpressure）的三种策略**

| 策略 | 做法 | 适用 |
|---|---|---|
| **阻塞生产者** | `await queue.put()` 满时挂起 | 生产者也异步、可接受延迟 |
| **丢弃** | 满了直接丢 | 允许丢（如埋点） |
| **拒绝（他选的）** | 满了返回错误 | 不允许丢且要快速失败 ✓ |

### L7｜某个 Worker 永远等不到任务——空转一天占多少资源？有空闲回收吗？ ✅

**答**：**几乎为零**（`await queue.get()` 挂起），**没有空闲回收**（**常驻是刻意的**）。

**★知识点：为什么"没有回收"是对的**

**回收协程 = 丢失它的全部状态**（虽然在你的场景里 worker 是无状态的）。但更重要的是：

- **重建代价 > 保留代价**：worker 的"体重"在于子 Agent 图 + 提示词 + 索引，**都在进程级共享**，协程对象本身很轻
- **常驻的真正收益**是**避免冷启动** —— 这正是你 `performance` 那条改造的核心

**所以"空闲回收"在这里是负优化**：回收一个空闲协程只省几 KB 内存，但下次任务来时要付重建成本。

**⚠️ 但有一个真实的对照**：如果 worker 持有了**重资源**（如独立模型实例），那"空闲回收"就有意义了——**面试官问这个，本质在看你知不知道"回收的收益和代价取决于什么"**。

## Q2 · Queue 的边界条件与背压

> **这组是模块一里最危险的一节** —— 因为它问的是 Queue，而你的队列确实缺治理。**但"承认缺口 + 说清正确做法"本身就能拿分。**

### L1｜`asyncio.Queue` 设了 maxsize 吗？ ❌

**答**：**没设，默认无界。**

**代码依据**：`mcpGateway/a2a_queue.py`

```python
self._task_queues: Dict[str, asyncio.Queue] = defaultdict(asyncio.Queue)
```

**见 Q1-L6 的答法。**

### L2｜没设——内存涨到多少会 OOM？你算过吗？ ⚠️

**答**：**没算过**（诚实）。

**但可以给出估算**（面试时这么说比"没算过"强）：

> 没精确算。但可以估：一个任务消息是 `{session_id, task_id, task_data}`，`task_data` 里含 `raw_segments` / `session_memory` / 上游结果，**单个大概几 KB 到几十 KB**。
> 按 50 KB 算，**堆到 100 万个任务才 50 GB**——所以在单机单用户的真实使用下，**永远堆不到 OOM**。
>
> **但"堆不到"不是"不用管"**：真正的风险不是 OOM，而是**堆积说明下游处理不过来，而我没有手段感知**。

**★知识点：为什么"算不出来"也要给出量级**

面试官问"算过吗"，**他真正想确认的是你有没有"容量意识"**。给出**量级估算 + 说明风险不在 OOM 而在"无感知"**，比"没算过"和"不会 OOM"都好。

### L3｜设了——满了 `queue.put()` 阻塞 Orchestrator，新请求进不来，怎么办？ ⚠️

**答**：**当前没设 maxsize，所以不存在这个问题**。但如果设了并阻塞 `put()`，**确实会把编排器一起卡死**。

**★知识点：为什么"阻塞 put"是错的**

因为**编排器自己也在同一个事件循环里**：

```
编排器协程：await queue.put(...)   ← 挂起等队列有空位
worker 协程：await queue.get()     ← 但因为编排器卡着，派发慢了…… 
```

**更糟的情况**：如果编排器是**唯一入口**，它一卡，**用户的新请求根本进不来**（连"排队"的机会都没有）。

**正确做法是"快速失败"**：

```python
if queue.full():
    return {"error": "系统繁忙，请稍后重试"}   # 而不是 await queue.put(...)
```

---

### L4｜有没有背压机制？Queue 超阈值时 Orchestrator 停止派发或降级？ ❌

**答**：**没有。**

**答法见 Q1-L6**（诚实承认 + 说清正确做法）。

**★知识点：这一类问题要"分层回答"**

> **L1 现状**：没做。
> **L2 正确做法**：设 `maxsize` + 快速失败 + 深度指标。
> **L3 为什么当时不做**：优先级排序——正确性（幂等/恢复）> 容量（背压）。
> **L4 什么时候必须做**：多用户 / 有真实流量时，**这是上线前的硬门槛**。

**这个"四层"结构适用于所有"没做"的问题**，它把"我没做"变成"我知道该怎么做、也知道为什么现在不做"。

### L5｜Queue 里传的是对象引用还是序列化数据？Worker 改了对象，Orchestrator 看得到吗？这算隐式共享状态吗？ ⚠️

**答**：**传引用**（`put_nowait(msg)` 直接放 dict 对象），**理论上存在隐式共享**。

**代码依据**：`a2a_queue.py`

```python
msg = {"session_id": ..., "task_id": ..., "task_data": task_data}
self._task_queues[target_agent].put_nowait(msg)     # ← 引用入队
```

**★知识点：`task_data` 是"浅拷贝后的新对象"还是"共享引用"？**

关键看他构造 `task_data` 时有没有深拷贝：

```python
# agents/orchestrator/nodes.py — dispatch_node
new_task_plan = copy.deepcopy(task_plan)              # ← 深拷贝
mem_export = mem.export_all()                          # ← 导出快照
cache = copy.deepcopy(state.get("agent_result_cache", {}))
```

**所以实际上**：
- `task_plan` / `cache` 都是**深拷贝**，worker 改了不影响编排器 ✓
- `mem_export` 是**导出快照** ✓
- **所以"隐式共享"在当前实现里被规避了** ✓

**答法**：

> 传的是引用，但**我在构造 `task_data` 时做了 `deepcopy`**，worker 改的是自己的副本。**这是刻意的**——如果共享引用，worker 改 `task_plan` 就会影响编排器的调度判断，那是很隐蔽的 bug。
>
> **不过我没做序列化**。所以严格说这是"靠深拷贝规避共享"，不是"从机制上不可能共享"。**如果 worker 拆到独立进程，天然就序列化了，这个问题自动消失。**

**这个回答很硬** —— 它同时说了"我做了什么"、"为什么这么做"、"机制的边界在哪"。

### L6｜Worker 消费速度远低于派发速度（如统计做复杂聚合），Queue 持续堆积——怎么感知？怎么处理？ ❌

**答**：**无法感知**（没有队列深度指标）✗

**★知识点：可观测性的三类指标**

| 类型 | 例子 | 他的现状 |
|---|---|---|
| **延迟** | 投递延迟、端到端耗时 | ✅ 有（`bench_a2a_latency.py` + `trace_span`） |
| **吞吐** | QPS、任务完成数 | ⚠️ 部分（`llm_call_stat`） |
| **饱和度** | **队列深度、worker 忙闲** | ❌ **没有** |

**"饱和度指标"是背压的前提** —— 不知道队列多深，就无法决定什么时候拒绝。

**答法**：

> 感知不了，这是缺口。**队列深度应该是最该做的饱和度指标**——有了它才能做背压决策。
>
> 补法很轻：`queue.qsize()` 定期采样写日志 / trace，超阈值告警。**问题不是"难做"，是"当时没排到优先级"。**

### L7｜如果 Orchestrator 自己也阻塞在 `queue.put()` 上——新请求还能进来吗？入口在哪？ ⚠️

**答**：**不能**（当前是 `put_nowait`，非阻塞，所以暂无此风险 ✓ 但如果改成阻塞 `put` 就会出现）。

**★知识点：入口的"单点阻塞"风险**

他的入口链路：

```
WebUI respond() → _loop.run_until_complete(ainvoke) → 编排图
CLI chat_loop → 同步等待 → 编排图
```

**注意**：**WebUI 用的是 `run_until_complete`** —— **它会把整个事件循环占住直到这轮跑完**。

**这带来一个真实后果**：`respond` 执行期间，**页面上的其它操作（包括"停止本轮"按钮）都无法通过同一个 handler 处理** —— 这就是我做 M16 取消时为什么用 `run_coroutine_threadsafe` 从别的线程投递取消。

**答法**：

> 当前用 `put_nowait`，不会阻塞。但**更值得说的一点是入口本身**：WebUI 用 `run_until_complete` 驱动图，**这轮不返回，页面的其它交互就走不动**。
>
> 所以我做「停止本轮」时，**没用同一个事件循环的 handler 去做**，而是用 `run_coroutine_threadsafe` 从别的线程把取消动作投递回去 —— 否则按钮点不动。

**这个回答的价值**：它展示了**你对自己架构里"哪里会卡"是清楚的**，而且有实际处理经验。

## Q3 · 单事件循环的并发天花板

> **⭐ 这一节要修正之前的判断** —— 我之前说"没做 CPU 密集隔离"是**错的**。你做了，而且是**三层系统性做的**。

### L1｜BM25/FAISS 是 CPU 密集的，检索期间事件循环被阻塞多久？ ⚠️

**答**：**分两处，一处做了隔离、一处漏了**：

| 检索 | 是否卸载线程池 | 代码依据 |
|---|---|---|
| **长期记忆** `search_history_consume` | ✅ **有** `to_thread` | `nodes.py:1548` |
| **笔记库** `search_user_docs` | ❌ **直接同步调用** | `nodes.py:1879` |

```python
# ✅ 长期记忆：有卸载
long_mem_text = await asyncio.to_thread(search_history_consume, user_text)

# ❌ 笔记库：直接同步调用（会阻塞事件循环）
user_docs_data = search_user_docs(q, top_k=USER_DOCS_TOP_K)
```

**⚠️ 这是一处真实的不一致，可以修**（见文末「可修补救」）。

**★知识点：为什么"没卸载"是有问题的**

`search_user_docs` 内部做了两件事：
1. **BM25 打分**（纯 CPU，遍历全部 chunk）
2. **FAISS `index.search()`**（纯 CPU，向量距离计算）
3. **`client.get_embedding(query)`**（**可能含模型推理，最重**）

**这三件事都在事件循环线程里同步执行** → **期间所有其他协程（包括 4 个 worker）全部停摆**。

**规模小的时候察觉不到**（毫秒级），**但它是"随规模线性恶化"的**——文档从千条到十万条，这个阻塞窗口会放大 100 倍。

---

### L2｜你测过 FAISS 检索期间事件循环的阻塞时长吗？具体数字？ ⚠️

**答**：**没测过**（诚实）。

### L3｜有没有考虑过把 CPU 密集部分丢 `run_in_executor`？为什么没做？ ✅

**答**：**做了，而且是三层系统性做的**：

| 层 | 机制 | 代码依据 |
|---|---|---|
| **工具层** | `LocalAdapter` 对同步函数**默认丢线程池** | `mcpGateway/adapters.py:233` |
| **数据层** | SQLite 调用走 `anyio.to_thread.run_sync` | `mcpGateway/sql_common/sql_mcp_base.py:75` |
| **记忆层** | 长期记忆检索 / 落盘走 `asyncio.to_thread` | `nodes.py:1548`、`bill_agent/nodes.py:252` |

**代码依据（工具层的通用机制）**：

```python
# mcpGateway/adapters.py:233
if spec.binding.get("to_thread", True) and not inspect.iscoroutinefunction(fn):
    return await asyncio.to_thread(fn, **kwargs)
```

**★知识点：`LocalAdapter` 这个设计很漂亮**

它把"同步函数要不要丢线程池"变成了**元数据声明**：

```python
# registry.py — 绝大多数工具
binding={"func": fact_tools.sum_month_bills, "to_thread": True}     # 同步函数 → 卸载 ✓

# ★个别必须保持 async 的（要持协程级锁）
binding={"func": fact_tools.upsert_habit, "to_thread": False}        # 不卸载 ✓
```

**为什么个别要 `to_thread: False`** —— 代码注释写明了原因：

> **★必须保持 async**：`LocalAdapter` 对同步函数默认走 `to_thread`（丢进线程池），**那样协程级的 `db_lock` 会随即失效**；async 函数被引擎直接 `await`，`async with db_lock` 在事件循环内持锁。

**这是一处很细的设计**：**线程池卸载会破坏协程级锁的语义**——因为 `asyncio.Lock` 只在同一个事件循环线程里有意义，一旦进了线程池，锁就形同虚设。

**答法**：

> 做了。而且我做的是**通用的机制**，不是逐处手写：工具层的 `LocalAdapter` 会**默认把同步函数丢进线程池**，我在工具元数据里用 `to_thread` 声明是否卸载。
>
> **但有两处例外我特意标了 `to_thread: False`**：`habit.upsert` 和 `habit.recalc`。原因是**它们要在协程内持有 `db_lock`**——`asyncio.Lock` 只在同一个事件循环线程内有效，**一旦丢进线程池，锁就失效了**，会变成假锁。
>
> 所以我的规则是：**纯 IO / 纯计算的同步函数 → 卸载；需要持协程级锁的 → 保持 async 不卸载。**

**这个回答非常强** —— 它展示了对"线程池卸载与协程锁的冲突"的理解，**这是很多人踩过但说不清的点**。

### L4｜如果以后加"导出月度报表"（大量数据聚合），单事件循环撑得住吗？ ✅

**答**：**撑不住**，但**现有机制已经给了正确的应对路径**。

> 「导出报表」是**纯 CPU 密集 + 大量数据**，比现在的检索重得多。
>
> **撑不住的原因**：即使丢线程池，**也只是把阻塞从事件循环挪到线程池**——如果报表导出要跑 30 秒，thread pool 占满后，**其它 `to_thread` 调用（SQLite、记忆检索）会排队**，整体一起变慢。
>
> **正确应对是两条**：
> ① **异步化**：导出任务走**同一套任务机制**（建单 → 后台执行 → 完成后通知），**不占请求链路** —— 这正是我 `task_state` 状态机 + A2A 总线能直接复用的能力；
> ② **进程化**：真正的重计算（如百万行聚合）**必须拆到独立进程**，因为**有 GIL，线程池对纯 Python 计算无效**。

**★知识点：线程池能解决什么、不能解决什么**

| 任务类型 | 线程池有用吗 | 原因 |
|---|---|---|
| **IO 等待**（网络、磁盘） | ✅ **非常有用** | 等待时释放 GIL |
| **C 扩展计算**（numpy / FAISS） | ✅ **有用** | C 代码里会释放 GIL |
| **纯 Python 计算**（循环、字符串） | ❌ **无效** | 被 GIL 串行化 |

**所以**：
- **FAISS 检索丢线程池是有效的**（C 层释放 GIL）✓
- **纯 Python 的大循环丢线程池没用**（还是要拆进程）✗

**这个区分能答出来，说明你理解 GIL 的实际影响边界。**

### L5｜asyncio 里 `await` 切走——但如果 Worker 里忘了 `await`（直接调同步函数），事件循环会怎样？有过这种 bug 吗？ ⚠️

**★知识点：`await` 是"协作式的让出点"**

```
协程 A：await something   ← 在这里让出控制权
   ↓ 事件循环切换到
协程 B：...
```

**如果一个协程里长时间没有 `await`，事件循环就无法切走** → **其它协程全部饿死**。

**这正是"协作式多任务"的含义**：**让不让出，取决于代码自己**，不像操作系统抢占式调度那样有"时间片"。

**他的真实案例**：

```python
user_docs_data = search_user_docs(q, top_k=USER_DOCS_TOP_K)   # ← 没有 await，纯同步
```

**答法（把它当成"我发现的自己的问题"，反而是加分项）**：

> 有过，而且我最近自查发现了一处：**笔记库检索 `search_user_docs` 是同步调用，没有走线程池**。
>
> 同一类检索里，**长期记忆的 `search_history_consume` 我是用 `asyncio.to_thread` 卸载的**，笔记库这条漏了。**这是一处不一致**——虽然当前规模下阻塞只有毫秒级，但它**随文档量线性恶化**。
>
> **修法就是用同一个模式**：`await asyncio.to_thread(search_user_docs, q, USER_DOCS_TOP_K)`。

### L6｜CPython 有 GIL——你的 asyncio 方案在多核机器上能利用几个核？其他核浪费了？ ✅

**答**：**主链路只用一个核**；**但线程池和 MCP 子进程会用到其它核**。

**★知识点：GIL 到底限制了什么**

| 场景 | 受 GIL 限制吗 |
|---|---|
| **纯 Python 代码**（同一进程内） | ✅ **受限**，同一时刻只有一个线程执行字节码 |
| **`await` 期间的 IO 等待** | ❌ 不受限（不占 CPU） |
| **C 扩展释放 GIL 时**（numpy / FAISS） | ❌ 不受限 |
| **多进程** | ❌ 不受限（每个进程独立 GIL） |

**他的实际核使用情况**：

```
主进程（编排器 + 4 worker 协程）  → 1 个核（协程共用主线程）
   └─ 线程池（to_thread 卸载）      → 额外核（FAISS/SQLite 在 C 层释放 GIL）
3 个 MCP 常驻服务                 → 3 个独立进程 → 各用 1 个核
```

**答法**：

> 主链路（编排器 + 4 个 worker 协程）确实是**一个核**——协程共用主线程，这是 asyncio 的固有特性，**我不回避这一点**。
>
> **但实际上不止一个核被用到**：
> ① **线程池卸载**：FAISS / SQLite 这类 C 扩展在计算时会释放 GIL，所以 `to_thread` 出去的活能跑在别的核上；
> ② **3 个 MCP 服务是独立进程**（`sql_bill` / `llm_base` / `llm_finance`），各占一个进程、各用各的核。
>
> **所以准确的说法是**：**编排逻辑单核，但计算和外部服务是多核分布**。
>
> **真正的单核瓶颈在于**：如果有一个**纯 Python 的重计算**任务，它会卡住整个事件循环**且无法靠线程池缓解**——**那种情况必须拆进程**。

## Q4 · Orchestrator 单点问题

### L1｜Orchestrator 挂了整个系统停——恢复机制能自动拉起吗？ ⚠️

**答**：**不能自动拉起**（没有进程守护）✗ **但"恢复"这一层是有的**——重启后能接上未完成的任务。

**★知识点：要区分两个概念**

| 概念 | 含义 | 他的现状 |
|---|---|---|
| **进程守护** | 挂了**自动重启** | ❌ 没有（无 systemd / supervisor） |
| **状态恢复** | 重启后**接着做** | ✅ **有**（`recover_orphans` + 重投） |
| **任务不丢** | 崩了也不丢任务 | ✅ **有**（`task_state` 持久化） |

**答案结构**：

> **自动拉起没有做**——我没配 systemd / supervisor。这是单机脚本形态的直接后果。
>
> **但"恢复"这一层是完整的**：任务状态**落到独立库**，进程即使被 `kill -9`，重启后 `recover_orphans` 会扫出遗留任务、**按 `task_id` 对账**（已落库 → 判完成；未落库 → 重投）——**不丢任务、也不重复记账**。
>
> **所以缺的只是"拉起"这一步**，生产上就是加一个 `Restart=always` 的 unit 文件。

**★知识点：`Restart=always` 与"崩溃恢复"是两件互补的事**

```
systemd Restart=always     → 进程存活（拉起）
recover_orphans            → 业务连续性（接着做）
```

**只有拉起没有恢复** → 重启后任务卡在 `running` 永远不动 ✗
**只有恢复没有拉起** → 崩了要等人手动启动 ✗
**两者都有** → 真正的自愈 ✓

**他能说清这个区分，说明理解了两层的职责。**

### L2｜重启后从哪恢复状态？任务表还是 LangGraph checkpoint？以谁为准？ ✅

**答**：**只有任务表（`task_state.db`）一套状态，我没有用 LangGraph Checkpointer。**

**★知识点：为什么"只有一套"是好设计**

**双重持久化最大的风险是"不一致"**：

```
Checkpointer 说：图执行到 wait_result 了
task_state  说：这个任务是 pending

→ 信谁？没定义过优先级 → 就是定时炸弹
```

**他主动避免了这个问题**：

> 我**刻意没有用 LangGraph 的 Checkpointer**。因为任务状态必须满足两个条件：
> ① **独立于图执行的生命周期**（子 Agent 跨请求常驻，Checkpointer 的粒度是"一次图执行"）；
> ② **支持崩溃后按业务表对账**（Checkpointer 不知道该查 `bill` 表）。
>
> **两套状态并存只会引入一致性问题，所以我只用一套** —— `task_state.db` 是**任务事实的唯一来源**，这一点在代码注释里也写明了。

**★知识点：什么叫"唯一事实源"（Single Source of Truth）**

**规则**：任何状态只允许有一处"权威记录"，其它都是它的投影。

**他的实现严格遵守了这条**：

```
task_state.db  ← 唯一事实源（DB）
     ↓ 投影
a2a_queue（内存队列）  ← 重启即失，启动时从 DB 重建
```

代码注释里明确写了：

> **DB 是队列事实的唯一来源**：`recover_orphans()` 只负责把状态改对，`submitted` 即"声明可重投"，再由 `resubmit_submitted()` 重发 `send_task`——**队列是 DB 状态的下游投影，重启即失，故不直接改内存队列。**

**这段话是整个可靠性设计的核心，建议背下来。**

### L3｜如果旧 Orchestrator 没完全死（假死但还占着资源），新实例怎么避免冲突？ ❌

**★知识点：分布式系统的"脑裂"（Split-brain）问题**

## Q5 · LangGraph 使用深度

> **⭐ 这一节是模块一最难的一节**，因为它直接质疑"你要不要用 LangGraph"。

### L1｜图里有循环吗？有条件边？有人机交互中断？ ⚠️

**答**：
- **编排图**：`plan → dispatch → wait_result → dispatch`（**有循环**）✓
- **条件边**：编排图用的是**条件路由（`Command(goto=...)`）**；子 Agent 图里有 `add_conditional_edges` ✓
- **人机交互中断**：**没有**（追问是应用层实现的，不是图中断）✗

**代码依据**：

```python
# agents/orchestrator/graph.py
builder.add_edge("plan_node", "dispatch_node")
builder.add_edge("wait_result_node", "dispatch_node")   # ← 循环边
builder.add_edge("collect_node", END)

# agents/stat_agent/graph.py —— 子图里有条件边
builder.add_conditional_edges(...)   # verify 自纠分流
```

**★知识点：LangGraph 里"循环"和"条件边"是两个不同机制**

| 机制 | 形态 | 他的用法 |
|---|---|---|
| **普通边 + 循环** | `A → B → A`，靠 `Command` 决定何时跳出 | **编排图**（dispatch ↔ wait_result 循环多位点派发） |
| **条件边** | `A → (条件函数) → B 或 C` | **子 Agent 图**（verify 通过→reply / 不通过→重试） |

**他的 `dispatch ↔ wait_result` 循环是有意义的**：因为任务有 DAG 依赖，**一波派发不完**——第一波跑完 `bill`，才轮到依赖它的 `stat`。**所以必须"派发→等待→再派发"。**

**答法**：

> 有循环。**编排图是 `plan → dispatch → wait_result → dispatch` 的循环结构**——因为任务有依赖关系，**一波派发不完**：第一波只发 `bill` 和 `price`，等 `bill` 完成后才轮到依赖它的 `stat`。
>
> 另外**子 Agent 的图里有条件边**，用于 `verify` 节点的自纠分流：校验通过走 reply、不通过回到 parse 重试。

---

### L2｜如果都没有——就是一条直线 DAG，为什么用 LangGraph 不用手写状态机？ ⚠️

**答**：**不是直线**（有循环 + 条件边 + 动态路由），**但仍然要说清"LangGraph 给了什么"**。

**★知识点：LangGraph vs 手写状态机的真实差别**

| 维度 | 手写状态机 | **LangGraph** |
|---|---|---|
| 控制流表达 | `while` + `if` + 状态字段 | **显式图 + 条件边** ✓ |
| **状态管理** | 自己定 dict 契约 | **`TypedDict` + reducer** ✓ |
| **循环与收敛** | 自己写终止条件 | **`Command(goto=...)` 显式跳转** ✓ |
| **可视化** | 无 | **图可导出为图结构** ✓ |
| **可测试性** | 节点可测，但路由要自己测 | **路由本身是图的一部分** ✓ |

**答法**：

> 不是直线，但**即使假设它是直线，我用 LangGraph 的理由也不是"省代码"，而是"控制流是显式可读的"**。
>
> **手写状态机的问题在于：路由逻辑散在 `while` 循环和 `if` 里，改一处要读全部。** LangGraph 把**节点、边、跳转条件**都变成声明式的 —— 我的 4 个节点和它们的跳转关系，看一眼 `graph.py` 就清楚了：
> ```python
> builder.add_edge(START, "plan_node")
> builder.add_edge("plan_node", "dispatch_node")
> builder.add_edge("wait_result_node", "dispatch_node")   # 循环
> builder.add_edge("collect_node", END)
> ```
> **9 行代码说清了整张图的拓扑** —— 手写同样的逻辑，路由判断会散在几个函数的 `if` 里。
>
> **代价我也清楚**：LangGraph 把控制权收走了，所以我"想在中间插自定义调度"就得绕开它 —— **这也是我后来为什么把 Agent 通信做成外部总线，而不是用子图。**

**最后那句把"代价"也说出来了** —— 这种"我用了它、也说了它的成本"的答法，比只讲优点可信得多。

### L3｜用了 Checkpointer 存的粒度是什么？每个节点存一次？ ✅

**答**：**没用 Checkpointer**，用的是自己的 `task_state` 表。

**答法见 Q4-L2**（这是**加分项**，因为你主动避免了双重状态）。

**补一句关于 Checkpointer 粒度的事实**（证明你了解它）：

> LangGraph 的 Checkpointer 默认是**每个 super-step 存一次**（一个节点执行算一个 super-step），所以粒度是"**节点级**"。
>
> **这个粒度对我太细也太错位**：我关心的是"**任务有没有成功**"，而不是"图执行到哪个节点了"。而且**一次请求会产生 4 个任务**，Checkpointer 记的是"这次图执行跑到哪"，**表达不了"4 个任务各自的状态"**。

### L4｜用了 reducer 吗？还是全默认覆盖？全默认跟普通 dict 有什么区别？ ❌

**答**：**没用 reducer**（用默认覆盖语义）✗

**★知识点：reducer 解决什么问题**

LangGraph 的 State 在多节点并发写同一字段时，**默认行为是"后写覆盖先写"**。reducer 让你自定义合并方式：

```python
from typing import Annotated
from operator import add

class State(TypedDict):
    # 默认：后写覆盖
    current_task: str
    # 指定 reducer：累加（list 拼接）
    all_results: Annotated[list, add]
```

**为什么他不需要 reducer**：

> 我的编排图**没有并发写同一字段的节点**——`dispatch_node` 和 `wait_result_node` 是**顺序执行**的（`plan → dispatch → wait → dispatch`），同一时刻只有一个节点在跑。
>
> **所以默认的"覆盖"语义对我够用**，加 reducer 反而是多余抽象。
>
> **反过来说，如果我要用 LangGraph 的并行节点**（比如把 4 个子 Agent 作为并行节点画在一张图里），**那就必须用 reducer 了**——否则多个节点的结果会互相覆盖。**这也是我没走子图路线的一个附带好处：不需要处理 State 合并问题。**

**⚠️ 这个回答把"没用 reducer"从缺陷变成了"因为我的架构不需要"** —— 而且**论证是成立的**（顺序节点确实不存在并发写）。

### L5｜如果去掉 LangGraph，核心逻辑剩多少行？去掉后丢的到底是什么能力？ ❌

**答**：不好估，**但要给出"丢的是什么"**。

**★知识点：这个问题考的是"你知不知道自己依赖了框架的什么"**

**他依赖 LangGraph 的**：

| 能力 | 如果去掉要自己写 |
|---|---|
| **节点编排 + 顺序执行** | 一个 `while` 循环 + 状态字典 |
| **条件跳转（`Command(goto=...)`）** | `if/elif` 判断 |
| **状态在节点间传递** | 自己定义 dict 契约 + 保证节点都遵守 |
| **循环终止保证** | 自己写终止条件（**容易漏，他的 `MAX_DISPATCH_ROUND` 就是手动加的**） |

**答法**：

> 不好精确估，但我可以说**去掉后要自己实现什么**：
>
> ① **节点调度**——一个 `while` 循环 + 状态字典，这部分不难；
> ② **条件跳转**——`Command(goto=...)` 变成 `if/elif`，也不难；
> ③ **状态契约**——这部分**反而是去掉后最大的隐患**：LangGraph 用 `TypedDict` 强制了 State 的字段契约，**手写的话没有静态检查，谁往里加字段都不会报错**；
> ④ **循环终止**——我需要自己保证终止。**顺便说：即使有 LangGraph，我也额外加了 `MAX_DISPATCH_ROUND=8` 的硬上限** —— 因为**框架不保证你的业务逻辑不会死循环**。
>
> **所以丢的主要不是"省下的行数"，而是"控制流的显式性和状态契约的强制力"。**

**★知识点：④ 那句很有价值**

**他主动加了 `MAX_DISPATCH_ROUND`** —— 这说明**他知道框架的终止保证只是"图不会自己转圈"，但业务层面的循环还是要自己防**。代码注释里也写了：

> 无任何 running 任务时打 ERROR 直接终止（**不可回 dispatch，否则 dispatch↔wait 死循环**）

### L6｜用过 LangGraph 的 `Send` API 吗？为什么不用它做扇出而非要自己写 Queue？ ❌❌

**答**（**必须背熟**）：

> 我用过 `Send`，但**它管不了我的场景** —— `Send` 只能在**单次图执行内**扇出，而我的子 Agent 需要**跨请求常驻**（作为 worker 持续消费）。
>
> **具体三个不匹配**：
> ① **生命周期**：`Send` 扇出的节点属于**当前这次图执行**，图跑完就结束；**我的子 Agent 是常驻 worker**，一直等待任务。
> ② **状态归属**：`Send` 的结果会回到**同一张图的 State**；而我的**任务状态必须落在独立的 `task_state` 表**，要支持崩溃后按 `task_id` 对账重投。
> ③ **调度粒度**：`Send` 是"图内扇出、图内收敛"，**没有中间的任务级控制点**；我需要**按 DAG 依赖分层派发、乱序收集、每个任务独立重试**。
>
> **所以分工是**：LangGraph State 管**一次请求内**的编排，消息总线管 **Agent 间通信**，`task_state` 表管**任务生命周期**。
>
> **如果我的场景只是"单次请求内跑几个无状态子任务"，我会直接用 `Send`——那更省事。**

**★知识点：`Send` 是什么**

`Send` 是 LangGraph 提供的**动态扇出**原语，用于 `map-reduce` 模式：

```python
def continue_to_workers(state):
    # 一次性把 N 个任务分发到 worker 节点（N 是运行时决定的）
    return [Send("worker", {"task": t}) for t in state["tasks"]]

builder.add_conditional_edges("planner", continue_to_workers, ["worker"])
```

**它的定位**：**图内的、动态数量的并行分支**。

**和他的需求差在哪**：

```
Send：   planner → [worker×N] → 收敛回同一张图的 State  → 图结束
他的：   编排器 → 消息总线 → [常驻worker×4] → 独立状态表 → 跨请求存活
```

**核心区别**：**`Send` 的扇出是"一次性的"，他的扇出是"持续性的"。**

### L7｜LangGraph 的 State 定义在哪？所有 Agent 共享同一个 State 对象？那 State 的并发读写安全吗？ ⚠️

**答**：**编排器有自己的 `OrchState`，每个子 Agent 有自己的 State，彼此不共享。**

**代码依据**：

```
agents/orchestrator/state.py   → OrchState
agents/bill_agent/state.py     → BillState（推断）
agents/stat_agent/state.py     → StatState
...
```

**★知识点：他的架构天然避免了 State 并发问题**

| | LangGraph 子图模式 | **他的模式** |
|---|---|---|
| State 归属 | 全图共享一个 State | **每个 Agent 一个 State** |
| 并发写 | 需要 reducer 处理 | **不存在**（各自独立） |
| 传递方式 | 框架内部 | **消息总线（`task_data` 显式传）** |

**答法**：

> **不共享 State。** 编排器有 `OrchState`，4 个子 Agent 各有自己的 State 定义，**它们之间不共享对象**。
>
> 编排器派发时会**把子 Agent 需要的数据打包进 `task_data`**（`raw_segments` / `session_memory` / 上游结果），worker 拿到后**映射成自己的 `init_state`**。
>
> **所以不存在"State 并发读写"这个问题** —— 这也是我一直强调的：**我不是用 LangGraph 的子图，Agent 之间是消息传递。**
>
> **代价是"传数据要显式打包"**（比如 `finance` 需要 `bill_result` / `stat_result` / `price_result`，我在 `_build_task_data` 里逐个取），**收益是不用处理共享状态的一致性问题**。

**★知识点：共享状态 vs 消息传递是两种根本不同的并发模型**

| | 共享状态 | **消息传递** |
|---|---|---|
| 通信方式 | 读写同一块内存 | 发消息（值拷贝） |
| 并发风险 | **竞态、死锁** | **无共享即无竞态** |
| 一致性 | 要加锁 / reducer | **天然一致** |
| 调试难度 | 难（时序相关） | **易（消息可打日志）** |
| 性能 | 高（无拷贝） | 略低（要拷贝） |

**这个对比是计算机科学的经典话题（"Do not communicate by sharing memory; share memory by communicating"——Go 的设计哲学）。能说出这个区分，说明你在并发模型上是有认知的，不只是会用 API。**
