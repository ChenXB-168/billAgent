## 第 1 章 · 硬伤（5 项，改变不了）

> 硬伤的共同特征：**不是"没准备好"，是"项目本来就不是那个东西"**。它们的正确应对是**主动交代**，而不是硬答。

### H1 · 单机单用户，无真实并发 / 流量 / 用户

**拷打来源**：Q25 真实使用情况、Q3 并发天花板、Q16 水平扩展

**为什么是硬伤**：项目定位就是个人工具，要"修"等于重写。所有并发优化在"并发=1"面前都要重新解释。

**面试答法**（必须背熟）：

> 当前确实没有并发压力，这个我如实说。**我优化的意义不在当前 QPS，而在验证一套工程方法**：先定位瓶颈（trace / profile），再按依赖顺序改造，最后用 A/B 数据验证——这套方法在真有流量时同样适用。
>
> 如果问"没流量你怎么发现瓶颈"：**从 `trace_span` 表里读每个子任务的真实耗时**，这跟有没有流量无关。

**❌ 不要说的话**：不要说"设计支持高并发"、不要暗示已有生产级容量。

### H3 · 无线上故障处理经验

**拷打来源**：模块八整体（Q27 告警 / Q4 单点 / 模块三全部）

**为什么是硬伤**：没上过线就是没上过线。

**面试答法**：**不要装"我处理过"**。改成展示你知道生产环境需要什么：

> 我没有线上运维经验，这个如实说。但我做项目时是按"它会出什么事"来设计的——异常重启（对账重投）、重复投递（幂等键）、外部依赖挂掉（降级路径）、可观测（span 树）。
>
> **我明确知道系统上线后需要补什么**：进程守护（systemd）、队列背压、告警（失败率 / 堆积量）、数据库定期完整性校验与备份。

**加分点**：主动列出"上线要补什么"，比"我做过线上"更可信（因为前者必然是你自己想的）。

### H4 · 同进程内无强制访问控制（权限是逻辑层约定）

**拷打来源**：Q13 L2「统计 Worker 直接 `sqlite3.connect().execute('INSERT INTO bill...')` 能拦住吗？」

**为什么是硬伤**：Python 同进程内做不到 OS 级隔离。拆进程才能强制，而拆进程会丢掉现在的全部架构。

**面试答法**（**诚实承认 + 补偿手段**）：

> **拦不住。** 同进程内没有强制访问控制，这是这套权限模型的**明确边界**——它是逻辑层隔离，不是机制层强制。
>
> **但我用另一种方式守这条线**：**工具平台的 `required_perm` 在引擎层强制校验**（越权调用直接抛错），
> 再加 `tests/unit/test_contract_check.py` 的**文档↔代码漂移检测**（文档里写的符号/行号/签名必须与代码一致）。
>
> ⚠️ **必须澄清（2026-10-09 复核修正）**：`contract_check.py` **做的是"文档漂移检测"，
> 不是"架构红线的权限防线"**。它只做三件事：① 符号存在性；② 行号引用有效；③ 签名参数一致
> —— **全文没有任何"编排器写操作"检查**。本节原文说"如果代码里出现编排器的写操作，测试直接红"
> 是**不成立的**，面试时**绝不能这么讲**（会被当场翻代码戳穿，见拷打 Q30）。
>
> **正确口径**：同进程内**没有强制访问控制**，`required_perm` 拦的是"正常路径不越权"，
> **拦不住恶意绕过**（直接 `sqlite3.connect()`）。要强制隔离必须**拆进程 + 各自持受限 DB 账号**，
> 代价是丢掉零 IPC 开销 —— 当前规模下没做，这是**明确边界**。
>
> 如果将来要真正的强制隔离，路径是把 Worker 拆成独立进程 + 各自持有受限数据库账号——**代价是丢掉零 IPC 开销**，所以当前规模下没有做。

**注意**：这个答案是**加分项**。多数候选人止步于"这是约定"，而你有"用测试锁死约定"的手段。

## 第 2 章 · 可修项目补救（10 项）

> 可修补救的共同特征：**改代码 / 补测试 / 补记录就能解决**。按优先级排序，P0 必须在投递前完成。

### 优先级 P0（投递前必须做）

#### F1 · 强杀验证无记录 ⭐ 最紧急

**拷打来源**：Q24「几次？什么信号？覆盖了哪些状态？」、Q11 L6、Q10

**现状**：
- `tests/unit/test_task_manager.py` 有 **15 个用例**覆盖恢复分支（但是 **mock 的**，不是真杀进程）
- 面试稿写着 `实测 kill -9 后重启可以恢复`，但**没有次数、信号、中间态记录** ✗

**为什么危险**：答不上来，面试官不会认为"你没测"，而会认为**这句话是照别人说的写的**——**会污染整份简历的可信度**。

**修法**（30 分钟）：

```
真实测 3 次，覆盖三个中间态各 1 次：
  中间态 A：任务在 Queue 里（已派发未执行）
  中间态 B：任务在 Worker 里（执行中）
  中间态 C：账单已写、状态未更新   ← 最关键

记录四项：
  信号：kill -9（SIGKILL）
  次数：3 次
  覆盖：A / B / C 各 1 次
  结果：A、B 重投成功；C 判定 completed、未重复记账
```

**产出**：把以上 4 行写进 `面试问答_Agent方向.md`。**有这 4 行，这一刀就变成加分项**（因为绝大多数候选人根本不会去测中间态 C）。

#### F3 · Queue 无界、无背压、无堆积监控 ⭐ 真实架构漏洞

**拷打来源**：Q2 全部 7 个追问点

**现状**（⚠️ **2026-10-09 代码复核** —— 与本节原有描述**有一处出入**）：
- `asyncio.Queue()` **默认无界** ✗ —— `a2a_queue.py:47` 的 `defaultdict(asyncio.Queue)` 确未传 `maxsize`
- **无背压机制** ✗
- **无队列深度指标 / 告警** ✗
- ⚠️ **校正（重要）**：原文（Q2-L7）写"`put()` 阻塞会连 Orchestrator 一起卡死"——
  **实测 `send_task` 用的是 `put_nowait()`（`a2a_queue.py:105`），当前并不会阻塞**
  （无界队列下 `put_nowait` 永不抛 `QueueFull`）。**真实风险是无上限内存增长（OOM）**，
  而不是"阻塞卡死"。**面试按实测口径讲，不要沿用旧描述**（否则被追问代码会露怯）。

**修法**（✅ **2026-10-09 已实施**，`设计/18` M20 / 契约 `09` §3.7）：
1. ✅ 设 `maxsize` —— `A2A_QUEUE_MAXSIZE`（默认 100，env `BILLAGENT_A2A_QUEUE_MAXSIZE` 可覆盖）
2. ✅ **满时拒绝**（`QueueFull` → 返回 `False` + WARNING），**不阻塞 Orchestrator**
3. ✅ 队列深度写日志（超 `A2A_QUEUE_WARN_DEPTH`=80 告警）+ 新增 `queue_depth()` / `snapshot_depths()` 查询接口
   · 实现要点：`clear_all()` 重建队列时**必须同样带 maxsize**（否则静默退化为无界）—— 已加单测锁定

**面试答法（现在可以答「已修」）**：

> 这是我在拷打复盘里自己找出来的真实漏洞：`asyncio.Queue()` 没设 `maxsize` 属无界队列，
> 且没有背压与堆积监控。**我按「拒绝而非阻塞」的原则修了** ——
> 因为 `send_task` 是**同步方法**（本来也只能 `put_nowait`），而且**阻塞会把派发方
> （Orchestrator，用户请求的持有者）一起挂死**，属故障扩散；拒绝只是优雅失败。
> 同时补了队列深度指标用于告警。
>
> 当时优先做崩溃恢复和幂等（正确性问题），背压是容量问题排在后面——**现在补上了**。

**加分点**：
- 主动说出"满时应该**拒绝**而不是阻塞"，并说清**为什么**（故障扩散 / 同步方法约束）；
- 主动说出"**队列深度**是四黄金信号里的**饱和度**指标"；
- 主动澄清"我们用 `put_nowait`，所以本来就阻塞不了——**真正缺的是上限**"（**体现你真读过代码**）。

### 优先级 P1（投递前尽量做）

#### F4 · "三步顺序不可换"无 profile 数据

**拷打来源**：Q7 L1「怎么证明的？有 profile 数据吗？」、`拷打3.md` 第十刀

**现状**：这句话是**判断**，但没有量化证据 ✗

**修法**：从 `trace_span` 表导出真实数据作为证据（✅ **2026-10-09 已取证**）——

```
✅ 证据 1：MCP 冷启动耗时 —— 从启动日志实测（logs/app.log）
     · 常驻化前（stdio 模式）：单次调用需 Popen + import 依赖 + 加载模型 ≈ 26~29s
     · 常驻化后（M3 · HTTP 常驻）：一次性拉起 3 个服务共 ~11.2s
       （实测时间戳差：sql_bill 1.6s / llm_base 2.1s / llm_finance 3.2s）
     · 之后复用 = 0s（日志原文："[M3] xxx 常驻服务已在运行，跳过拉起（复用现有进程）"）
     · 侧证：tool.llm.chat  n=666  avg=7.4s  max=284s（本地模型单次推理量级）

⚪ 证据 2：并行派发在"未常驻"时的表现 —— **待实测**
     （需用 BILLAGENT_MCP_STDIO=1 跑一次 A/B 对比；本轮未跑，**不用推算值冒充实测**）
     · 机制推演：若每次调用都要冷启动 ~11s，多任务并行会**各自排队等冷启动** → 收益被抵消

✅ 证据 3：单波 vs 多波的耗时差 —— 从 trace_span 实测（表内 2209 条 span）
     · 多任务 run（23 次）：平均总耗时 20045ms
     · 同批 run 的「各 agent 耗时之和」平均 55152ms
     · ★并行收益比 = sum/total = 2.75x（10/23 的 run 判定为存在真实时间重叠）
     · 单任务 run（18 次）：平均 ~20s（无并行空间，作为对照）
```

**★一句结论（面试可直接讲）**：

> 「三步顺序不可换」不是拍的，是 **trace_span 实测**出来的：
> 多任务请求里，**各 agent 的耗时之和是端到端耗时的 2.75 倍** ——
> 说明并行派发确实产生了时间重叠；**但前提是 MCP 必须常驻**，
> 否则每次调用的冷启动（11s+）会把并行收益整个吃掉。

**注意**：**不要删这句话**（它是最有价值的洞察），只用数据把它撑起来。

#### F5 · 白名单不覆盖中文数字

**拷打来源**：Q15 L3「模型输出中文数字（"五十"）覆盖了吗？」、L4「"五十多"提取到 50 还是 51？」

**现状**：`utils/number_whitelist.py` **只处理阿拉伯数字** ✗

**修法**（✅ **2026-10-09 已实施**，`设计/18` M20 / 契约 `09` §9.4）：
1. ✅ 加中文数字解析：`五十`→50、`一百二`→**120**（省略尾"十"）、`两千`→200、`三千五`→3500
2. ✅ 取值口径明确：`五十多` → **50（取下界）**

**★L4 的标准答案（"五十多"提取到 50 还是 51）**：

> **取 50**。因为白名单闸门的目的是**防编造**，不是"精确对齐口语"。
> 取 51 需假设"多"= "+1"，是**无依据的推断**（"多"可能是 51~59 任意值）；
> 取 50 使**下界确定** —— 模型若输出 51 而白名单只有 50，容差 0.5 下会被判幻觉并触发修正重试，
> 属"**多拦一次**"的保守失败。**在防幻觉场景，宁可误拦，不可漏放。**

**⚠️ 实施中发现并处理的边界（★这段能体现工程判断力）**：

> 朴素实现（只要是中文数字就抽）会**引入误报**：`"没有数字的一句话"` 里的"一"
> 会被抽成 `1.0`。而白名单是**「全量包含」语义**（一个数字落不进就整体不通过）——
> 这会让**大量含"一/两/三"的正常回复被误判为幻觉**（触发修正重试乃至回退本地渲染）。
>
> **权衡后的取舍：只抽长度 ≥ 2 的中文数字串**（`五十` 抽、单字 `一` 不抽）。
> 代价是"花了三块"这类**单价中文数字会漏检** —— 属**已知边界**，
> 与"模型汇总以阿拉伯数字为主"的现状相容。
> **误报的危害（正常回复大面积被拦）远大于漏检。**

**已知边界（不得过度承诺）**：
- 不覆盖"半"（"五十半"）、分数、成数（"八成"）、"廿/卅"；
- **不做上下文消歧**："十点"的"十"会被抽取 —— 该行为**与既有阿拉伯数字一致**（"10点"本来就会被抽），属既存边界。

#### F11 · 用户中途取消能力缺失 ⭐ 一定会被问

**来源**：自查发现（三份拷打文档未覆盖，但产品视角面试官必问：「用户说'算了不记了'怎么办？」）

|---|---|---|
| 协程取消机制 | ✅ 有 | `webUI/app.py::shutdown()`（全局关停） |
| `interrupted` 状态 | ✅ 有 | `startup/task_manager.py::mark_interrupted` |
| 全局关停（`SHUTDOWN_FLAG` + `task.cancel()`） | ✅ 有 | `startup/bootstrap.py` |
| **单任务取消入口（用户级）** | ✅ **有** —— `cancel_session(session_id)`，注释即写「用户级取消入口」 | `startup/task_manager.py` |
| `cancelled` **独立终态** | ✅ 有 —— 与 `interrupted` **语义相反**：`interrupted` 重启后**参与重投**；`cancelled` 是**终态、不重投、不再回复** | `task_manager.py`（模块 docstring 第 4 条） |
| 取消的**在途任务清理** | ✅ 有 —— `INFLIGHT_STATUS = (submitted, running)` + `cancel_running` 精准中断内层 runner | `task_manager.py` |
| 副作用回滚 | ❌ 没有（**有意为之**，见下方 L4） | — |

> ⚠️ **原文写「单任务取消入口 ❌ 没有」「`interrupted` 不含用户取消」—— 与代码不符**（拷打 Q24/Q42）。
> **面试口径**：直接说"**取消我做了**"，并点出**最关键的设计点**：
> **`cancelled` 与 `interrupted` 是两个语义相反的中断，不可复用同一状态**
> —— 若把用户取消也标成 `interrupted`，重启后会自动重投并回复，与"用户已明确不要了"直接冲突。

**问题要分四层看**（难度递进，成本差一个数量级）：

| 层 | 用户真正要什么 | 技术动作 | 难度 | 现状（2026-10-09 复核） |
|---|---|---|---|---|
| **L1 停止等待** | 「不想等了，先给结果」 | 断开等待，**任务继续跑**，结果落库可查 | ⭐ | ✅ 已定义（任务状态在独立表，不依赖连接） |
| **L2 停止派发** | 「后面别发了」 | 置取消标志 → 编排器每波派发前检查 → 不再发新任务 | ⭐⭐ | ✅ **已实现**（`cancelled` 置位后 `dispatch_node` / `wait_result_node` 双闸） |
| **L3 中断执行** | 「正在跑的也停」 | 对运行中子任务 `task.cancel()` → 标 `cancelled` 终态 | ⭐⭐⭐ | ✅ **已实现**（`cancel_session` **先落终态、再 cancel 内层 runner**） |
| **L4 撤销副作用** | 「刚才那笔账不算」 | 补偿事务 / 反记账 | ⭐⭐⭐⭐⭐ | ❌ **没做，且是有意的**（见下） |

**关键洞察①**：**用户说"停止"，90% 的情况只是 L1** —— 他不想等，不是要任务必须停。

**关键洞察②**：**L4 的难点不在技术，在业务语义**——

```
任务 A（记账）已成功 → 账单已落库
任务 B（统计）还在跑
用户：停止！
→ A 的那笔账要不要撤？撤了可能用户确实想记（只是不想等统计）；不撤用户可能说"我按了停止"
```

分布式系统里这叫 **cancellation 语义**（Temporal 专门设计了 cancellation scope + 补偿活动）。**SQLite 事务能 rollback，但账单一旦落库就跨过了事务边界。**

**修法状态**：✅ **L1 + L2 + L3 已完成**（对应 **M16**「用户取消」与 **M19**「请求级终止语义」两个里程碑，
见 `设计/17` 与契约 `09` §2.17）；**L4 明确不做**（理由见下方「关键洞察②」）。
下文保留**原始设计推演**（作为"我是怎么想清楚这四层的"的素材）：

1. **L1（0.5h）** —— 主要是**明确语义**，不是写代码：用户断开后**任务继续跑完**、结果落库、下次可查（这是正确的产品行为，记账不该因用户不等而丢弃）。
2. **L2+L3（2h）** —— 加取消入口：
   ```python
   # startup/task_manager.py 新增
   def request_cancel(self, task_id: str) -> None: ...

   # 编排器 dispatch 前检查
   if task_mgr.is_cancelled(session_id):
       return Command(goto="collect_node")   # 收口，不再派发

   # 对运行中的子任务
   worker_task.cancel()   # 复用现有 track() 的 CancelledError 分支
   ```
3. **状态复用**：`interrupted` 语义正好匹配（"非失败的中断"），只需把触发源从"进程关闭"扩展为"进程关闭 **或** 用户取消"。

**⚠️ 取消必须处理的坑**：**取消要尊重写操作边界** —— `track()` 里已有"写任务 `retriable=0`"逻辑，取消后重启对账必须走"查业务表"分支（已写 → `completed`），**否则会把已记账的任务重投**。

**面试答法**（**这题答"分层"会加分，答案「做不到」或「能取消」都扣分**）：

> 这个问题我按四层来看，**我的系统支持前两层，第三层有基础设施，第四层明确没做**。
>
> **第一层"用户不想等"** —— 任务应该**继续跑完、结果落库**，用户下次能查到。记账是有价值的工作，不该因为用户不等就丢掉。这层我机制上支持（任务状态在独立表，不依赖连接）。
>
> **第二层"别发新任务"** —— 编排器每波派发前检查取消标志，置位后不再派发。
>
> **第三层"正在跑的也停"** —— 对运行中子任务发 `cancel()`。我的 worker 侧已捕获 `CancelledError` 并标 `interrupted`（不是 `failed`，因为并非执行失败），**基础设施是现成的，缺的是从 UI/CLI 到编排器的取消入口**。
>
> **第四层"撤销已产生的副作用"，这层我没做** —— 而且难点**不在技术，在业务语义**：并行任务里可能 A 已记账成功、B 还在跑，用户说停止时，**A 那笔账要不要撤？** 撤销需要补偿事务或反记账记录。**SQLite 事务能 rollback，但账单一旦落库就跨过了事务边界。** 这是我明确的边界。

**为什么加分**：面试官问这题是看**你有没有区分"用户的字面要求"和"他的真实意图"**，以及**知不知道"反向操作"比"正向操作"难多少**。

**⭐ Q6-L5 专答（这是你最强的回答，务必讲满）**：

> 94.9ms **不是**"sleep 的实际睡眠时长"，而是**端到端投递延迟的 P95**。
>
> 基准脚本模拟的是**真实调度场景**：消息到达时刻相对 100ms 轮询周期**是随机的**（不是我掐着点 sleep）。所以延迟均匀分布在 **[0, 100ms]** ——
>
> - **理论值**：均匀分布的 P50 = 50ms、P95 = 95ms、均值 = 50ms
> - **实测值**：P50 = 47.6ms、P95 = 94.9ms、均值 = 50.4ms
>
> **三个指标都与理论值吻合**，说明测量方法本身是对的。**如果我测出来是 100ms 或者 110ms，那才说明我测错了**（把 sleep 的实际时长当成了延迟）。

**为什么这个回答强**：它证明你**知道自己在测什么**，而不是"跑了个脚本记个数"。

### 模块七 · 叙事与概念准确性 ❌❌ 最危险模块

#### Q22 · "多 Agent 系统"的定义 ❌

| 追问 | 评级 | 应对要点 |
|---|---|---|
| L1 4 个 Worker 同进程同事件循环，跟"起 4 个函数"本质区别？ | ❌❌ | **必须准备** — 见下方专答 |
| L1b **为什么是 4 个？不是 2 个或 8 个？** ⭐ | ❌❌ | **必问，见下方「为什么是 4 个」专答** |
| L1c 为什么不按"意图"分（查询 Agent / 建议 Agent）？ | ⚠️ | 见下方专答末段 |
| L2 Worker 有独立身份吗？独立记忆吗？能拒绝任务吗？ | ⚠️ | 有身份（`agent_id`）、有独立提示词与子图、**能拒绝**（`need_more_info` 追问分支）|
| L3 去掉 Queue 直接函数调用，用户感知什么差别？ | ❌ | 答"**感知不到功能差别**，差别在**故障隔离与可恢复性** —— 函数调用失败即整链失败，消息总线让单任务失败可独立重试" |
| L4 为什么叫多 Agent 不叫多 Worker 并发？ | ❌❌ | 见下方专答 |

**⭐ Q22-L1b 专答：「为什么是 4 个」**（★ 由本人补充的设计理由，是目前最完整的一个答案）

> **为什么是 4 个？不是按功能数量凑的，是按「最小完备集合」选的。**
>
> 我先把消费场景拆成**四个正交的基类业务**——它们的**输入输出契约互不重叠**：
>
> | 基类 | 能力类型 | 输入 → 输出 |
> |---|---|---|
> | **记账** `bill` | **写入** | 消费描述 → 落库确认 |
> | **统计** `stat` | **聚合** | 时间范围 + 维度 → 聚合数字 |
> | **比价** `price` | **外部对标** | 品类 + 金额 → 溢价率 |
> | **理财** `finance` | **建议生成** | 上游结果 + 消费习惯 → 分析结论 |
>
> **这四类组合起来能覆盖绝大部分消费对话**：
> - 「记午饭30」→ 只用到记账
> - 「这个月花了多少」→ 统计
> - 「打车20贵不贵」→ 比价
> - 「给我点省钱建议」→ 理财（消费统计的结果）
> - **「记午饭30，这个月花了多少，打车贵不贵」→ 记账 + 统计 + 比价 三者并行**
> - **「午饭32记一下，查7月开销，对比餐饮物价，给省钱建议」→ 四个全部用上**
>
> **所以 4 不是"业务碰巧分了四类"，是"这四类基业务可以拼出问题空间"。**
>
> **这个分解方式的实际好处是："要不要加第 5 个"有判断依据** —— 来了新需求，
> **先看能不能用已有基类组合解决**：比如「看看这个月餐饮超没超」是 **统计 + 理财的组合，不需要新 Agent**。
> **只有当出现四个基类都覆盖不了的新维度**（如多人分账、账单导入）**才加第 5 个**。

**顺带的追问：为什么不按"意图"分？**

> 因为**按意图分会让职责重叠**——「给我点省钱建议」既是"查询"也是"建议"，一个意图 Agent 兜不住。
> **按业务能力分，每类都有明确的输入输出契约**（统计：时间范围+维度 → 聚合数字；比价：品类+金额 → 溢价率），
> **契约清晰才能独立测试、独立替换** —— 我 4 个子 Agent 各有独立的测试文件与独立的图，就是靠这个契约边界做到的。

**⭐ Q22 专答（**必须准备，这是"过度包装"最容易被抓的点**）**：

> **它们是同进程的协程，不是独立进程或服务** —— 这一点我如实说。
>
> **我称它为"多 Agent"而不是"多 Worker"，因为每个子 Agent 具备三样独立的东西**：
> 1. **独立的工具可见面与权限**（仅记账 Agent 可写账单；理财 Agent 独享专属模型通道）；
> 2. **独立的提示词与子图**（各自有 Plan/Execute/Verify 节点与自纠闭环，不是同一个函数换参数）；
> 3. **独立的失败域**（一个失败转追问，不阻断其他任务；函数链式调用做不到）。
>
> **如果要更严格地定义 Agent 需要进程隔离 + 自主规划，那我的实现介于"多 Agent"与"多 Worker 并发"之间。** 我倾向于把它描述成 **Orchestrator-Worker 模式的多 Agent 编排**，而不是"自主多 Agent 系统"。

**关键**：**主动说出边界，比被追问出来强十倍**。

#### Q23 · "RBAC 权限模型"的实现深度 ❌

| 追问 | 评级 | 应对要点 |
|---|---|---|
| L1 建了角色表、权限表吗？ | ❌ | **没有** → 见 R1 |
| L2 还是几个 if-else？ | ⚠️ | 不是 if-else，是**权限枚举 + 代码内映射表**（`AGENT_PERMISSION_MAP`）|
| L3 那写 RBAC 是不是过度包装？ | ❌ | 见下方专答 |
| L4 能动态配置吗？ | ❌ | **写死在代码里** |

**⭐ Q23 专答**：

> 严格说不算完整 RBAC —— **没有角色表和权限表，是代码里的静态权限映射**（Agent → 权限枚举集合）。我用"RBAC"是想表达"**基于身份的权限模型**"；按严格定义，我的实现是它的最简形式。
>
> **为什么不做成可配置的**：当前 Agent 集合固定（5 个），动态配置会引入"配置与代码不一致"的风险。**演进方向是当 Agent 增长或多租户时把映射表外置。**

**同时建议改简历措辞**（见 R1）。
